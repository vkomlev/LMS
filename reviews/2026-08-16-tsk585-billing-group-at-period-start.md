# tsk-585 — деньги берут тарифную группу на первое число месяца

**Дата:** 2026-08-16 · **Ветка:** `worktree-tsk-585-pricing-period` · **Скилл:** `/fastapi-api-developer`
**Задача:** [tsk-585](D:\Work\Root\tasks\tsk-585-smena-tarifa-perepisyvaet-tekuschij-mesyats-vopreki-resheniyu-14.md) — блокер фазы 9 [tsk-301](D:\Work\LMS\docs\briefs\tsk-301-subscription-model.md)

## Что было не так

[Контракт прав](../docs/specs/2026-08-08-contract-entitlements.md) §7 разводит две вещи:
права берутся из строки подписки, действующей **сегодня**, деньги — из строки,
действовавшей **на первое число расчётного месяца**. Из этой пары выведено решение 14
брифа: «права при апгрейде сразу, деньги со следующего месяца», без отдельного
механизма отсрочки.

Код так не делал: `pricing_service.active_subscription_groups` брал строку
`WHERE ends_on IS NULL`, то есть действующую **на момент запроса**. Смена тарифа
посреди месяца немедленно переписала бы уже открытое начисление — сумму, которую
человеку уже назвали.

Сегодня недостижимо (единственный существующий переход `demo` → `base` — это не смена,
а появление платности), но фаза 9 tsk-301 — ровно про смену тарифа персоналом.

## Правило после правки

Резолвер группы **для денег** получает период (первое число месяца):

1. на первое число была строка с платной группой → берётся **она** (смена тарифа
   текущий месяц не переписывает);
2. на первое число платной группы не было (её не было вовсе либо это Demo/Test/
   Выпускник без группы) → берётся **текущая** строка. Это «появление тарифа», и оно
   начисление как раз создаёт;
3. подписки нет вовсе → прежнее поведение, группы из проданных курсов.

Правило «наличие ключа = подписка есть, значение `None` = денег нет вовсе» сохранено:
без него ученик на Test/Demo вернулся бы к группам из курсов и получил бы начисление.

В день смены под условие «действовала на первое число» попадают ОБЕ строки (`change_plan`
закрывает старую и открывает новую одной датой) — `DISTINCT ON … ORDER BY starts_on DESC,
id DESC` отдаёт новую: смена ровно первого числа действует с этого же месяца.

Главное — **разница двух случаев**, а не каждый по отдельности:

* `demo` → `base` посреди месяца → текущий месяц начисляется (появление тарифа);
* `base` → `ai` посреди месяца → текущий месяц НЕ трогается (смена тарифа);
* следующий месяц после смены считается уже по новой группе — без этой проверки правку
  можно было бы «выполнить» вечной заморозкой старой группы.

Тесты проверены на способность падать: со старым поведением резолвера (одна строка
`if period is None:` → `if True:`) падают 3 из 8 — смена тарифа, разделение
«права сегодня / деньги на первое число» и неприкосновенность закрытого месяца.

Отдельная находка из этой проверки: со старым резолвером смена тарифа при **закрытом**
месяце заводила в этом закрытом месяце вторую строку по новой группе. После правки —
одна строка, поправок (`charge_adjustment`) не возникает.

## Риски и хвосты

1. **Поведение при уходе в `alumni` среди месяца изменится в будущем** — когда у ученика
   на первое число уже будет платная строка, месяц останется начисленным. Это прямое
   следствие контракта §7 («смена тарифа не переписывает текущий месяц») и решения 13
   брифа; сегодня на данных не проявляется. Если оператор захочет для выпуска другое
   правило — это отдельная развилка, не эта задача.
2. `charge_cron_service` (детектор «ходит, но не выставлен») по-прежнему смотрит на
   сегодняшнюю подписку. Он read-only и деньгами не управляет, но текст причины у
   ученика, сменившего тариф среди месяца, может назвать не ту группу. Мелко, вынесено
   в хвост, а не поправлено молча.
3. Пересечения с чипом tsk-615 (`student_payment`) нет: правка не касается платежей.
   Пересечения с чипом tsk-301 фаз 7–8 (`app/api/deps.py`, `app/api/v1/me.py`) нет —
   файлы не общие.
