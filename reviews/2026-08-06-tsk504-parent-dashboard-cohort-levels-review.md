# Review-gate: tsk-504 — дашборд родителя, цветовая подсветка метрик относительно сверстников

**Дата:** 2026-08-06
**Скилл:** `/review-gate` (независимая проверка перед интеграцией)
**Скоуп:** LMS (backend) + SPW (frontend), незакоммиченные изменения на момент ревью.

## Решение: **ПРИНЯТО**

## Шаг 0 — Якорь контекста

Исходная задача (`D:\Work\Root\tasks\tsk-504-*.md`): дашборд родителя (tsk-494/tsk-478)
получает цветовую подсветку трёх метрик (темп прохождения, доля пропусков,
активность между занятиями) относительно сверстников того же курса. Все три
развилки решены оператором 2026-08-06: метрики (3, не весь состав дашборда),
порог когорты (≥5 активных учеников, "других"), шкала (3 уровня, терциль).

Acceptance criteria покрыты полностью:
- [x] Backend: агрегация распределения по когорте ОДИН раз на дашборд (не N+1).
- [x] Классификация в 3 уровня — терциль, выбор задокументирован в коде и здесь.
- [x] Минимизация данных (tsk-460): API отдаёт только уровень своего ребёнка.
- [x] SPW: визуальная подсветка поверх графиков tsk-023, не заменяет их.
- [ ] Живая проверка на проде — **не в скоупе этого ревью**, запланирована
      отдельным шагом после деплоя (см. «Necessary tests»/«Operator handoff»).

DRIFT: не обнаружен — реализация не выходит за рамки трёх утверждённых метрик
(`period_total`/`in_class_hours` намеренно НЕ подсвечены).

## Находки

Блокирующих не найдено.

**Не блокирует, на заметку:**
- Bulk-запросы для курсов с очень большими когортами (88/112, 30+ активных
  учеников) — синтаксически корректны и используют существующие индексы
  (`task_id`/`user_id`/`student_id`), но реальная задержка под нагрузкой не
  замерена (EDA-профилирование вне скоупа review-gate). Рекомендация:
  зафиксировать P95 времени ответа `/students/{id}/dashboard` для курса 88/112
  на живой проверке на проде (следующий шаг).
- `AttendanceChart`: при `planned=0` бейдж `insufficient_data` не рендерится
  (ранний return, есть только текст "Нет занятий за период") — осознанное
  решение (текст уже explicit), задокументировано отдельным тестом
  (`planned=0 — пустое состояние, без бейджа`). Если оператор при живой
  проверке сочтёт это недостаточно явным — тривиально добавить бейдж и туда.
