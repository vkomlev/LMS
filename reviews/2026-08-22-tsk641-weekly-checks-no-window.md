# tsk-641 — еженедельные чеки мигали окном PowerShell по понедельникам

**Дата:** 2026-08-22
**Задача:** [tsk-641](../../Root/tasks/tsk-641-lms-ezhenedelnye-cheki-migayut-oknom-powershell-po-ponedelnikam.md)
**Повод:** хвост [tsk-636](2026-08-22-tsk636-stale-verdicts-review.md) — заводя туда четвёртый чек, наткнулись на то, что три соседних мигают окном
**Решение гейта:** **ПРИНЯТО**

---

## 1. Что было

Три чека прода (`tsk-237` порядок разделов, `tsk-361` непроверяемые задания,
`tsk-369` задания без файла) запускались обёртками на PowerShell. `powershell.exe` —
консольная программа: планировщик создаёт ей окно и лишь потом прячет. Каждый
понедельник в 09:00 и 09:10 на экране моргал чёрный прямоугольник.

Обёртки делали ровно две вещи сверх запуска: доставали боевое подключение из
`.mcp.json` (в `.env` проекта лежит dev-база, tsk-246) и писали итог в журнал —
под планировщиком вывод читать некому.

## 2. Что сделано

Общий вход `scripts/weekly_checks.py <имя чека>`, рассчитанный на запуск через
`pythonw.exe`. Обе обязанности обёрток переехали туда; сами обёртки удалены.

Задачи ставит `scripts/install_weekly_checks.ps1`. Имена задач и время оставлены
прежними — включая исторически кривое `LMS - chek poryadka razdelov (tsk-237)`:
переименование ничего не чинит, а оператора, привыкшего искать задачу глазами,
сбивает.

| Задача | Чек | Понедельник |
|---|---|---|
| `LMS - chek poryadka razdelov (tsk-237)` | `section-order` | 09:00 |
| `LMS ungradable tasks weekly` | `ungradable` | 09:10 |
| `LMS stale verdicts weekly` | `stale-verdicts` | 09:20 |
| `LMS missing attachments weekly` | `missing-attachments` | 09:30, **не заведена** (см. раздел 6) |

### Почему именно `pythonw`

`pythonw.exe` собран как GUI-программа — консоль ей не выделяется вовсе. Два других
варианта отпали на проверке:

- `powershell.exe -WindowStyle Hidden` — окно создаётся и прячется уже после старта,
  вспышка остаётся;
- тип входа S4U («выполнять независимо от того, вошёл ли пользователь») — требует
  права «Вход в качестве пакетного задания», без администратора отвечает
  `Access is denied`;
- обёртка `.vbs` — в этом проекте уже пробовалась для задачи с Redis и была
  откатена: `wscript.exe` после `shell.Run` не завершался, задача навсегда
  оставалась «выполняется» и при `MultipleInstances=IgnoreNew` глушила все
  последующие срабатывания.

### Скрытая ловушка, которая вернула бы мигание

Два чека при импорте зовут `os.system("chcp 65001 >nul 2>&1")`. Под `pythonw`
консоли нет, `cmd.exe` получил бы **свою** — и окно моргнуло бы, несмотря на всю
затею. Вход выставляет `LMS_CHECK_NO_CONSOLE=1`, чеки на этот флаг вызов пропускают.
Строка выглядит необязательной, поэтому закреплена тестом.

### Побочно закрытая хрупкость

Обёртка чека порядка разделов брала DSN из `D:\Work\CreateCourses\.mcp.json` —
переезд или переименование чужой папки убили бы чек молча. Подключение там ровно то
же, что в `.mcp.json` самой LMS (сверено: один хост, порт, база и роль), поэтому
источник теперь один — свой.

## 3. Что изменилось в поведении журналов

- В строку итога добавлено, **куда** чек сходил (`host:port/db`, без пароля).
  Подмена боевой базы на dev — самый неприятный отказ такого чека: он выглядит как
  успех. Теперь это видно.
- При коде 0 вывод чека по-прежнему отбрасывается: `section-order` и
  `missing-attachments` даже в тихом режиме печатают шапку «База: …», и подшивать её
  каждую неделю — значит утопить настоящую находку в шуме. Исключение —
  `stale-verdicts`: её тихий режим по-настоящему молчит, поэтому любая строка при
  коде 0 значима (смежные сигналы: сменённый тип задания, работа, не прошедшая
  валидацию схемой).
- Имена файлов журнала сохранены — иначе история наблюдений разорвалась бы на
  середине.

## 5. Проверки

**Все четыре чека прогнаны через новый вход** на боевой базе (только чтение):
`section-order` → 0, `ungradable` → 1 (13 непроверяемых заданий), 
`missing-attachments` → 0, `stale-verdicts` → 1 (10 работ). Журналы пишутся
корректно, кодировка в порядке.

**Три задачи прогнаны планировщиком** после перевода: состояние вернулось в `Ready`,
коды результата 0 / 1 / 1 — то же, что при ручном запуске. Значит окружение задачи
(рабочий каталог, отсутствие консоли, venv) чек не ломает.

**Тесты:** 15 новых, зелёные. Плюс 33 смежных (сверка незачётов, проверка ответов) —
без регрессий. Полный `pytest` не гонялся: dev-база общая с параллельными сессиями.

**mypy** по `scripts/weekly_checks.py` — чисто.

**Чего проверкой НЕ доказано.** Отсутствие вспышки окна я не наблюдал глазами —
это утверждение структурное: `pythonw.exe` относится к GUI-подсистеме Windows, и
консоль такому процессу не выделяется, а единственный источник дочерней консоли
(`os.system` с `chcp`) устранён явным флагом. Если по понедельникам окно всё-таки
мелькнёт — искать надо новый `os.system`/`subprocess` без `CREATE_NO_WINDOW` внутри
чеков.

## 6. Находки и что с ними

| # | Находка | Статус |
|---|---|---|
| 1 | У чеков три разных соглашения о `main()`: async без аргументов с argparse внутри, async с `quiet=`, sync с argparse внутри. Первый прогон упал на `int(coroutine)` | **Исправлено:** различия описаны в реестре (`is_async`, `takes_quiet`). Приводить три работающих чека к одной сигнатуре ради красоты — трогать код без нужды |
| 2 | Первая версия подшивала в журнал шапку «База: …» каждую неделю | **Исправлено:** `report_on_zero`, по умолчанию False — как вели себя прежние обёртки |
| 3 | `prod_dsn` мог бы молча отдать dev при кривом `.mcp.json` | **Проверено:** падает с внятной ошибкой, два теста |
| 4 | `check_missing_attachments` **не стоит в планировщике** — скрипт и обёртка были с tsk-369, задачу так и не завели | **Вынесено оператору** (раздел 7): молча добавлять еженедельный отчёт, которого не просили, неправильно |
| 5 | Историческое имя задачи `LMS - chek poryadka razdelov (tsk-237)` | Оставлено намеренно |
| 6 | Отчёты `reviews/` за июль ссылаются на удалённые обёртки | Не трогал: это датированные записи о том, что было тогда |

## 7. Оператору

Чек `tsk-369` (задания требуют файл-приложение, а файла нет) написан год назад, но в
планировщике его нет — то есть он не запускался ни разу автоматически. Ручной прогон
сегодня: находок нет. Завести четвёртой задачей:

```
powershell -ExecutionPolicy Bypass -File scripts\install_weekly_checks.ps1 -Only missing-attachments
```
