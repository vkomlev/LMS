## Живая проверка — пройдена (после двух отдельных фиксов окружения)

Первая попытка живой проверки `pnpm dev` (Next.js 16.2.4, Turbopack) на этой машине
**дважды подряд** приводила к аварии: сервер стартовал («✓ Ready»), но на первом же
HTTP-запросе Rust-бинарь Turbopack падал с `0xC0000409`
(`STATUS_STACK_BUFFER_OVERRUN`) и в течение 1–2 минут порождал 700–830 процессов
`node.exe` (16–18 ГБ RSS при 16 ГБ RAM) — машина уходила в OOM. Оба раза откачено
аварийной остановкой всех `node.exe`, запущенных в текущий день.

По решению оператора расследование вынесено в отдельный фоновый чип
(`task_85564208`), который под сторожевым скриптом (посекундный мониторинг числа
`node`) подтвердил причину эмпирически: Turbopack — 2→74 процесса за секунду, всего
332; webpack — стабильно 2–3 процесса. Фикс — форс `--webpack` (тот же приём уже был
применён для `next build` в tsk-470 из-за другого бага Turbopack). SPW commit
`afaa693`.

При повторной попытке живой проверки — **второй, отдельный от Turbopack баг**:
webpack-предупреждение «multiple modules with names that only differ in casing» на
`D:\Work\SPW\node_modules\...` vs `D:\Work\spw\node_modules\...` (Git Bash отдавал
`process.cwd()` в исходном регистре вызова, а не регистре диска), вслед за которым
React ронял синглтон layout-router контекста — `invariant expected layout router to
be mounted`, страница зависала на клиенте. Тот же класс бага, что уже чинили для
`next build` (tsk-470) и Playwright (tsk-552), но `next dev` эту нормализацию не
проходил. Фикс — `scripts/dev.mjs` (тот же приём `realpathSync.native()`), плюс
очистка `.next`-кэша (в нём осели модули со старыми путями от предыдущих крашей).
SPW commit `65878bf`.

После обоих фиксов — **полная интерактивная живая проверка** через `claude-in-chrome`
(живой вход методиста через magic-link, dev-БД, курс 147 «Задание 19-21 ЕГЭ по
информатике. Теория игр», 92 реальных активных EASY+NORMAL задания):
- панель «Выборка заданий по сложности» рендерится в карточке курса, бейдж
  «выключена» — стартовое состояние совпадает с `sampling_config=NULL`;
- кнопка «Настроить» открывает форму; чекбокс включения раскрывает поля порога и
  доли EASY только когда включено (условный рендер работает);
- подсказка над полем порога — «Сейчас в подкурсе 92 EASY+NORMAL заданий» — реальное
  число, совпадающее с прямым запросом к БД, не выдумка UI;
- плейсхолдер порога «например, 30» — не хардкод, поле пустое до ввода;
- заполнение порога (40) и сохранение → бейдж сразу обновился на «включена: 40 из
  EASY+NORMAL, доля EASY 50%»;
- **персистентность подтверждена полной перезагрузкой страницы** — значение осталось

SPW-фронтенд задеплоен на прод (`65878bf`) — сборка на самом сервере прошла чисто

## Побочная находка (операционная гигиена фоновых процессов)

Первая попытка поднять dev-сервер (`nohup pnpm dev &` в Git Bash) при остановке
`kill <PID>` убила только обёртку bash, а не дерево процессов Node — сирота-процесс
продолжал крашиться/респауниться в фоне несколько минут, что и стало основным
источником взрыва до 742 процессов в первый раз. Дальнейшие попытки шли через
отслеживаемый `run_in_background` Bash-инструмента и `TaskStop` — не голый `nohup &`
— но обрыв всё равно требовал добивать процесс, слушающий порт 3000, отдельно
(`TaskStop` останавливал только обёртку). Урок: для Node/Next dev-серверов проверять
факт освобождения порта (`Get-NetTCPConnection -LocalPort <port>`), а не полагаться
на статус остановки самого task-раннера.
