## Проверка по измерениям (актуальные для data-only правки)

**1. Соответствие целям (DRIFT).** Пункты 1-5 выполнены полностью и верифицированы дважды
(верификация внутри скрипта + независимый read-only MCP `learn_prod_db` после commit).
Пункт 6 — условие исполнения не выполнено: tsk-528 п.2 установил, что отключение
самопроверочных материалов было ОСОЗНАННЫМ решением методиста, а не техническим
сбоем (100%-сегментация по типу контента на 18 материалах в 15 темах, без
исключений) → декомпозиция tsk-530 явно требует активации только «если тех.
сбой» → пропуск корректен, не DRIFT, задокументирован в docstring скрипта и в
Истории движения задачи.

**2. Корректность.** Триггеры `set_course_parent_order_number`/
`set_material_order_position` дают каскадный сдвиг соседа при одном UPDATE —
скрипт полагается на это штатное поведение (тот же путь, что ручной
drag-and-drop реордер в API), а не отключает триггер вручную — меньше риска
рассинхронизации. До записи прочитано текущее состояние и захардкожены
assert-проверки на него (BEFORE), после записи — assert на ожидаемый результат
(AFTER); при несовпадении — исключение → ROLLBACK всей транзакции (все 5 шагов
атомарны, не по одному). Живой прогон SPW (аккаунт 142, реальный Chrome)
подтвердил: тема «Задание 9» — 164 перед 161 ✓; тема «Задание 2» — материал
395 «Таблица истинности» перед 397 «Python-построение» ✓; тема «Задание 14» —
видео «Представление чисел…» перед текстовым «Разбор типовых заданий» ✓;
UI-лейблы `Обязательно`/`Желательно`/`Можно пропустить` корректно отражают
`requirement_level`. Курс 143 и материалы Turtle/408/410 — верифицированы
через независимый MCP-канал (не только UI), т.к. виртуализированный список
программы курса на проде мешал детерминированному клику по конкретному узлу
(типовая помеха инструмента, не дефект проверяемого кода).

**3. Безопасность данных/миграций.** DDL/схема не менялись. Запись — по
установленному протоколу проекта: локальный скрипт → scp на прод-сервер →
`sudo -u app` → dry-run (ROLLBACK) → `--apply` (COMMIT) → независимая
верификация через MCP `learn_prod_db` (не через тот же канал, что писал —
устраняет класс ошибок из `feedback_local_env_prod_dsn_gotcha`). Явный
пре-write safety-гейт внутри шага 5 (перепроверка нулевой активности в
курсах 151-154 прямо перед UPDATE, не только на этапе разведки) — процитирую
из скрипта: при обнаружении активности бросает `RuntimeError` с явной
инструкцией на `manual_progress_service.grant_course_subtree`, COMMIT не
происходит.

**Regression-риск отката прогресса (прецедент tsk-524) — явно проверен и
задокументирован для каждого пункта:**
- П.1-3 (порядок): не входят в фильтр `compute_course_state`
  (`is_active AND requirement_level IN (required, skippable)`) — переставить
  местами уже пройденные материалы невозможно откатить, меняется только
  последовательность показа следующего незавершённого элемента.
- П.4 (required→recommended): исключает материалы из знаменателя
  `total_items` — может только УЛУЧШИТЬ done/total, откат недостижим по
  конструкции фильтра (`recommended` не входит в `('required','skippable')`).
- П.5 (is_active false→true, `required` без изменений): единственный пункт с
  реальным векторным риском (тот же класс, что и инцидент tsk-524). Проверено
  ДО записи: `student_course_state` для course_id=112 — 12 студентов
  IN_PROGRESS, 0 COMPLETED (регрессия COMPLETED→IN_PROGRESS невозможна
  физически); из этих 12 — 0 записей `task_results`/
  `student_material_progress` в курсах 151/152/153/154 у ЛЮБОГО студента
  (полная выборка, не только эти 12 — проверено отдельным запросом без
  фильтра по student_id). Ни один ученик не дошёл до этой части курса →
  обходной путь `grant_course_subtree` не требовался, реактивация безопасна.

**4. Безопасность/секреты.** DSN не хардкожен в скрипте (читается из
серверного `.env` через `async_session_factory`), в выводе/коммите секретов
нет.

**5. Покрытие проверками.** Data-fix скрипт — тесты pytest не пишутся по
установленной практике проекта (см. соседние `scripts/*_tskNNN.py`); вместо
этого — dry-run на реальных прод-данных ДО apply + независимая верификация
ПОСЛЕ + живой браузерный прогон (ветка А operator-handoff, задеплоено сразу
на прод — user-facing изменение проверено в этой же сессии, без пунта на
оператора).

**6-10.** Docs/API/схема/классификаторы/date-time — не затронуты, неприменимо.

**11. Cross-project memory sync.** Не требуется: изменение — данные курса, не
HTTP-эндпоинт/Alembic-миграция/Pydantic-схема/зависимость/CORS — ни один
триггер `CLAUDE.md` §Cross-project не сработал.

**12. Public API Contract Sync.** Не применимо — `app/api/v1/**` не менялся.

**7. Phase Integrity.** `git diff --cached --stat` перед коммитом = ровно
`scripts/fix_course112_structure_tsk530.py` (+ авто-сгенерированный
`docs/openapi.json` от pre-commit хука — не блокер: хук регенерит схему из
ВСЕГО дерева, включая незакоммиченный код параллельной сессии по tsk-372,
это документированное и ожидаемое поведение хука в общем рабочем дереве
проекта, не утечка постороннего кода в мой diff). Ни один файл чужой
параллельной сессии (`app/api/v1/task_results_extra.py`,
`app/api/v1/teacher_reviews.py`, `app/schemas/teacher_next_modes.py`,
`app/services/teacher_queue_service.py`, `tests/test_review_kind_pending_tsk372.py`)
в коммит НЕ попал — staged pathspec-ом только свой файл.
