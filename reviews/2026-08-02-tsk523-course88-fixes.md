## Незапланированная находка и фикс: `course_dependencies` без backfill ломал живую навигацию

При живой проверке материала 227 (п.9 критериев готовности) обнаружено: сразу после
записи 9 строк `course_dependencies` (п.5) методист-аккаунт (id=2) потерял доступ к
разделу «Множества» через обычную навигацию по программе курса — раздел показывался
заблокированным (🔒), хотя раньше (до этой правки) открывался свободно.

**Причина** (`app/services/me_service.py::_BLOCKED_COURSES_SQL`): SPW-эндпоинт синтабуса
считает подкурс заблокированным, если в `student_course_state` НЕТ строки
`state='COMPLETED'` для его `required_course_id`. Таблица `student_course_state`
пополняется ТОЛЬКО функцией `LearningEngineService.compute_course_state`, а та
вызывается ТОЛЬКО из `resolve_next_item` для зависимостей КОРНЯ (`course_id=88`) — а у
корня зависимостей нет и не добавлялось. Итог: `student_course_state` не содержала ни
одной строки для всех 10 подкурсов курса 88 ни для одного из 34 активных студентов —
после записи `course_dependencies` это означало бы «заблокировано» для ВСЕХ студентов
по ВСЕМ подкурсам (кроме первого, «Установка Python», у которого нет required), включая
студентов, реально прошедших пререквизиты (проверено: студент id=3 полностью сдал курс
103, но `student_course_state` для 106 не существовало вовсе).

**Фикс:** backfill `student_course_state` для всех 34 активных студентов курса 88 × 10
подкурсов (340 пар) — состояние (`NOT_STARTED`/`IN_PROGRESS`/`COMPLETED`) посчитано по
ТОЙ ЖЕ формуле, что в `compute_course_state` (задания с последним результатом ≥50% или
skip, UNION по task_id, + материалы `completed`/`skipped`, против `total = required+
skippable` активных задач и материалов). Результат: 184 `COMPLETED`, 21 `IN_PROGRESS`,
135 `NOT_STARTED`. После бэкфилла студент id=3 для курса 103 (пройден) — `COMPLETED`,
блокировка снята; для курса 106 (доделано 20/21 заданий) — `IN_PROGRESS`, что корректно
не разблокирует курс 103 (гейт всё ещё требует завершить 106) — поведение ожидаемое.

**Follow-up для оператора:** `student_course_state` для подкурсов (не только курса 88)
в принципе не поддерживается в актуальном состоянии никаким фоновым процессом — она
пишется только реактивно через `resolve_next_item`, и то только для явных
`course_dependencies`-целей корневого курса. Если в будущем добавятся
`course_dependencies` для подкурсов других курсов — этот же класс регрессии повторится
без такого же ручного backfill. Возможное системное решение (не в объёме tsk-523):
триггерить `compute_course_state(update_state_table=True)` при любом material/task
progress-событии для ВСЕХ курсов в цепочке `course_parents`, а не только для корня.
