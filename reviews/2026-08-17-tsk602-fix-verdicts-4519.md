## Что было

«в формате x,y». Эталон был записан без пробела после запятой (`10,0`, `3,5`), а
нормализация задания — `["trim","lower"]` — пробел не снимает. Ученик 4519
(Рахимжанов Вадим Маратович) ввёл `10, 0` и `3, 5`: верно по смыслу, вердикт «не зачёт»

(`scripts/fix_answer_format_traps_tsk602.py`), но вердикты остались прежними.

## Откуда взят вердикт

Не из SQL с догадками о нормализации (на разборе этой же задачи такой SQL дал 4 ложных
совпадения из 10), а из настоящего `CheckingService.check_task` — того же кода, что
работает на приёме ответа. Прогон по всему курсу 157
(`scripts/audit_stale_false_verdicts_tsk602.py --course 157`) до правки:

```
Проверено работ: 10
Расходятся с нынешними правилами: 2   ← ровно 11396 и 11403
```

После правки тот же прогон: `Расходятся с нынешними правилами: 0`.

Балл в базу записан тот, который вернул движок (`score = 1`), а не константа: скрипт
отказывается писать, если движок вернул другой вердикт или другой `max_score`.

## Последствия: что пересчиталось, а что осталось как есть

Разобрано **до** записи, проверено после.

### 1. Прогресс курса и состояние задания — НЕ меняются (пересчёт не нужен)

`compute_task_state` и `compute_course_state` берут **последний** результат по заданию
(`DISTINCT ON (task_id) … ORDER BY submitted_at DESC`) и сравнивают `score/max_score`
с порогом 0.5. Последние сдачи по 4836/4837 — это 11399 и 11408, они остались
неверными, поэтому числитель не сдвинулся:

```
Прогресс по курсу 157 до записи:    пройдено заданий 16
Прогресс по курсу 157 после записи: пройдено заданий 16
```

`student_course_state` у ученика 4519 менять не потребовалось: кеш считается по той же
величине. Строки для курса 157 в кеше нет вовсе (ведётся по корням и целям зависимостей),
корень 112 остаётся `IN_PROGRESS`.

**Следствие для ученика (решение оператора: оставить как есть).** Исправленные попытки
показаны зачётом в истории и в сводной статистике («Правильных 98 %», там вердикт берётся
как `bool_or` по всем попыткам задания), но сами задания 4836/4837 остаются «не решено»,
потому что последняя сдача ученика по ним неверна. Если когда-нибудь понадобится довести
их до «решено», для этого есть штатная кнопка «Зачесть задание» в кабинете преподавателя
(`manual_progress_service`) — она заводит НОВУЮ запись `task_results` c
`source_system='manual_teacher'`, которая становится последней сдачей. Отдельным UPDATE
этого делать нельзя.

### 2. Вехи удержания — пересчитались сами, штатным путём

Обе работы сданы вне окна занятия, поэтому они считаются шагами «между занятиями»
(`retention_service`, критерий `is_correct = true`). Уникальных элементов было 23,
стало **25**. Порог достижения №6 «25 шагов между занятиями» достигнут, и его
зафиксировал штатный фоновый тик `retention_achievements_cron_service` — без моего
вмешательства:

```
achievement_id 6 «25 шагов между занятиями», earned_at 2026-08-17 06:14:47.639+00
```

На экране «Прогресс» ученика видно: «Достижения (3)», следующая цель «50 шагов — 25 / 50».

### 3. Очередь проверки преподавателя

Обе работы — `SA_COM` с `manual_review_required = false`, то есть в **обязательную**
очередь они не входили никогда (единый предикат `mandatory_review_sql`, tsk-597/598).
Из **опционального** списка просмотра (`checked_at IS NULL`) они теперь уходят — это
верно: работы проверены.

### 4. Счётчик попыток и лимит

`attempts_used` считается числом строк `task_results`, а не вердиктами. Число строк не
менялось — лимит попыток у ученика прежний.

### 5. Освоение тем, пробелы, статистика методиста

`topic_mastery_service`, `learning_gaps_service`, `student_dashboard_service` считают всё
на лету по `task_results`; материализованных таблиц под эти величины нет. Доля ошибок по
теме «Исполнитель Черепаха» у этого ученика естественным образом улучшилась на две работы.

## Протокол записи

1. **Чтение текущего состояния** — типы колонок `task_results` (`is_correct boolean NULL`,
   `score integer NOT NULL`, `metrics jsonb`), эталоны обоих заданий, все шесть работ
   ученика, `attempts` 8628 (не хранит агрегированного балла), `student_course_state`,
   `user_achievements`, каталог достижений.
2. **Прогон настоящим движком** — `CheckingService.check_task` по всем шести работам.
3. **План и выборка** — dry-run скрипта с построчной сверкой «было → станет».
4. **Запись в транзакции** — `scripts/fix_stale_verdicts_4519_tsk602.py --apply`,
   `rowcount = 1` на каждую строку, `WHERE` дополнительно сужен по ожидаемому «до».
5. **Верификация до коммита** — перечитывание всех шести строк; при любом расхождении
   `ROLLBACK`. Независимая проверка после коммита — read-only через MCP.

Хук `db_write_gate` пройден осознанно (`DBCHECK_OK=1`), протокол выполнен целиком.

### Ловушка, которую поймала верификация

Первая попытка дописать пояснение использовала
`COALESCE(metrics,'{}'::jsonb) || jsonb_build_object(...)`. В `metrics` у этих строк лежит
не SQL NULL, а **JSON-null**, поэтому `COALESCE` его не ловит, а `'null'::jsonb || {...}`
в PostgreSQL даёт **массив**, а не объект. Верификация это увидела и откатила транзакцию;
в рабочей версии стоит проверка `jsonb_typeof(metrics) = 'object'`. Тот же класс, что
известная ловушка `metrics IS NULL` в этой таблице.
