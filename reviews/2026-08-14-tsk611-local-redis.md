# tsk-611 — локальный Redis: подъём, проверка перед прогоном, честные пропуски

Дата: 2026-08-14
Ветка: `worktree-tsk-611-redis` (worktree `.claude/worktrees/tsk-611-redis`)
Файл изменений: [2026-08-14-tsk611-local-redis.diff](2026-08-14-tsk611-local-redis.diff)

## Что болело

Чистый прогон `pytest tests/` на машине оператора давал **1 упавший и 25 ошибок**.
Все 26 — из-за отсутствия Redis на `localhost:6379`, а не из-за кода. Ни один тест
об этом не сообщал:

- `tests/test_y5_guest_endpoints.py` — 19 ошибок, `OSError: Connect call failed ('127.0.0.1', 6379)` внутри драйвера;
- `tests/test_tsk423_demo_task_limit.py` — 6 ошибок, то же;
- `tests/test_session_refresh_http_race_tsk235.py` — 1 падение с другим симптомом: окно
  благодати на ротацию refresh-токена лежит в Redis, пишется best-effort и fail-open,
  поэтому без Redis пять одновременных продлений дают `[200, 401, 401, 401, 401]` вместо
  пяти двухсоток. Со стороны — «сломали tsk-235».

Цена — полчаса на доказательство того, что регрессии нет.

## Почему Redis не было

Разведка на месте (не по документации):

- Redis-совместимый сервер **уже установлен** — Memurai 4.1.8 (`C:\Program Files\Memurai\`),
  служба `Memurai` зарегистрирована и стоит на «Автоматически».
- При этом служба была **Остановлена**, порт 6379 никто не слушал. Причина в
  `memurai-log.txt`: `12 Aug 21:57:40 # Memurai Developer Edition automatic shutdown...` —
  бесплатная Developer-редакция сама себя выключает после нескольких суток непрерывной
  работы и обратно не поднимается.

Отсюда вывод, который определил решение: **«служба на автозапуске» ≠ «служба работает»**.
Одного автозапуска мало, нужна периодическая перепроверка.

Прод не трогали и трогать не нужно: там Redis внешний (отдельный узел), соединение есть.

## Решение

### 1. Чем поднимаем — Memurai процессом пользователя

Способ выбран из трёх (служба Windows / WSL / контейнер):

| Вариант | Почему не он |
|---|---|
| Служба Memurai | Управление службой требует прав администратора: `Start-Service Memurai` из обычной сессии отдаёт «Отказано в доступе». Значит любой ручной подъём — это запрос к оператору, а требование было «без ручных действий». |
| WSL | Из дистрибутивов установлен только `docker-desktop` (служебный, Stopped). Ставить Ubuntu ради Redis — самый тяжёлый путь. |
| Контейнер Docker | Docker Desktop установлен, но не запущен; контейнер поднимется только после старта самого Docker Desktop. Лишнее звено, которое само может быть выключено. |
| **Memurai процессом пользователя** | **Выбрано.** Тот же уже установленный бинарник, прав администратора не требует, стартует за ~1 секунду. Рабочий каталог — `%LOCALAPPDATA%\MemuraiDev` (в `C:\Program Files` пользователю писать нельзя). |

Скрипт пробует оба пути по порядку: сперва службу (сработает, если сессия с правами
администратора), при отказе — процесс пользователя. Контейнер остаётся запасным
вариантом и назван в тексте ошибки, если Memurai вдруг нет.

### 2. Самоподъём без участия оператора

`scripts/dev/install-redis-autostart.ps1` регистрирует задачу планировщика **«LMS Dev Redis»**
в контексте текущего пользователя (прав администратора не нужно):

- триггер «при входе в систему» — закрывает перезагрузку;
- повтор раз в 15 минут — закрывает самовыключение Memurai Developer (иначе после
  очередного «automatic shutdown» машина осталась бы без Redis до следующей перезагрузки);
- второй триггер, ежедневный в 00:05, заводит суточное окно повторов заново на машине,
  которую не перезагружают: бесконечную длительность повтора планировщик не принимает
  («value is incorrectly formatted or out of range» на `TimeSpan::MaxValue`).

Две вещи всплыли только на живой проверке и были переделаны:

1. **Обёртка `.vbs` (чтобы окно консоли не мигало) не годится.** `wscript.exe` после
   `shell.Run` не завершался, задача оставалась в состоянии «выполняется», а при
   `MultipleInstances=IgnoreNew` это глушило все последующие срабатывания — автоподъём
   молча не работал бы. Задача зовёт `powershell.exe` напрямую с `-WindowStyle Hidden`.
2. **Бесконечная длительность повтора** — см. выше, заменена на суточное окно + ежедневный триггер.

`ensure-redis.ps1` идемпотентный: если Redis отвечает на PING — не делает ничего,
поэтому частые срабатывания ничего не стоят.

### 3. Тесты больше не падают внутренностями драйвера

- В `tests/conftest.py` — однократная за прогон проверка PING (синхронный клиент,
  таймаут 1.5 с) и маркер `requires_redis`. Помеченные тесты пропускаются с причиной:
  `нужен Redis на redis://localhost:6379/2 — не отвечает на PING. Поднять: .\scripts\dev\ensure-redis.ps1`.
- Маркер проставлен трём модулям: `test_y5_guest_endpoints.py`, `test_tsk423_demo_task_limit.py`,
  `test_session_refresh_http_race_tsk235.py`.
- `test_session_refresh_grace_window_tsk235.py` не помечен намеренно: там уже есть
  собственный пропуск на уровне фикстуры, а один из тестов файла (`test_refresh_without_redis_still_rotates_normally`)
  проверяет поведение **именно без Redis** и обязан идти всегда.
- Пропуски видны в итоговой строке прогона (`N skipped`) — зелёный прогон без Redis не
  выглядит как полное покрытие.

Поведение самого grace-окна не менялось — это охват [[tsk-604]].

### 4. Одна команда на вход

`scripts\dev\run-tests.ps1` = `ensure-redis.ps1` + `pytest` из `.venv` с `-ra`
(чтобы причины пропусков были на виду). Аргументы уходят в pytest как есть.
Если Redis поднять не удалось — прогон продолжается, но печатается явное предупреждение,
что часть тестов будет пропущена.

## Проверка (оба способа, полный прогон)

| Прогон | Результат | Время |
|---|---|---|
| Полный `pytest tests/` **с** Redis | **2262 passed, 11 skipped, 0 failed, 0 errors** | 12:53 |
| Полный `pytest tests/` **без** Redis (Memurai остановлен намеренно) | **2234 passed, 39 skipped, 0 failed, 0 errors** | 13:46 |

Разбор пропусков прогона без Redis (39):

- 26 — маркер `requires_redis` с причиной «нужен Redis на …» (ровно те 26, что раньше
  падали непрозрачно: 1 упавший + 25 ошибок);
- 3 — фикстура `redis_client` в `test_session_refresh_grace_window_tsk235.py` (свой
  пропуск, был и до задачи);
- 10 — пропуски, не связанные с Redis, они же есть и в прогоне с Redis (снапшот-инвариант,
  триггерные smoke, `CB_LMS_LIVE_SMOKE_Y15`, отсутствие подходящих данных).

Разница прогонов сходится точно: 2262 − 2234 = 28 = 39 − 11.

Проверка скриптов вживую:

- `ensure-redis.ps1` при поднятом Redis → «Redis уже отвечает на 127.0.0.1:6379 — ничего делать не нужно», код 0;
- он же после принудительной остановки Memurai → попробовал службу («нужны права администратора»),
  поднял процессом пользователя, дождался PONG, код 0;
- он же при `REDIS_URL` на недоступный нелокальный адрес → внятная ошибка без стека PowerShell, код 1;
- `run-tests.ps1` из корня проекта → «Redis уже отвечает…», затем прогон (6 passed);
- он же при недоступном Redis → предупреждение «тесты будут ПРОПУЩЕНЫ» и 6 пропусков вместо ошибок;
- **задача планировщика проверена вживую**: Memurai остановлен → `Start-ScheduledTask 'LMS Dev Redis'`
  → через 10 секунд порт 6379 отвечает, `LastTaskResult = 0`, следующий запуск назначен через 15 минут.

## Соседи: TG_LMS

Заглянул, как просили. **Той же ямы в тестах нет**: `grep` по `TG_LMS/tests/` не находит
ни одного упоминания Redis — тесты работают с замоканным HTTP-клиентом и Redis не трогают.
Redis там нужен только **при запуске самих ботов** (`RedisStorage` для FSM в
`src/main_bots_*.py`, `redis://localhost:6379/0`, у бота студента — БД 2). Без Redis бот
не стартует, но падает это на старте и явно, а не 26 непрозрачными ошибками в прогоне.
Побочная польза: та же задача планировщика держит Redis для ботов.

**Чинить в этой задаче не стал — это отдельная задача**, если решим, что подъём Redis
должен быть частью `run_bot_*.bat`.

Мелкое замечание на будущее (не дефект): бот студента использует ту же БД Redis (`/2`),
что и `REDIS_URL` LMS. Наборы ключей разные (FSM aiogram против `guest_session:*`), но
уборка ключей в тестах LMS идёт по своим шаблонам, так что пересечений сейчас нет.

## Риски и что осталось

- **Redis доступен на 127.0.0.1 без пароля.** Так было и раньше (`bind 127.0.0.1`,
  `protected-mode yes`), скрипт эту рамку не расширяет: слушает только петлевой адрес.
- **Задача планировщика привязана к пути `D:\Work\LMS\scripts\dev\ensure-redis.ps1`.**
  Переедет репозиторий — задачу надо перерегистрировать (одна команда, описана в README).
- **Маркер надо не забывать ставить** новым тестам, которым нужен Redis. Правило записано
  в `CONTRIBUTING.md`; механического сторожа нет — тест без маркера снова упадёт драйвером.
- Поведение grace-окна (fail-open запись в Redis) не трогали — это [[tsk-604]].
