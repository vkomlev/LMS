# tsk-670 — «прогресс 0 %» в статистике: почему не ставится finished_at

Дата: 2026-08-25
Кто: фоновый чип Claude (скиллы: `/fastapi-api-developer` — код LMS, `/db-check` — боевая база только на чтение)
Решение `/review-gate`: **ПРИНЯТО** (причина установлена по коду и данным, правка доказана тестом на регрессию и живым ответом прода)

---

## 1. Вопрос, с которого начали

Эндпоинты `/api/v1/task-results/stats/by-task|by-course|by-user` (их показывает бот
преподавателя) отдавали `progress_percent = 0`, `passed_tasks_count = 0`,
`last_* = 0` почти у всех. Показатели считаются по «последней **завершённой**
попытке» (`a.finished_at IS NOT NULL`), а признак завершения на проде стоял у 91
попытки из 12 611 (0,7 %).

Формулировка задачи предполагала, что `finished_at` «забыли ставить». Проверка
показала другое.

## 2. Ответ: признак ставится ровно там, где задуман, — это не поломка

Разбор по коду и по данным:

| Факт | Источник |
|---|---|
| Попытка в LMS — **курсового уровня**: одна на пару (ученик, курс), копит результаты многих заданий и живёт открытой, пока курс проходят | `learning_engine_service.compute_task_state` (докстринг), `me_service` (комментарий tsk-261) |
| Кабинет закрывает попытку **только когда курс пройден до конца** — `finish.mutateAsync()` вызывается в ветке `next-item = "none"` | SPW, `app/(authed)/courses/[course_uid]/task/[external_uid]/page.tsx:615` |
| Ручной зачёт (tsk-297) создаёт служебную попытку и `finished_at` ей не ставит вовсе | `manual_progress_service.grant` |
| По данным прода: `spw_web` — 397 попыток, завершено 13; `manual_teacher` — 11 948 попыток, завершено 0 | боевая база, только чтение |

То есть `finished_at` означает «курс пройден до конца», а не «задание сдано».
Ошибкой был не пропуск признака, а **опора на него** в статистике: она брала
только те результаты, что лежат внутри полностью завершённых курсовых попыток.

Тот же дефект теми же словами уже чинили в `me_service` (tsk-261 — жалоба QA
«задачи все пройдены, но по ним ноль, прогресс 37 %»): там фильтр сняли и
записали правило. В `task_results_service` он дожил до сегодня.

## 3. Правка

`app/services/task_results_service.py`, `_last_attempts_flat`:

- условие `a.finished_at IS NOT NULL` убрано, осталось `a.cancelled_at IS NULL`;
- порядок «последнего» — `tr.submitted_at DESC, tr.id DESC` вместо `a.finished_at DESC`.

Правило теперь дословно совпадает с `learning_engine.compute_task_state` и
`me_service`: **последний результат по заданию, попытка не аннулирована.**
Аннулированные попытки по-прежнему не считаются — это правило не менялось.

Тест: `tests/test_tsk670_progress_without_finished_attempt.py` — ученик с
**открытой** попыткой, два задания (одно решено со второй попытки, другое нет):
прогресс 50 %, пройдено 1, не пройдено 1; по заданию берётся последний результат,
а не лучший; аннулированная попытка обнуляет счёт.

**Тест проверен на способность падать:** со старым условием `finished_at IS NOT NULL`
3 из 4 тестов падают, с правкой — 4 из 4 проходят. Смежные наборы
(`test_last_attempt_stage6`, `test_attempt_cancel_stage35`, `test_tsk663_*`,
`test_tsk433_correct_percentage`) — зелёные.

## 4. Выкат и живая проверка

Выкачено на прод (`daba7c7`, миграции прошли, служба поднялась, `/health` — 200).

Живой ответ боевого API под учётной записью методиста,
`GET /api/v1/task-results/stats/by-user/4536` — до и после:

| Поле | Было | Стало |
|---|---|---|
| `progress_percent` | 0.0 | **100.0** |
| `passed_tasks_count` | 0 | **291** |
| `failed_tasks_count` | 0 | 0 |
| `current_score` / `last_max_score` | 0 / 0 | **436 / 436** |
| `total_attempts`, `correct_percentage` | 78, 92.31 % | без изменений (это tsk-663) |
| `completion_percentage` | 98.65 % | без изменений |

Числа совпали с расчётом по базе, сделанным до правки (291 задание с
результатом, все пройдены, 436 из 436 баллов).

**Что осталось непроверенным, честно.** Второй случай — ученик с реальными
ошибками (#4495, по расчёту 88,5 % и 7 непройденных заданий) — живьём проверить
не успел: браузерная сессия оператора протухла между двумя прогонами
(`live-auth.mjs --status` → «нет входа»). Расчёт по базе есть, живой ответ по
этому ученику — нет. В самом боте преподавателя глазами тоже не смотрел: входа в
Telegram в этой сессии нет.

## 5. Что НЕ делал

- Не менял модель попыток и не заставлял кабинет закрывать попытку на каждом
  задании — признак завершения работает как задумано, менять его семантику ради
  одного отчёта было бы дороже и рискованнее.
- Не пересчитывал ничего задним числом: правка меняет только чтение.
