# tsk-306 — рекомендация квиза для взрослых с интересом к Python

## Цель правки

Живой аудит (D:\Work\Root\tasks\tsk-306-*.md) + read-only диагностика через
`/db-check` на `learn_prod_db` установили: гость, выбравший «Взрослый — для
себя или для работы» на вопросе 1 квиза-лид-магнита, но также выбравший
python/бот-ориентированные ответы на вопросах 2/3/6, получал рекомендацию
детского курса «Python для подростков (11-14)». Причина не в коде движка
подбора, а в данных: среди 7 активных правил `assignment_rule`
(`trigger_event='quiz_scale'`, `course_id=1465`) для шкалы «питон» есть
только детская цель — взрослой не заведено вовсе, при том что на сайте есть
подходящий курс «Создание чат-ботов» (LMS `course_uid='wp:chat-boty-tg-vk-max'`,
`id=917`, подтверждено read-only).

`quiz_scale_matched` (движок сопоставления) до этой правки умел проверять
только ОДНО условие на правило: `{"mode":"argmax","scale":X}` или
`{"min_score":N,"scale":X}`. Различить «школьника, увлечённого Python» и
«взрослого, увлечённого Python» одной шкалой «питон» невозможно — обеим
аудиториям одинаковые опции квиза дают одинаковые баллы по этой шкале.

## Решение (по выбору оператора)

Расширить условие правила необязательным ключом `"none"` — списком
исключающих под-условий той же простой формы. Правило срабатывает, если
основное условие истинно **и ни одно** условие из `none` не истинно.
Оставили минимально необходимое расширение (без общего `"all"`, который
для этой задачи не нужен) — обоснование ниже.

### Итоговый JSON двух прод-правил (для следующего шага — записи в БД через `/db-check`, НЕ выполнено в рамках этой кодовой правки)

**UPDATE `assignment_rule` id=60** (детский Python, было `target_course_uid='wp:python-podrostki-11-14'`):
```json
{"mode": "argmax", "scale": "питон", "none": [{"scale": "работа", "min_score": 3}]}
```
Срабатывает как раньше (питон — строгий максимум среди всех накопленных шкал),
но перестаёт срабатывать, если параллельно накоплено `работа >= 3` — это
происходит только когда вопрос 1 отвечен как «Взрослый» (даёт `работа: 3`
сам по себе) или человек выбрал «Получить профессию или поменять работу» на
вопросе 2 (тоже `работа: 3`).

**INSERT новое правило** (тот же `course_id=1465`, `trigger_event='quiz_scale'`,
`is_active=true`, `target_course_uid='wp:chat-boty-tg-vk-max'`):
```json
{"mode": "min_score", "scale": "работа", "min_score": 3}
```
Обратите внимание: это **простое** (не составное) условие — `none` ему не
нужен. Причина в самом порядке вычисления правил (`ORDER BY id`, возврат на
первом совпадении): к моменту, когда исполнение дойдёт до этого правила (оно
получит id больше существующих семи), уже отсеялись все argmax-правила по
остальным шести шкалам — если бы школа/огэ/егэ/техника/работа/бизнес была
строгим максимумом, соответствующее правило сработало бы раньше. Значит,
дойти до этого правила с `работа>=3` можно только если: (а) питон был
argmax'ом, но исключён обновлённым правилом id=60 из-за `работа>=3` — ровно
целевой случай; либо (б) редкая ничья на вершине шкал при этом же условии —
приемлемый fallback на тот же взрослый курс, не хуже отсутствия рекомендации
вовсе. Проверено вручную перебором обеих раскладок (взрослый/школьник) на
реальных баллах квиза — см. тесты.

### Почему не составное условие у нового правила

Составное `{"scale":"питон","mode":"argmax","<и>":{"scale":"работа","min_score":3}}`
было бы избыточным: раз правило и так стоит ПОСЛЕ (по id) единственного
argmax-правила на шкалу «питон» (которое уже отфильтровало «питон — не
максимум» случаи через свой собственный argmax), а `работа` argmax'ом быть не
может (иначе сработало бы id=62 раньше) — из «дошли досюда» логически уже
следует «максимум был либо у питона (и исключён), либо ничья». Добавлять
`"all"` в движок ради одного правила, где последовательность id и так даёт
тот же результат — лишняя сущность (anti-bloat).

  fallback-правила действительно матчится на реальных баллах взрослого профиля.

## Что НЕ входит в эту правку

- Сама запись новых значений `assignment_rule` в прод-БД — отдельный шаг
  через `/db-check` (read → план → выборка → транзакция → верификация),
  выполняется мной отдельным заходом сразу после review-gate по этой
  кодовой правке.
- `guest_quiz_service.py` не тронут — контракт `_resolve_recommendation`
  не менялся, только внутренний примитив сопоставления условия.
- Другие правила/шкалы квиза не тронуты.

## Rollback note

Точечное расширение одной функции (обратно совместимое — старые условия без
`"none"` работают идентично). Откат — `git revert` этого коммита в LMS; на
уже записанные (следующим шагом) строки `assignment_rule` откат кода не
влияет, их отдельно вернёт `/db-check` при необходимости (значения до правки
сохраняются в её review-артефакте).
