## Контекст

Курс ЕГЭ разросся (~3000 заданий), прохождение затягивается. Части 2/3: настраиваемый
на подкурс параметр выборки — если EASY+NORMAL заданий подкурса больше порога, студенту
выдаётся не всё, а случайная стабильная часть. THEORY — исключение, всегда всё.

## Design

- **Конфиг** — `courses.sampling_config JSONB NULL`, поле на курсе (не отдельная
  таблица правил, решение оператора). Формат: `{enabled, threshold, easy_ratio}`.
  `threshold` — порог И размер итоговой выборки при превышении (сумма EASY+NORMAL
  заданий курса); `easy_ratio` — доля EASY в выборке (0..1, NORMAL — остаток).
  По образцу уже существующего `tasks.difficulty_provenance` (tsk-381).
  Pydantic-схема — `app/schemas/course_sampling.py`.
- **Сэмплинг** — `app/services/task_sampling.py`, чистые функции без БД:
  - `deterministic_seed(student_id, course_id)` — `sha256(f"{student_id}:{course_id}")[:16]`
    как int. НЕ Python `hash()` — тот рандомизирован `PYTHONHASHSEED` между процессами/
    рестартами и не даёт стабильности между запросами.
  - `sample_task_ids(...)` — отбирает `threshold` id из EASY+NORMAL пулов с долей
    `easy_ratio`; если один пул не дотягивает до своей доли, недостача добирается
    из другого (итог всегда = `threshold`, пока суммарно заданий достаточно).
- **Интеграция** — `learning_engine_service.py`:
  - `_sampling_enabled_courses(db, course_ids)` — один лёгкий запрос по PK; фильтр
    `enabled` в Python (не SQL-каст `::boolean` — битое значение уронило бы запрос
    для ВСЕХ студентов, не только владельца конфига).
  - `_sampled_out_task_ids(db, course_id, student_id, config)` — валидация конфига
    через `CourseSamplingConfig.model_validate` с fail-open (невалидный конфиг →
    пустое множество, лог WARNING, никакого 500 в student-facing пути).
  - `_effective_task_rows(db, course_id, student_id)` — обёртка над
    `_ordered_task_rows`, вычитающая sampled-out. Подключена в ДВУХ точках
    `resolve_next_item` (position-narrowing + `_first_incomplete_task`) — тот же
    список, что видит обход, иначе позиция могла бы указывать на вырезанное задание.
  - `compute_course_state` — денаминатор `total_tasks` тоже уменьшен на sampled-out
    (см. «Находка при реализации» ниже).

## Находка при реализации (не в исходной декомпозиции, но необходима)

Задача явно называла точкой интеграции только `resolve_next_item`. При реализации
обнаружено: `resolve_next_item` сам вызывает `compute_course_state` для gate по
`course_dependencies` и для обновления кеша пройденного узла. Если `total_tasks` в
`compute_course_state` продолжает считать ВСЕ EASY/NORMAL задания (включая вырезанные
выборкой), то подкурс с включённой выборкой **никогда не дойдёт до `COMPLETED`** —
студент решает все ПРЕДЛОЖЕННЫЕ ему задания, но знаменатель всё равно больше числителя
на количество sampled-out. Это заблокировало бы:
- сам подкурс — вечный `IN_PROGRESS`, даже если ученик решил всё, что видел;
- любую `course_dependencies`, ссылающуюся на этот подкурс как на `required_course_id`.

Числитель (`tasks_with_last_pass`) правки не потребовал: у вырезанного выборкой
задания по определению нет `task_result` этого студента (никогда не было предложено).

Исправлено: `compute_course_state` вычитает из `total_tasks` сумму sampled-out по
всем курсам дерева с включённой выборкой (`_sampling_enabled_courses` + `_sampled_out_task_ids`
по каждому). Cтоимость в общем (сегодня — единственном) случае «выборка нигде не
настроена» — один лёгкий запрос по PK, ноль дополнительных JOIN.

Regression-тест на это — `test_resolve_next_item_only_offers_effective_set_and_reaches_completed`
в `tests/test_tsk314_engine_sampling.py`: полный обход + решение только предложенного →
`COMPLETED`.

## Risks / Follow-ups

- **Config drift не переносит прогресс.** Если оператор ПОЗЖЕ поменяет
  `threshold`/`easy_ratio` на подкурсе, где студенты уже что-то решали, набор
  пересчитается с тем же сидом, но новыми целевыми размерами — задание, которое
  студент уже начал решать, теоретически может выпасть из выборки. Текущая
  декомпозиция такого сценария не требовала (никакого «заморозить набор после
  первого показа»); если станет проблемой на реальном контенте — отдельная задача.
- **`compute_course_state` числитель не гарантированно ниже знаменателя после
  ретроактивного enable.** Если задание было пройдено ДО включения выборки, а потом
  выборка его исключила — оно остаётся в числителе (`tasks_with_last_pass`), но
  выходит из знаменателя. Эффект — `COMPLETED` может наступить чуть раньше
  (никогда не блокируется, не уходит в отрицательные величины) — направление риска
  безопасное (fail open в сторону «раньше засчитать», не «никогда не засчитать»).
- **Механизм НЕ активирован ни на одном реальном подкурсе.** `sampling_config`
  везде `NULL` на проде. Нет PATCH-эндпоинта — активация только прямым SQL по
  протоколу `/db-check`, отдельным решением оператора (по инструкции задачи).
- **tsk-178 (чередование)** не реализовано в коде — взаимодействие с выборкой
  архитектурно не проверялось (нечего проверять). Если чередование появится позже —
  сверить с `_effective_task_rows` отдельным чипом.
