# tsk-629: вход через ВК поверх живого сеанса привязывается, а не двоит аккаунт

**Дата:** 2026-08-19
**Скилл:** `/fastapi-api-developer` (+ `/db-check` для разбора данных на проде)
**Задача трекера:** `tsk-629` (P1), найдена при разборе обращения ученика ([tsk-628](../../SPW/reviews/2026-08-19-tsk628-login-loop.md))
**Решение `/review-gate`: ПРИНЯТО**

---

## Зачем

Ученик пожаловался, что не может войти. При разборе выяснилось, что у него **два
аккаунта**: рабочий (вход по почте, два курса) и заведённый входом через ВК —
пустой, без единого курса. Второй такой случай нашёлся сразу же у другого
ученика, зеркально: там курсы остались на ВК-аккаунте, а по почте он попадал в
пустой.

Механика была такая: ВК почту **не отдал** (её отдаёт не всегда), поэтому защита
от совпадения почты (ADR-0021) не срабатывала — сравнивать было нечего, — и
заводился новый пользователь. По логам прода вход через ВК случился **через 21
секунду** после входа по почте, то есть прямо поверх живого сеанса: человек уже
был в кабинете и нажал «Войти через ВК», рассчитывая добавить второй способ
входа.

---

## Что сделано

В `get_or_create_user_by_vk` добавлена одна развилка — **между** проверкой «этот
ВК уже кому-то принадлежит» и созданием нового пользователя:

| Что известно | Что делаем | Изменилось? |
|---|---|---|
| ВК уже закреплён за аккаунтом | входим в него | нет |
| ВК свободен, **сеанс жив** | **привязываем ВК к текущему аккаунту** | **да** |
| ВК свободен, сеанса нет, почта совпала с чужой | 409, слияние запрещено | нет |
| ВК свободен, сеанса нет | заводим нового пользователя | нет |

Живой сеанс — это доказательство владения аккаунтом, поэтому привязка к нему
безопасна. Слияние по совпадающей почте остаётся запрещённым: почту от ВК
провайдер не заверяет, а сеанс заверен нами.

**Порядок веток важен и закреплён тестом.** Если ВК уже принадлежит другому
аккаунту, до новой ветки дело не доходит — сработает обычный вход в аккаунт
владельца. Иначе на общем компьютере второй ученик, забыв про чужой незакрытый
сеанс, привязал бы свой ВК к чужому профилю.

Сеанс определяется мягко (`_live_session_user_id` в роутере): нет cookie,
протухла, отозвана — просто обычный вход через ВК, как раньше.

Отдельно поправлен текст отказа 409: он говорил про почту всегда, хотя причина
теперь бывает и «этот ВК уже привязан к другому профилю» — человек искал бы
проблему не там.

аккаунтов откатом кода не затрагиваются — они уже проверены и корректны.

### Живая проверка на проде (версия `e52e6c4`)

| Проверка | Результат |
|---|---|
| Служба и миграции | `alembic upgrade head` прошёл, служба активна, `/health` → `{"status":"ok"}` |
| Путь входа через ВК жив | негодный код → **401** с понятным отказом; в логе видно, что запрос дошёл до обмена кода с ВК (`device_id is invalid`) — то есть эндпоинт работает, а не падает |
| Кабинет под живой сессией | `/courses` → 200, курсы отрисованы, **все запросы к API 200**, на вход не увело |
| Ошибки приложения после выката | только записи от самой проверки негодным кодом; посторонних нет |
| Данные учеников | оба слияния проверены независимым запросом: у каждого один аккаунт с обеими привязками и курсами |

**Чего проверить нельзя:** полный вход через ВК живьём — для него нужен
настоящий код авторизации от ВК, который выдаётся только реальному человеку в
браузере ВК. Поэтому поведение развилки доказано тестами (все четыре ветки,
включая обе защитные), а на бою проверено, что путь входа исправен и кабинет
работает.
