## 0. Важное изменение обстановки: подписки уже расставлены

## 1. Пятеро: причина по каждому отдельно

Общий механизм: сумма месяца считается только если у ученика есть **тарифная
группа** И **цена в этой группе разрешилась**. Цена в группах 1 и 6 подбирается
по числу активных слотов в неделю (`match_kind='attendance_frequency'`). Нет
слотов → статус `no_schedule` → цены нет → строки месяца нет.

## 3. Что будет, если нажать «Пересчитать месяц» за август прямо сейчас

Смоделировано SQL по той же формуле, что в коде (группа → частота → тариф →
доля за вычетом перерыва, округление вниз):

- **прибавится ровно одна строка**: Терехов Илья, группа 6, 10 занятий по
  расписанию, перерывов нет → **6 000 ₽**;
- **все 37 существующих строк остаются с теми же суммами** — сверено построчно,
  включая нестандартные: Грабовский 4400 ₽ (2 занятия в перерыве), Костенков 0 ₽
  (весь месяц в перерыве), Харькова 3055,55 ₽ (4 занятия в перерыве), четыре
  ручные цены по 5500 ₽;
- ничего не удалится.

То есть пересчёт августа безопасен. Но он **не** решает вопрос с четырьмя
остальными — им сумму считать не из чего, пока не решено про расписание и тариф.

## 4. Почему месяц не создаётся сам

В `app/api/main.py` восемь фоновых заданий, про начисления нет ни одного.
Строка месяца появляется только:

1. `charge_service.recalculate_open_months_for_student` — из
   `lesson_calendar_service` при изменении расписания ученика;
2. руками: `POST /charges/recalculate` из кабинета маркетолога.

На проде в `student_monthly_charge` ровно один период — август 2026 (37 строк,
168 055,55 ₽, созданы 01.08–03.08 руками). **1 сентября не выставится ничего.**

Само по себе повторение пересчёта безопасно: вставка идёт с
`ON CONFLICT DO NOTHING`, открытый месяц переписывается, закрытый не трогается
(расхождение уходит поправкой в следующий месяц). Значит планировщику достаточно
звать существующий `recalculate_month` — новую логику расчёта писать не нужно.

## 5. Побочная находка вне охвата задачи: генератор занятий не запускается

В `app/api/main.py:510-511` два декоратора `@app.on_event("startup")` подряд, и
из-за этого функция `_start_lesson_occurrence_generator_scheduler` (строка 528)
осталась **без декоратора вовсе**.

Внесено коммитом `066002e` (tsk-572 фаза 7): новый обработчик вставили ровно
между декоратором и функцией генератора занятий.

Следствие: фоновая генерация занятий (tsk-428) на проде **не стартует** —
занятия появляются только как побочный эффект правок расписания.

**Подтверждено на живом проде, а не выведено из кода** (2026-08-09):

```
grep -c 'tsk-428|lesson_occurrence_generator'  /opt/lms/logs/app.log →  0
grep -c 'tsk-521'   (проверка ссылок)          /opt/lms/logs/app.log → 21
grep -c 'learning_gaps' (датчик пробелов)      /opt/lms/logs/app.log → 42
```

Соседние тики пишут в лог, генератор занятий не пишет ничего. Исходник на
сервере (`sed -n '505,532p' /opt/lms/app/api/main.py`) показывает ту же пару
декораторов подряд и функцию без декоратора.

Чинится одной строкой; оператор 2026-08-08 разрешил починить здесь же.
