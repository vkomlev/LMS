# /review-gate — tsk-564: глобальный поиск задания/материала в кабинете методиста

**Дата:** 2026-08-05
**Проекты:** LMS + SPW
**Тип:** закрытие утечки данных (`solution_rules`) + подключение существующего backend-поиска к фронтенду

## Контекст

Разведка (см. `D:\Work\Root\tasks\tsk-564-*.md`) нашла: `GET /api/v1/tasks/search`
и `GET /api/v1/materials/search` существовали давно, но не были подключены ни
к одному фронтенду. `/tasks/search` при этом звал `TaskRead.model_validate(task)`
напрямую вместо привилегированного `_task_read_for` и сидел на legacy `get_db`
(любой валидный API-ключ, без разбора роли) — держатель ЛЮБОГО сервисного
ключа мог вытащить `solution_rules` (верные ответы) поиском по тексту/курсу.
Тот же класс утечки, что tsk-460 закрыл для трёх других эндпоинтов.

## Решение: ПРИНЯТО

## Проверка по 12 измерениям

1. **Соответствие целям** — все 6 пунктов декомпозиции покрыты: (1) `/tasks/search`
   переведён на `_STRUCTURE_GATE`, `solution_rules` через `_task_read_for`; (2)
   `/materials/search` — тот же гейт для единообразия; (3) SPW-компонент по
   образцу `TaskSearchBox`/tsk-353, новая страница `/methodist/search` + иконка
   в шапке; (4) одно поле + две секции результатов (решение задокументировано в
   `.skill-engaged-note.md`); (5) тесты auth-гейта + утечки + SPW; (6) живой
   прогон в браузере под методистом. DRIFT не обнаружен.

2. **Корректность** — `_STRUCTURE_GATE` пропускает `is_service` bypass (сервисный
   ключ) и роли `methodist`/`admin`; оба случая по семантике `_task_read_for`
   привилегированы (сверено с `assert_task_access`, где `is_service` и
   extended-role одинаково дают `privileged=True`). `course_id`-фильтр
   регресс-тестирован. Edge case: короткий запрос (`min_length=2`/`1`) не
   менялся, поведение прежнее.

3. **Безопасность данных/миграций** — миграций нет, схема не менялась.

4. **Безопасность и секреты** — IDOR sweep: у обоих эндпоинтов нет
   `{user_id}`/`{attempt_id}`-путей, только `q`/`course_id`/`limit`/`offset` —
   не применимо. Утечка `solution_rules` закрыта СТРУКТУРНО: непривилегированный
   вызывающий получает 403 до формирования тела ответа, а не `solution_rules:
   null` внутри 200 (сильнее исходной формулировки декомпозиции — гейт уже не
   пускает никого, кому нужно было бы обнулять поле).

5. **Покрытие тестами** — LMS: `tests/test_tsk564_methodist_search.py` (10
   тестов: 401 без auth, 403 student, 200 methodist/admin с непустым
   `solution_rules`, 200 сервисный ключ (регресс TG_LMS), фильтр по чужому
   `course_id` → пусто, аналогично для materials). Полный `pytest` — 1711
   passed, 11 skipped, 0 failed. SPW: `tests/unit/methodist-global-search.test.tsx`
   (4: пустой ввод, результаты+ссылки на карточки, «не нашли», дебаунс).
   Полный `vitest` — 1008 passed. Живой прогон в браузере (Kate Silver,

   пробел (non-blocking):** нет отдельного admin-теста для
   `/materials/search` — тот же `_STRUCTURE_GATE`, что уже покрыт
   admin-тестом для `/tasks/search`; дублирование теста идентичной гейт-
   функции сочтено избыточным (DRY), риск низкий.

6. **Docs/Config/Runtime Drift** — `docs/ai/PROJECT_MEMORY.md`/`AGENTS.md` не

## Находки

Блокирующих не найдено.

Non-blocking (не требуют правки перед закрытием):
- Отсутствие экранирования `%`/`_` в ILIKE-паттерне обоих `/search`
  (`f'%{q}%'` без escape) — не инъекция (SQLAlchemy параметризует значение),
  чисто UX-квирк при поиске буквального `%`. Существовало до этой задачи,
  вне охвата декомпозиции tsk-564, аналогичный сосед (`task_search_service.py`
  для tsk-353) уже экранирует — можно унифицировать отдельной задачей, если
  оператор сочтёт нужным.
