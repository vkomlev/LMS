# tsk-701 — приём ответа не проверял активность задания (`tasks.is_active`)

Дата: 2026-08-26 · Ветка: `main` · Diff: `2026-08-26-tsk701-inactive-task-answer-gate.diff`

## Контекст

Хвост линии tsk-695 (материал) → tsk-697 (`GET /tasks/{id}`, `/tasks/by-external/{uid}`
→ 404 ученику) → tsk-696/tsk-700 (клиентская фильтрация в ТГ-ботах) → tsk-699
(`GET /tasks/by-course/{id}`). Чтение выключенного задания ученику закрыли,
**запись — нет**.

`POST /api/v1/attempts/{attempt_id}/answers` проверял три вещи: владение попыткой,
запись ученика в курс задания (`assert_task_access`, tsk-272) и вхождение задания в
дерево корня попытки (`root_contains_course`, tsk-264). Активности среди проверок не
было: ответ по снятому с публикации заданию проверялся `CheckingService` и ложился в
`task_results` — то есть попадал в прогресс, статистику освоения и расход лимита
попыток по контенту, которого для ученика больше нет.

## DB Findings (MCP `learn_prod_db`, read-only, 2026-08-26)

| Факт | Значение |
|---|---|
| Заданий всего / выключено | 7629 / **1220** |
| Выключенных заданий с записями в `task_results` | **443** |
| Строк `task_results` по выключенным заданиям | **1552**, 7 учеников, 20–22 июля |
| Из них `source_system = 'manual_teacher'` | **1552 (все)** |
| Настоящих сдач ученика по выключенному заданию | **0** |
| Выключений в `task_audit` (с 5 по 14 августа) | 201, ни у одного из этих заданий нет результатов вообще |

Ключевой вывод: все 1552 строки — **пакетные ручные зачёты преподавателя**
(442 задания за две минуты на ученика), а это отдельный путь записи —
`manual_progress_service.grant_task` пишет `attempts` и `task_results` сырым INSERT
мимо разбираемой ручки. Правка его не касается и касаться не должна: преподаватель
закрывает старый долг осознанно.

Случая «ученик сдал после выключения» на проде не было ни разу: у `task_results` нет
ни одной строки с `source_system != 'manual_teacher'` по выключенному заданию, а по
201 заданию с известной датой выключения нет результатов вообще. **Дыра реальна в
коде и никогда не была использована — правка предупредительная, чистка данных не
нужна.**

Схема: `tasks.is_active` — `boolean NOT NULL DEFAULT true`, NULL-веток нет.

## Решение

**Отказ ученику**, а не приём с пометкой. У пометки нет потребителя: ни один экран и
ни один расчёт (прогресс, освоение тем, лимит) не умеет отличать результат по снятому
контенту, а значит пометка означала бы «принять и всё равно испортить». Риск «ученик
потерял работу, потому что методист выключил задание при открытой странице» на проде
не подтверждён (0 сдач), а сам ученик до выключенного задания через интерфейс не
доходит: `/learning/tasks/{id}/state` отдаёт 404 давно, и SPW рисует «Задача
недоступна».

**Отсечка по владельцу попытки, а не по вызывающему.** `assert_task_access` возвращает
`privileged` для ВЫЗЫВАЮЩЕГО, и опереться на него здесь нельзя: все боты TG_LMS ходят
по сервисному ключу, поэтому bypass по транспорту означал бы «через браузер нельзя,
через Telegram можно». Это ровно та дыра, которую в чтении пришлось закрывать
клиентской фильтрацией в ботах (tsk-696, tsk-700) — повторять её на записи нельзя.
Модель взята у `payment_access_service.assert_content_allowed` (tsk-617) и
`graduation_service.assert_course_work_allowed` (tsk-673), которые в этой же ручке уже
считают по `attempt.user_id`. Владелец попытки с ролью teacher/methodist/admin
проходит: превью «как ученик» и разбор старой сдачи — его законные сценарии.

**400, а не 404** как на чтении. На чтении 404 скрывал сам факт существования; здесь
скрывать нечего — `assert_task_access` выше уже прошёл, то есть ученик зачислен на
курс задания. При этом 404 на этой ручке означает «попытка не найдена», а 400 — код
остальных поштучных отказов того же цикла (задание не найдено, задание вне дерева
корня). Текст отказа человеку понятен: SPW печатает `detail` в тосте
(`lib/api-error-messages.ts`), правки фронта не нужны.

Гейт стоит **до записи**, per-item — отказ по одному заданию не оставляет частичный
результат по остальным (проверено тестом).

## Живая проверка на проде (после выката, та же сессия)

Выкат: `Deployed: bdd6063`, `/health` 200. Проверка — HTTP к боевому API
(`127.0.0.1:8000` на сервере, сервисный ключ из `/opt/lms/.env`), задания реальные:
6246 (курс 1064, SC, `is_active = false`) и 4995 (курс 139, SC, активное, верный
вариант `C`).

| Сценарий | Ожидалось | Факт |
|---|---|---|
| A. Сервисный ключ на попытке **ученика 142** + выключенное 6246 | 400 | **400** `"Задание снято с публикации и больше не принимает ответы."` |
| B. Та же попытка, активное 4995 | 200 | **200**, `is_correct=true`, `score=1` |
| C. Попытка **персонала (id 2**, admin/methodist/teacher) + выключенное 6246 | 200 | **200**, результат записан |
| D. Пачка «выключенное + активное» на попытке ученика | 400 и НИ ОДНОЙ записи | **400**, `task_results` по попытке 12874 — **0 строк** |

Сценарий A — главный: он доказывает, что отсечка идёт **по владельцу попытки**, а не
по транспорту. Тот же вызов до правки прошёл бы: сервисный ключ проходит
`assert_task_access` насквозь.

Журнал прода подтверждает срабатывание, а не «просто 400 откуда-то»:

```
{"level":"INFO","logger":"app.services.tasks_acl_service",
 "message":"tsk-701: deny answer student_id=142 task_id=6246 (is_active=false)"}
```

Состояние БД после сценария B/C: у попытки 12872 записан результат **только** по
активному 4995, по выключенному 6246 — ничего; у попытки 12873 (персонал) результат по
6246 записан. То есть обе ветки гейта видны в данных, а не только в кодах ответа.

**Уборка:** попытки помечены `source_system='live-check-tsk701'` и удалены вместе с
двумя строками `task_results` через `scripts/tsk701_cleanup_live_check.py --apply`
(протокол `/db-check`: чтение → план → одна транзакция → верификация). После уборки:
попыток по метке 0, строк 18441/18442 нет, сдач ученика по выключенным заданиям на
проде по-прежнему **0**.

## Risks / Follow-ups

1. **Гостевой и embed-контур не покрыт.** `learning_guest_service.get_demo_task`
   выбирает задание только по `Courses.is_public_demo`, без `Tasks.is_active`; так же
   `POST /embed-api/auth/issue`. На проде в демо-курсах 63 выключенных задания из 4146.
   Это соседний класс (гость, запись идёт в `guest_attempts`, а не в `task_results`) —
   отдельной задачей, чтобы не расширять охват этой.
2. **`manual_progress_service` осознанно не тронут** — преподаватель вправе закрыть
   долг по снятому заданию.
3. Один лишний запрос (`_user_has_extended_role`) выполняется **только** когда задание
   выключено, то есть на нормальном пути стоимости нет.
