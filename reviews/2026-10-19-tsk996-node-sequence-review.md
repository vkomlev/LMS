## Что ревьюировалось

Рефакторинг без изменения поведения: порядок «материалы узла → подразделы → задания узла»
собирается одной функцией `app/services/node_sequence.py` для всех мест обхода; прежний
код сохранён за рубильником `NODE_SEQUENCE_ENABLED=false`. Тест эквивалентности
`tests/test_tsk996_node_sequence.py`, read-only скрипт `scripts/tsk996_sequence_snapshot.py`.

## Проверено ревьюером (по коду и прогоном)

- Курсор next-item (`_locate_item_position` + `_next_in_root_by_sequence`) совпадает с прежним во
  всех крайних случаях: позиция на `recommended`/неактивном элементе, `host_alt` прозрачного
  подкурса, материал поглощённого подкурса, позиция вне дерева.
- `material_seq_key(op, id, cid) == (SEG_HEAD, cid, _order_key(op, id))` — внутри шага `cid`
  постоянен, сравнение совпадает с прежним.
- Пустые шаги запросов не делают; логи и поля `NextItemResult` те же.
- `_walk_plan` эквивалентен прежней рекурсии: дедупликация tsk-261, порядок `get_child_rows`,
  post-order.
- Syllabus/прогресс: ключ с `_src_course_id` воспроизводит SQL `course_id, order_position, id` для
  материалов прозрачного подкурса; вынесенные `_syllabus_*_item`/`_course_item` побайтно равны
  прежним словарям; служебные ключи в ответ не попадают.
- Число запросов next-item (прежний/новый): старт 15/15, после материала 34/34, после задания 22/22.
- Мутационная проверка ревьюера (через плагин pytest) — тест ловит подмены.
- Скрипт снимка — только чтение; после ошибки транзакция переоткрывается как READ ONLY.

## Собственная мутационная проверка исполнителя

8 намеренных порч нового кода — все пойманы тестом эквивалентности: обратный порядок заданий
в хвосте; курсор `>=` вместо `>`; материалы прозрачного подкурса без учёта курса; подразделы в
обратном порядке; syllabus по id; строка узла в карточке прогресса в хвосте; предпросмотр в
обратном порядке; grace в обратном порядке внутри шага. Скрипт снимка на порче порядка
возвращает код 1 и показывает первую разницу.
