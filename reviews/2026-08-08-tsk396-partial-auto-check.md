# tsk-396 — гибридный режим проверки: авто-сверка части ответа + обязательный ручной гейт

**Дата:** 2026-08-08 · **Задача:** tsk-396 (заменяет обход tsk-395) ·
**Решение ревью:** ПРИНЯТО (с одной находкой, исправленной в ходе гейта) ·
**Diff:** [2026-08-08-tsk396-partial-auto-check.diff](2026-08-08-tsk396-partial-auto-check.diff)

## Контекст

Класс заданий, где часть ответа формализуема, а часть проверяет только человек:
ОГЭ-14 (курс 1179) — два числовых ответа плюс построение круговой диаграммы.
Движок так не умел: `manual_review_required=true` подавлял авто-вердикт целиком.

## Что выяснилось до написания кода (важнее исходной постановки)

Задача исходила из того, что при `manual_review_required=true` ученик НЕ получает
проходной балл до ручной оценки, и что это намеренная защита. **Живая проба опровергла это.**

`checking_service` действительно отдаёт `is_correct=None, score=0`, но `attempts.py` 2.3d
затем применяет оптимистичный зачёт по условию `check_result.is_correct is None`. У
SA_COM/TBL_COM этот признак возникает по ДВУМ разным причинам — «эталона нет» (замысел
tsk-210) и «эталон есть, но включён ручной гейт» (tsk-230). Вторая попала в условие не по
замыслу: `_check_short_answer` короткозамыкает ДО чтения `short_answer`-правил.

Проба (SA_COM, `manual_review_required=true`, эталон `12 516,30`, ответ `999 999`):

```
task_state = state=PASSED, last_score=1/1, last_is_correct=True, last_checked_at=None
```

Заведомо неверный ответ засчитывался сразу, курс кредитовался до проверки человеком.
Обход tsk-395 не держал гейт, на который рассчитывал. Затронуто 45 активных заданий прода
(25 ОГЭ-14 курса 1179 + 20 «напиши программу целиком» в курсах 864–869, 1405–1415).

## Решение

Разведены две оси; подробности и отклонённые варианты — [ADR-0007](../docs/ai/adr/0007-partial-auto-check-manual-gate.md).

- **Новый флаг `solution_rules.partial_auto_check`** (opt-in, default false). Требует
  `manual_review_required=true` и непустой эталон — иначе `422` при заведении задания.
- **Авто-сверка выполняется**, её итог сразу виден ученику в `feedback`; **`score`
  остаётся нулевым всегда** до ручной оценки (движок гейтит PASS по
  `score/max_score >= 0.5`, поэтому авто-часть балла не касается).
- Числа сошлись → `is_correct=None`, работа в обязательной очереди. Не сошлись →
  `is_correct=False`, в очередь НЕ попадает: ученик правит сам (решение оператора).
- **Эталон не раскрывается**: `details` в этом режиме не заполняется.
- **Корень дефекта:** условие оптимистичного зачёта переведено с `is_correct is None` на
  `not solution_rules.has_reference_answer()` — то, что и описывал комментарий в коде.
  Миссии без эталона зачёт сохраняют, задания с эталоном + ручным гейтом — нет.
- Диаграмма сдаётся **обязательным файлом** через существующий `requires_attachment`
  (tsk-227 + tsk-575). Нового слоя медиа-загрузки не потребовалось — поправка к оценке
  объёма в задаче.

## Находка гейта (исправлена в ходе ревью)

**Эскалация не видела ждущие работы режима.** `escalation_service` ловит SA_COM/TBL_COM с
`is_correct IS TRUE` (оптимистичный зачёт), а гибридный режим даёт ЖДУЩЕЙ работе
`is_correct=NULL`. Без правки залежавшаяся работа ОГЭ-14 не эскалировалась бы методисту
никогда — рецидив класса tsk-438 (там тот же тихий провал был у SA-manual). Добавлена
ветка + тест `test_pending_hybrid_work_is_escalated`.

## Смежный дефект — НЕ мой, заведён отдельно

Крон эскалации отбирает кандидатов условием
`metrics IS NULL OR (jsonb_typeof(metrics)='object' AND NOT metrics ? 'escalated_at')`, но
на сдаче в `metrics` попадает **JSON-null**, а не SQL NULL. Замер прода (2026-08-08):
SQL NULL — **0 строк вообще**; `jsonb null` — 1912 строк, из них **1910 непроверенных**;
`jsonb array` — 8, все непроверенные. То есть методист не получает уведомления о 1918
зависших работах. Дефект шире tsk-396 и чинить его молча нельзя: первый тик после правки
разошлёт накопленную за месяцы очередь. Заведён отдельной задачей.

## Риски и follow-ups

- **Не закоммичен `docs/openapi.json`.** В рабочем дереве есть ЧУЖОЙ незакоммиченный код
  (tsk-032, retention/dashboard), а pre-commit регенерирует схему из ВСЕГО дерева —
  коммит схемы унёс бы чужую работу. Схема самовосстановится на следующем коммите в этом
  репозитории. По этой же причине поля в SPW `lib/api-types.ts` добавлены точечно, а не
  полной перегенерацией.
- Ученик видит «числа сошлись» — при малом числе вариантов это канал подбора; сдерживается
  лимитом попыток и тем, что числа ОГЭ-14 считаются по файлу-таблице.
- Преподаватель больше не увидит работы с неверными числами — намеренно, решение оператора.
- Миграция данных курса 1179 выполняется отдельным скриптом ПОСЛЕ выката кода: до выката
  `requires_attachment=true` подействовал бы без сопровождающей обратной связи.
