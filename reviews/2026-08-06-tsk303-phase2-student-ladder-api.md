## Что закрыто

Главный пробел, найденный при планировании: **у ученика не было способа
увидеть на странице задания, что стало с его заявкой**. Ответ преподавателя
долетал только уведомлением в общей ленте, а сама страница о заявке не знала.
Без чтения состояния кнопкам «Вернуть заявку» и «Запросить разбор» негде
появиться.

## Новые эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/learning/tasks/{task_id}/help-request` | состояние заявки ученика по заданию (`null`, если не просил) |
| POST | `/learning/help-requests/{id}/reopen` | уровень 1 → повтор: «ответ не помог» |
| POST | `/learning/help-requests/{id}/request-individual-review` | уровень 2: запрос разбора |
| POST | `/learning/help-requests/{id}/rate-review` | уровень 3: оценка после разбора |

`openapi.json` перегенерирован: 265 → **269** эндпоинтов.

## Ключевые решения

**Гейты уровней считает сервер, не клиент.** Ответ GET несёт `can_reopen`,
`can_request_individual_review`, `can_rate_review` — те же условия, что
проверяют сами операции. Второй экземпляр правил в UI неизбежно разъехался бы
с сервером, и ученик получил бы кнопку, отдающую 409 при нажатии. Сквозной
тест `test_full_ladder_flow_visible_to_student` фиксирует именно связку
«признак → операция».

**`student_id` не приходит из тела запроса** ни в одной из трёх операций.
Владелец берётся из самой заявки (для сервисного ключа) либо из сессии (для
человека), поэтому подставить чужой нечем, а перебор `request_id` упирается в
403. Негативный тест есть на каждый из трёх маршрутов с `{id}` — проверка
владельца своя в каждой операции, и пропуск в одной из них общим тестом бы не
поймался.

**Двойной клик сериализован.** Каждый шаг берёт advisory-лок по заявке в
отдельном пространстве ключей (`303`), чтобы не пересечься с уже имеющимися
локами по паре (ученик, задание) для `blocked_limit`. Без этого два «Вернуть
заявку» дали бы две строки возврата — то есть задвоенный KPI преподавателя.

**Оценка принимается ровно один раз.** Это развилка маршрута, а не мнение:
«понятно» после «непонятно» закрыло бы заявку, которую уже забрал методист, а
обратный порядок повторно дёрнул бы методистов.

**Эскалация не закрывает заявку.** При «непонятно» заявка остаётся открытой —
методисту с ней ещё работать. Закрывает он её через уже существующий
`POST /teacher/help-requests/{id}/close` (методист входит в ACL заявок по
роли); новый канал закрытия не заводился. Уведомление получает новый вид
`help_request_escalated`, и он **сразу добавлен в
`GET /methodist/escalations/pending`** — иначе уведомление создавалось бы, а
показать его было бы негде (тест проверяет видимость в очереди, а не только
факт записи).

**TTL вебинар-ссылки реализован в `close_help_request`** — закрытие учителем,
системное закрытие и подтверждение ученика после разбора обнуляют ссылку.

> **Поправка (фаза 3).** Утверждение «единственная точка закрытия» оказалось
> неверным: вторая живёт внутри `reply_help_request` (ответ с закрытием) и
> обнуления не делала. Исправлено в фазе 3, с тестом — см.
> `2026-08-06-tsk303-phase3-4-teacher-kpi-feedback.md`.

**Гейт оплаты применён избирательно.** `reopen` и
`request-individual-review` — новые требования к времени преподавателя, гейт
тот же, что у `request-help`. Чтение состояния и `rate-review` — без гейта:
читать состояние собственного обращения должник вправе, а блокировка оценки
оставила бы заявку висеть открытой без маршрута дальше.

**Новых записей в `learning_events` нет — сознательно.** Все три шага durable
отражены в доменных таблицах (`help_request_reopens`, `request_type`,
`escalated_to_methodist_at`), а `learning_events` в приложении никем не
читается: второй, несогласуемый источник правды был бы чистым удорожанием.

## Находка review-gate (исправлена в этой же фазе)

**Гейт уровня 2 был уже формулировки оператора.** Первая реализация считала
повтором только возврат этой заявки. Но оператор задал условие как «второй
запрос помощи именно по этому же `task_id`», а `request-help` дедуплицирует
обращения лишь коротким окном — то есть ученик достижимо заводит по одному
заданию **вторую заявку**, не нажимая «Вернуть заявку». Такому ученику —
ровно тому, кто просил помощь дважды, — разбор бы не открылся.

Исправлено: `_repeat_ask_count` считает оба вида повтора (возвраты этой
заявки + другие заявки лестницы по тому же заданию), и на нём стоят и признак
`can_request_individual_review`, и гейт самой операции. Тест
`test_second_help_request_on_same_task_also_opens_review`. Формулировка
ошибки 409 приведена к тому же смыслу («после повторного обращения по этому
заданию», не «после возврата»).

## Атрибуция возврата (то, ради чего в фазе 1 была таблица)

Возврат начисляется тому, **чей ответ не помог** — `closed_by` на момент
возврата, с откатом на `assigned_teacher_id` при системном закрытии. Снимок
делается до очистки полей закрытия, иначе атрибутировать было бы нечем.
Проверено тестом с расхождением: назначен один преподаватель, ответил другой —
возврат достаётся ответившему.

## Закрыт блокер фазы 3

Проверено в `D:\Work\TG_LMS`: бот преподавателя зовёт
`reply_teacher_help_request` **с жёстко заданным `close_after_reply=False`**
(единственная точка вызова, `src/bots/common/dialogs/help_requests_base.py:565`)
и после ответа остаётся на карточке заявки.

**Вывод: форс-закрытие на сервере затронет бота.** `reply_help_request`
отвечает 409 на ответ в закрытую заявку, а бот раскладывает 409 как конфликт
блокировки (`MSG_409_LOCK`) и сбрасывает диалог в режим claim-next. То есть
обычный сценарий «ответил, потом дописал уточнение» после форс-закрытия дал бы
преподавателю ложное сообщение про блокировку. Правится в фазе 3 вместе с
ботом; развилки нет — правило «ответ текстом закрывает заявку» оператор
зафиксировал.

## Risks and Follow-ups

- **Прод не тронут.** Ни миграция фазы 1, ни эти эндпоинты не выкачены —
  выкат общий, после фазы 4.
- **Дата/время.** `escalated_to_methodist_at` пишется через `now()` в SQL и
  нигде не сравнивается в Python — класс из `docs/ai/ERRORS.md` (2026-03-03)
  не задет. Останется актуальным для фазы 6, если KPI-панель начнёт сравнивать
  `reopened_at` со временем в коде.
- **Фаза 3** — сторона преподавателя: эндпоинт вебинар-ссылки, форс-закрытие
  `manual_help` + парная правка бота TG_LMS (см. выше).
