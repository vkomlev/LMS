# tsk-539 — очередь проверки: фильтр по ученику/датам + пагинация (LMS)

## Контекст

Запрос оператора 2026-08-03 после приёмки [[tsk-372]]: «Добавь на этом экране
ещё фильтр по ученику и датам. И ленивую загрузку или пагинацию, так как
список обрывается».

Список действительно обрывался: SPW-хук жёстко брал `limit=100`, а после
tsk-372 follow-up в очереди 930 работ — 830 были недостижимы вообще.
`limit`/`offset` на бэкенде уже были (с tsk-298), не использовались фронтом.

## Plan

1. `list_pending_reviews` — четыре новых опциональных параметра:
   - `user_id` — точный ученик (SQL-фрагмент скопирован с `claim_next_review`,
     где `user_id` уже был — единый паттерн, не новая идея);
   - `student_name` — `ILIKE '%...%'` по `users.full_name` (для UI, где ID
     ученика неизвестен). Потребовал `LEFT JOIN users u` в count-запросе —
     раньше он был только в page-запросе;
   - `submitted_from`/`submitted_to` — тип `date`, обе границы включительно.
2. Верхняя граница переводится в exclusive `+1 день` **в Python**, а не через
   SQL `INTERVAL`: иначе результат зависел бы от таймзоны сессии БД. Без этого
   работа, сданная в 15:30 дня `submitted_to`, не попала бы в выборку (день
   обрезался бы по полуночи) — на это есть отдельный тест.
3. Эндпоинт — те же параметры + валидация `submitted_to < submitted_from` →
   422 «Конец периода раньше начала» (дословно тот же паттерн и текст, что в
   `marketer_payments.py:142-145`, чтобы не плодить диалектов).
4. `student_name` с `min_length=2` на уровне Query — короче двух символов
   422, а не молчаливая выдача всей очереди.

## Тесты (что именно проверено)

- `user_id` оставляет работы только этого ученика;
- `student_name` находит по части имени в другом регистре (ILIKE);
- `student_name` короче 2 символов → 422;
- диапазон дат включителен с обеих сторон — работа, сданная в 15:30 дня
  `submitted_to`, попадает в выборку (ловит ошибку обрезания по полуночи);
- инвертированный диапазон → 422;
- `limit`/`offset` режут страницы, страницы не пересекаются, хвост короче
  `limit`, `total` остаётся полным (5), а не размером страницы, FIFO-порядок
  сохраняется между страницами;
- фильтры ортогональны `review_kind` (комбинируются через AND).

## DB Findings

Data impact: read-only (новые query-параметры существующего SELECT). Схема не
менялась, миграция не нужна.

## Risks / Follow-ups

- `student_name` — `ILIKE '%...%'` без индекса. На текущих объёмах
  (`users` — тысячи строк, выборка уже сужена ACL + `checked_at IS NULL`)
  это несущественно; если очередь вырастет на порядок — смотреть в сторону
  `pg_trgm`. Сознательно не оптимизирую заранее.
- Фильтры не влияют на `pending-count`/`workload` (бейдж в шапке) — он и
  раньше был про обязательную очередь целиком, см. tsk-372.
