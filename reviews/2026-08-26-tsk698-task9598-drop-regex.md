# tsk-698 — задание 9598: снят обход `use_regex`

**Дата:** 2026-08-26 · **Проект:** LMS · **Курс:** 1407 (Мехатроника, Arduino `map()`) ·
**Связано:** обход поставлен в tsk-687, общая причина починена в tsk-694

## Почему обход нельзя было снять «просто так»

Ожидание было: раз tsk-694 научил `strip_punctuation` ставить пробел вместо удаления знака,
задание 9598 заработает и без regex. **На деле — нет:** у 9598 в `normalization` этого шага
и не было (`["trim", "collapse_spaces", "code_ast"]`), а `code_ast` на Arduino-коде падает и
откатывается к тексту. Прогон реальных сдач показал: снятие одного лишь regex завернуло бы
**6 из 7** ранее принимавшихся ответов.

Второе: единственный эталон был `int urovenj = map(syroe, 0, 1023, 0, 50);`, а стем просит
дописать команду к уже объявленной переменной — ответ без `int` тоже верен, и regex это
допускал (`(int\s+)?`).

## Что сделано

Правка `tasks.solution_rules->'short_answer'` у задания 9598 ([scripts/tsk698_task9598_drop_regex.py](../scripts/tsk698_task9598_drop_regex.py)):

| ключ | было | стало |
|---|---|---|
| `use_regex` | `true` | `false` |
| `regex` | `(int\s+)?urovenj\s*=\s*map\s*\(…\)\s*;?` | `null` |
| `normalization` | `[trim, collapse_spaces, code_ast]` | `[trim, strip_punctuation, collapse_spaces, code_ast]` (канон для кода) |
| `accepted_answers` | 1 эталон (с `int`) | +`urovenj = map(syroe, 0, 1023, 0, 50);` (score 1) |

Остальные ключи `solution_rules` не тронуты (проверено сравнением набора ключей и `max_score`).

## Протокол записи в боевую базу

Чтение состояния → план → выборка реальных сдач → `SELECT … FOR UPDATE` в транзакции →
`UPDATE` → верификация в той же транзакции → `COMMIT`. Скрипт **сам откатывается**, если
regex в базе не совпал с ожидаемым или если хоть один ранее принимавшийся ответ перестаёт
проходить.

Вердикты по 7 различным реальным сдачам + 2 контрольным неверным ответам:

| ответ | было | стало |
|---|---|---|
| `urovenj=map(syroe,0,1023,0,50);` | зачёт | зачёт |
| `int urovenj=map(syroe,0,1023,0,50);` | зачёт | зачёт |
| `urovenj=map(syroe ,0 ,1023 ,0 ,50);` | зачёт | зачёт |
| `urovenj=map(syroe , 0 , 1023 , 0 , 50);` | зачёт | зачёт |
| `urovenj=map(syroe, 0, 1023 ,0 ,50);` | зачёт | зачёт |
| `urovenj=map(syroe, 0, 102 , 0, 50);` (опечатка) | незачёт | незачёт |
| `int urovenj = map(syroe, 0, 102 , 0, 50);` (опечатка) | незачёт | незачёт |
| `urovenj = map(syroe, 0, 1023, 0, 500);` (контроль) | незачёт | незачёт |
| `urovenj = map(syroe, 0, 1023);` (контроль) | незачёт | незачёт |

Баллы задним числом не пересчитывались.

## Живая проверка на проде

Правила прочитаны **из боевой базы** и прогнаны **выкаченным кодом на сервере**
(`sudo -u app /opt/lms/venv/bin/python`): `use_regex: False`,
`steps: [trim, strip_punctuation, collapse_spaces, code_ast]`;
`urovenj=map(syroe,0,1023,0,50);` → зачёт, вариант с `int` → зачёт, опечатка `102` → незачёт.

Сдачу через HTTP не делал намеренно: курс 1404 доступен только живому ученику 4509, и сдача
от его имени исказила бы его историю. Проверка на сервере отвечает на тот же вопрос
(как прод судит этот ответ) без записи в данные ученика.

## Что стало слабее

Текстовая сверка мягче регулярки: она игнорирует все знаки, поэтому ответ без скобок
(`urovenj map syroe 0 1023 0 50`) теперь тоже пройдёт. Числа и имена по-прежнему значимы —
именно на них ломались реальные ошибки учеников. Цена принята осознанно: обход в виде
`use_regex` был точечной заплаткой на одном задании, и держать его дороже, чем эту слабость.
