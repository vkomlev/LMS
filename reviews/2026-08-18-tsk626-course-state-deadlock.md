# tsk-626 — взаимоблокировка на кеше состояний курсов

**Дата:** 2026-08-18
**Проект:** LMS Core API
**Класс:** отказ на проде (500 ученику), устраняется причина, а не ответ
**Ветка:** `worktree-tsk-626-deadlock`

---

## 1. Что случилось

17.08.2026 в 12:56:38 UTC на проде `GET /api/v1/learning/next-item` упал с
`asyncpg.exceptions.DeadlockDetectedError`. Ученик получил 500.

```
Process 1599269 waits for ShareLock on transaction 832460; blocked by process 1599234.
Process 1599234 waits for ShareLock on transaction 832461; blocked by process 1599269.
[SQL: INSERT INTO student_course_state (student_id, course_id, state, updated_at)
      VALUES ($1,$2,$3, now())
      ON CONFLICT (student_id, course_id) DO UPDATE SET state = EXCLUDED.state, updated_at = now()]
[parameters: (3, 1455, 'NOT_STARTED')]
```

Это отдельный класс от перегрузки пула (tsk-624): под обработчик 503 он не
попадает и до правки отдавал голую 500.

---

## 2. Что показала боевая база (read-only, MCP)

Запрос по строкам кеша ученика 3 и по всей таблице:

| Замер | Значение |
|---|---|
| Всего строк `student_course_state` | 536 (48 учеников, 54 курса) |
| Строк у ученика 3 | 26 |
| Из них с ОДНИМ `updated_at` (2026-08-17T18:40:00.913Z) | 25 |
| Самая крупная группа по одному `updated_at` во всей таблице | **460 строк, 40 учеников** |

`now()` в PostgreSQL — время **начала транзакции**. Значит 460 строк по 40
ученикам записаны ОДНОЙ транзакцией, и она держала все 460 блокировок строк до
самого конца прохода. Это фоновый тик `course_dependency_state_cron_service`
(tsk-541) — вторая сторона аварии.

Порядок захвата у него был вдобавок невоспроизводимым: внешний цикл шёл по
курсам, внутренний — по `Set[int]` учеников, то есть в порядке хеша. Согласовать
такой порядок с порядком любого другого писателя нельзя в принципе.

Первая сторона — сам `next-item`: он пишет кеш узла текущей позиции
(`learning_engine_service.py:968`), затем кеш каждой зависимости корня
(`:997`). Набор и порядок зависят от позиции ученика, то есть у двух
параллельных запросов одного ученика они разные.

**Итог разбора:** порядок захвата строк не согласован ни у одного писателя.
Сортировка самих строк проблему не закрывает — набор курсов у писателей разный
и заранее неизвестен (узел позиции резолвится по ходу обхода).

---

## 3. Решение

**Правило одно на всех: любой писатель `student_course_state` до первой записи
берёт транзакционную блокировку ученика.** Порядок задаётся не строками, а
одним ключом — учеником; цикл ожидания собирать не из чего.

| Файл | Правка |
|---|---|
| `app/services/learning_engine_service.py` | `lock_course_state()` + `upsert_course_state()` — единственная точка записи в таблицу. `compute_course_state` пишет только через неё. `backfill_dependency_state` обходит учеников по возрастанию `student_id`. |
| `app/services/course_dependency_state_cron_service.py` | Проход раскладывается по ученикам и идёт по возрастанию `student_id`, коммит — **после каждого ученика**, а не один на весь тик. Блокировка одного worker'а переведена с транзакционной на сессионную (транзакционная слетела бы на первом коммите) и снимается в `finally`. |
| `app/services/user_merge_service.py` | Слияние удаляет строки кеша source — тоже писатель, берёт ту же блокировку (обе учётки, по возрастанию id). |
| `app/api/error_handlers.py` | `is_deadlock_error()` — распознавание по SQLSTATE `40P01`, не по тексту и не по имени класса драйвера. |
| `app/api/v1/learning.py` | `_resolve_next_item_with_retry` — одна повторная попытка `next-item` после взаимоблокировки. |

Схема БД не менялась, миграция не нужна.

### Почему многоучениковые писатели сортируют учеников

Блокировка транзакционная, значит транзакция, пишущая нескольких учеников,
копит их блокировки. Два таких писателя во встречном порядке замкнули бы круг
уже на самих блокировках. Возрастание `student_id` — общий порядок для тика и
бэкфилла.

### Почему тик коммитит по ученику

Прямое следствие замера: одна транзакция на весь проход держала 460 строк
несколько секунд. Теперь блокировки живут ровно столько, сколько считается один
ученик, и параллельный `next-item` ждёт миллисекунды вместо всего тика.

## 4. Что показывать ученику, если взаимоблокировка всё же случится (пункт 5 декомпозиции)

**Решение: одна повторная попытка внутри `next-item`; при повторном отказе —
прежняя 500, без маскировки под 503.**

Обоснование:

1. **Повтор здесь безопасен, а не «попробуем и посмотрим».** PostgreSQL снимает
   транзакцию-жертву ЦЕЛИКОМ. За снятой стороной не остаётся ничего: записи
   кеша откачены, уведомление методисту (`escalate_course_completion`) — это
   строки `inbox`/`task_results.metrics` в той же транзакции, наружу за время
   запроса не уходит ни одного вызова. Повтор — буквально то же самое с чистого
   листа.
2. **Одна попытка, а не три.** Основное лечение — блокировка ученика; после неё
   этот класс не собирается вовсе. Повтор оставлен сеткой на случай ДРУГОГО, ещё
   не известного порядка захвата. Такой случай вторая и третья попытки уже не
   спасли бы — только удлинили бы ожидание ученика.
3. **Только `next-item`, не общий обработчик.** Общий повтор задваивал бы
   отправку там, где транзакция успела отправить что-то наружу.
4. **Не 503.** 503 сказал бы «сервис занят, приди позже» — неправда: сервис
   свободен, это дефект порядка блокировок. Замаскировав его, мы потеряли бы
   сигнал о новом лок-ордер баге. Оставшаяся 500 — честный громкий отказ.
5. **Пережитая взаимоблокировка видна в логе.** Повтор пишет `WARNING` с именем
   класса исключения, поэтому `grep -c DeadlockDetected /opt/lms/logs/app.log`
   считает и её тоже. Молчаливого «само прошло» не будет.

## 10. Дефект, который нашла только живая проверка (и его исправление)

Первая версия правки держала блокировку одного worker'а **сессионной**
(`pg_try_advisory_lock`) — потому что коммит по ученику снял бы транзакционную.
Все тесты были зелёными, прогон на проде прошёл штатно. И тем не менее:

```sql
SELECT pid, objid, state FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE locktype = 'advisory';
-- 1644131 | 1128551252 (= 0x43445354, ключ тика) | idle
```

Блокировка осталась висеть на соединении в пуле после того, как тик
закончился.

**Механизм.** Сессионная блокировка привязана к КОНКРЕТНОМУ соединению, а
`Session` после коммита возвращает соединение в пул и на следующем запросе
берёт свободное. Проверено прямым замером:

```
pool_size=5; взяли соединение → COMMIT → посторонний потребитель забрал
освободившееся → следующий запрос той же сессии
pid до коммита: 140488   pid после: 28008   СОЕДИНЕНИЕ СМЕНИЛОСЬ: True
```

На **пустом** пуле (dev, одиночный тест) пул возвращает то же самое соединение
— и всё выглядит исправным. На **боевом** пуле, занятом запросами учеников, —
почти всегда другое: блокировка остаётся на первом соединении навсегда, а
`pg_advisory_unlock` в `finally` отрабатывает вхолостую на чужом.

**Последствие, если бы не поймали:** следующий тик не смог бы взять ключ и
счёл бы, что работу делает другой worker. Фоновый пересчёт `student_course_state`
замолчал бы до перезапуска сервиса — **без единой ошибки в логе**. То есть
правка от взаимоблокировки тихо сломала бы то, ради чего этот тик существует
(tsk-541/tsk-523).

**Исправление** (коммит `15cc901`): сторож живёт в ОТДЕЛЬНОЙ сессии, чья
транзакция не закрывается до конца прохода. Соединение поэтому не
возвращается в пул, а блокировка снова транзакционная — снимается сама при
закрытии сессии, забыть её негде и утечь она не может, в том числе при падении
процесса. Цена — второе соединение из пула (`pool_size=10 + overflow 20`) на
~5 секунд раз в 15 минут.

Закрывается сторож **коммитом, а не откатом**: под тестовой изоляцией обе
сессии сидят на одном соединении, и откат сторожа — это откат к точке ДО
работы, стирающий уже записанное. Это поймал существующий тест tsk-541, а не
мой новый.

**Чем закреплено, чтобы не вернулось:**
- поведенчески — тик прогоняется на `QueuePool` (не `NullPool`: тот закрывает
  соединение вместе с сессией и прячет ровно эту утечку), пул при этом
  намеренно размешивается посторонним потребителем, а ключ проверяется ДО
  `dispose()`;
- структурно — `test_cron_worker_guard_is_transaction_scoped` запрещает в этом
  сервисе сессионные `pg_try_advisory_lock` / `pg_advisory_unlock` текстом.
  Поведенческий тест ловит подмену только при удачном совпадении по времени,
  поэтому одного его мало.

Обе проверки падают, если вернуть сессионную блокировку (мутация выполнена).

**Подтверждение на проде после исправления** (тик 20:22:44, `pairs=82
recomputed=460 students=40`):

| Проверка | Значение |
|---|---|
| Висячих advisory-блокировок после тика | **0** (было: 1, ключ `0x43445354` на idle-соединении) |
| Транзакций на проход | 40 на 40 учеников, 460 строк |
| Ошибок тика в логе | нет |

**Урок для памяти:** зелёные тесты + штатный прогон на проде + верный лог не
означают, что правка работает. Разница dev/прод здесь не в данных и не в
нагрузке, а в **занятости пула подключений** — на dev пул пуст, и подмены
соединения не происходит в принципе.
