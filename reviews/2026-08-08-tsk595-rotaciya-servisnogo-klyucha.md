# tsk-595 — ротация сервисных ключей LMS и вычистка секретов из логов

**Дата:** 2026-08-08
**Скиллы:** `/executor-lite` (правка клиентов) поверх ручной прод-операции
**Хосты:** `lms-spw-vds` (5.42.102.20), `tg-lms-vds` (72.56.247.22)
**Повод:** побочная находка §6.4 в [2026-08-08-tsk586-service-key-header-gate.md](2026-08-08-tsk586-service-key-header-gate.md)

---

## 1. Что оказалось на самом деле

В задаче стояло «27 строк в `/var/log/lms/app.log` с одним действующим ключом».
Пересчёт по всем ключам из `VALID_API_KEYS` дал другую картину.

| Ключ | Длина | `app.log` | логи nginx | Потребитель |
|---|---|---|---|---|
| key1 | 48 | 27 | 3 | нет (ручные вызовы с localhost и с самого сервера) |
| key2 | 48 | 25 135 | 5 898 + архивы | ContentBackbone (`CB_LMS_TOKEN`) |
| key3 | 48 | 1 | 0 | QSMImport (`LMS_API_KEY`) |
| key4 | 64 | 0 | **77 431** | TG_LMS прод (`API_KEY`) |

Ключ ботов считался чистым, потому что смотрели только `app.log`. **Маскировка
tsk-496 (`app/core/logger.py::AccessLogRedactingFilter`) — это фильтр питоновского
логгера LMS. До access-лога nginx он не достаёт вовсе**, а nginx пишет строку
запроса целиком. Пока TG_LMS ходил с `?api_key=` (до tsk-497, 7 августа),
ключ лёг в `access.log` 77 тысяч раз.

Итог: скомпрометированы были все четыре ключа, а не один.

### Третья находка: в логи попал весь набор секретов LMS

`auth.log` и журнал systemd на обоих хостах хранили строки вида

```
sudo:  root : PWD=/opt/lms ; USER=app ; COMMAND=/usr/bin/env DATABASE_URL=… VALID_API_KEYS=… python …
```

Это деплой-практика «передать окружение аргументами `sudo -u app env`»: sudo пишет
командную строку в аудит, а вместе с ней — **пароль боевой БД, ключ ЮKassa, Resend,
magic-link, ключ подписи сессий, Fernet, токен ТГ для initData, секрет VK ID, пароль
Redis, ключи S3, CloseRouter** (12 строк от 2026-08-07). На хосте ботов тем же путём
утёк `MARKETER_BOT_TOKEN`.

Тот же секрет виден в `ps` любому локальному пользователю в момент запуска.

## 2. Что сделано

### 2.1 Ротация (без простоя, окном двойных ключей)

1. Сгенерированы три новых ключа (`secrets.token_urlsafe(48)`), добавлены к старым
   в `/opt/lms/.env`, рестарт `lms.service` — старые продолжали работать.
2. Потребители переведены на новые: ContentBackbone (`CB_LMS_TOKEN`),
   QSMImport (`LMS_API_KEY`), TG_LMS (`/opt/tg_lms/.env`, рестарт четырёх юнитов).
3. Все четыре старых ключа выброшены из `VALID_API_KEYS`, рестарт.
   key1 замены не получил: постоянного потребителя у него не было.

Проверка после: старые ключи → 401 на всех четырёх, новые → 200; боты дают
340 подряд ответов 200; живой прогон клиентов CB и QSMImport против прода — 200.

### 2.2 Транспорт: `?api_key=` → заголовок `X-API-Key`

Ротация сама по себе бесполезна, если новый ключ снова ляжет в лог nginx.
Клиенты переведены на заголовок (LMS принимает его с tsk-586):

* ContentBackbone `monolith/lms_client/client.py` — коммит `a138003`;
* QSMImport `app/datasources/lms_api.py` — коммит `e3d5261`
  (там ключ печатался ещё и в собственный debug-лог: `params=%s`).

### 2.3 Маскировка на уровне nginx (durable)

В `http`-блок `/etc/nginx/nginx.conf` добавлены `map` для `$request` и `$http_referer`
плюс формат `combined_masked`; формат `withhost` переведён на `$request_masked`.
Проверено канарейкой: запрос с `?api_key=TEST-CANARY-tsk595` лёг в лог как
`api_key=***REDACTED***`. Резервная копия конфига — `/etc/nginx/nginx.conf.bak-tsk595`.

Теперь заслон двухслойный: клиенты не шлют ключ в адресе, а если пришлёт кто-то
ещё (старый скрипт, ссылка на медиа), nginx его замаскирует.

### 2.4 Вычистка истории

Файлы переписаны по тому же inode, поэтому пишущим процессам рестарт не потребовался.

| Что | Затёрто вхождений |
|---|---|
| `/var/log/lms/app.log` | 25 163 |
| `/var/log/nginx/access.log` + `.1` + 10 архивов `.gz` | 83 088 |
| `/var/log/auth.log` (LMS-хост) | 50 (весь набор секретов) |
| `auth.log` хоста ботов | 3 (ключ LMS + токен бота) |

Журнал systemd отредактировать нельзя — по решению оператора обрезан
(`journalctl --rotate` + `--vacuum-time=1d`): освобождено 1,2 ГБ на LMS-хосте и
2,1 ГБ на хосте ботов. На хосте ботов дополнительно удалены два архивных
журнальных файла, куда живой токен бота попал уже во время этого разбора
(см. §4).

Контрольная проверка обоих хостов скриптом, который читает `.env` сам и не
получает секреты аргументами: **живых секретов в логах не осталось**.
Внешней отправки логов нет (только локальный rsyslog), бэкапов `/var/log`
на машинах нет.

## 3. Решения оператора

* **Остальные секреты не отзываем.** Читать `auth.log` и журнал может только
  root/adm на этих машинах, наружу логи не уходят, файлы вычищены.
* **Журнал обрезан до суток** на обоих хостах.

---

## 4. Мои ошибки в ходе работы (без них картина неполная)

1. **Сам записал секреты в журнал.** Диагностика вида
   `sudo grep -c -F "$KEY" /var/log/...` подставляет значение в командную строку —
   и sudo пишет её в аудит. Ровно тот канал, который расследовался. На LMS-хосте
   так попали уже отозванные ключи (безвредно), на хосте ботов — живой
   `MARKETER_BOT_TOKEN`; эти журнальные файлы удалены. Правильный способ —
   привилегированный скрипт читает `.env` сам, наружу отдаёт только счётчики.
2. **Сломал права на `.env` ботов.** Скрипт выставил владельца от root-овой резервной
   копии, четыре бота на минуту упали с `PermissionError: '.env'`. Возвращено
   `app:app 0600`, боты подняты.
3. **Затёр не секрет.** Эвристика «значение длиннее 16 символов = секрет» приняла за
   секрет `API_URL` и заменила его на маску в `syslog` хоста ботов (≈521 тыс. строк)
   и `LLM_JUDGE_MODELS` в `app.log` (76). События в логах целы, но адрес и список
   моделей в старых строках теперь не прочитать. Фильтр в скрипте исправлен
   (пропускаем `*_URL`, `*_HOST`, пути), но на хосте ботов первый прогон уже прошёл
   старой версией.

## 5. Осталось следом

1. **`sudo -u app /usr/bin/env SECRET=… python …` — так больше не запускать.**
   Правильно: `sudo -u app bash -c 'set -a; . /opt/lms/.env; set +a; python …'` —
   секреты не попадают ни в `ps`, ни в аудит sudo.
2. **Скрипты CB со своей сборкой URL** ещё кладут ключ в query:
   `scripts/import_oge_sdamgia_variants.py` (в т.ч. ссылки на медиа),
   `scripts/smoke_b2_lms_import.py`, `scripts/tsk174_reparent_sections.py`.
   Сейчас их прикрывает маскировка nginx, но транспорт стоит поправить.
3. **Ссылки на медиа с `?api_key=` в теле заданий** — класс tsk-405, на стороне LMS
   не проверялся.
4. **Резервные копии `.env`** (`/opt/lms/.env.bak-*`, `/opt/tg_lms/.env.bak-*`,
   локальные `.env.bak-tsk595` в CB и QSMImport) содержат уже отозванные ключи —
   вреда нет, но их стоит подчистить, чтобы мёртвые секреты не копились.
