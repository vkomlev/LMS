## Что было

Продляющий (refresh) токен одноразовый: при успешном продлении LMS выдаёт новую пару и
отзывает старую сессию, проставляя ей `replaced_by_session_id` на преемника. Повтор того же
токена позже 20-секундного окна благодати (tsk-235) считался кражей и вызывал
`revoke_all_sessions` — отзыв **всех** сессий пользователя на **всех** устройствах.

По фактам прода за две недели защита сработала дважды, и оба раза на живом ученике 4506,
а не на воре. Причина мирная: браузер не сохранял новую пару cookie, потому что её ставил
ответ с чужого поддомена — устранено в tsk-603.

Вторая часть: причину отказа продления не писал никто. В tsk-594 её восстанавливали по
размеру тела ответа в логе nginx (49 байт — токена нет, 73 — недействителен).

## Решение оператора (09.08, вариант Б задачи)

1. При повторе гасить только цепочку сессий, которой принадлежит токен.
2. Причину отказа продления писать в лог приложения в любом случае.

## Что сделано

### 1. Радиус отзыва сужен до цепочки

`app/services/auth/session_service.py`:

- Новая функция `revoke_session_chain(db, session_id) -> int`. Идёт вперёд по
  `replaced_by_session_id` одним рекурсивным запросом (`WITH RECURSIVE` + `UPDATE ... FROM`),
  гасит только ещё живые строки (у отозванных сохраняется исходная отметка времени),
  возвращает число погашенных. Глубина ограничена `_CHAIN_MAX_DEPTH = 1000`.
- Ветка replay в `refresh_session` зовёт `revoke_session_chain(db, old.id)` вместо
  `revoke_all_sessions(db, old.user_id)`.
- `revoke_all_sessions` **остаётся** и используется по-прежнему в
  `user_block_service.block_user` — там отзыв всех устройств и есть замысел.

Почему один запрос, а не цикл обращений: между шагами цикла успевает проскочить очередное
продление, и голова цепочки уедет из-под отзыва. Почему только вперёд: предшественники уже
отозваны самой ротацией, а сессии других устройств растут из своего входа и в эту цепочку
не входят.

Угон это по-прежнему обрубает: вор и владелец сидят в одной цепочке, кто бы из них ни
прислал повтор — цепочка гасится целиком.

### 2. Причина отказа продления в логе

Новая функция `log_refresh_denied(reason, *, user_id, session_id, detail)`. Формат строки
стабилен и рассчитан на поиск по логам прода:

```
auth.refresh denied reason=<код> user_id=<id|-> session_id=<uuid|-> [detail]
```

| Код | Когда | Уровень |
|---|---|---|
| `no_token` | ни cookie, ни тела (обычный незалогиненный визит) | INFO |
| `malformed` | токен не шестнадцатеричная строка | INFO |
| `unknown` | такого токена нет в базе | INFO |
| `expired` | срок продления истёк | INFO |
| `revoked` | отозван логаутом или блокировкой, не ротацией | INFO |
| `grace_cache_miss` | распознанная гонка вкладок, кэш окна пуст | WARNING |
| `replay` | повтор вне окна благодати; в `detail` — число погашенных сессий | WARNING |

Сам токен в лог не попадает никогда — только идентификаторы пользователя и сессии.
`no_token` пишет роутер (`app/api/v1/auth/session.py`), остальное — сервис.

Оговорка: по одной БД нельзя отличить, был ли конкретный массовый отзыв вызван повтором
токена или блокировкой пользователя — журнала причин до этой задачи не было. Именно эту
слепоту и закрывает вторая часть правки.

## Тесты

Новый файл `tests/test_session_refresh_replay_scope_tsk604.py`:

1. `test_replay_revokes_only_own_chain` — вход с телефона и с ноутбука; повтор токена
   ноутбука гасит цепочку ноутбука, телефон жив. **Главный тест задачи.**
2. `test_replay_revokes_chain_deeper_than_one_hop` — цепочка из трёх звеньев гасится
   целиком, а не только ближайший преемник.
3. `test_replay_logs_reason_and_scope` — ровно одна строка `reason=replay` с `user_id`
   и `revoked_sessions=1`; самого токена в строке нет.
4. `test_denied_reason_logged_for_malformed_and_unknown`
5. `test_denied_reason_logged_for_expired_and_revoked`
6. `test_missing_token_logged_by_router` — HTTP-запрос без cookie: 401 и `reason=no_token`.

**Доказательство, что тесты не пустые.** Тот же файл прогнан против кода до правки
(в основном дереве): падают 5 тестов из 6, в том числе главный —
`assert await validate_session(db, phone_access) is not None` даёт `assert None is not None`,
то есть телефон умирал вместе с ноутбуком. Шестой (глубина цепочки) до правки проходил,
потому что `revoke_all_sessions` покрывал его заодно; он остаётся сторожем нового обхода.

## Риски и что осталось

- **Цена изменения.** Настоящий угон теперь не выкидывает вора с других устройств
  пользователя, если он успел войти отдельным логином. Это осознанный размен: за 21 день
  ни одного подтверждённого угона не было, а мирных срабатываний — два.
- **Функции «выйти со всех устройств» у пользователя по-прежнему нет** — это вне границ
  задачи. `revoke_all_sessions` доступен только через блокировку пользователя.
- **Проверить на проде через неделю** (пункт 4 декомпозиции задачи): сколько строк
  `reason=replay` и на ком. Теперь это один grep по `/var/log/lms/app.log`, а не разбор
  размеров тела ответа.
