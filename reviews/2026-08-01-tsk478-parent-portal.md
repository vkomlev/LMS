2. **Корректность** — композитный гейт (`_ensure_dashboard_access`) читается

   И существующей связке. 403 с единым текстом (не раскрывает, какая ветка
   могла бы сработать).
3. **Безопасность данных/миграций** — `parent_student_links` создаётся/

## Блокирующие проблемы (найдена и исправлена ЖИВОЙ проверкой на проде, после первого PASS)

- **[Исправлено]** `courses[]` в ответе дашборда молча оставался ПУСТЫМ для
  роли `parent` у реально записанного на курсы ученика.
  Причина: `student_dashboard_service.get_student_dashboard` звал
  `manual_progress_service.list_accessible_student_courses`, которая
  ВНУТРИ повторно проверяет `can_edit_progress` ПО КАЖДОМУ курсу — а та
  функция не знает о роли `parent`/`parent_student_links` вообще, поэтому
  для любого родителя фильтр молча отсекал все курсы. Доступ к ученику уже
  проверен вызывающим роутом (`_ensure_dashboard_access`) ДО вызова сервиса
  — повторная per-course ACL-проверка внутри избыточна и для parent-ветки
  ломала контракт. Юнит-тесты этого не поймали: тестовый ученик в
  `test_parent_sees_own_linked_student_dashboard` не был записан ни на один
  курс, пустой список выглядел "правильным" случайно.
  **Найдено только живой проверкой на проде** (реальный ученик 4508 с двумя
  курсами, реальный тестовый родитель без magic-link — session bootstrap
  через `scripts/tsk478_live_parent_check.py`, минтящий сессию тем же
  внутренним `session_service.create_session`, что и прод auth-flow) —
  ровно то расхождение, о котором предупреждает п.5 этого чек-листа
  ("зелёные тесты ≠ работает у пользователя").
  Фикс: новая `_list_active_student_courses` — прямой запрос активных
  `user_courses` БЕЗ повторной ACL-фильтрации (доступ уже дан на входе).
  Доказано НЕ менять поведение для teacher/admin/methodist: `can_edit_progress`
  для напрямую привязанного учителя возвращает `True` до проверки `course_id`
  (`linked`-ветка), а учитель ТОЛЬКО с course-level ACL и без прямой связки
  получил бы 403 ещё на уровне роута — per-course фильтр внутри
  `list_accessible_student_courses` был для этих вызывающих мёртвым кодом,
  не защитой. Регресс-тест дополнен реальной записью на курс + assert на
  непустой `courses[]`. Повторная живая проверка на проде после фикса —
  `courses[]` содержит оба реальных курса ученика 4508.

- **[Исправлено, SPW]** `app/(parent)/parent/page.tsx` звала
  `defaultDashboardPeriod()` ПРЯМО В ТЕЛЕ рендера компонента — функция
  строит `{from, to}` от `new Date()`, поэтому каждый ре-рендер получал
  новый объект периода → у `useParentDashboard` менялся `queryKey`
  (`period.from`/`period.to` внутри него) → уходил новый запрос → компонент
  ре-рендерился на изменение состояния запроса → снова новый период —
  бесконечный цикл перезапроса, дашборд НИКОГДА не оседал ("Загружаем…"
  бесконечно, в Network — только повторяющиеся OPTIONS preflight с разными
  `from`/`to`, ни одного завершённого GET). Найдено ТОЛЬКО живым прогоном в
  claude-in-chrome под реальной сессией (curl-проверки backend этого не
  ловят — они не рендерят React). Фикс: `useState(() =>
  defaultDashboardPeriod())` — период фиксируется один раз при монтировании.

## Гочта auto-assign роли `student` — подтверждено безопасной

Родитель, входящий впервые по email/TG, получает роль `student` от
существующего self-heal (`ensure_student_role`, вне рамок этой задачи) ДО
того, как оператор создаст связку и добавит роль `parent`. Роль `student` —
самая слабая в системе (доступ только к собственным данным вызывающего,
никаких чужих) — присутствие этой роли у родителя не создаёт повышенных
прав, только потенциальную UX-путаницу (пустой "мой прогресс"), задокументировано
как операционная инструкция оператору, не баг.
