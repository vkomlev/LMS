## 3. Критические находки этого захода (все проверены на данных, не гипотезы)

### 3.1. БЛОКЕР: ручная проверка преподавателя стирает отчёт о качестве кода

`POST /task-results/{id}/manual-check` (`app/api/v1/task_results_extra.py:333-339`) собирает `TaskResultUpdate(..., metrics=payload_data.get("metrics"))` — поле `metrics` передаётся **явно**, поэтому `model_dump(exclude_unset=True)` его не отбрасывает. Проверено эмпирически:

```python
u = TaskResultUpdate(score=5, checked_by=1, checked_at=..., is_correct=True, metrics=None)
u.model_dump(exclude_unset=True)  # -> {'metrics': None, ...}  => перезапись
```

Следствие: как только преподаватель проверит работу вручную (а это основной сценарий для методиста!), отчёт по качеству кода в `metrics` **обнуляется**. Направление 1 нельзя выводить на прод в текущем виде.

Дополнительно: `metrics` уже занят чужой семантикой — на проде 13817 записей, ключи `comment` (11651), `manual_grant` (11643), `completion_escalated_at` (252), `escalated_at` (201). То есть поле — «свалка» разнородных данных, а не место под структурированный отчёт.

### 3.2. Языки: Arduino/C++ — это не «будущее», а 42% корпуса прямо сейчас

Задания с флагом `code_ast` (метка «ответ — код») на проде:

| Язык | Заданий | Курсов |
|---|---|---|
| Python | 51 | 19 |
| **Arduino / C++** | **40** | **11** |
| QA (неясно) | 3 | 3 |
| Python (ОГЭ) | 1 | 1 |

Курс 1405 буквально называется «Занятие 1. Arduino C++, Wokwi, цифровой выход». pylint/radon на этом коде **не работают в принципе** (`ast.parse` на `void setup(){...}` → `SyntaxError`).

Отдельно: флаг `code_ast` **не гарантирует Python** — он означает лишь «сравнивать через AST», и для Arduino-заданий сравнение молча деградирует до текстового.

### 3.3. Время решения: из текущих данных не выводится для 84% сдач

| Факт | Значение |
|---|---|
| Всего сдач | 13817 |
| Попыток с ОДНИМ результатом | 11668 (84% сдач) |
| Попыток с несколькими результатами | 172 (2149 сдач, 16%) |
| События `task_open` / «задание показано» в `learning_events` | **отсутствуют** (есть только `hint_open`, `help_*`, `attempt_limit_*`) |

`attempts.created_at` — это момент открытия **попытки** (сессии работы), а не конкретного задания. В 84% случаев попытка создаётся практически в момент сдачи → дельта ≈ 0, время решения неизмеримо.

Работающий частичный прокси есть только для многорезультатных попыток — дельта между соседними сдачами внутри попытки: медиана **27.9 сек**, p05 = 4.2 сек, 560 случаев быстрее 15 сек, 122 быстрее 5 сек. Покрывает 16% сдач и включает время чтения условия следующего задания.

**Вывод: без новой телеметрии сигнал времени построить нельзя.** Нужно событие «задание выдано/открыто учеником» — это затрагивает SPW (фронт), то есть cross-project изменение.

### 3.4. LLM на проде: сеть есть, ключа нет, CB как прокси не годится

- Исходящий доступ с прод-LMS к `api.closerouter.dev` **работает** (проверено: HTTP 401 за 1.3 сек — сервер ответил, не хватает только ключа).
- В прод `.env` LMS **нет ни одной LLM-переменной**.
- CloseRouter — **облачный** API. В ContentBackbone локально живёт только конфиг и клиент-библиотека `cb_llm_client`; CB **не является** HTTP-прокси, через который LMS могла бы ходить. Значит «переиспользовать API CB» в смысле «звать CB как сервис» — нельзя; переиспользуется только сам провайдер и, при желании, ключ.
- Стоимость незначительна: CloseRouter берёт $0.20–0.30 за 1M токенов; один вызов судьи ≈ 800 токенов. Текущий темп — 1398 сдач/мес (июль 2026, 37 учеников), из них с кодом — доли. Даже при 1500 вызовах/мес это ≈ **$0.30/мес**. Стоимость блокером не является.

### 3.5. БЛОКЕР №2: преподаватель не видит отчёт в принципе — его нет в контракте

Даже если развернуть направление 1 на прод и починить перезапись (3.1), **методист и преподаватель всё равно ничего не увидят**. Проверено по коду:

| `PendingReviewItem` (`app/schemas/teacher_next_modes.py:94`) | `GET /teacher/reviews/pending`, `claim-next` | **нет** |
| `ReviewClaimItem` (там же, `:71`) | `POST /teacher/reviews/{id}/claim` | **нет** (есть `answer_json`, вложения, балл) |

То есть весь кабинет преподавателя (`/teacher/reviews/*`) поле `metrics` не отдаёт — только пишет в него (`teacher_queue_service.py:770-798` — комментарий при оценке, `:914-948` — история переоценок). Наружу `metrics` выходит лишь через `TaskResultRead`-эндпоинты (`by-user`, `by-task`, `by-attempt`, `by-pending-review`, `manual-check`, generic-CRUD), которые SPW на экране проверки не вызывает.

В SPW поле `metrics` **не отображается нигде**: grep по всему фронту даёт попадания только в сгенерированном `lib/api-types.ts`. Косвенно наружу идёт лишь `metrics.comment`, и то развёрнутый бэкендом в отдельное поле `TaskHistory`.

**Точка встраивания UI найдена:** `D:\Work\SPW\components\teacher\ReviewGradePanel.tsx`, строки **241–265** — между блоком «Вложения» и формой «Оценка». Данные брать из уже загруженного `claim.data.item` — значит нужно **аддитивно расширить `ReviewClaimItem`** узким полем (`code_review` / `ai_authorship`), а не тянуть второй запрос.

## 4. Развилки, требующие решения (для анализа)

### Р1. Куда писать отчёт (следствие находки 3.1)

| Вариант | За | Против |
|---|---|---|
| **A.** Новая JSONB-колонка `task_results.code_review` | Изолировано от чужой семантики, миграция тривиальна | +1 колонка в горячей таблице |
| **B.** Отдельная таблица `code_review_reports` | История/переоценка, не раздувает `task_results` | Сложнее, JOIN на каждом чтении |
| **C.** Оставить `metrics`, но починить перезапись (merge вместо replace) | Без миграции | Смешивает ручные комментарии и авто-отчёт; чинить перезапись всё равно нужно |

Замечание: перезапись `metrics` (3.1) — **самостоятельный баг**, затрагивающий и существующие ручные комментарии (повторная проверка без `metrics` в теле стирает предыдущий). Чинить нужно независимо от выбора варианта.

### Р2. Чем оценивать качество кода для не-Python (следствие 3.2)

| Вариант | За | Против |
|---|---|---|
| **A.** LLM для всех языков (единый механизм) | Язык-агностично, один код, оператор прав: «принцип одинаков» | Недетерминированно, нет объективных чисел (цикломатическая сложность) |
| **B.** Гибрид: Python → pylint/radon + LLM; остальные → только LLM | Для Python сохраняются объективные метрики | Две ветки логики |
| **C.** Per-language линтеры (cpplint, eslint, …) | Объективно для всех | Каждый язык — своя установка/поддержка; для Arduino в песочнице это заметная работа |

Сопутствующий вопрос: **как система узнаёт язык задания?** Сейчас явного поля нет. Варианты: новое поле у задания (`task_content.language`), вывод по курсу, автоопределение по содержимому. Без этого решения любой вариант выше повисает.

### Р3. Когда запускать проверку

| Вариант | За | Против |
|---|---|---|
| **A.** Синхронно при сдаче (как сейчас в направлении 1) | Результат сразу | +3–5 сек к ответу ученику (замер по pylint); LLM добавит ещё; занимает слот песочницы |
| **B.** Фоново после сдачи (очередь/APScheduler — в проекте уже есть) | Не тормозит ученика | Нужен воркер/планировщик, результат появляется с задержкой |
| **C.** По запросу преподавателя («проверить эту работу») | Ноль лишних вызовов, платим только за нужное | Препод ждёт результат в момент клика |

Замечание: ADR-0005 не рассматривал вариант C, а он может оказаться самым дешёвым и безопасным для старта — при нём вопрос «а не флагуем ли мы всех подряд» вообще не возникает.

### Р4. Сигнал времени (следствие 3.3)

Реализуемо только с новой телеметрией. Минимальный контур: SPW при показе задания шлёт событие → LMS пишет `learning_events` (`task_open`) → время решения = `submitted_at − task_open`. Это cross-project изменение (SPW + LMS), нужно согласование контракта.

Открытые вопросы: что считать «слишком быстро» (порог зависит от типа задания — вставить одно слово vs написать программу); как не штрафовать за исправление опечатки в повторной сдаче (в данных таких пересдач много — ученик 3 отправлял по 5 вариантов подряд с интервалом в секунды).

### Р5. Что видит преподаватель

Оператор просит: препод и методист видят оценку чистоты кода и сигнал ИИ. Открыто: на каком экране, в каком виде (число/светофор/текст), и — важно — **что делать по сигналу** (сигнал без предписанного действия превращается в шум).

Выбор «ИИ для всех языков» + «фоном» означает, что уже написанный и прошедший ревью код направления 1 (`dd6084b`) сохраняется лишь частично:

| Что | Судьба | Почему |

Плюс независимо починить перезапись `metrics` — это самостоятельный баг, затрагивающий и существующие ручные комментарии.

## 5. Что зафиксировано как решённое и не пересматривается без причины

- Ученику оценка стиля и сигнал ИИ **не показываются** (решение оператора 2026-08-06).
- Детектор ИИ — **advisory-сигнал методисту**, не автоматическая санкция, не блокировка, не изменение балла (ADR-0005).
- Пилот и любые прогоны — **read-only**, без уведомления учеников.

## 5-бис. Целевая схема с учётом решений оператора (черновик для критики)

```
   ученик сдаёт ответ
          │
          ▼
   POST /attempts/{id}/answers  ──► проверка корректности (как сейчас)
          │                          ответ ученику уходит СРАЗУ (без ожидания ИИ)
          │
          └──► ставит задачу в очередь «оценить работу»
                        │
                        ▼
             фоновый обработчик (APScheduler — уже есть в проекте)
                        │
                        ├─ определить язык задания        ← нужно решить, откуда берётся
                        ├─ собрать код (текст ответа ИЛИ .py-вложение с диска)
                        ├─ [если Python] pylint/radon → объективные числа   (бесплатно, уже написано)
                        ├─ ИИ-судья через LLM-клиент LMS → стиль + признак ИИ-авторства (любой язык)
                        └─ [позже] сигнал времени: submitted_at − task_open  ← нужна телеметрия
                        │
                        ▼
             запись в task_results.code_review (новая JSONB-колонка)
                        │
                        ▼
             ReviewClaimItem расширяется полем  →  ReviewGradePanel.tsx (строки 241-265)
                                                    видят teacher + methodist
```
