# tsk-752 — разбивка строк не решает судьбу зачёта

**Дата:** 2026-08-31
**Файлы:** `app/services/checking_service.py`, `tests/test_checking_table_tbl_com_tsk366.py`,
`docs/frontend-contract-sa-com.md`
**Решение review-gate:** ПРИНЯТО

## Контекст

Продолжение [[tsk-751]]: там неверный эталон 9515 (467 → 11907) и точечные правки формы
эталона у 4579 и 9518 (данными). Здесь — системная причина.

Ученик отвечает на объединённое задание 19-21 по строке **НА ВОПРОС**
(`244 / 247 248 / 252` — на 20-е два числа), а эталон хранится по строке
**НА ЗНАЧЕНИЕ** (`244 / 247 / 248 / 252`). Значения и порядок совпадают, но при
`table.columns = 1` многострочный ответ разбирался построчно (tsk-383): ячейки
`["244", "247 248", "252"]` против `["244","247","248","252"]` — незачёт. Тот же ответ
**одной строкой** при этом засчитывался: он режется по пробелам. То есть судьбу зачёта
решала форма записи, а не знание.

## Что изменено

`checking_service`, ветка TBL_COM: если построчный разбор не дал полного балла, ответ
сверяется ещё раз БЕЗ учёта границ строк. Путь **дополнительный** (по образцу `code_ast`):
ужесточить проверку он не может, только спасти верный ответ.

Граница правила — новый предикат `_line_split_is_significant(expected)`: плоский путь
включается, только если **каждая ячейка эталона атомарна** (нет пробела внутри). Там, где
ячейка — фраза (`"Первое число больше"`, мини-тесты Python из tsk-383), граница строки
разделяет реальные сущности, и стирать её нельзя — инвариант сохранён.

Дополнительно сужено условием `columns == 1`: при большем числе столбцов обе стороны и так
режутся по любым пробелам, и правило там ничего не меняет.

## Замер (правило «правку сверки выбирать перебором на боевых сдачах»)

Прогнаны **все 644** боевые сдачи TBL_COM с непустым ответом (471 зачёт, 172 незачёт)
через старое и новое правило — боевым кодом, не моделью на SQL:

| Метрика | Значение |
|---|---|
| незачёт → зачёт | **4** |
| зачёт → незачёт | **0** |
| изменился частичный балл | **0** |

Замер выполнен в режиме «у задания оставлен только первый эталон», то есть данные
возвращены в состояние ДО правок формы из tsk-751 — иначе спасённые случаи уже закрыты
данными и код выглядел бы бездействующим (первый прогон так и показал: 0/0/0).

Спасённые проверены глазами — все четыре содержательно верны:

- `17941` — задание 4579, ученик 4512, 23.08: `244\n247 248\n252`
- `18261` — задание 9518, ученик 4512, 26.08: `51\n46 50\n45`
- `20111`, `20113` — мои проверочные сдачи 31.08 (те же формы)

## Ветка короткого ответа (SA / SA_COM) — не тронута сознательно

Там разбивка строк тоже может мешать (`_normalize_text` схлопывает переводы строк только
при `collapse_spaces`), но замер по **75** боевым сдачам всех SA-заданий с многострочным
эталоном дал **0** пострадавших. Пробельно-нечувствительное сравнение в SA пришлось бы
включать без защиты «атомарности» (у короткого ответа нет ячеек), то есть с ненулевым
риском ложного зачёта — при нулевой пользе по фактическим данным. Не делаю.

## Риски и follow-up

- Форма через запятую (`247, 248`) по-прежнему не принимается: это уже смена набора шагов
  нормализации у конкретных заданий, а не разбор ответа.
- Добавленные в tsk-751 вторые формы эталона у 4579 и 9518 стали избыточны, но безвредны
  (тест на совместимость есть). Удалять данные ради чистоты не стал — лишняя запись в прод.
