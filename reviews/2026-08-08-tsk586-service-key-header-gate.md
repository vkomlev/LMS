## 1. Что было сломано

Жалоба оператора: в боте методиста при привязке курса ученику бот пишет
«Недостаточно прав для этого действия».

Цепочка (проверена по коду и живыми запросами на проде):

1. TG_LMS с коммита `8ceed6f` (2026-08-03, tsk-497) шлёт сервисный ключ ТОЛЬКО
   заголовком `X-API-Key` (`src/common/api_client.py:187`).
2. `app/api/deps.py::get_api_key` читал ТОЛЬКО `APIKeyQuery(name="api_key")` —
   заголовок эта дверь не смотрела вовсе.
3. На `Depends(get_db)`, то есть за этой дверью, стоит **116 пар метод+путь**
   (в задаче фигурировала цифра 45 — это уникальные эндпоинты без учёта
   методов CRUD-роутеров).
4. LMS отдавал 403 → `dialogs.py:60` переводил его в «Недостаточно прав».

### Уточнение окна аварии: 1 сутки, а не 5

В файле задачи стояло «живёт с 2026-08-03, то есть 5 дней». Это дата коммита в
TG_LMS, а не выката. На боевом сервере ботов:

```
/opt/tg_lms/src/common/api_client.py — mtime Aug 7 12:53
tg-lms-bot@{admin,methodist,student,teacher} — ActiveEnterTimestamp Fri 2026-08-07 12:53 UTC
```

Реальное окно: **2026-08-07 12:53 UTC → 2026-08-08**. Это меняет оценку ущерба
(п. 5), поэтому вынесено отдельно, а не спрятано в примечание.

## 2. Правки

### 2.1 `app/api/deps.py::get_api_key` — заголовок наравне с query

Вариант А из решения оператора. Дверь принимает ключ из `X-API-Key` ИЛИ из
`?api_key=`; заголовок проверяется первым как текущий транспорт клиентов, query
оставлен для обратной совместимости (ContentBackbone ходит с query). Поведение
при неверном/отсутствующем ключе прежнее — 403 с тем же текстом.

Маскировка ключа в логах (tsk-496) **не затронута**: `AccessLogRedactingFilter`
редактирует `api_key=` в query-строке и точные значения из `VALID_API_KEYS` в
любом месте строки, а заголовки в access-лог uvicorn не попадают в принципе.
Новый транспорт секрет в лог не выносит — наоборот, убирает его из request line.
Тесты `tests/test_access_log_redaction_tsk496.py` (5 шт.) зелёные.

### 2.2 `app/repos/base.py` — 500 на `GET /courses/` и `GET /meta/tasks`

Отдельный дефект, к гейту отношения не имеет. В `paginate` стояло:

```python
if items and hasattr(items[0], 'parent_courses'):
```

`hasattr` на атрибуте-связи SQLAlchemy — **не проверка наличия поля, а чтение**:
на незагруженной связи он запускает lazy-load посреди async-сессии и падает с
`MissingGreenlet` (`hasattr` глотает только `AttributeError`). Проверка типа
переведена на `isinstance(items[0], Courses)` — множество проходящих объектов то
же самое, побочного чтения связи больше нет.

Доказательство с прода (лог `/var/log/lms/app.log`):

```
File "/opt/lms/app/repos/base.py", line 422, in paginate
sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here.
```

Та же идиома нашлась в `BaseRepository.update` (строка 202). Сейчас она не
падает — объект приходит туда с уже загруженной связью (проверено живым
`PATCH /courses/{id}` → 200 до и после правки), — но идиома одна и та же,
поэтому переведена на `isinstance` тем же способом. Правка строго сужающая:
`hasattr(...) and isinstance(...)` → `isinstance(...)`.

**Охват шире, чем в задаче.** В задаче значился только 500 на `/meta/tasks`.
Тот же корень ломал и `GET /courses/` (список курсов) — это подтверждено на
проде отдельным curl:

```
/api/v1/courses/?skip=0&limit=5   qry=500
/api/v1/meta/tasks                qry=500
```

## 3. Тест, который ловит именно этот класс

`tests/test_service_key_header_gate_tsk586.py`.

Точечный тест на один эндпоинт этот дефект не ловит: ломается не эндпоинт, а
общая дверь. Поэтому тест **обходит все маршруты**, у которых `get_api_key` есть
в дереве зависимостей (116 пар), реальным ASGI-клиентом и проверяет два
свойства, по отдельности бесполезные:

| Проверка | Смысл |
|---|---|
| валидный ключ в **заголовке** → не 401/403 | дверь пускает |
| мусорный ключ → 401/403 | дверь вообще существует (иначе первая проверка зеленела бы и на снятой авторизации) |
| сторож `len(LEGACY_ENDPOINTS) > 50` | обход не выродился в пустой список |

Плюс точка из жалобы оператора (`POST /user-courses/` с заголовком → 422, а не
403), обратная совместимость query, юнит-проверки самой dependency (заголовок,
query, откат на query при мусорном заголовке, 403 на всех невалидных парах) и
два теста на 500 (`GET /courses/`, `GET /meta/tasks`).

**Мутационная проверка** (тест обязан краснеть на старом коде): временный откат
`get_api_key` к чтению только query → `3 failed, 6 passed`, в том числе падает
сам обход. Тест не декоративный.

Побочные эффекты обхода безопасны: `conftest._override_app_db` сажает
ASGI-запросы на соединение с откатываемой транзакцией, id-заглушка в путях
(`999_999_999`) заведомо отсутствует в БД, тело POST/PUT/PATCH пустое (422 до
хендлера).

## 5. Что за время аварии молча не прошло

Окно: 2026-08-07 12:53 UTC → 2026-08-08. Источники — журнал ботов
(`journalctl -u "tg-lms-bot@*"`) и access-лог LMS.

Со стороны ботов за окно зафиксировано:

| Операция | Следы |
|---|---|
| Привязка курса ученику (`POST /user-courses/`) | жалоба оператора + 3 запроса с 403 в access-логе LMS |
| Открытие карточки результата задания (`GET /task-results/{id}`) | 6 `APIClientError: HTTP 403` на id 15843, 3 подхода, ошибка `bots.common.dialogs.results_base` |

Больше ничего: ручных проверок работ, отправок сообщений, массовых импортов с
403 в журнале **нет** — за сутки эти сценарии просто не запускались.

**Данные чинить не нужно и нечего.** 403 отдаётся дверью до хендлера, то есть
транзакция не открывалась вовсе: не бывает половинчатой записи, задвоения или
частично применённой привязки. Отказ был полным и виден пользователю текстом
«Недостаточно прав» — операции нужно просто повторить, они пройдут.
