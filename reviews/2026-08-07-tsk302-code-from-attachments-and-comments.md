## 1. Что было не так

Отбор работ на оценку шёл от **пометки у задания** (`turtle_sim` / `code_ast`). Решение было принято сознательно: «не угадываем код по тексту, у задания и так есть пометка». Прод-данные показали, что оно неверное — пометка есть у витринных заданий, а не у настоящих курсов.

Где на самом деле лежит код ученика:

| Форма сдачи | Работ на проде | Из них с оценкой |
|---|---|---|
| Вложение (`task8.py`), в ответе — **вывод** программы | 101 (8 учеников) | **0** |
| Комментарий к ответу | 370 | **5** |

У Лашкова таких работ 42, у Кузнецкого — все показанные.

Ни одна из них не могла быть подхвачена: у заданий нет пометки, а прежний отбор читал только `value` и `comment` и только у помеченных заданий.

## 2. Что изменено

**Признак кодовой работы перенесён с задания на саму работу.** Условие теперь одно: удалось ли достать из работы программу. Функция `_needs_code_review` удалена — мёртвого кода не оставляю.

| Что | Как |
|---|---|
| Вложения | `pick_code_attachment` + `read_code_attachment` — читаем файл с диска, защита от выхода из каталога, потолок 64 КБ, нечитаемый файл не роняет приём ответа |
| Языки | Список расширений широкий: Python, C/C++/Arduino, C#, Java, Kotlin, JS/TS, PHP, Go, Rust, Swift, Ruby, Dart, Lua + школьные ЕГЭ/ОГЭ — Pascal, КуМир, Basic. Картинки, таблицы, PDF, архивы отсекаются: отдавать модели произвольный файл ученика — риск без пользы |
| Тетради Jupyter | Разбираются по кодовым ячейкам, а не отдаются моделью как JSON |
| Комментарии | Новый признак `looks_like_source_code` — код это или проза |

### Приоритет: вложение важнее текста

Это поймал упавший тест, а не рассуждение. Вывод программы из нескольких строк (`1 / 22 / 333 / 4444 / 55555`) **сам проходит** порог «похоже на программу». Читай мы сначала текст — преподаватель получил бы разбор «чистоты кода» столбика цифр. Файл-исходник заведомо надёжнее: это буквально то, что ученик написал.

## 3. Снимок кода вместо чтения файла потом

При разборе вскрылся дефект, который сильнее моей фичи: **загрузка нового вложения удаляет все предыдущие файлы той же попытки**, а попытка охватывает много заданий.

| | |
|---|---|
| Ссылок на `.py` в ответах | 101 |
| Файлов на диске | **8** — ровно по одному на попытку |

То есть код ~93 работ потерян, и ссылка «скачать» у преподавателя ведёт в никуда. Это не моя правка сломала — так было. Заведена отдельная задача (tsk-575), и соседняя сессия её **уже починила** (`aea9f91`): вложение теперь привязано к паре «попытка + задание», файлы соседних заданий не стираются.

Снимок кода при этом остаётся нужен, но по другой причине — её подсказала соседняя сессия, заметив, что моё обоснование устарело. Файл вложения **изменяем**: повторная загрузка по той же паре по-прежнему вытесняет прежний. Прочитай фоновый тик файл позже — он взял бы уже другую редакцию решения и приписал её этой сдаче. Снимок прибивает ровно то, что сдали в этот момент; копия временная, тик перезапишет её отчётом.

Историю снимок не воскрешает: у 93 работ файлы потеряны до починки, оценивать там нечего.

Из-за этого пересчёт задним числом восстановит только работы с уцелевшими файлами; для остальных исходников больше нет. Комментариев это не касается — они в базе.

## 7. Ревью-гейт: три захода, все три ОТКЛОНЕНО, все три по делу

### Заход 1 — три способа уронить приём ответа данными ученика

`meta.attachments` приходит из тела запроса и схемой не проверяется: `{"filename": 5}` роняло разбор внутри эндпоинта — **ученик не мог сдать задание вообще**. Третий случай тоньше: содержимое тетради Jupyter целиком задаёт ученик, и `{"source": [1, 2]}` — валидный JSON с валидными метаданными.

Закрыто проверками типов плюс страховка внутри сервиса (обёртка над разбором), а не в эндпоинте: так защищены все вызывающие. Тесты проверяют и внутреннюю функцию отдельно — иначе широкий перехват «удовлетворял» бы тест, оставляя дыру.

### Заход 2 — подмена файла (главная находка)

Файл для оценки выбирался по `meta.attachments`, **вопреки запрету, записанному в том же эндпоинте**: этому полю нельзя доверять, оно подделывается. Эксплуатация в один шаг: ученик грузит один вылизанный `solution.py` к заданию 1 и подставляет его идентификатор в задания 2..N той же попытки — преподаватель получает оценку и вердикт детектора ИИ по чужому коду. Для фичи про списывание это обход её самой.

Вдобавок расширение проверялось у **заявленного** имени: гейт проверил живьём — `dannye.csv` под именем `moe.py` читался и уходил модели, то есть закрытый список расширений не закрывал ничего.

**Решение по безопасности (принято 2026-08-07):**

| Проверка | Как |
|---|---|
| Принадлежность попытке | Имя разбирается каноном `attempt_attachments` (тот же, которым живут загрузка и выдача), `attempt_id` обязателен и должен совпасть |
| Принадлежность заданию | Файл ОБЯЗАН нести метку задания (`{attempt}_t{task}_…`), и она должна совпасть. Безметочные файлы на живом пути не читаются вовсе |
| Реальное расширение | Проверяется у файла на диске, а не у `filename` из запроса |
| Нет `attempt_id` | Вложение не читается вовсе — отказ безопаснее догадки |

**Почему одной сверки задания было мало — и это нашёл гейт.** Первая редакция сверяла задание «когда метка есть», а я записал «для новых загрузок риск снят». Это переобещание: **формат имени выбирает не сервер**. Приём вложений намеренно принимает загрузку без `task_id` (ради старых клиентов), а грузит файл сам ученик — значит он просто не отправляет `task_id`, получает безметочный файл и обходит сверку в один шаг. Довод «на проде 0 случаев переиспользования» говорил о прошлом, а не о поведении после раскатки фичи про списывание.

Поэтому на живом пути безметочные файлы **не читаются вовсе**. Оба клиента (SPW, TG_LMS) `task_id` уже шлют, так что охват не страдает. Историю разбирает только скрипт пересчёта — явным `allow_untagged=True`: задним числом ученик её не перезальёт, и это единственный способ дотянуться до 8 уцелевших старых файлов.

### Заход 3 — мой fail-closed убил боевой путь

Самая дорогая находка. Сделав `attempt_id` обязательным, я **не обновил вызов в приёме ответа** — потому что откладывал правку файла, который переписывала соседняя сессия. В итоге ни одна новая сдача формата «приложи файл» больше не вставала бы в очередь: сервисные тесты вызывали функцию правильно, а боевой код — нет.

Починено: `attempt_id`/`task_id` проброшены в приём ответа, параметр сделан обязательным (именно значение по умолчанию позволило старому вызову молча остаться валидным). Заведён **тест на уровне эндпоинта** — `tests/test_code_review_endpoint_tsk302.py`: сдача с настоящим файлом через `POST /attempts/{id}/answers` обязана дать `code_review.pending` со снимком кода. Ровно его отсутствие пропустило дефект.

### Прочее из находок гейта

| Что | Решение |
|---|---|
| Кеш каталога вложений (`lru_cache`) | **Откачен**: сломал изоляцию тестов — путь запоминался от первого вызова, тесты читали чужой каталог. Корректность важнее нескольких системных вызовов; соседняя сессия в своём модуле пришла к тому же выводу |
| `skipped/no_code` скрывал поломку разбора | Причина различается: `extract_failed`, когда вложение с кодом есть, а достать не вышло — иначе такие работы уже не найти |
| Признак принимал арифметику за код | Требуется явный признак (вызов/ключевое слово). Перекалибровано на проде: 269/101 → 267/103, потеряно 2 работы из одних присваиваний |
| Первое вложение «съедало» попытку | Перебираются все вложения с кодовым именем до первого успешно прочитанного |
| Дублирование раскладки вложений | Снято: переиспользуется канон соседней задачи после её коммита |
