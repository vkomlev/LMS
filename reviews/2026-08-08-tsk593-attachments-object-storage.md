# tsk-593 — вложения ответов, переписки и чеки переехали в объектное хранилище

Дата: 2026-08-08 · Ветка: `worktree-tsk-593-attachments` · Артефакт diff:
[2026-08-08-tsk593-attachments-object-storage.diff](2026-08-08-tsk593-attachments-object-storage.diff)

## Зачем

Три вида файлов лежали на диске приложения, на корневом разделе `/dev/sda1`,
без отдельного тома:

- `uploads/attempts` — вложения ответов учеников (46 файлов на проде),
- `uploads/messages` — файлы переписки (0),
- `uploads/receipts` — чеки об оплате (0).

Ровно так уже потеряли **все** файлы материалов: в tsk-519 машину переносили,
базу перенесли, каталог `uploads/` нет — осталось 0 файлов и битые ссылки, о
которых база не знала. Материалы после этого перевели в объектное хранилище
(tsk-520), а эти три вида остались на старой схеме, хотя чек об оплате —
платёжный документ, по которому разбирают спор о деньгах.

Прямая причина жалобы оператора («фотки грузятся, но не открываются») закрыта
раньше, в tsk-575, и здесь не переделывалась.

## Что сделано

### 1. Общий слой хранилища — `app/services/attachment_storage.py`

Три пространства ключей: `attempts/`, `messages/`, `receipts/`. Пространства
разные намеренно: у чека другой круг читателей и другой срок хранения, чем у
учебного вложения.

**Имя файла не менялось.** В отличие от материалов (там имя — хэш содержимого),
здесь имя само является идентификатором и уже записано в базе: в
`answer_json.response.meta.attachments[].attachment_id`, в
`messages.attachment_id`, в `student_payment.receipt_file`. Переименование
означало бы переписывание истории работ и платежей. Ключ = префикс + имя.

**Раздача — потоком через приложение.** Переадресация на бакет (как у публичного
`/api/v1/media`) запрещена: она обошла бы проверку прав.

**Без S3** (разработка, тесты) всё работает как раньше — на диске. Тот же
каталог остался запасным путём чтения для файлов, ещё не перенесённых.

### 2. Доступ к бакету сужен

Найдено при разведке: у бакета `lms-media-cas` политика разрешала анонимное
чтение **любого** объекта по прямой ссылке (перечисление ключей закрыто).
Класть туда чеки об оплате в таком виде было нельзя.

Политика сужена до CAS-пространства заданий (`??/*` — папки `00/`…`ff/`), на
которое `/api/v1/media` отдаёт переадресацию в браузер ученика. Проверено
анонимными запросами до и после: файлы-приложения заданий всех типов
(`rar, doc, docx, xls, xlsx, ods, odt, zip, csv, txt, png, gif, svg`) —
по-прежнему 200; `materials/…` — стало 403. Приложение читает материалы по
ключам (проверено на сервере: 75800 байт, `image/jpeg`).

Побочно закрылась незамеченная дыра: файлы материалов, защищённые проверкой
доступа к курсу (tsk-516), до этого читались по прямой ссылке в обход неё.

Откат — одна команда (`bucket_policy.py restore`), старая политика сохранена.

### 3. Суточная проверка целостности — `attachment_audit_service.py`

«Ссылка на файл есть, файла в хранилище нет» → уведомление. Учебные вложения и
переписка — методисту, чек — маркетологу (методист платёжный документ не
восстановит).

**Молчит, пока нет НОВОЙ утраты.** 180 файлов, потерянных до починки tsk-575, не
восстановятся; ежедневное одинаковое письмо про них превратило бы проверку в
шум, за которым новую потерю не заметят. Известные утраты живут в новой таблице
`attachment_missing_seen` (миграция `tsk593_missing_seen`); исходный уровень
заносит разовый скрипт. Файл вернулся — память очищается, повторная потеря снова
считается новой.

Отказ хранилища прерывает прогон целиком: «нет ответа» — не «файла нет».

### 4. Перенос существующих файлов — `scripts/tsk593_migrate_attachments_to_s3.py`

Сверка **поштучная**: каждый файл после записи скачивается обратно и сверяется
по sha256 байт в байт, плюс проверяется тип содержимого (урок tsk-536: файлы
уезжали с `binary/octet-stream`, ответ был 200, а картинка у человека не
рисовалась). Совпадение количества файлов доказательством не считается.

### 5. Хвост tsk-575 — `scripts/tsk593_lost_attachments_report.py`

Список «кого просить приложить заново»: ученик, задание, курс, дата сдачи. Данные
не правятся. Тот же скрипт заносит исходный уровень для проверки из п. 3.

## Изменения поведения API

| Место | Было | Стало |
|---|---|---|
| `GET /messages/{id}/attachment` | 404 «Attachment file missing on server» | 410 + русский текст (как у вложений ответов после tsk-575) |
| `GET /attempts/{id}/attachments/{aid}` | 410 при отсутствии файла | то же; добавлен 503, если хранилище не ответило |
| `POST /attempts/{id}/attachments` | 201 всегда при записи на диск | 503, если хранилище не приняло файл (вложение НЕ записано) |
| `POST /me/payments`, `GET …/receipt` | файл с диска | поток из хранилища; 503 при отказе хранилища |
| `content_type` в ответе загрузки | заголовок клиента | выводится из имени файла |

Отдельно: 503 вместо молчаливого успеха — принципиальный пункт. «Успешная»
загрузка без файла и есть та битая ссылка, ради которой заведена задача.

## Проверки

**Полный прогон pytest с нуля (моя ветка):** `2183 passed, 11 skipped, 0 failed` (14:43).

**Про первый прогон, где было 6 падений** — разобрано поимённо, замолчать нельзя:

- три падения были МОИ: `test_attachment_missing_flag_tsk575.py` звал пометку «файл
  утрачен» по старой сигнатуре (одна функция ходила в хранилище сама). Тест
  переписан под разделение «чистая пометка» / «пометка со сходом в хранилище»,
  плюс добавлены два случая: мусорный `attachment_id` из тела запроса и одиночная
  пометка;
- три падения (`test_attempts_limit_enforced_tsk269`, `test_auto_register_magic_link`,
  `test_help_request_autoclose_tsk339`) — плавающие, не про хранилище: у них
  пропадают строки `users`, созданные соседними тестами без изоляции транзакции.
  Проверено тремя способами: по отдельности проходят и в моей ветке, и на чистой
  `main`; **полный прогон на чистой `main` — 2169 passed, 0 failed**; повторный
  полный прогон моей ветки — 0 failed. То есть это не регресс задачи.

**Новые тесты:** `test_tsk593_attachment_storage.py` (15), `test_tsk593_attachment_audit.py`
(5), `test_tsk593_receipts_storage.py` (4), плюс переписанный
`test_attachment_missing_flag_tsk575.py` (5).

**Анонимные проверки бакета** до и после правки политики — в разделе 2 (13 типов файлов).

## Риски и остаточные вопросы

1. **Миграция и соседние чипы.** Миграция основана на голове `tsk032_retention_ach`.
   Параллельно идут чипы tsk-587/595/596; если кто-то из них добавит миграцию на ту же
   голову, получится две головы — сверить перед выкатом.
2. **Диск не очищается.** Файлы остаются на месте как запасной путь чтения. Убирать
   их — отдельное решение и отдельный день.
3. **Проверка наличия файла стала сетевой.** Там, где вложений на экране много
   (очередь преподавателя, история работ, экран курса), наличие спрашивается пачкой
   параллельно, один поход на страницу. Это единственное место, где изменилась
   форма вызова: `mark_missing_attachments` теперь принимает готовый набор имён.
4. **Клиенты (SPW, TG_LMS)** контрактов не меняли, кроме кода 410 у переписки
   (вложений переписки на проде ноль).
