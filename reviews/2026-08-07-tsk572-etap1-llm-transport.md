# tsk-572 этап 1 — общий LLM-транспорт

Дата: 2026-08-07
Контракт: `docs/specs/2026-08-06-contract-llm-client.md` (spec-gate пройден, §12.1)
Оркестрация: `docs/specs/2026-08-06-orkestraciya-tsk302-tsk572.md`, этап 1
Владелец модуля — tsk-572; tsk-302 потребляет, не правит.

## Что сделано

`app/services/llm/` — два входа над одним конвейером (резолв → остывание →
вызов по цепочке моделей → учёт → таксономия ошибок):

| Файл | Роль |
|---|---|
| `contracts.py` | типы, бюджеты, таксономия ошибок с `retryable` и `try_next_model` |
| `providers.py` | подключение по ADR-0046, нормализация `/v1`, цепочки моделей |
| `cooldown.py` | остывание провайдера после 429 (в процессе, не в БД) |
| `usage.py` | запись расхода в СВОЕЙ сессии, вне транзакции потребителя |
| `client.py` | httpx-транспорт: `complete()` батч, `stream()` интерактив |
| миграция `tsk572_llm_usage` | таблица `llm_usage_event` + два индекса |

## Решения, которые стоит объяснить

**Два признака у ошибки вместо одного.** `retryable` (просьба чипа tsk-302, §12.1)
и `try_next_model` разведены намеренно: на 429 повторять нельзя И менять модель
бессмысленно — остывает провайдер целиком; а на «модель не найдена» наоборот —
повторять той же моделью бесполезно, но следующая в цепочке ответит. Одним флагом
эти два случая не описываются.

**Переход по цепочке моделей запрещён после первого куска потока.** Иначе ученик
получит склейку двух разных ответов на середине фразы. Держится тестом
`test_stream_does_not_switch_model_midphrase`.

**Обрыв после начала ответа — не ошибка, а `truncated=True`.** Поднять исключение
значит убрать с экрана уже прочитанное учеником и показать красное. Отдаём то, что
успели, потребитель предложит продолжить (контракт §4.2).

**Учёт пишется в собственной сессии, и у НЕУСПЕШНЫХ вызовов особенно.** Транзакция
потребителя в этот момент может как раз откатываться из-за той же ошибки, а именно
по неуспешным строкам видно, как часто отбивает квота и куда уходят деньги без
результата.

**Остывание — в памяти процесса, а не в БД.** Переживать перезапуск не требуется,
запись в горячем пути не нужна. При нескольких воркерах остывание независимо —
принято сознательно: цель не идеальная синхронизация, а «не долбить провайдера
всей толпой».

## Валидация

**21 тест** (`tests/test_tsk572_llm_client.py`), провайдер подменён транспортом
httpx. Ключевые:

| Тест | Что ловит |
|---|---|
| `..._error_inside_successful_response` | HTTP 200 + `error` в потоке → исключение, а не пустой ответ ученику |
| `..._quota_error_is_separate_class` | отбой по квоте КЛЮЧА — отдельный класс с алертом персоналу |
| `..._429_never_retried_and_starts_cooldown` | ровно один запрос + остывание (брейкер провайдера) |
| `..._cooldown_refuses_without_network_call` | во время остывания в сеть не ходим вовсе |
| `..._429_does_not_walk_the_model_chain` | 429 — свойство провайдера, цепочку не перебираем |
| `..._break_after_first_chunk_is_truncation` | обрыв не стирает написанное |
| `..._base_url_normalized_both_spellings` | адрес с `/v1` не даёт `/v1/v1` (гоча tsk-302) |

**Живой прогон против настоящего CloseRouter** (не только заглушка):

```
стриминг : x-ai/grok-4.1-fast · первый токен 2.7 c · 29 кусков · обрыв нет
           «Range(1,5) выводит числа от 1 до 4, потому что верхняя граница
            в Python не включается.»
батч     : openai/gpt-5.4-mini · 4252 мс · {"ok": true} · seed=42 доехал
учёт     : обе строки в llm_usage_event с outcome='ok'
```

Наблюдение для будущей тарифной модели: односложный ответ наставника стоил
**692 входных / 251 выходной** токен — reasoning-токены делают «дешёвую» модель
дороже, чем кажется по прайсу. Ровно поэтому §8 требует считать по факту
`llm_usage_event`, а не по прайс-листу.

## Два решения оператора, снятые перед этапом 2

Оба вскрылись при чтении методики и оба меняли бы поведение у ученика, поэтому
вынесены до написания промпта, а не после.

**1. Первый ход наставника.** Методика требует «НЕ предполагай тему, первый ход —
спроси, что я принёс». Но точка входа автоматическая, сразу после неверного
ответа: задание уже известно. Дословная вставка ядра дала бы лишний ход ровно
там, где ученик расстроен ошибкой.
**Решение:** наставник знает формулировку задания и ответ ученика (эталона нет
физически), но первая реплика — вопрос о ходе мысли: «что ты уже попробовал и
почему решил так». Дух методики сохранён (подсказки только после попытки), лишний
ход убран. **Ядро промпта адаптируется, а не вставляется дословно.**

**2. Где показывать кнопку.** Методика прямо не рекомендует наставника на «тонких»
заданиях в одну конструкцию: любой конкретный пример там почти равен ответу. При
этом большинство заданий курса именно такие.
**Решение:** кнопка везде, но на одноконструкционных заданиях — урезанный режим:
только механика и позиции, без единого числового примера, пока ученик сам не
назвал границы. Это не изобретение — в методике такой структурный запрет уже
описан, здесь он становится отдельным режимом промпта.

## Границы этапа

Клиент — только транспорт. Не парсит предметные ответы, не знает про задания и
педагогику, не хранит историю диалога, не режет по лимитам. Промпт наставника,
сессии диалога и защита от утечки эталона — этап 2.

## Остаточные риски

- **Ограничение частоты на нашей стороне не сделано** — остывание закрывает главный
  риск, вернуться при росте нагрузки ×10 (контракт §11).
- `LLM_COOLDOWN_SECONDS=120` — первое приближение, калибруется по реальным 429.
- **Квота ключа** остаётся near-zero ($0.000004) при кредитах аккаунта $7.04 — две
  модели (`claude-sonnet-4.5`, `deepseek-v3.2`) так и не измерены и в цепочки не
  поставлены. Поднять лимит ключа — за оператором.
- На проде LLM-переменных ещё нет: ключ добавляется отдельным шагом перед этапом 2
  (в прод-`.env` только латиница).
