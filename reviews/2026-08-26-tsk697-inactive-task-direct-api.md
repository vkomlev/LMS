# tsk-697 — выключенное задание отдавалось ученику по API

**Дата:** 2026-08-26
**Скилл:** `/fastapi-api-developer`
**Файлы:** `app/api/v1/tasks_extra.py`, `tests/test_tasks_acl_post_s5.py`

## Что было

Две ручки чтения одного задания не смотрели на `tasks.is_active`:

- `GET /api/v1/tasks/{task_id}` — `get_task_by_id`
- `GET /api/v1/tasks/by-external/{external_uid}` — `get_task_by_external_uid`

Выключенное задание отдавалось ученику целиком — стем, варианты, служебные поля.
`solution_rules` при этом уже скрывался (tsk-460), а вот сам факт снятия задания
с публикации ручки игнорировали.

Проверено живьём на проде 26.08.2026 под учеником 142:
`GET /api/v1/tasks/by-external/ext%3Ad4%3Akompege%3A20260602%3A2054`
(задание 2133, курс 138, `is_active = false`) → **200** с содержимым.
Выключенных заданий на проде: **1220 из 7629**.

Особенность дефекта: **на экране SPW он не проявлялся**. Соседний
`GET /api/v1/learning/tasks/2133/state` отвечает 404 (движок фильтрует по
`is_active` давно), и страница рисует «Задача недоступна». Утечка шла мимо
интерфейса — по API.

Тот же класс, что закрытый час назад tsk-695 для материалов.

## Что сделано

Общий помощник `_deny_if_inactive_for_student` рядом с `_task_read_for`
(`app/api/v1/tasks_extra.py`), вызывается в обеих ручках после
`assert_task_access`:

```python
if privileged or task.is_active:
    return
logger.info("tsk-697: deny student user_id=%s task_id=%s (is_active=false)", ...)
raise HTTPException(status.HTTP_404_NOT_FOUND, "Задача не найдена")
```

`assert_task_access` уже возвращал признак `privileged` (tsk-460) — новых
запросов к БД правка не добавляет.

**404, а не 403:** разница между кодами сама по себе выдавала бы факт
существования, а SPW уже обрабатывает 404 на экране задания (tsk-447 —
`page.tsx:298-312`, «Задача недоступна» + ссылка «К курсу»).

Заодно уточнены описания 404 в OpenAPI обеих ручек.

## Проверка потребителей (до правки)

Риск был в том, что на текущем поведении может стоять чей-то рабочий экран.
Снят инвентарь по трём клиентам:

| Потребитель | Как ходит | Влияние правки |
|---|---|---|
| Кабинет методиста SPW (`/methodist/tasks/[task_id]`, `useTask`) | cookie пользователя с ролью `methodist` | нет — `privileged=True` |
| Экран проверки ответа SPW (`useReviewTask`, преподаватель + методист) | cookie с ролью `teacher`/`methodist` | нет — `privileged=True` |
| Экран задания ученика SPW (`useTaskByExternal`, ветка `id-<N>`) | cookie ученика | 404 → «Задача недоступна» (уже реализовано) |
| История сдач ученика (`/me/history`, `/me/tasks/{id}/history`) | cookie ученика | **нет** — карточку задания не запрашивает вовсе |
| ТГ-боты TG_LMS (15 точек вызова `get_task`) | единый сервисный `X-API-Key` на все 4 бота | нет — `is_service=True` |

Проверка истории была ключевой: на проде **443 выключенных задания имеют сдачи**
(7 учеников, 1552 записи в `task_results`). История ходит своей ручкой
`/me/tasks/{task_id}/history`, которая `is_active` не смотрит и не затронута —
закреплено отдельным тестом.

## Соседние точки того же класса

Учебный движок проверяет `is_active` во всех своих точках — новых дыр рядом нет:
`app/api/v1/learning.py:381` (`/skip`), `:434` (`start-or-get-attempt`),
`:565` (`/state`), `:699` (`request-help`), `:942` (`hint-events`).
В отличие от tsk-695, где `complete` для материалов пришлось чинить вместе с
карточкой, здесь вторая точка не понадобилась.

## Тесты

`tests/test_tasks_acl_post_s5.py` — хелпер `_create_task` принял параметр
`is_active`, добавлено 7 сценариев:

- ученик + выключенное задание по id → 404, стем не утёк в тело ответа;
- то же по `by-external`;
- чужое выключенное задание → 403/404, содержимое не отдано;
- методист видит выключенное задание (обе ручки), `is_active: false` в теле;
- преподаватель видит (экран проверки сдачи);
- сервисный ключ видит (превью «как ученик» в ТГ-ботах, переиздание);
- своя история ученика по выключенному заданию по-прежнему 200.

Прогон: `.venv/Scripts/python.exe -m pytest tests/test_tasks_acl_post_s5.py -q`
→ **17 passed**. Смежные (tsk-460, tsk-349, learning-routes, tsk-559) → 31 passed.
Полный прогон `pytest tests/ -q` → **2814 passed, 12 skipped**.

## Follow-ups

- **Бот ученика TG_LMS остаётся с прежним поведением.** Все четыре бота ходят
  под одним сервисным ключом (`src/common/api_client.py:241`), то есть для LMS
  неотличимы от привилегированного вызывающего — фильтр по роли на них не
  действует в принципе. Это тот же класс, что открытая tsk-696 (выключенные
  материалы в списке у ученика в боте); отсечка нужна на стороне TG_LMS.
- `POST /api/v1/check/task` (`app/api/v1/checking.py`) `is_active` не смотрит.
  Практически край: попытку по выключенному заданию не открыть
  (`start-or-get-attempt` проверяет), но попытка, начатая до выключения, ещё
  живёт. Отдельной задачей.
