# tsk-383: мини-тесты Python SA_COM → TBL_COM (несколько выводов программы в отдельные поля)

## Контекст

Мини-тесты вида «Запустите программу N раз со значениями X, Y, Z. Поместите вывод всех N
запусков в поле "Ответ" через пробел/перенос строки» жили как `SA_COM` — одно поле ввода
на весь ответ. Тип `TBL_COM` (tsk-366) даёт по полю на значение, но раскладка «один столбец»
(`table.columns=1`) до сих пор использовалась только для однострочных числовых
последовательностей (например `"True False True"`).

## Отбор кандидатов

154 совпадения по маркерам «Запустите программу»/«через пробел»/«Вывод[ы] программы» —
**не критерий отбора**. Вручную прочитано ~80 полных стемов по всем 9 курсам-источникам
(103, 104, 105, 106, 107, 108, 109, 110, 111). Итог: **53 годных мини-теста**, остальные —
ложные срабатывания:
- один запуск/одно значение («Запустите программу с вводом: `10`») — не мини-тест;
- одно выполнение, один список-результат (`print(*sorted(...))`) — один цельный ответ,
  не N независимых выводов (id 268, 298, 350 и т.п. — исключены сознательно, тот же
  принцип, что различает «table» от «одна строка вывода» в tsk-366 `ODNA_STROKA_VYVODA`);
- квиз-стиль «значение, тип, значение, тип» без повторных запусков (id 114) — другая форма.

Полный список id — `scripts/tsk383_migrate_to_tbl_com.py::CANDIDATES`.

## Архитектурная находка: движок не умел «фразу-в-строке»

Операторские примеры (задача #179 «двузначное число», курс 111) — это НЕ список чисел,
а список ФРАЗ: `"Первое число больше\nВторое число больше\nЧисла равны"`. Старый
`_table_cells` резал ЛЮБОЙ пробельный символ как границу ячейки — при `columns=1` фраза
«Первое число больше» дробилась на 3 отдельных «ячейки»-слова вместо одной.

**Фикс** (`app/services/checking_service.py::_table_cells`): при `columns=1` и >1 строк
после `re.split(r"\r?\n", value)` — каждая непустая строка становится ОДНОЙ ячейкой целиком
(внутренние пробелы сохраняются). Однострочный ответ (существующие tsk-366 задания вида
`"True False True"`) режется как раньше — по любому пробельному символу.

**Обратная совместимость подтверждена эмпирически** (read-only сверка прод-БД): ни одно из
200+ уже мигрированных TBL_COM-заданий не хранит `columns=1` вместе с многострочным
ответом — новая ветка кода была *мёртвой* для старых данных, активируется только для новых
задач tsk-383.

Зеркальный фикс в SPW: `lib/task/table-answer.ts` (`valueToCells`/`countCells`) и
`components/task/TaskFormTBL_COM.tsx` (`pasteFrom` — вставка многострочного текста при
`columns=1` режется по строкам, не по `/\s+/`).

## Вторая находка: fallback «как SA_COM», иначе исторические ответы ломаются

Первый прогон исторической регрессии (см. ниже) дал **27 регрессий**: студенты, набравшие
ответ ОДНОЙ строкой без реального переноса (старая привычка/копипаст — до появления сетки
полей у них было только одно текстовое поле), переставали засчитываться, хотя `SA_COM`
принимал их благодаря `collapse_spaces`, который схлопывает `\n` и пробел одинаково.

**Фикс**: в `_check_table_answer` добавлен fallback — если построчное сравнение не даёт
балл, ответ ДОПОЛНИТЕЛЬНО сверяется целиком против эталона целиком через
`_matches_short_answer` (тот же метод, что использует `SA_COM`). Инвариант «TBL_COM не
строже SA_COM на том же правиле» уже был зафиксирован в tsk-366
(`test_инвариант_tbl_com_засчитывает_всё_что_засчитывал_sa_com`) — этот fallback его
дораспространяет на line-aware ветку.

После fallback осталась 1 регрессия (task_id=111, result_id=1843) — проверена отдельно:
даже под ЧИСТЫМ `SA_COM` на ТЕКУЩЕМ правиле (без миграции) тот же ответ сегодня даёт
`is_correct=False`. Значит расхождение — дрейф правила между моментом проверки ученика и
сегодня (правило `accepted_answers` могло быть отредактировано), не эффект миграции.
Финальная логика верификации сравнивает не с застывшим `task_results.is_correct`, а с
вердиктом `SA_COM` «сейчас» (на правиле ДО миграции) — так эффект самой миграции изолирован
от независимого дрейфа правил во времени.

## Исключение из миграции: id=223

Ответ — треугольник из символов `*` (`"*\n**\n***\n..."`). Нормализация задания включает
`strip_punctuation`, который стирает `*` как пунктуацию с ОБЕИХ сторон сравнения — под
TBL_COM все ячейки после нормализации становятся пустыми, `_score_table` возвращает 0
безусловно. Это латентный дефект уже у `SA_COM` (совпадение по случайно схлопнутой в
пустую строку записи — платформа "работала" только потому, что 0-длины строки равны
0-длины строкам), не специфичный для TBL_COM и не в объёме tsk-383. Задание оставлено
`SA_COM`; чинить отдельной задачей (снять `strip_punctuation` с этого конкретного правила).

## Миграция (/db-check протокол)

`scripts/tsk383_migrate_to_tbl_com.py`:
1. dry-run (транзакция с откатом) — прогнан до записи, все проверки зелёные.
2. `--apply` под `DBCHECK_OK=1` — 53 задания переведены (`task_content.type=TBL_COM`,
   `table={"columns":1}`), правила проверки НЕ переписаны, кроме 4 заданий (75, 77, 80, 94),
   где несколько запусков были склеены в одну строку без переноса — граница расставлена
   вручную и проверена реверсивностью (`" ".join(rows) == исходное value`, ассерт в коде).
3. Верификация поштучно (не агрегатом):
   - самосогласованность: эталон + 3 мутации (регистр/пробелы/переносы) на каждое из 53
     заданий — все засчитаны;
   - историческая регрессия: 97 реальных исторических ответов учеников (task_results) —
     0 регрессий (TBL_COM после перевода не хуже, чем SA_COM на текущем правиле).
4. Независимая верификация после коммита (отдельный read-only запрос вне транзакции
   скрипта): 53/53 `TBL_COM`, 53/53 `columns=1`, id=223 подтверждён `SA_COM`.
