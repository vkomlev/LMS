## Дефект

`POST /api/v1/attempts/{attempt_id}/attachments` при каждой загрузке удалял **все**
прежние файлы попытки:

```python
existing_files = _attempt_attachment_files(attempt_id)   # {attempt_id}_* в upload-dir
...
for old_file in existing_files:
    if old_file != file_path:
        os.remove(old_file)
```

Замысел «одно вложение на ответ» был бы верен, будь попытка про одно задание. Но
попытка (`attempts`) охватывает много заданий: ученик сдавал задание 1 с `task1.py`,
брался за задание 2 — и файл первого исчезал вместе со ссылкой в уже сданной работе.
Преподаватель, открывая работу, получал 404 «Attachment file missing on server».

Тот же корень портил и гейты: `requires_attachment` (tsk-227) и «комментарий или файл»
(tsk-419) считали любой файл попытки доказательством по любому её заданию — один
скриншот к заданию 1 открывал зачёт заданиям 2..N без единого файла.

## Инвариант

**Одно актуальное вложение на пару «попытка + задание»**, а не на попытку.

Отдельной таблицы вложений нет — каталог плоский, вся принадлежность живёт в имени файла:

* `{attempt_id}_{uuid32}_{имя}` — исторический формат, остаётся валидным (так лежат все
  25 уцелевших прод-файлов и такие имена записаны в `answer_json`);
* `{attempt_id}_t{task_id}_{uuid32}_{имя}` — текущий.

Разбор однозначен: в старом формате после `{attempt_id}_` идёт uuid из 32 hex-символов, а
`t` в hex не входит.

## Решения оператора (2026-08-07)

1. **Утраченные файлы — пометка «файл утрачен».** Метаданные в `answer_json` не чистим:
   имя и размер — след того, что ученик файл присылал, и доказательство при разборе
   жалобы и в аудите гейтов tsk-227/419. Флаг считается на чтении по диску, в БД не
   хранится, поэтому самолечащийся. Прод-БД не тронута вовсе.
2. **Гейт вложения сузить до задания, со страховкой.** Файлы без метки задания (старый
   клиент) продолжают засчитываться любому заданию попытки — иначе обновление сервера в
   одиночку сломало бы приём ответов из бота.

## Обратная совместимость

| Ситуация | Поведение |
|---|---|
| Старый файл `{attempt}_{uuid}_{имя}` на диске | Читается и скачивается как раньше |
| Загрузка без `task_id` (необновлённый клиент) | Принимается; вытесняет только другие файлы попытки без метки; засчитывается гейтом любому заданию |
| Загрузка с `task_id` | Вытесняет только файл этой пары; файл без метки не трогает |
| Скачивание вытесненного/утраченного | 410 + текст (было 404) |
| Некорректный `attachment_id`, чужая попытка | 404 как раньше |

Порядок раскатки безопасен в любую сторону: сервер работает и со старыми клиентами, а
клиент с `task_id` на старом сервере просто получит проигнорированное поле формы.

## Risks / Follow-ups

* **Уже утраченное не вернуть.** 199 непроверенных работ придётся или проверять по тексту
  ответа/комментарию, или просить учеников приложить файлы заново. Список
  `task_results.id` восстанавливается запросом из этого отчёта.
* **Сужение гейта строже прежнего.** Ученик, приложивший файл к другому заданию той же
  попытки, теперь получит отказ там, где раньше проходил. Это и есть исправление, но при
  раскатке стоит посмотреть логи `requires_attachment ... без вложения → не зачёт`.
* **Дубли имён у бота.** На попытке 7173 один и тот же файл из Telegram загружен трижды с
  разными uuid — с меткой задания такие дубли теперь разложатся по заданиям, а не будут
  затирать друг друга. Отдельной чистки не требуется.
* **Живая проверка на проде** — обязательна после развёртывания, в той же сессии.
