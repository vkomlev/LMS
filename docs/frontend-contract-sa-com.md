# Контракт для фронта: ответы типов «с комментарием» (SA_COM, TBL_COM)

**Эндпоинт:** `POST /api/v1/attempts/{attempt_id}/answers`

Документ описывает оба типа из `COMMENT_TASK_TYPES` (`app/schemas/task_content.py`):
**`SA_COM`** (короткий ответ) и **`TBL_COM`** (табличный ответ, tsk-366). Правила приёма
ответа у них одинаковые; отличается только формат `response.value`.

## Поля ответа

| Поле | Обязательность | Роль |
|---|---|---|
| `response.value` | обязательно | Основной ответ. Участвует в автопроверке и баллах |
| `response.comment` | **обязательно, если не приложен файл** | Ход решения / код. В автопроверке не участвует, но без него (и без файла) ответ не засчитывается — см. «Гейт доказательства» |

Формат `value`:
- `SA_COM` — строка (для многострочного эталона допустимы переводы строки);
- `TBL_COM` — таблица одной строкой: ячейки ряда через пробел, ряды через перевод строки
  (`"10 2786\n12 3140"`); сравнение поячеечное. **Исключение (tsk-383):** при
  `table.columns=1` и МНОГОСТРОЧНОМ ответе строка не режется по пробелу — целая
  строка (с внутренними пробелами) становится одной ячейкой. Так хранятся
  мини-тесты Python, где вывод одного запуска программы — фраза
  (`"Первое число больше\nВторое число больше"`, 2 ячейки, не 6 слов).
  Однострочный ответ при `columns=1` (например `"True False True"`) по-прежнему
  режется по словам.

## Гейт доказательства: комментарий ИЛИ файл (tsk-419)

Для **всех** заданий типа `SA_COM`/`TBL_COM` — независимо от `manual_review_required` и от
`requires_attachment` — сервер требует **непустой `response.comment` ИЛИ реально
загруженный файл**. Если нет ни того, ни другого, ответ принимается (HTTP 200 и запись в
`task_results`), но **не засчитывается**:

```json
{ "score": 0, "is_correct": false,
  "feedback": { "general": "Добавьте комментарий (например, ход решения) или приложите файл — без этого ответ не засчитывается." } }
```

Правило универсально по ТИПУ задания (в отличие от `requires_attachment` — это per-task
флаг, см. ниже). Причина: часть заданий решалась подбором без единой строчки решения, и
преподавателю в очереди нечего было проверять.

**Комментарий из одних пробелов не считается заполненным** (сервер применяет `strip`).

### Файл засчитывается только реально загруженный

Файл должен быть отправлен через `POST /api/v1/attempts/{attempt_id}/attachments`
(multipart, поля `file` и `task_id`, ответ `201`) **до** сдачи ответа.

⚠️ **`response.meta.attachments` в теле ответа гейт НЕ удовлетворяет.** Это клиентские
данные, их можно подделать; сервер проверяет наличие файла на диске.
Оба клиента (SPW, TG_LMS) грузят файл отдельным запросом до сдачи.

⚠️ **`task_id` в загрузке обязателен по смыслу** (tsk-575). Попытка охватывает много
заданий; `task_id` говорит серверу, вложение какого задания заменяет новая загрузка, и
по нему же гейт ищет файл при сдаче. Загрузка без `task_id` принимается ради старых
клиентов: такой файл считается вложением попытки целиком, вытесняет прежние файлы без
метки и засчитывается любому заданию попытки. До tsk-575 иначе было нельзя — и загрузка
файла ко второму заданию стирала файл первого (на проде так утрачено 180 файлов).

### Файл утрачен

`GET /api/v1/attempts/{attempt_id}/attachments/{attachment_id}` отдаёт **410 Gone**, если
имя вложения разобрано, а файла на диске нет (утрачен дефектом tsk-575 либо вытеснен
перезаливкой того же задания). `404` остаётся только для некорректного имени и чужой
попытки. В `answer_json`, который клиент получает на чтении, такие вложения приходят с
`"missing": true` — показывать их надо пометкой «файл утрачен», а не ссылкой. Флаг
считается на лету по диску, в БД его нет.

### Исключения

- **`requires_attachment: true`** (per-task флаг, `solution_rules`) — файл обязателен, и
  комментарий его не заменяет. Сообщение при отсутствии файла своё, приоритетнее общего:
  «Прикрепите файл-подтверждение (скриншот/файл) — без вложения задание не засчитывается».
- **Истёкшая попытка** (`time_expired`) — гейт не применяется: ответ и так уже провален
  (`score=0`), приложить файл уже нельзя.

## Проверка (scoring)

**По умолчанию** `SA_COM`/`TBL_COM` авто-проверяются по `value`
(`accepted_answers`/`regex`, как `SA`): задание засчитывается без преподавателя, он может
пересмотреть результат опционально (`/regrade`).

**При `solution_rules.manual_review_required=true`** (tsk-230) авто-вердикт не выставляется
вовсе, и работа уходит в обязательную очередь преподавателя (`checked_at IS NULL`).

Что происходит дальше, зависит от того, **есть ли у задания эталон**:

- **эталона нет** (`short_answer` не задан или пуст) — сверять нечем, вступает
  оптимистичный зачёт (tsk-210): ученик **сразу** получает `score=max_score,
  is_correct=true`, чтобы учебный поток не блокировался, а преподаватель может зачёт
  снять через `POST /teacher/reviews/{id}/regrade`. Так работают миссии флагмана;
- **эталон есть** — оптимистичного зачёта **нет** (tsk-396). Балл остаётся нулевым до
  оценки преподавателем. До tsk-396 здесь был дефект: условие оптимистичного зачёта
  опиралось на `is_correct=null`, а этот признак возникает и при «эталон есть, но включён
  ручной гейт», — и заведомо неверный ответ получал `PASSED` до проверки человеком.

> Порядок важен: гейт доказательства применяется **после** оптимистичного зачёта и
> перекрывает его. То есть «нет комментария и файла» → `score=0, is_correct=false`, даже
> если авто-вердикта у задания нет в принципе.

## Гибридный режим: `partial_auto_check` (tsk-396)

Для заданий, где **часть** ответа формализуема, а часть проверяет только человек
(канонический пример — ОГЭ-14: два числа плюс построение круговой диаграммы).
Включается флагом `solution_rules.partial_auto_check=true`; требует
`manual_review_required=true` и непустой эталон (иначе `422` при заведении задания).

Поведение на сдаче:

| Формализуемая часть | `is_correct` | `score` | Очередь преподавателя |
|---|---|---|---|
| сошлась с эталоном | `null` | `0` | да, обязательная |
| не сошлась / пустой ответ | `false` | `0` | **нет** — ученик пересдаёт сам |

```json
{ "is_correct": null, "score": 0, "max_score": 1, "details": null,
  "feedback": { "general": "Числовая часть сошлась с эталоном. Задание отправлено преподавателю — он проверит построение диаграммы и выставит балл." } }
```

Ключевые свойства контракта:

- **`score` остаётся нулевым всегда** до ручной оценки. Движок считает зачёт по
  `score/max_score >= 0.5`, поэтому авто-часть балла не касается — иначе задание и курс
  зачлись бы до проверки человеком. Ученику показывать «на проверке», а не «сдано»;
- **эталон не раскрывается**: `details` в этом режиме не заполняется (`matched_short_answer`
  вернул бы ученику правильный ответ), в тексте `feedback` эталона тоже нет;
- **`is_correct=false` здесь — законченный авто-вердикт**, а не оценка преподавателя:
  числа не сошлись, работа к нему не пойдёт, ученик правит расчёты и сдаёт заново
  (в пределах лимита попыток);
- поведение **одинаково** у `SA_COM` и `TBL_COM`.

`GET /learning/tasks/{id}/state` отдаёт `partial_auto_check: bool` — UX-сигнал (как
`requires_attachment` и `has_reference_answer`), сервер остаётся источником истины. Клиент
по нему объясняет ученику, что числа сверятся сразу, а балл поставит преподаватель: иначе
`is_correct=null` при непустом `feedback` читается как «проверка сломалась».

В очереди преподавателя элемент несёт `auto_checked_part_matched: bool` — «числовая часть
уже сверена и совпала, проверьте только диаграмму». Работы с несошедшимися числами в
обязательную очередь не попадают, поэтому флаг там всегда означает «числа верны».

Задания ОГЭ-14 курса 1179 (25 штук) переведены на этот режим вместе с
`requires_attachment=true` — диаграмма сдаётся файлом `.ods`/`.xlsx`. Подробности решения —
[ADR-0007](ai/adr/0007-partial-auto-check-manual-gate.md).

Именно смена типа `SA` → `SA_COM` даёт заданию это поведение: у плоского `SA` ни
оптимистичного зачёта, ни гейта доказательства нет (tsk-438, tsk-546).

## Пример тела запроса

```json
{
  "items": [
    {
      "task_id": 2,
      "answer": {
        "type": "SA_COM",
        "response": {
          "value": "основной ответ",
          "comment": "ход решения или код"
        }
      }
    }
  ]
}
```

Без комментария — только если файл уже загружен через `/attachments`:

```json
{
  "type": "SA_COM",
  "response": { "value": "основной ответ" }
}
```

## Выдача

Во всех ответах API, где возвращается `answer_json` или результаты попытки (в т.ч.
`GET /attempts/{id}`, `POST /attempts/{id}/finish`), комментарий приходит в том же месте:
**`answer_json.response.comment`**.

## Поведение клиента (SPW)

Форма `TaskFormSA_COM` блокирует отправку **до** запроса и показывает причину, а не даёт
серверу молча отклонить ответ: «Заполните поле “Ответ”…», «Добавьте комментарий … или
приложите файл…», «Приложите файл-подтверждение…» (при `requires_attachment`). Поле
«Комментарий» — редактор кода с подсветкой.
