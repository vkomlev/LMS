# Постановка: LMS П3–П5 — повторение по следам ошибок, помощь после попытки, итоговый срез

> Задачи: tsk-992 (П3), tsk-993 (П4), tsk-994 (П5). Источник — педагогический аудит
> `docs/qa/lms-pedagogy-audit-2026-09-17.md`. Решения оператора по развилкам — 2026-10-14.
> Факты о коде сверены с main 2026-10-14 (пути и строки — на эту дату).

## Цель

Ученик сначала пробует сам (П4), закрепляет то, на чём ошибался (П3), и после курса
видит, что навык сохранился (П5) — без изменения линейного движка подачи
(`resolve_next_item`) и логики завершения курса.

Сверка с `docs/NORTH_STAR.md` («ученик доходит до результата, а время преподавателя —
только на то, ради чего нужен человек»): П4 разгружает преподавателя от заявок без
попытки, П3/П5 — про результат ученика. Расхождений нет.

## Решения оператора (обязательны, не пересматривать при реализации)

| # | Развилка | Решение |
|---|---|---|
| Р1 | Что открывает помощь (П4) | ≥1 сдача ответа по заданию **ИЛИ** текст «застрял на X» (≥20 символов после обрезки пробелов) |
| Р2 | Что ставится на повтор (П3) | Только задания «сначала завалил, потом сдал»; интервалы 3 → 7 → 21 день; незачёт на повторе — откат к 3 дням |
| Р3 | Где блок «Повторение» (П3) | На странице курса, над программой курса |
| Р4 | Роль итогового среза (П5) | Только диагностика: статус курса, зависимости и выпуск не меняются |

## Границы

**Входит:**
- П4: серверный гейт в `request_help` и при открытии сессии ИИ-наставника; поле «где застрял»; привязка `attempt_id`; понятный отказ в SPW.
- П3: таблица расписания, планировщик при сдаче, API выдачи «пора повторить», сдача повтора, блок в SPW, рубильник на курс.
- П5: флаг итогового среза на курсе, выборка заданий, API среза, экран итога в SPW.

**Не входит:**
- изменения `resolve_next_item`, `compute_course_state`/COMPLETED, `graduation_service`;
- гейт на заявку по МАТЕРИАЛУ (`/learning/materials/{id}/request-help`) и на автозаявки `blocked_limit` — они уже возникают после попыток;
- уведомления (ТГ/почта) о том, что пора повторить — отдельная задача после пилота;
- включение рубильников на проде и выбор пилотного курса — решение оператора после выката;
- бот TG_LMS (отдельный клиент; отметить в отчёте, если он вызывает `request-help` без попытки).

## Ограничения

- Миграции — `app/db/migrations/versions/`, голова на 14.10: `tsk1220_task_hint_drafts`. Перед созданием — проверить голову заново (`alembic heads`), параллельные сессии могли добавить свою.
- Все новые возможности — **выключены по умолчанию** (рубильники ниже). Выкат кода не меняет поведение на проде, пока оператор не включит.
- П4 — без рубильника на курс, но с глобальным `HELP_REQUIRES_ATTEMPT` (env, по умолчанию `false`), чтобы выкат не сломал поведение молча.
- `task_results.source_system` — `String(50)` без CHECK. Аналитика пробелов считает только `IN ('spw_web')`, часть отчётов исключает `'manual_teacher'`. Новое значение `'retrieval'` не должно попадать в «настоящие пробелы» (`learning_gaps_service.py:36`) — проверить и зафиксировать.
- `attempts` — на уровне курса (одна открытая на пользователя и курс); повтор и срез используют существующую механику попыток, не создают свою.
- Ручной зачёт преподавателя (`source_system='manual_teacher'`) — **не** считается попыткой ученика для П4 и **не** запускает планировщик П3.
- Облачная реализация: нет боевой БД и живого сайта. Проверка — тесты против тестовой БД проекта; живая проверка — после выката на машине оператора.

## План

### Фаза A — П4: помощь после самостоятельной попытки (tsk-993)

1. Функция `has_own_attempt(db, student_id, task_id, root_course_id) -> bool` рядом с `compute_task_state` (`app/services/learning_engine_service.py`): ≥1 строка `task_results` с не отменённой попыткой и `source_system IS DISTINCT FROM 'manual_teacher'`. Тест на 4 случая: нет сдач / есть сдача / только ручной зачёт / отменённая попытка.
2. `request_help` (`app/api/v1/learning.py:719`): в теле запроса — необязательное `stuck_note: str | None` (макс. 1000 символов). При `HELP_REQUIRES_ATTEMPT=true`: если `has_own_attempt` ложно и `stuck_note` после `strip()` короче 20 символов → `DomainError` 409, `payload.code="attempt_required"`, текст «Сначала попробуй решить сам — отправь ответ или опиши, где застрял». Если попытка есть — передать в `get_or_create_help_request` `attempt_id` последней сдачи; `stuck_note` сохранить в заявке (колонка `help_requests.stuck_note TEXT NULL`, миграция) и показывать в карточке заявки преподавателю.
3. ИИ-наставник (`app/api/v1/ai_tutor.py:127`, создание сессии): тот же гейт при открытии **новой** сессии; `stuck_note` — параметр запроса, уходит в контекст первой реплики наставника (рядом с `_last_student_answer`, `session_service.py:115`). Отказ — 409 `attempt_required`.
4. SPW: `components/task/HintPanel.tsx` — до первой сдачи вместо кнопки «Запросить помощь преподавателя» поле «Где застрял?» + кнопка (активна от 20 символов); обработка 409 `attempt_required` с текстом из ответа (сейчас любая ошибка — «Не удалось отправить запрос», `HintPanel.tsx:124-146`). Кнопка наставника и так показывается только после неверной сдачи (`TaskResult.tsx:147`) — не менять.
5. Тесты API: 409 без попытки и без заметки; 201 с заметкой ≥20; 201 после сдачи с заполненным `attempt_id`; при `HELP_REQUIRES_ATTEMPT=false` поведение прежнее.

### Фаза B — П3: повторение по следам ошибок (tsk-992)

6. Миграция: таблица `task_review_schedule` — `id`, `student_id` FK users, `task_id` FK tasks, `course_id` FK courses (корневой курс, в контексте которого шло обучение), `interval_stage SMALLINT` (0→3 дня, 1→7, 2→21), `due_at TIMESTAMPTZ`, `last_result_id` FK task_results NULL, `created_at`, `updated_at`, `completed_at NULL` (заполняется после верного повтора на стадии 2). Уникальность `(student_id, task_id, course_id)`. Индекс `(student_id, course_id, due_at) WHERE completed_at IS NULL`.
7. Рубильник на курс: `courses.retrieval_config JSONB NULL` по образцу `sampling_config` (`app/models/courses.py:72`, схема `app/schemas/course_sampling.py`), формат `{"enabled": false}`; `GET/PUT /courses/{id}/retrieval` по образцу `/courses/{id}/sampling` (`courses_extra.py:1306/1340`), права — методист/админ.
8. Планировщик: в блоке после записи результата (`app/api/v1/attempts.py:1358-1380`, где сейчас `compute_task_state` → `close_blocked_limit_if_resolved`) — если рубильник корневого курса включён, задание стало PASSED, сдача не `manual_teacher`, и в истории `task_results` по паре (ученик, задание) есть хотя бы один непрошедший результат до этой сдачи → создать запись стадии 0, `due_at = now + 3 дня` (если записи нет). Нестрого, как соседний блок: исключение — в лог, сдачу не роняет.
9. API ученика: `GET /learning/courses/{course_id}/review-due` → список заданий с `due_at <= now`, `completed_at IS NULL` (id, название, стадия, сколько дней назад решал). Пустой список, если рубильник выключен.
10. Сдача повтора: через существующую сдачу ответа с признаком повтора (`review=true` в теле `POST /attempts/{attempt_id}/answers` либо отдельный тонкий эндпоинт — выбрать по коду, обосновать в отчёте); результат пишется в `task_results` с `source_system='retrieval'`. Верно → следующая стадия (`due_at` = now + 7 / 21 дней) или `completed_at` после стадии 2; неверно → стадия 0, `due_at = now + 3 дня`. Повтор **не меняет** PASSED-статус задания в линейном пути (проверить, что `compute_task_state`, считающий по последнему результату, не превращает пройденное задание в FAILED из-за неверного повтора: либо исключить `'retrieval'` из этого расчёта, либо доказать тестом, что вреда нет).
11. `learning_gaps_service` и отчёты: `'retrieval'` не считается «реальной сдачей» для пробелов; подсчёт попыток `attempts_used` и лимит попыток не расходуются повтором. Тесты на оба пункта.
12. SPW: на странице курса (`app/(authed)/courses/[course_uid]/page.tsx`) над программой — блок «Пора повторить: N заданий» со списком ссылок на экран задания в режиме повтора; блок не рендерится при пустом списке. Экран задания в режиме повтора — без подсказок до сдачи.

### Фаза C — П5: итоговый срез (tsk-994)

13. Флаг: `courses.final_check_config JSONB NULL` — `{"enabled": false, "size": 10}`; API `GET/PUT /courses/{id}/final-check` по образцу п.7. (В аудите — `is_final_assessment` на узле; конфиг на корневом курсе выбран, чтобы не создавать новый тип узла в графе и не задеть `compute_course_state` — Р4.)
14. Выборка: при первом открытии среза — детерминированно (сид как в `task_sampling.deterministic_seed`, `app/services/task_sampling.py:28`, но с отдельной солью «final») выбрать `size` заданий из **ПРОЙДЕННЫХ** учеником заданий курса и всех подкурсов, равномерно по подкурсам-главам (не меньше 1 на главу, если глав ≤ size). Состав сохранить (таблица `final_check_runs`: student_id, course_id, task_ids JSONB, started_at, finished_at, result JSONB), чтобы повторное открытие показывало тот же набор.
15. Гейт доступа: `compute_course_state(...) == COMPLETED` для корневого курса и включённый конфиг; иначе 409 `final_check_locked`.
16. Сдача заданий среза — `source_system='final_check'`, не меняет статусы заданий и курса (как п.10–11). Итог: доля верных + список глав с ошибками; ошибочные задания, если включён П3 на курсе, ставятся в повторение (стадия 0).
17. SPW: на странице завершённого курса — карточка «Итоговый срез: проверь, что навык остался» → прохождение → экран итога «Навык сохранился» (≥80 % верных) / «Есть пробелы в темах: …» со ссылками на главы.

## Критерии готовности

1. `pytest` LMS — без регрессий; новые тесты на пункты 1, 5, 8, 10, 11, 14–16 зелёные.
2. Миграции применяются и откатываются на чистой БД (`alembic upgrade head` → `downgrade -1` для каждой).
3. При всех рубильниках в положении по умолчанию поведение API и SPW **не отличается** от main: тест-набор движка (`resolve_next_item`, `compute_task_state`, `compute_course_state`) зелёный без правок ожиданий.
4. П4: без сдачи и без заметки — 409 `attempt_required`; с заметкой ≥20 символов — заявка создаётся, заметка видна в карточке заявки; после сдачи — заявка с непустым `attempt_id`.
5. П3: задание «незачёт → зачёт» на курсе с включённым рубильником даёт запись стадии 0 с `due_at` = +3 дня; неверный повтор не делает задание FAILED в линейном пути и не тратит лимит попыток; `'retrieval'` не попадает в пробелы.
6. П5: срез недоступен до COMPLETED (409); набор детерминирован и сохраняется; результат не меняет `course_state`.
7. SPW: `tsc --noEmit` и eslint без новых ошибок; vitest на блок «Повторение», поле «Где застрял?» и экран итога среза.
8. Отчёт содержит: выбранный вариант п.10 с обоснованием, список затронутых файлов, что требует живой проверки на проде.

## Риски

| Риск | Мера |
|---|---|
| Неверный повтор/срез ломает PASSED в линейном пути (последний результат решает) | Исключить `'retrieval'`/`'final_check'` из `compute_task_state` или доказать тестом (п.10, критерий 5) |
| Повтор расходует лимит попыток → автозаявки `blocked_limit` | Не учитывать `'retrieval'`/`'final_check'` в `attempts_used` (п.11) |
| Гейт П4 ломает бот TG_LMS или старые клиенты | Глобальный `HELP_REQUIRES_ATTEMPT=false` по умолчанию; в отчёт — кто ещё зовёт `request-help` |
| Ученики пишут «застрял» мусором ради доступа | Порог 20 символов + текст уходит преподавателю — видно сразу; метрику смотреть на пилоте |
| Конфликт миграций с параллельными сессиями | Проверить `alembic heads` перед созданием и перед мержем; одна миграция на фазу |
| Выкат ветки «прицепом» до решения оператора (tsk-672) | Все рубильники выключены по умолчанию — выкат безопасен; включение = решение оператора |
| Новые значения `source_system` всплывают в отчётах преподавателя как сдачи | Grep всех запросов по `source_system` и `task_results`, перечислить в отчёте, где новые значения учтены/исключены |
