# tsk-652 — хуки на отклонения: доставка «требует внимания» преподавателю

**Дата:** 2026-09-13. Источник цифр — боевая база (read-only) и живой прогон
под сессией оператора (аккаунт 2, роль teacher).
**Задача:** [[tsk-652]], последний пункт комплекса [[tsk-589]]. Урок, ради
которого задача отдельная: механизм уже дважды срабатывал правильно (страж
«ходит, но не выставлен», простой на занятии 22.08 из [[tsk-591]]), а сигнал
не доходил до человека. Мера успеха — `read_at`, а не факт отправки.

---

## 1. Свод отклонений в один список

Не строил новых метрик — свёл то, что уже есть:

| Источник | Где живёт | Кому адресован | Как решил |
|---|---|---|---|
| `learning_gap_signal` (reason `error_rate`/`ai_authorship`/`dropout_risk`, tsk-646/647) | `learning_gap_signal.status='new'` | ЛЮБОМУ преподавателю (не привязан к конкретному, пока не возьмут в работу — тот же принцип, что у `/learning-gaps/students`) | посчитал **общий** счётчик, не per-teacher |
| `notifications.kind='student_idle'` (простой на занятии) | таблица `notifications`, уже пишет `lesson_idle_cron_service` | конкретному `user_id` (учитель уже назначен) | посчитал `read_at IS NULL` по этому `user_id` |
| `notifications.kind='lesson_missed'` (пропуск занятия) | пишет `lesson_attendance_cron_service` | конкретному `user_id` | то же |
| tsk-648 (очерёдность внимания) / tsk-649 (пора усложнить) | поля в `GET /teacher/lesson-occurrences/{id}/summary`, экрана/уведомления НЕТ вовсе (см. историю tsk-649) | по занятию, не персонально | **не включил в хук** — см. §2 |

**Почему tsk-648/649 не вошли в хук.** Это не отдельные события с собственным
жизненным циклом «создано → прочитано», а поля внутри карточки конкретного
занятия — они не «висят непрочитанными», они просто не увидены ДО занятия.
Доставка для них уже есть и работает: `lesson_reminder` (61% прочтения за
14 дней на боевых данных, см. §3) — именно он приводит преподавателя на
карточку занятия, где эти поля видны. Строить для них отдельный хук — значит
дублировать существующий `lesson_reminder`, а не чинить дыру.

## 2. Новый эндпоинт — агрегатор, не новая метрика

`GET /api/v1/teacher/attention/summary?teacher_id=` (`app/api/v1/teacher_attention.py`,
`app/services/teacher_attention_service.py`) — три счётчика:
`gap_signals_new` (общий), `student_idle_unread`, `lesson_missed_unread`
(персональные). Ни новой таблицы, ни новой миграции, ни нового вида
`notifications.kind` — только SELECT поверх существующих данных.

`learning_gap_signal`: **29 сигналов в статусе `new`**, необработанные —

Ещё 4 сигнала висят в `escalated` дольше 3 дней (частично тот же тупик, что
описан в [[project_lms_dropout_risk_signal]] — `resolve` методистом
существует с tsk-653, но им, похоже, не пользуются регулярно). Это и есть
конкретное доказательство урока задачи: сигнал сработал (строка создана),
человек не пошёл смотреть (статус не сдвинулся месяц).

Все три источника (`student_idle`, `lesson_missed`, `learning_gap_signal`) до
этой задачи **не доходили до Telegram вообще** — teacher-бот их не читал
(два имевшихся поллера дёргают только `pending-count` проверок и заявок
помощи, отдельно от `notifications`/`learning_gap_signal`).

## 4. Канал: Telegram teacher-бот (третий независимый поллер)

Решение по памяти [[project_lms_bot_is_secondary_surface]] («веб-кабинет —
основной инструмент, бот — для оповещений и быстрых действий») плюс by-design
факт: `learning_gap_signal`/`student_idle`/`lesson_missed` уже видны в
кабинете (экран есть, tsk-651/tsk-572) — недостающая часть именно
**оповещение**, не экран. Реализовано push-хуком: `poll_teacher_attention` в
`TG_LMS/src/bots/teacher/poller.py`, тот же паттерн, что у review/help-requests
поллеров (рост счётчика между тиками → ephemeral-сообщение), плюс две новые
защиты от шума, которых у тех двух нет:

- **тихие часы** (по умолчанию 22:00–08:00 МСК, `common/quiet_hours.py`,
  настраивается `TEACHER_ATTENTION_QUIET_HOURS_START/END`) — рост есть, но
  сейчас ночь: не шлём и НЕ обновляем internal-курсор, чтобы дельта дошла,
  как только час кончится, а не потерялась;
- **минимальный интервал между push одному преподавателю**
  (`TEACHER_ATTENTION_MIN_GAP_SEC`, по умолчанию 300 сек) — та же логика
  накопления дельты вместо потери;
- **один дайджест**, а не три отдельных сообщения на три источника —
  `format_attention_message` включает только реально выросшие части.

Канал для методиста и оператора в эту задачу не входил (методист — уже
Telegram по факту аудита [[project_lms_bot_is_secondary_surface]] /tsk-600,
оператор решает сам при необходимости — постановка явно выносила это ему).

## 5. Живая проверка (прод, 2026-09-13, аккаунт 2 = Виктор Комлев, роль teacher)

1. Задеплоено: LMS `55dea98` (`main`), TG_LMS `27b9087`→тесты дофиксил в
   `4ad73b2` (файл теста обновлён на сервере вручную, без рестарта ботов —
   поведение не менялось). Все 4 бота TG_LMS стабильны после рестарта.
2. Смоук: `GET /teacher/attention/summary?teacher_id=2` через боевой
   сервис-ключ — реальные счётчики (`gap_signals_new=26`,
   `student_idle_unread=35`, `lesson_missed_unread=47`).
3. Логи teacher-бота подтверждают: поллер стартовал, взял всех 4 реальных
   преподавателей из ростера (id 2, 3, 4495, 4496), для каждого получил
   baseline без ложного уведомления на первом тике, дальше стабильно опрашивает
   раз в 60 сек без ошибок.
4. **read_at меняется по факту прочтения, не по факту отправки** — под живой
   сессией (реальный Chrome, `/me` подтвердил id=2, `tg_id` реально
   привязан) открыл `/teacher/notifications`, прочитал реальное уведомление
   `student_idle` (id 3339, Ундасынова Василина, простой 11 мин, 12.09
   12:32) через настоящий интерфейс кабинета. Замер сводки ДО/ПОСЛЕ:

   | счётчик | было | стало |
   |---|---|---|
   | `student_idle_unread` (teacher_id=2) | 35 | 34 |
   | `lesson_missed_unread` (teacher_id=2) | 47 | 46 (кабинет пометил читанным заодно ещё один «Ученик не пришёл» при открытии списка — существующее поведение экрана, не моя правка) |
   | `gap_signals_new` (общий) | 26 | 26 (не менялся — верно: чтение notifications на gap-сигналы не влияет) |

5. **Чего не проверил живьём и почему.** Полный цикл «новое отклонение →
   push в Telegram → прочитано по push» не пронаблюдал: на момент проверки
   (суббота, 23:30 МСК) нет идущего живого занятия, а первый тик поллера
   после рестарта — baseline без уведомления по конструкции (см. §4,
   тот же принцип, что у review/help-requests поллеров). Механизм проверен
   до этого стыка (агрегатор верный, доставка при росте счётчика написана и
   покрыта тестами, поллер реально опрашивает боевых преподавателей); сам
   push от роста счётчика на реальном занятии — предстоит увидеть в
   ближайшие рабочие дни.
