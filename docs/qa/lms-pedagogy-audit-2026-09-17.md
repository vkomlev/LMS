- **Дата:** 2026-09-17
- **Задача:** tsk-979 (courses/группа «в» — улучшение системы LMS: уроки, ДЗ, подача, кабинеты, процедуры)
- **Поверхность:** LMS backend + кабинеты (репозиторий `D:\Work\LMS`)
- **Педагогическая опора:** `D:\Work\ContentAnalyzer\reviews\methodist-courses-tz-2026-09-17.md` — модули M2 (обратная связь/рефлексия), M3 (память/усвоение), M4 (мотивация/видимость), M6 (инструменты/удержание ETE-TRC), M7 (этика/помощь после попытки)
- **Метод:** механический инвентарь из роутеров/схем/моделей/сервисов (4 параллельных прохода), сверка каждой гипотезы с боевыми данными read-only через MCP `learn_prod_db`. Гипотеза из статичного кода вердиктом не считалась.
- **Границы захода:** READ-ONLY по боевой БД, только SELECT. Ни одной правки кода/миграции — это заход **анализа**. Реализация каждого пункта — отдельное решение оператора.

## Главный вывод

**LMS уже считает почти все педагогически ценные сигналы — темп, прогноз окончания, «где застрял», покритериальный разбор ответа, застрявшие задания, вехи удержания. Пробел не в том, что сигналов нет, а в том, что они (а) не доходят до нужной аудитории и (б) не превращаются в педагогическое действие.** Три из четырёх аспектов — это работа «на последней миле» (показать/подсказать поверх готового расчёта), недорогая и с высоким эффектом. Единственный аспект с настоящей дырой в модели данных — **удержание навыка** (интервальное повторение / retrieval): его нет вовсе.

Подтверждающие цифры с прода (детали в Приложении):

- **99% ручных зачётов идут без единого слова фидбека** — 15 146 из 15 321 записей с `manual_grant` имеют пустой `comment`. Развивающей обратной связи (M2) на основном пути практически нет.
- **148 заданий с развёрнутым ответом (TA) имеют написанную методистом рубрику (472 пункта), которой не пользуется никто** — машина такие работы не судит, человек ставит зачёт целиком «не глядя» (`rubric_review_service` docstring, tsk-658).
- **Ученик в своём кабинете не видит темпа, прогноза окончания и точки затыка** — всё это считается в `student_dashboard_service`, но гейт открыт только персоналу/родителю (`student_dashboard.py:34-51`).
- **Интервального повторения и проверки «остался ли навык» нет ни строкой** — grep по `spaced|repetition|next_review|review_due|decay|recall` пуст; движок идёт только вперёд, пройденное не возвращает.

## Аспект 1. Проверка ДЗ и обратная связь

### Инвентарь (из источника)

**Как устроено сейчас.**
- Сдача ответа: `POST /attempts/{attempt_id}/answers` (`attempts.py:332`), учебный вход — `POST /learning/tasks/{id}/start-or-get-attempt` (`learning.py:419`).
- Результат — `task_results`: `score`, `is_correct` (`None` = ждёт ручной проверки), `checked_by`/`checked_at`, `metrics` JSONB, `code_review` JSONB (машинная оценка кода/ИИ-авторства, ученику не видна). **Статусов-enum нет** — состояние вычисляется Learning Engine (`compute_task_state`: OPEN/IN_PROGRESS/PASSED/FAILED/BLOCKED_LIMIT).
- Лимит попыток — **есть, но не хранится полем**: считается по корню курса, default 3, форс при сдаче (`attempts.py:656-756`, 409). У `tasks.max_attempts` на проде **не заполнено ни одной строки** — работает вычисляемый дефолт.
- Ручная проверка: очередь + вердикт в `teacher_reviews.py` (`claim-next`, `grade`, `regrade`), второй путь — `POST /task-results/{id}/manual-check`. Вердикт задаёт `ReviewGradeRequest` (`teacher_next_modes.py:266`): только `score` + опциональный `comment`. «Принять» = score=max, «Отклонить» = score=0.
- Комментарий преподавателя хранится строкой в `task_results.metrics["comment"]` (`teacher_queue_service.py:1241`) — **отдельной колонки под фидбек нет**.
- Покритериальный разбор: `rubric_review_service` (tsk-658) раскладывает развёрнутый ответ по пунктам рубрики и **предлагает** балл (машина разбирает — человек решает). Автопроверочный фидбек ученику: `CheckFeedback` (`checking.py:161`) — `general` + `by_option`.

**Что ОТСУТСТВУЕТ (искали, не нашли).**
- Структурированных полей развивающего фидбека (сильные стороны / рекомендации в будущем времени / ободрение) — нет нигде; везде одно свободное текстовое поле.
- `FeedbackReports` — это **не** фидбек по ДЗ, а инбокс «баг/контент/идея» для методиста (`report_type: bug|content|feature_idea`), к паре (ученик, задание) не привязан.
- Срока проверки ДЗ у `task_results` нет. `due_at` у `help_requests` есть как поле, но **кодом не заполняется** (INSERT его не пишет — остаётся NULL). Напоминаний преподавателю о непроверенном и метрик скорости проверки — нет.

### Сигнал из данных

- `metrics.comment` присутствует у 15 369 результатов, но **на пути ручного зачёта пуст в 99%**: из 15 321 `manual_grant` — 15 146 пустых, 174 содержательных (≥60 симв.). Осмысленный фидбек живёт почти только на 48 «неавтоматических» зачётах (30 из них ≥60 симв.).
- Очередь на проверку **не копится**: `is_correct IS NULL` — единицы записей за месяц. Значит проблема аспекта не в объёме непроверенного, а в **качестве и наличии фидбека**.
- Рубрика TA: по замеру tsk-658 из 64 сдач зачтено 60 на полный балл, ни в одной не проставлены баллы по пунктам.

### Предложения

**П1 (P0, M) — черновик покритериального разбора в момент оценки + мягкая структура фидбека.** `rubric_review_service` уже умеет разложить ответ по пунктам и предложить балл, но его выход никуда не подаётся преподавателю в UI-момент оценки. Предложение: `POST /teacher/reviews/{id}/grade` (и `manual-check`) на входе отдаёт преподавателю **предзаполненный черновик** — баллы по пунктам рубрики + шаблон «Сильные стороны → Что улучшить (в будущем времени) → Ободрение». Преподаватель редактирует, а не пишет с нуля. Это снимает главный барьер («писать долго → ставлю зачёт молча»). Хранить можно в том же `metrics` расширенной структурой (`comment` + `strengths`/`next_steps`/`encouragement`), без ломки схемы.
*Педагогика M2:* развивающая ОС = сильные стороны → рекомендации в будущем времени → ободрение; структура делает форму дефолтной. *Эффорт M:* сервис-склейка `rubric_review_service` ↔ `teacher_queue_service`, расширение схемы вердикта, правка SPW-экрана оценки.

**П4 (P1, S–M) — мягкий гейт «помощь после попытки» (M7).** Сейчас `request_help` (`learning.py:692`) гейтит только оплату и подписку; проверки «а была ли попытка» нет, у `manual_help` `attempt_id = NULL`. AI-наставник открывается из задания по подписке/квоте, без требования попытки (страж ответа `answer_guard` уже режет готовые решения — эту сторону M7 система держит). Предложение: на конкретном задании manual_help и AI-наставник разблокируются после **≥1 сданной попытки** (или явного «я попробовал, застрял на X»). Автозаявка `blocked_limit` в эту логику уже вписана (создаётся после исчерпания лимита). *Педагогика M7:* «индивидуальный темп + помощь только после самостоятельной попытки». *Эффорт S–M:* условие в `request_help`/входе в тьютора, привязка `attempt_id`.

**П6 (P2, S–M) — регламент проверки.** Заполнять `due_at` при создании заявки/при появлении непроверенной работы (инфраструктура сортировки/`overdue` уже есть в `teacher_queue_service`), вывести преподавателю счётчик «непроверенное и просроченное» (в `teacher_attention`/`teacher_workload`), считать метрику скорости проверки. *Педагогика M2:* регламент проверки ДЗ. *Ниже приоритет, потому что очередь не копится* — это про предсказуемость и качество, не про завал.

**П10 (P3, S) — рефлексия ученика после разбора.** Расширить существующее `help_requests.review_understood` (сейчас «понял/не понял») в короткую саморефлексию («что было главное / что осталось непонятным») — валидный измеритель по M2 (Бейтсон: рефлексия/самооценка). Дёшево, встраивается в готовый ладдер помощи tsk-303.

## Аспект 2. Кабинеты и видимость прогресса

### Инвентарь (из источника)

**Кабинет ученика (`me.py`, гейт «свой профиль»).** `GET /me/courses` → `CourseProgress` (`tasks_done/total`, `materials_done/total`, `percent`); `GET /me/streak` (суточная серия); `GET /me/retention` (серия активных недель + вехи); `GET /me/last-position` (следующий шаг через `resolve_next_item`); `GET /me/history`, `/me/courses/{id}/syllabus-states`.

**Богатая аналитика — но не ученику.** `student_dashboard_service` считает `pace_level` (терциль против когорты), `fact_per_week`, `forecast_completion_date`, `on_track`, `current_item_title`, `behind_count`, `behind_item_title` (`course_position.py:145-151`). **Гейт `student_dashboard.py:34-51` пускает только персонал и родителя со связкой — сам ученик свой дашборд получить не может.**

**Кабинет преподавателя.** `teacher_progress.py` — дерево ученика с per-item `needs_attention` (BLOCKED_LIMIT / заявка / на проверке / возврат), `is_current` (над чем работает сейчас). `teacher_activity_feed`, `teacher_attention` (gap-сигналы / idle / пропуски), `teacher_workload` (открытые заявки / просрочка). Точной строки «застрял на элементе X» в карточке преподавателя **нет** (только per-item флаги; строка `behind_item_title` живёт в дашборде для персонала/родителя).

**Освоение тем (`topic_mastery`) — только методисту** (`require_role("methodist","admin")`): `correct_rate`, `median_pace_seconds`, `pace_ratio`, `signal` (hard/easy/ok).

**Достижения.** Модель `achievements` (`condition` JSONB, `reward_points`) + `user_achievements` (`earned_at`, `progress`). **Но `condition` нигде не вычисляется** — общего движка начисления нет; реально начисляются только вехи удержания (`retention_achievements_cron_service`). `GET /me/achievements` **отсутствует** — ученик значков/баллов в кабинете не видит.

### Сигнал из данных

- `student_task_progress` — **1 строка** на проде (это лишь маркер skip; счётчики/серии живут в `task_results`/`attempts`). Прогресс считается на лету.
- `student_material_progress` — 10 821 `completed`, 16 `skipped` (материалы отмечаются пройденными штатно).
- `learning_events`: `task_opened` 14 035 (питает расчёт темпа), `hint_open` 1 505, `attempt_limit_reached` 1 005.

### Предложения

**П2 (P0, S–M) — показать ученику то, что уже посчитано.** Ввести student-facing read-эндпоинт (`GET /me/courses/{id}/progress-detail`), переиспользующий `student_dashboard_service`/`course_position`, с безопасным для ученика срезом: «сколько осталось» (штук и минут — вес берёт `task_effort_service`, tsk-851), прогноз окончания, «ты сейчас здесь → следующий шаг», и мягкий сигнал темпа (**без сравнения с когортой** — терциль оставить персоналу, ученику показать «в графике / отстаёшь на N», чтобы не демотивировать; когорты у большинства курсов <5 человек, tsk-504). *Педагогика M4:* видимость прогресса/темпа/затыка — «раньше замечать, где остановился». *Эффорт S–M:* расчёт готов, нужен эндпоинт + student-safe схема + экран SPW. Самый дешёвый высокоэффектный пункт.

**П8 (P3, M) — достижения ученику + движок условий.** Реализовать `GET /me/achievements` и вычисление `achievements.condition` (сейчас поле есть, но мёртвое). Держать в рамках вывода tsk-032/tsk-504: **не соревновательные** механики (лидерборд демотивирует в малых когортах), а личные вехи/усилие. *Педагогика M4:* похвала за усилие (Дуэк), а не за талант; мотивирующая среда. *Эффорт M.*

## Аспект 3. Удержание: повторение и квизы

### Инвентарь (из источника)

**Чего НЕТ (снято грепом по всей `app/`).**
- **Интервального повторения / spaced repetition — нет ни строкой.** Ключи `spaced|repetition|next_review|review_due|revisit|decay|recall` в контексте повтора задач не встречаются. `retention_service` — это удержание **ученика** между занятиями (недельная серия/вехи, tsk-032), **не** удержание навыка.
- **Retrieval practice — нет.** `resolve_next_item` идёт по дереву только вперёд, `PASSED` пропускается и повторно не предлагается («что ученик знает — то знает, перерешивать не нужно», `compute_task_state` docstring). Пройденное, добавленное позже, приходит рекомендацией, а не повтором.
- **Decay освоения со временем — нет.** `topic_mastery` — снимок в окне (по умолчанию 90 дней), `mastered = correct ≥ total`; окно не моделирует забывание.
- **Проверки «остался ли навык» (ETE/TRC) после паузы — нет.** `course_dependencies` — это gate «курс A завершён → открыть B», не срез удержания. `is_exam` — лишь флаг «экзаменационный курс», отключающий сигнал «усложнить».
- **Итогового/выходного контроля по курсу — нет.** Завершение = доля пройденных заданий → `COMPLETED`, без финального теста. `graduation_service` — перевод на тариф «Выпускник», не контроль знаний.

**Что ЕСТЬ рядом (но это не удержание навыка).**
- Гостевой квиз подбора программы (`guest_quiz.py`, типы `SC_Qw/MC_Qw`, баллы по шкалам) и гостевая диагностика-зонд входного контроля (`guest_diagnostic.py`) — **лид-магниты для незарегистрированных**. Для зачисленного ученика отдельного квиза-на-знание нет; `SC_Qw/MC_Qw` внутри курса — это scale-задания (1 попытка), не «верно/неверно».
- `learning_gaps_service` → заявка методисту на «мини-курс повторения» по темам с массовой ошибкой (порог 0.35) — ручное переобучение по агрегату, без автоматического возврата конкретной задачи конкретному ученику.

### Сигнал из данных

- `guest_attempt` — 65 (гостевой контур, малый).
- `learning_gap_signal` — 74 (аналитика для методиста).
- Механизмов возврата навыка ученику — 0.

### Предложения

**П3 (P1, L) — «Повторение по следам ошибок» (retrieval с интервалом).** Новая лёгкая модель `task_review_schedule (student_id, task_id, due_at, interval_stage)`: задание, которое ученик сначала завалил, потом сдал, планируется к повторному показу через интервал (наивный SM-2-подобный шаг: 3д → 7д → 21д). Показ — отдельным блоком «Повторение» в кабинете (не ломая линейный `resolve_next_item`), вердикт пишется обычным `task_results` с `source_system='retrieval'`. Начать можно на одном курсе (рубильник, по образцу `sampling_config`/`AI_TUTOR_ENABLED`, выключен по умолчанию). *Педагогика M3:* retrieval practice, интервальное повторение, борьба с иллюзией компетентности; M6: проверка, что навык сохранился. *Эффорт L:* новая таблица + планировщик + блок в кабинете; движок вперёд не трогаем.

**П5 (P2, M) — итоговый контрольный срез по курсу.** Узел графа с флагом `is_final_assessment`, набираемый retrieval-выборкой из ранее пройденных заданий курса (переиспользуя `task_sampling`, tsk-314), доступный при `COMPLETED`. Даёт ETE/TRC-ответ «навык остался после прохождения», не только «дошёл до конца». *Педагогика M3/M6.* *Эффорт M:* флаг курса + выборка + гейт доступности; типы заданий и проверка уже есть.

## Аспект 4. Формат подачи уроков

### Инвентарь (из источника)

**Граф курсов.** Узел = `Courses`; иерархия — M2M `course_parents` (`order_number` подкурса ставит триггер), защита от циклов в БД. **Атрибута типа узла (курс/модуль/урок/подкурс) нет** — тип определяется только позицией в графе (есть ли родители/дети). Ученик закрепляется только на корне.

**Материалы.** `materials.type` — enum `text/video/audio/image/link/pdf/office_document/script/document`; тело в `content` JSONB; `format` (markdown/html/plain) живёт внутри JSONB, отдельной колонки нет. `order_position` — своя колонка, триггеры. **На проде реально используются только 2 типа: `text` 3428, `video` 330** — интерактива внутри материала нет.

**Задания.** Висят напрямую на узле (той же связью, что материал), `order_position` — своя независимая колонка. Типы (`task_content.py:8`): `SC/MC/SA/SA_COM/TA/SC_Qw/MC_Qw/TBL_COM`. Автопроверка кода — три механизма: `code_ast`, `io_tests` (песочница stdin→stdout), `turtle_sim`. Медиа в заданиях (`image/audio/video_url`), подсказки (`hints_text/hints_video`).

**Движок подачи.** `resolve_next_item`: активные курсы по порядку → проверка пререквизитов → post-order обход дерева → **внутри узла строго «все материалы (по `order_position`) → все задания (по `order_position`)»**. Правило «материалы раньше заданий» жёстко зашито.

**Что ОТСУТСТВУЕТ.**
- **Чередование теория↔практика в движке — нет.** Нет логики «после N материалов — задание». Чередование достигается **только ручным дроблением на подкурсы** (каждый мелкий подкурс = свой блок материалов+заданий) — движок про это не знает.
- Общего порядкового ключа «материал+задание» внутри узла нет (две независимые `order_position`).
- Интерактивной контрольной точки внутри материала нет (материал — пассивный контент).

### Сигнал из данных

- Задания активные: SC 2487, SA_COM 2264, SA 1793, MC 319, TBL_COM 306, TA 150, SC_Qw 9 (богатый парк типов, автопроверка кода в ходу — 11 864 результатов с `code_review`).
- Материалы: только `text`/`video` — потенциал `pdf/script/interactive` не задействован.

### Предложения

**П7 (P2, M–L) — опциональное чередование теория↔практика в движке.** Дать узлу режим подачи `interleave` (флаг на курсе/узле): вместо «все материалы → все задания» движок чередует по общему порядковому ключу или по правилу «материал → закрепляющее задание». Это убирает необходимость вручную дробить тему на десятки микро-подкурсов ради чередования. *Педагогика M1/M6:* практико-ориентированность, чередование (interleaving также усиливает M3). *Эффорт M–L:* правка `resolve_next_item` + признак режима; риск регрессии в ядре подачи — требует тестового покрытия и рубильника, выключенного по умолчанию.

**П9 (P3, L) — контрольная точка внутри материала (embedded checkpoint).** Разрешить материалу нести короткий встроенный вопрос-чекпоинт (retrieval сразу после теории) — тип `content` с 1-2 вопросами, verdict не блокирует, но пишет сигнал усвоения. *Педагогика M6:* инструменты интерактива (H5P-подобное), проверка «понял ли сразу». *Эффорт L:* новый тип content + рендер в SPW + запись сигнала; самый дорогой пункт, ниже приоритет.
