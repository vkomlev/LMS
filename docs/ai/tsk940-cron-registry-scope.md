# tsk-940 — общий хелпер регистрации крон-джоб APScheduler: оценка охвата

Роль: `/architect-system-analyst`. Реализация не производилась — это Шаг 0-9
(AS-IS → TO-BE → ADR → план поставки → Go/No-Go) перед стартом кода.

## Problem Framing

**Objective.** Устранить класс бага (первый тик крона откладывается на полный
интервал от момента КАЖДОГО рестарта процесса, а не от абсолютного времени)
одним общим механизмом регистрации, а не повторной копипастой фикса.

**Project/Scope.** `D:\Work\LMS`, только `app/services/*_cron_service.py` +
`app/core/config.py` (новые настройки) + `app/api/main.py` (только замена
вызовов `add_job` внутри уже существующих `start_scheduler()`, без изменения
порядка/состава startup-хуков). Данные, бизнес-логика самих тиков — вне
охвата, не трогаются.

**Non-goals.**
- Не строим общий реестр *запуска* startup-хуков в `main.py` (кто и в каком
  порядке вызывает `start_scheduler()`) — это отдельная, более рискованная
  проблема (см. Gaps), не входит в tsk-940.
- Не меняем бизнес-условия внутри тиков (например, недельный гейт в
  `curator_report_cron_service`).
- Не вводим внешний scheduler (Celery beat, cron+systemd timer) — APScheduler
  остаётся.

**Success criteria.**
1. Есть один модуль (`app/core/cron_registry.py`) с одной функцией
   регистрации interval-джобы, и вызвать `add_job` без `next_run_time`
   в `app/services/*_cron_service.py` нельзя, не написав явно
   `startup_delay_min` — обязательный параметр без default.
2. Все 6 уже-починенных сервисов используют эту функцию вместо локальной
   копии `_startup_run_at`; их регрессионные тесты (5 из 6 — прямые тесты на
   `next_run_time`) проходят без изменения логики теста.
3. Написано отдельное unit-покрытие хелпера (не через сервисы).
4. Принято и записано (ADR) решение по оставшимся 8 сервисам.

**NFR:** reliability (главный драйвер — не потерять достигнутое в
tsk-653/tsk-939), maintainability (единая точка правды), security/perf — не
затронуты этим изменением.

## AS-IS Snapshot

**C4-Context.** Один процесс `lms.service` (FastAPI + APScheduler в том же
event loop) на `lms-spw-vds`. 14 фоновых джоб живут внутри одного процесса,
каждая — свой `AsyncIOScheduler` (не общий!) на модуль-синглтон. Внешние
акторы: деплой (частые рестарты, 2-4ч в среднем), PostgreSQL (advisory-lock
на мультиворкер-защиту), Telegram/WP (получатели уведомлений некоторых
тиков).

**C4-Container / поток регистрации.** `app/api/main.py` — 14 отдельных пар

по файлу (не единым блоком), каждый в своём `try/except Exception:
logger.exception(...)` — падение регистрации одной джобы не валит старт
приложения и не помечается как ошибка health-check. Внутри каждого
`start_scheduler()` — свой `AsyncIOScheduler(timezone="UTC")` и свой

## Gaps and Ambiguities

1. **Название теста #5 не совпадает с сервисом** (`test_tsk653_ai_authorship_
   signal.py` тестирует `learning_gaps_cron_service`) — при миграции этого
   файла искать тест по номеру задачи, не по имени сервиса, иначе легко
   решить, что регрессии нет, хотя она есть.
2. **`llm_chain_check_cron_service.py` не имеет регрессионного теста** на
   `next_run_time` вовсе — при миграции на общий хелпер нужно ДОБАВИТЬ тест
   по образцу остальных пяти, иначе эта миграция ничем не подтверждена.
3. **Порядок регистрации в `main.py` уже один раз ломался** (комментарий на
   строке 622-624 фиксирует инцидент tsk-596 — decorator потерялся из-за
   перестановки блоков). Это существующий риск ДО tsk-940, не создаваемый
   этой задачей — но раз мы трогаем каждый `start_scheduler()`, стоит не
   менять порядок/расположение блоков в `main.py`, только тело функций
   (снижает blast radius правки).
4. **`curator_report_cron_service` — особый случай**, интервал джобы (1ч) не
   равен реальной периодичности рассылки (неделя, гейт внутри тика по дню
   недели/часу). Общий хелпер лечит только "первый тик после рестарта", а не
   риск "рестарт совпал с окном понедельник-утро" — это НЕ регрессия
   хелпера, это существующий отдельный риск, который tsk-940 не обязан
   закрывать (зафиксировать явно, чтобы не спутали с результатом этой
   задачи).
5. Допущение, требующее подтверждения оператором, не догадки: **включаем ли
   в объём миграцию всех 8 непочинённых сервисов, а не только рефакторинг
   6 уже-починенных?** Это ключевая развилка охвата — см. ADR-0008 ниже,
   решение и обоснование даны, но это расширение исходно запрошенного
   объёма ((а) без (б)), поэтому вынесено оператору отдельным вопросом в
   чате, не решено единолично.

## Anti-patterns found

- **Copy-paste вместо переиспользуемой функции** (6 идентичных тел
  `_startup_run_at` + 14 идентичных троек `coalesce/max_instances/replace_
  existing`) → статус **must-centralize**. Обоснование: не гипотетический
  риск — это уже дважды (tsk-653, tsk-939) стоило отдельного инцидента с
  живой диагностикой на проде, включая один случай с финансовым сервисом
  (`charge_cron_service`).
- **8 из 14 файлов — живые примеры БЕЗ фикса**, которые следующий
  разработчик скопирует при добавлении нового крона (копирует ближайший
  похожий файл — обычная практика в этой кодовой базе, видно по
  единообразной структуре всех 14). Пока таких примеров большинство (8/14),
  вероятность, что новый крон скопирует именно баг, выше 50% — то есть
  хелпер, который никто не обязан использовать, не решает задачу "класс
  бага не может повториться". Это главный аргумент за пункт (б) ниже.
- **Регистрация startup-хуков разбросана по `main.py`** (14 отдельных
  блоков, не единый список/реестр) → статус **acceptable divergence в
  рамках tsk-940**: реальная проблема (пример — инцидент tsk-596), но
  устранение — отдельная, более крупная задача (единый реестр startup-хуков
  сам по себе меняет порядок инициализации приложения, это отдельный ADR и
  отдельный blast radius). Зафиксировать как отдельную рекомендацию
  оператору, не смешивать с tsk-940.

## Duplication Decisions

| Дублирование | Статус | Причина |
|---|---|---|
| `_startup_run_at` (6 копий) | must-centralize | Два реальных инцидента, тело идентично, только источник `delay_min` уже разошёлся |
| Тройка `coalesce/max_instances/replace_existing` (14 копий) | must-centralize | Ни одного отклонения по факту за все 14 — безопасный default |
| Регистрация startup-хуков в `main.py` (14 блоков) | temporarily local | Реальный риск (tsk-596), но отдельный ADR — не смешивать объём |

## 6-Dimension Review

1. **Scalability** — OK. Один процесс, локальный in-memory scheduler,
   изменение не меняет модель масштабирования.
2. **Security** — OK. Не затрагивает auth/данные/сеть.
3. **Maintainability** — сейчас RISK (копипаста расходится, видно на
   6 уже "починенных" файлах), после внедрения — OK.
4. **Performance** — OK. `next_run_time` — разовое вычисление при
   регистрации, не в горячем пути.
5. **Deployment/Operability** — WATCH. Каждый деплой = рестарт = новая
   регистрация всех 14 джоб; хелпер снижает риск "не тикнет сутками", но
   сам факт частых рестартов (2-4ч) остаётся вне этой задачи — если
   частота рестартов вырастет ещё, даже 5-минутный startup-delay может не
   успеть выполниться до следующего рестарта у самых нагруженных тиков.
   Не блокирует tsk-940, но стоит знать на будущее.
6. **Documentation/Observability** — WATCH → OK после задачи: хелпер в
   одном месте с docstring на русском фиксирует сам механизм бага, а не
   только память tsk-653/tsk-939 в трекере.

## Target Architecture (TO-BE)

**Новый модуль** `app/core/cron_registry.py`:

```python
def register_interval_job(
    scheduler: AsyncIOScheduler,
    func: Callable[..., Any],
    *,
    job_id: str,
    startup_delay_min: float,   # обязательный, БЕЗ default
    **interval_kwargs: Any,     # hours=..., minutes=... — прямиком в IntervalTrigger
) -> Job:
    ...
```

Почему сигнатура именно такая (обоснование архитектурного выбора, не только
"как в tsk-939"):

- **`startup_delay_min` без default** — единственный способ сделать
  "физически не может забыть": если параметр опционален с default=5, новый
  крон на 2 минуты интервала мог бы унаследовать чужой default молча и
  получить неподходящее число, а автор хелпера, который забыл про него,
  просто получит старое поведение без ошибки. Обязательный kwarg даёт
  `TypeError` на этапе импорта модуля — падает при старте приложения, а не
  тихо мимо тикает сутками на проде.
- **`**interval_kwargs` вместо `interval_hours`/`interval_minutes` двумя
  параметрами** — 6 файлов используют `hours=`, 7 используют `minutes=`;
  проброс `**kwargs` напрямую в `IntervalTrigger(**interval_kwargs)`
  покрывает оба случая без дополнительной ветки в самом хелпере и без
  разрастания сигнатуры на будущее (если появится `seconds=`).
- **`coalesce=True, max_instances=1, replace_existing=True` — захардкожены
  внутри функции, не параметры.** Обоснование — см. AS-IS: 0 отклонений на
  14 сервисах. Если когда-нибудь понадобится другое поведение — это будет
  осознанный повод завести отдельную функцию или явный override-параметр
  тогда, а не заранее.
- **`_startup_run_at` переезжает внутрь `cron_registry.py`** как
  приватная функция модуля, вызывается самим `register_interval_job` —
  наружу не экспортируется, сервисам она больше не нужна.

**Пример вызова после миграции** (было — 12 строк с локальным хелпером,
станет — один вызов):

```python
from app.core.cron_registry import register_interval_job

register_interval_job(
    scheduler,
    link_audit_tick,
    job_id="link_audit_tick",
    hours=settings.link_audit_interval_hours,
    startup_delay_min=settings.link_audit_startup_delay_min,
)
```

## ADR-0008 (черновик)

```markdown
# 0008 — Общий хелпер регистрации interval-крон-джоб

## Статус
Предложено (2026-09-15), tsk-940

## Контекст
Два инцидента подряд (tsk-653, tsk-939) — один и тот же баг
(`add_job(IntervalTrigger(...))` без `next_run_time` отсчитывает первый тик
от момента рестарта процесса) в разных cron-сервисах LMS. Фикс копипастился
почти дословно в 6 файлах и уже разошёлся деталями (источник `delay_min`:
модуль-константа / settings-атрибут / `getattr` с default). 8 из 14
сервисов с `IntervalTrigger` остаются непочинёнными и служат живым
примером для копипасты новых кронов.

## Решение
Ввести `app/core/cron_registry.register_interval_job(scheduler, func, *,
job_id, startup_delay_min, **interval_kwargs)` — единственная точка
регистрации interval-джобы, с обязательным (без default) параметром
`startup_delay_min` и захардкоженными `coalesce=True, max_instances=1,
replace_existing=True` (0 отклонений на все 14 текущих сервисов).
Мигрировать ВСЕ 14 сервисов, не только 6 уже-починенных — иначе цель
("новый крон не может физически завести тот же баг") не достигается, пока
большинство существующих примеров для копипасты остаются без фикса.

## Альтернативы
- Оставить как есть, полагаться на code review — отклонено: уже дважды не
  сработало на практике (баг находили постфактум, через диагностику
  инцидента, не на этапе ревью).
- Мигрировать только 6 уже-починенных (объём (а) без (б)) — отклонено как
  основной путь: не устраняет источник копирования бага для новых кронов;
  предложено оператору как более дешёвая альтернатива с явным
  компромиссом (см. решение в чате).
- Единый реестр/loop, который сам вызывает `start_scheduler()` для всех
  сервисов централизованно (закрыл бы и разброс в `main.py`) — отклонено
  для этой задачи: больше blast radius (меняет порядок инициализации
  приложения), отдельный ADR при отдельном запросе.

## Последствия
- Новый крон обязан явно передать `startup_delay_min` — небольшое трение
  при написании (один обязательный параметр), в обмен на невозможность
  тихо забыть.
- 8 сервисов получают НОВУЮ настройку `*_STARTUP_DELAY_MIN` — потребуется
  прогнать по каждому осмысленное значение (для minute-based сервисов
  разумный делэй — секунды/1 минута, не 5 минут, иначе делэй становится
  сопоставим с самим интервалом).
- `llm_chain_check_cron_service.py` получает новый регрессионный тест
  (сейчас отсутствует) — единственный из 6 "починенных", где его не было.
```

## Implementation Phases

**Фаза 1 — хелпер + unit-тесты (низкий риск, изолированно).**
- `app/core/cron_registry.py` + `tests/test_cron_registry.py` (unit,
  без реального старта FastAPI/приложения: создать `AsyncIOScheduler`
  напрямую в тесте, зарегистрировать джобу-заглушку, проверить
  `next_run_time`, проверить, что вызов без `startup_delay_min` падает
  `TypeError`, проверить проброс `hours=`/`minutes=` по отдельности).
- Exit criteria: новые тесты зелёные, `mypy`/type hints проходят,
  ничего в `app/services/` ещё не тронуто (нулевой риск регресса).
- Rollback: удалить файл, никто ещё не зависит.

**Фаза 2 — миграция 6 уже-починенных сервисов.**
- Замена локального `_startup_run_at` + блока `add_job` на
  `register_interval_job(...)`, значения `delay_min`/интервалов не
  меняются (поведение сохраняется бит-в-бит).
- Для `learning_gaps_cron_service.py` — сверить тест по номеру задачи
  (`test_tsk653_ai_authorship_signal.py`), не по имени сервиса.
- Для `llm_chain_check_cron_service.py` — добавить недостающий
  регрессионный тест по образцу остальных пяти.
- Exit criteria: все 6 файлов используют общий хелпер, старый
  `_startup_run_at` удалён из каждого, полный прогон тестов затронутых
  файлов зелёный (без изменений в самих тестах, кроме нового теста для
  llm_chain_check), `git diff` не меняет `main.py` вне точки вызова.
- Rollback: `git revert` коммита фазы — публичное поведение (next_run_time)

**Фаза 3 — миграция 8 оставшихся сервисов** (при подтверждении охвата (б)

- Для 7 minute-based сервисов подобрать `startup_delay_min` осмысленно

- Для `curator_report_cron_service` — startup_delay_min по аналогии с
  остальными часовыми (не меняет его внутренний недельный гейт).
- Добавить новые настройки `*_STARTUP_DELAY_MIN` в `app/core/config.py`

- Новый регрессионный тест на `next_run_time` для каждого из 8 (сейчас ни

- Exit criteria: 14/14 сервисов используют `register_interval_job`, 0

- Rollback: те же гарантии, что в фазе 2, файлы независимы друг от друга —
