# ADR-0007: Гибридная проверка — авто-сверка части ответа при обязательном ручном гейте

- **Статус:** Accepted
- **Дата:** 2026-08-08
- **Задача:** tsk-396 (заменяет обход tsk-395)
- **Контекст-связи:** tsk-230 (`manual_review_required`), tsk-210 (оптимистичный зачёт),
  tsk-227 (`requires_attachment`), tsk-247 (единый предикат очереди), tsk-546 (SA vs SA_COM)

## Контекст

Есть класс заданий, где часть ответа формализуема, а часть проверяется только человеком.
Канонический пример — ОГЭ-14 (курс 1179, 25 активных заданий): два числовых ответа
(формализуемы, эталон известен) плюс построение диаграммы в электронной таблице (только
глазами преподавателя).

Движок так не умел. `manual_review_required=true` перегружал ДВЕ независимые оси:

1. «авто-сверке нельзя доверять / сверять нечем» → не выносить вердикт;
2. «человек обязан подтвердить до зачёта» → держать зачёт.

Из-за склейки осей «числа проверяются сразу, но задание не принято без диаграммы» было
невыразимо: либо всё авто (`false`), либо всё вручную (`true`).

### Обнаруженный дефект (важнее исходной постановки)

Задача tsk-396 исходила из того, что при `manual_review_required=true` ученик НЕ получает
проходной балл до ручной оценки, и что это намеренная защита. **Живой прогон опроверг это.**

`checking_service._check_short_answer` действительно возвращает `is_correct=None, score=0`.
Но `attempts.py` 2.3d затем применяет оптимистичный зачёт:

```python
optimistic_manual = task_content.type == "TA" or (
    task_content.type in COMMENT_TASK_TYPES and check_result.is_correct is None
)
```

Условие опирается на `is_correct is None`, а этот признак у SA_COM/TBL_COM возникает по
ДВУМ разным причинам: «эталона нет» (замысел оптимистичного зачёта, о нём и говорит
комментарий в коде — «SA_COM без правил») и «эталон есть, но включён ручной гейт»
(tsk-230). Вторая причина в условие попала не по замыслу: строка 554 в
`_check_short_answer` короткозамыкает ДО чтения `short_answer`-правил.

Проба (`SA_COM`, `manual_review_required=true`, эталон `"12 516,30"`, ответ `"999 999"`):

```
task_state = state=PASSED, last_score=1/1, last_is_correct=True, last_checked_at=None
```

То есть заведомо неверный ответ засчитывался сразу, курс кредитовался до проверки
человеком, а преподавателю оставалась лишь возможность снять зачёт. Обход tsk-395 не
держал гейт, на который рассчитывал. Затронуто 45 активных заданий (25 ОГЭ-14 курса 1179
+ 20 «напиши программу целиком» в курсах 864–869, 1405–1415).

## Решение

**Развести две оси. Ввести отдельный флаг `solution_rules.partial_auto_check`,
дополняющий `manual_review_required`, и починить условие оптимистичного зачёта.**

### 1. Модель данных (вопрос 1 задачи)

Новый булев флаг, по умолчанию `false` — существующие задания не меняют поведение:

```json
{
  "max_score": 1,
  "manual_review_required": true,
  "partial_auto_check": true,
  "requires_attachment": true,
  "short_answer": { "accepted_answers": [{ "value": "12 516,30", "score": 1 }] }
}
```

Семантика `partial_auto_check=true`:

- авто-сверка `response.value` по эталону выполняется как обычно;
- ученик СРАЗУ видит её итог текстом (без раскрытия эталона);
- **зачёт не выдаётся**: `score=0` всегда до оценки преподавателем;
- при совпадении → `is_correct=None`, работа в обязательной очереди;
- при несовпадении → `is_correct=False`, в очередь НЕ попадает, ученик пересдаёт.

Валидатор требует `manual_review_required=true` и наличие эталона: без ручного гейта
флаг бессмыслен, без эталона — нечего сверять.

#### Отклонённые варианты

| Вариант | Почему отклонён |
|---|---|
| Структура подответов (числовой блок + ручной блок) | Ответ ученика — одно поле `value`; «ручная часть» — это ФАЙЛ, отдельная сущность, а не подответ. Потребовало бы нового парсера ответа, нового UI и миграции всех типов ради «числа + картинка». |
| Новый `scoring_mode` | `scoring_mode` отвечает за НАЧИСЛЕНИЕ баллов (`all_or_nothing`/`partial`/`custom`). Здесь вопрос не в баллах, а в том, кто выносит финальный вердикт. Смешение осей повторило бы исходную ошибку перегрузки `manual_review_required`. |
| Переопределить сам `manual_review_required` (авто-сверка всегда, гейт всегда) | Снял бы оптимистичный зачёт у 230 SA_COM-миссий без эталона и 152 TA — ученики флагмана встали бы в ожидание преподавателя. Регресс далеко за пределами tsk-396. |

### 2. Семантика зачёта (вопрос 2)

`compute_task_state` / `compute_course_state` гейтят по `score/max_score >= 0.5`. Поэтому
авто-часть НЕ трогает `score` — она живёт только в `feedback`. Пока преподаватель не
поставил балл, `score=0` → `state=FAILED`/`BLOCKED_LIMIT`, не `PASSED`; курс не
завершается. Это и было исходным замыслом tsk-230 — теперь он выполняется фактически, а
не только на уровне `CheckingService`.

Сопутствующая правка (корень найденного дефекта): условие оптимистичного зачёта
переводится с `is_correct is None` на признак «сверять нечем»
(`not solution_rules.has_reference_answer()`). Это ровно то, что описывает комментарий в
коде. Миссии без эталона сохраняют оптимистичный зачёт, задания с эталоном и ручным
гейтом перестают засчитываться вслепую.

### 3. Контракт фронта (вопрос 3)

`GET /learning/tasks/{id}/state` получает поле `partial_auto_check` — тем же способом, что
`requires_attachment` (tsk-227) и `has_reference_answer` (tsk-547): UX-сигнал, не гейт.
Сервер остаётся источником истины. Ученик видит авто-итог в `check_result.feedback.general`
и статус «ждёт преподавателя» (по `is_correct=None` + `checked_at=None`).

**Эталон не раскрывается:** `details.matched_short_answer` в гибридном режиме не
заполняется (tsk-460 — видимость полей отдельный слой; `CheckResult` эхо-возвращается
ученику, tsk-302).

### 4. Очередь преподавателя (вопрос 4)

Подсказка не требует новой колонки. Работы с несошедшимися числами в очередь не попадают,
значит **само присутствие работы в очереди при `partial_auto_check=true` означает «числа
сверены автоматически»**. Флаг задания отдаётся в элементе очереди, UI рендерит
«числа сошлись — проверьте только диаграмму».

`metrics` для этого не годится: это поле ручной проверки, `manual-check` его перезаписывает.
`code_review` занят отчётом детектора (tsk-302).

Единый предикат `mandatory_review_sql` (инвариант tsk-247 — одно определение на
claim-next, список и счётчик) расширяется вторым алиасом:

```sql
(t.task_content->>'type' = 'TA'
 OR (t.task_content->>'type' IN ('SA','SA_COM','TBL_COM')
     AND COALESCE((t.solution_rules->>'manual_review_required')::boolean, false) IS TRUE
     AND NOT (COALESCE((t.solution_rules->>'partial_auto_check')::boolean, false) IS TRUE
              AND tr.is_correct IS FALSE)))
```

Опора на `is_correct` ограничена гибридным режимом — вне него ось остаётся task-level,
как требует tsk-247.

### 5. Сдача диаграммы (вопрос 5) — решение оператора

Обязательный файл (.ods/.xlsx) через уже существующий `requires_attachment` (tsk-227) +
вложения по конкретному заданию (tsk-575). Нового слоя медиа-загрузки не требуется —
поправка к оценке объёма в задаче.

## Последствия

**Положительные:** мгновенная обратная связь по числам; курс больше не зачитывается до
ручной оценки; закрыт дефект ложного зачёта на 45 заданиях; оси «доверие авто-сверке» и
«нужен человек» разведены и переиспользуемы (ОГЭ-13, задания ЕГЭ с файлом-результатом).

**Отрицательные / риски:** ученик получает сигнал «числа сошлись» — при малом числе
вариантов ответа это канал подбора; сдерживается лимитом попыток и тем, что числа ОГЭ-14
считаются по файлу-таблице. Очередь преподавателя по ОГЭ-14 наполняется только работами с
верными числами — намеренно (решение оператора), но работы с неверными числами он больше
не увидит вовсе.

**Нейтральные:** флаг opt-in, задания без него не меняются.
