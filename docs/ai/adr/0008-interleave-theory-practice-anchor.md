# ADR-0008: Чередование теории и практики в узле курса — якорь задания к материалу

- **Статус:** принято (accepted) — решение оператора 2026-10-19: форма «якорь задания к материалу»
- **Дата:** 2026-10-19
- **Задача:** tsk-996 (П7 педагогического аудита `docs/qa/lms-pedagogy-audit-2026-09-17.md`)
- **Входные данные:** `docs/briefs/2026-10-19-p7-interleave-options.md`
- **Решение оператора 19.10:** вариант Б — «общая позиция без слияния сущностей» (не подкурсы, не материал-как-задание)

## Контекст (факты, сверено с кодом 19.10)

1. Движок строит обход шагами `(course_id, "materials"|"tasks")`: материалы узла → подразделы → задания
   узла (`learning_engine_service._walk_tree` ~1494–1533, кеш `("walk", root_id)`). Курсор продолжения —
   `_locate_item_course` ~1130–1182; в шаге позиции `material_ids = []` для задания (~1394–1396).
2. Тот же порядок «материалы → задания» собирается ещё в 5 местах: `me_service` syllabus-states
   (~1209–1340), `content_grace_service._walk_sequence` (~644–688), `preview_navigation._ordered_items`
   (~77–128), `manual_progress_service` (~1097–1147, ~1462–1472), `teacher_progress` (~104).
3. Порядок внутри типа: `materials.order_position` (триггеры сдвигов, уплотнение при удалении, UNIQUE нет);
   `tasks.order_position` (то же + `UNIQUE(course_id, order_position) DEFERRABLE`, tsk-813).
4. **Импорт пересортировывает задания по сложности:** `tasks_service.bulk_upsert` →
   `_reorder_tasks_by_difficulty` (~653–713) при каждой публикации, где задание без позиции или сменило
   сложность. CB `to_task_payloads` позицию заданий не передаёт.
5. Прозрачные подкурсы (tsk-1198): `tasks.host_order_position = место*100 + ранг`, «место» — значение
   `tasks.order_position` задания хозяина.
6. Не зависят от позиции внутри узла: выборка tsk-314 (`sorted(ids)`), `demo_task_limit`, ДЗ
   (`homework_items.position`), `course_position`, П3 (`due_at`), П5 (`sorted(ids)`), бот TG_LMS
   (next-item без `after_*`).
7. SPW порядок не строит: единственный источник — `syllabus-states` (tsk-684).

## Рассмотренные формы варианта Б

**Б1. Общая сквозная колонка `seq` у материалов и заданий** (одно число на узел для обоих типов).
Минусы: два набора триггеров должны поддерживать одну общую нумерацию через две таблицы (сдвиги,
уплотнение, переезд между курсами) — гонки и рассинхрон; при каждой публикации CB задания
пересортировываются по сложности (факт 4), и `seq` нужно пересчитывать заново, иначе порядок
разъезжается; прозрачные подкурсы привязаны к `tasks.order_position` — нужно переводить на `seq`.
Миграция: заполнить `seq` у всех ~1300 узлов.

**Б2. Якорь задания к материалу (выбрано).** Задание получает необязательную ссылку
`tasks.anchor_material_id` → материал того же узла. Порядок узла выводится, а не хранится:
материал 1 → задания с якорем на материал 1 → материал 2 → его задания → … → задания без якоря
(как сейчас, «после всех материалов»). Внутри группы задания идут по своему `order_position`.

## Решение

Принять **Б2 — якорь задания к материалу**.

Почему:
- **Без миграции данных.** Новая колонка `NULL` у всех заданий = ровно текущий порядок «все материалы,
  затем все задания». Эквивалентность прежней выдаче — по построению, а не по проверке пересчёта.
- **Устойчиво к пересортировке по сложности.** Импорт меняет `tasks.order_position`, но не якорь:
  задание остаётся после своего материала, внутри группы — порядок по сложности, как сейчас.
- **Не трогает существующие инварианты:** триггеры и UNIQUE `order_position`, reorder по типам,
  прозрачные подкурсы (`host_order_position` по-прежнему относительно `tasks.order_position`),
  гостевые/демо пути, ДЗ, П3, П5, выборка tsk-314.
- **Устойчиво к перестановке материалов:** якорь — id материала, а не номер; материал переставили —
  его задания едут вместе с ним.
- **Совместимо с публикатором:** CB знает, под каким H2-разделом стоит задание (блоки идут в исходном
  порядке) — ставит якорь на материал `#m{N}` этого раздела.

Ограничение (сознательное): задание нельзя поставить **перед первым материалом** узла. Педагогически
задание до теории в разделе — редкий случай (входная диагностика), он решается отдельным подкурсом.
Если понадобится — второй шаг: специальное значение «до всех материалов» без изменения модели.

## Модель данных

```
tasks.anchor_material_id  INTEGER NULL
    REFERENCES materials(id) ON DELETE SET NULL
tasks.anchor_source       VARCHAR(16) NULL   -- 'publish' | 'manual'
    -- инвариант: materials.course_id = tasks.course_id (проверка в сервисе + триггер-страж)
index ix_tasks_anchor_material (anchor_material_id) WHERE anchor_material_id IS NOT NULL
```

- **Удаление материала** → якорь NULL (задания уходят в конец узла, не теряются).
- **Переезд задания в другой курс** (tsk-802) → якорь обнуляется (материал другого узла недопустим).
- **Переезд материала** в другой курс → якоря заданий старого узла на него обнуляются.
- **Неактивный материал** (`is_active=false`) → его задания встают туда, где был бы материал
  (якорь не обнуляется: включили материал обратно — порядок восстановился).
- Рубильника нет: при всех якорях NULL поведение = сейчас; включение = методист/публикатор ставит якоря.

## Правило построения порядка узла (одно, общее)

`node_sequence(course_id) -> [(kind, id)]`:
1. материалы узла по `_order_key(order_position, id)`;
2. после каждого материала — задания с `anchor_material_id = этот материал`, по `task_key` (как сейчас);
3. затем подразделы узла (как сейчас);
4. затем задания без якоря (или с якорем на материал другого узла/несуществующий) по `task_key`,
   с прозрачными подкурсами как сейчас.

Одна функция в `learning_engine_service` (или отдельный модуль `node_sequence.py`), которую используют
**все 6 мест** из факта 1–2 вместо своих копий. Это заодно убирает дублирование обхода
(`must-centralize` — сейчас 5 копий одной логики).

## Изменения по слоям

| Слой | Что | Объём |
|---|---|---|
| БД | миграция: колонка + индекс + триггер-страж «тот же узел»; обнуление при переезде (в функцию tsk-802) | S |
| Движок | `_walk_tree` / шаги: шаг узла становится `(course_id, "node")` со смешанной последовательностью; курсор `_locate_item_course` сравнивает позицию в последовательности; ветка ~1356–1406 и `material_ids=[]` уходят | M |
| Копии обхода | `me_service` syllabus-states, `content_grace_service`, `preview_navigation`, `manual_progress_service`, `teacher_progress` → общая `node_sequence` | M |
| API | `PATCH /tasks/{id}` принимает `anchor_material_id` (валидация узла); выдача задания отдаёт поле; эндпоинт сортировки «узла» не нужен (reorder по типам + якорь) | S |
| SPW | порядок уже с сервера; методисту — в редакторе задания выбор «после материала…» (список материалов узла) | S |
| CB | `extract_lms_tasks` — номер H2-раздела задания; `to_task_payloads` — `anchor_external_uid` (`{base}#m{N}`), LMS резолвит в id при bulk-upsert; без раздела — NULL | S–M |
| Бот TG_LMS | не затронут (next-item без `after_*`) | — |

## План поставки (с откатом)

1. **Общая функция `node_sequence` при всех якорях NULL** + перевод 6 мест на неё. Exit: снимок выдачи
   (syllabus-states + цепочка next-item) по 30 реальным узлам до/после совпадает побайтно; полный pytest
   без новых падений. Откат: выкат предыдущей версии (схема не менялась).
2. **Миграция колонки + API якоря** (выкат без данных: все NULL). Exit: тесты инвариантов (удаление,
   переезд, неактивный материал). Откат: `downgrade` удаляет колонку (данных в ней ещё нет).
3. **Публикатор CB ставит якоря** по H2 — только при переиздании курса и только если в уроке задания
   стоят между разделами. Exit: dry-run на 3 курсах, сравнение порядка с исходником урока. Откат:
   переиздание без якорей (флаг публикатора) или `UPDATE tasks SET anchor_material_id = NULL WHERE course_id = …`.
4. **Пилот на одном курсе** (выбор оператора) + замер в рамках tsk-1372.

## Риски

| Риск | Мера | Основание |
|---|---|---|
| Курсор next-item «перескакивает» или зацикливается на смешанной последовательности | Тест цепочки next-item по всему узлу (каждый элемент ровно один раз) для узлов с якорями, без якорей и с прозрачными подкурсами | факт 1, проверено по коду |
| Grace (tsk-1261) и обязательность (tsk-1361) считаются по позиции в обходе | Перевести `_walk_sequence` на `node_sequence` в шаге 1, снимок до/после | факт 2, проверено по коду |
| Выборка tsk-314 исключает задание из обхода — его якорная «группа» пустеет | Пустая группа просто не даёт шагов; тест | факт 6, проверено по коду |
| Якорь на материал другого узла (ручная правка БД, переезд) | Триггер-страж + обнуление при переезде + в `node_sequence` такой якорь = NULL | предположение (нужен тест) |
| Счётчики «N из M» и прогресс | Не меняются: множества материалов/заданий те же, меняется только порядок | факт 2, проверено |
| Пилоты П3/П5/П9 | Не зависят от позиции | факт 6, проверено |

## Владение якорем: публикатор или методист

- Якорь, поставленный **методистом в LMS**, помечается источником (`tasks.anchor_source = 'manual'`);
  поставленный публикатором — `'publish'`.
- Повторная публикация из CB **перезаписывает только якоря с источником `publish` или пустые**;
  ручной якорь сохраняется. Если публикатор не прислал якорь — существующий не трогается
  (отсутствие поля ≠ «обнулить»; обнуление — явным значением).
- Тест: переиздание курса после ручной перестановки методистом не меняет порядок узла.

## Переключатель на время перехода

Шаг 1 плана (общая `node_sequence` вместо 6 копий) выкатывается за настройкой
`NODE_SEQUENCE_ENABLED` (env, по умолчанию `true` после сверки снимков; старый обход остаётся в коде
до конца шага 3). Откат шага 1 — `false` + рестарт, без выката. Старый путь удаляется отдельным
коммитом после пилота.

## Второе мнение (Codex, 2026-10-19, ADR-0006)

- Прогон 1 оценил входной документ вместо выбора варианта (отзыв: 1 подтверждена, 2 отклонены).
- Прогон 2 (`reviews/codex-p7-interleave-decision-20261019-155851.json`, уверенность низкая — код в его
  песочнице был недоступен): выбран **вариант Б**, но в форме **отдельной таблицы общего порядка**
  `course_content_order(course_id, item_type, item_id, position)`.
- **Сведение:** вариант Б — согласие. Форма: оставлен **якорь (Б2)**, а не таблица — по фактам кода,
  которых Codex не видел: (а) импорт пересортировывает задания по сложности при каждой публикации
  (`tasks_service._reorder_tasks_by_difficulty`) — таблицу пришлось бы пересобирать, якорь это переживает;
  (б) таблица требует заполнения для всех ~1300 узлов и транзакционной поддержки двух типов, якорь —
  нет. Риск Codex «повторный импорт сбросит ручное чередование» — принят и закрыт разделом
  «Владение якорем». Его предложения о переключателе старого обхода и сравнении выдачи до/после
  — приняты (разделы выше и шаг 1 плана).
- Реального спора нет: Codex выбирал вслепую по коду; решение формы — за оператором.

## Дополнение 2026-10-20: якорь задания банка на материал прозрачного хозяина (фаза D)

Пилот 20.10 (курс ОГЭ): задания уроков ОГЭ живут в курсах-банках (6308 в 1948
«lms:tsk1161:bank:oge1»), подвешенных к узлу урока (1111 «wp:oge-z1») прозрачной связью
(tsk-1198) — ученик видит их внутри урока. Инвариант «материал того же курса» не давал
поставить им якорь (422 на материал 2358).

- **Правило якоря:** материал курса задания **или** курса P, если есть
  `course_parents(course_id = курс задания, parent_course_id = P, is_transparent)`. Одно правило в
  трёх местах: триггер `trg_tasks_anchor_guard` (миграция `tsk996_bank_anchor`),
  `TasksService.anchor_course_ids` (PATCH, `GET /tasks/{id}/anchor-materials`, bulk-upsert),
  `node_sequence.anchor_of` (порядок).
- **Порядок:** в списке хозяина такое задание встаёт в голову сразу после материала, в одной группе
  с заданиями хозяина с тем же якорем; внутри группы — `task_key` (тот же ключ, которым банк и
  хозяин сливаются в хвосте, `host_order_position` против `order_position`). Без якоря — хвост, как
  раньше. В банке как разделе практикума (второй родитель без прозрачности) якорь на материал
  хозяина не действует — порядок практикума не меняется. Якорь задания банка на материал **самого
  банка** в списке хозяина по-прежнему не действует (tsk-1198).
- **Отвязка:** снятие прозрачности, удаление связи, перенос родителя (`set_parent_courses` делает
  его UPDATE-ом) — триггер `trg_course_parents_anchor_on_unlink` обнуляет якоря заданий подкурса на
  материалы бывшего хозяина (с источником). Триггер, а не сервис: связь правят несколько путей
  (репозиторий, персональные курсы, скрипт tsk-1198, ручной SQL, каскад удаления курса).
- **Правило «ушёл вперёд»** обходит прозрачные подкурсы разделами (как и прежде), но задание банка
  с якорем на материал хозяина ставит в голову хозяина — туда, где его видит ученик.
- Задания HARD, уходящие публикацией в подкурс сложных (tsk-347), якорь по-прежнему не получают.

## Явно НЕ вводим

- Общую сквозную нумерацию материалов и заданий (Б1) и слияние сущностей (В).
- Новый эндпоинт «сортировка узла целиком» — хватает reorder по типам и якоря.
- Рубильник: без якорей поведение не меняется.

## Последствия

- Методист и публикатор получают чередование одним полем; программа курса не дробится.
- Логика обхода узла сводится в одну функцию вместо пяти копий — дешевле следующие правки движка.
- Если позже понадобится полностью произвольный порядок (включая задание до первого материала) —
  новый ADR, superseding этот, на базе той же `node_sequence`.
