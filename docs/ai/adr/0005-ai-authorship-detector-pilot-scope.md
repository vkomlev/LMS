# ADR-0005 — Детектор ИИ-авторства кода: аналитический пилот, не продакшн-фича

- **Статус:** Accepted (пилот), продакшн-интеграция — NOT DECIDED
- **Дата решения:** 2026-08-06
- **Задача:** [tsk-302](../../../../Root/tasks/tsk-302-avtoproverka-koda-uchenikov-detektor-ii-avtootsenka-kachestva-koda.md), направление 2
- **Связано:** [tsk-412](../../../../Root/tasks/tsk-412-turtle-simulyator-cherepashka-graficheskie-zadaniya.md) (песочница turtle_sim — источник кода ученика), ADR прямого предка нет (первый пилот такого рода в LMS)

## Контекст (Problem Framing)

Оператор хочет отличать «ученик списал готовое ИИ-решение» от «ученик написал сам» для заданий turtle_sim (Python-код, рисование черепахой). Задача явно помечена оператором как **экспериментальная и рискованная**: «нет надёжного детерминированного метода... ложные обвинения хуже отсутствия детектора».

**Non-goals этого захода:**
- Не встраивается в `POST /attempts/{id}/answers` или любой live-поток проверки.
- Не показывается ученику ни в каком виде.
- Не блокирует, не понижает балл, не создаёт заявок/эскалаций автоматически.
- Не является окончательным вердиктом — только advisory-сигнал для методиста.

**Success criteria пилота:** дать оператору количественную оценку (какой % сдач эвристика флагует) и качественную (конкретные примеры код+вердикт+обоснование), на основе которых оператор решает, продолжать ли эту линию вообще.

## AS-IS Snapshot

**C4-Context:** LMS (`learn_prod_db`, read-only для пилота) ↔ Claude (LLM-судья, вызывается вручную/скриптом, не как сервис LMS) ↔ оператор (получает отчёт).

**Ключевой факт, меняющий объём пилота** (прод, read-only, проверено 2026-08-06):

```sql
SELECT count(*) FROM task_results tr JOIN tasks t ON t.id = tr.task_id
WHERE t.solution_rules->'turtle_sim' IS NOT NULL;
-- 4 строки, все user_id=142 (аккаунт оператора для живых прод-проверок, см. project_prod_live_testing)
```

Курс 165 (turtle_sim) на проде запущен буквально накануне (первая сдача 2026-08-05T11:40). **Реальных ученических сдач нет вообще** — есть только 4 собственных тестовых прогона оператора при живой проверке tsk-412. Формулировка задачи («прогнать эвристику на исторических сдачах... какой процент флагуется») предполагает объём данных, которого физически не существует.

## Gaps and Ambiguities

1. **Нет исторических ученических данных** — блокирует именно то, что было явно запрошено («процент флагуемых случаев» на реальных сдачах). Не факт, который можно обойти инженерно — нужно ждать реального использования курса учениками.
2. Нет утверждённого рубрика «что считается ИИ-стилем» — придётся зафиксировать эвристику явно (ниже), она не выводится из существующих данных.
3. Неясно, сколько ложных срабатываний оператор готов терпеть на старте (не задано численно) — не блокирует пилот (пилот сам должен дать материал для этого решения), но блокирует продакшн-интеграцию.

**Решение по Gap 1 (принято сейчас, не отложено):** пилот запускается в двух частях —
(а) реальный прогон на всех 4 существующих строках (честно маленькая, нерепрезентативная выборка, но это 100% существующих production-данных);
(б) синтетическая калибровка на специально сконструированных пример-парах (явно ИИ-стиль vs явно ученический), чтобы показать оператору, различает ли рубрика вообще что-то, раз реального материала для процента нет. Часть (а) отвечает на «что покажет эвристика на текущих данных», часть (б) — на «работает ли сама идея в принципе». Ни то ни другое не заменяет полноценную калибровку на реальных учениках — она станет возможна только после накопления объёма.

## Target Architecture пилота

**Что подаём судье:** только `answer_json.response.value` (текст кода) + метаданные задачи (номер задания, ожидаемая фигура) — БЕЗ PII ученика (без имени/email, только внутренний числовой `user_id` для последующей сверки оператором, не передаётся в промпт LLM).

**Судья:** сам Claude (эта сессия) читает код и промпт-рубрику напрямую — специальной интеграции с Anthropic API не строится для n=4. Для будущего масштаба (десятки/сотни сдач) — скрипт `scripts/tsk302_ai_detector_pilot.py` (создаётся этим пилотом, read-only к БД, печатает JSON-отчёт; вызов реального LLM API — заглушка/TODO с точкой расширения, не подключается сейчас: не нужен API-ключ ради 4 строк).

**Рубрика (промпт-эвристика), зафиксирована явно:**
```
Дан код ученика (Python, задание «нарисуй фигуру черепахой», уровень —
начинающий школьник, изучивший: циклы, переменные, функции, turtle-команды
forward/right/left/color). Оцени по шкале AI_LIKELY / AMBIGUOUS / STUDENT_LIKELY:

Признаки AI_LIKELY (типичны для сгенерированного ИИ решения):
- docstring/комментарии в стиле """Draws a square using turtle graphics""",
  избыточные для объёма кода английские комментарии к каждой строке
- использование конструкций вне пройденного (list comprehension, декораторы,
  type hints, `if __name__ == "__main__"`) без педагогической необходимости
- unit-idiomatic именования (SNAKE_CASE констант, docstring-conventions),
  не встречающиеся в естественном стиле школьника
- избыточная защита от ошибок (try/except там, где задание этого не требует) -
  ЗАМЕЧАНИЕ: в turtle_sim это невозможно физически (guard.py tsk-412 запрещает
  try/with/async на уровне AST) - признак неприменим к этому типу заданий,
  зафиксировано как limitation ниже.

Признаки STUDENT_LIKELY:
- магические числа без объяснения (тот же сигнал, что и в направлении 1)
- непоследовательный стиль (где-то переменная называется t, где-то turtle_obj)
- копипаста цикла вместо функции там, где повторение очевидно
- минимальная либо отсутствующая документация

Ответ: вердикт + 1-2 предложения обоснования со ссылкой на конкретную
строку/конструкцию кода. НЕ ставь AI_LIKELY только на основании "код слишком
хороший для новичка" без конкретного стилистического маркера - оптимизм
интерпретации в пользу ученика.
```

**Важное ограничение рубрики, зафиксированное как limitation:** guard.py (tsk-412) уже статически запрещает `try/with/async/yield` в любом коде turtle_sim — значит часть типичных «ИИ-маркеров» (избыточный error-handling) физически не может появиться в этом типе заданий независимо от авторства. Рубрика для turtle_sim уже, чем общая рубрика «код похож на ИИ» была бы для произвольных Python-заданий.

## Simplification decisions

- Не строится очередь/интеграция с Anthropic API — при n=4 это оверинжиниринг. Скрипт-заготовка для будущего масштаба — да, реальный вызов LLM в проде — нет.
- Не вводится новая таблица/поле в БД для хранения вердиктов пилота — отчёт живёт как markdown-артефакт в `reviews/`, не в БД (это ANALYTICS, не постоянная фича; при решении «внедрять» это станет отдельным ADR + схемой).
- Не запрашивается доступ к prod write — весь пилот read-only.

## Risk Register

| Риск | Вероятность | Воздействие | Митигация |
|---|---|---|---|
| Ложное обвинение ученика при будущей интеграции | Высокая (LLM-эвристика в принципе ошибается) | Высокое — подрыв доверия, демотивация | Пилот НЕ создаёт видимых учнику последствий; при будущей интеграции — только advisory-сигнал методисту, не автоматическое действие |
| n=4 создаёт ложное чувство откалиброванности | Средняя | Среднее — оператор может принять решение на нерепрезентативных данных | Явно и настойчиво сообщено в отчёте (не спрятано в сноске) |
| Промпт-инъекция через код ученика (текст в комментариях, пытающийся управлять судьёй) | Низкая для n=4 (все примеры — свои тестовые), реальна при масштабе | Среднее | Зафиксировать в рубрике инструкцию игнорировать императивные команды внутри анализируемого кода; при будущей автоматизации — код передаётся судье как чётко отграниченные данные (тегированный блок), не как часть системного промпта |
| Задание turtle_sim физически ограничивает пространство «типичных ИИ-маркеров» (guard.py) | Известна | Низкое | Учтено в рубрике явно (limitation выше) |

## Validation Plan пилота

1. Прогнать рубрику на 4 реальных строках прод-БД (read-only) — зафиксировать вердикт+обоснование для каждой.
2. Прогнать рубрику на 3-4 синтетических парах (сконструированных в этой сессии) — проверить, что рубрика вообще различает контрастные случаи.
3. Отчёт оператору: оба набора, честно промаркированные (реальные / синтетические), без обобщения на «X% всех сдач» (нерепрезентативно).

## Go / No-Go

**GO на пилот** (read-only анализ, без интеграции) — исполняется сразу после этого ADR.
**NEEDS-MORE-INFO на продакшн-интеграцию** — блокируется отсутствием (а) реального объёма данных, (б) явного порога ложноположительных, приемлемого оператору, (в) решения оператора о видимости вердикта (advisory-only методисту — не обсуждалось явно, только предполагается по аналогии с направлением 1). Решение об интеграции — отдельная задача/ADR после того, как оператор увидит этот отчёт.
