# Спецификация: кабинет маркетолога (tsk-505) + мини-CRM лидов (tsk-506)

- **Дата:** 2026-08-01
- **Задачи трекера:** `tsk-505` (P1, блокер `tsk-010`), `tsk-506` (P2, зависит от tsk-505)
- **Проекты:** LMS (backend), SPW (frontend)
- **Статус:** COMPLETE (обе развилки закрыты решениями оператора, см. «Контекстные якоря»)

---

## Цель

Дать оператору в роли `marketer` отдельный кабинет, где ведётся справочник тарифов на курсы,
видна расчётная цена каждого ученика и ведётся простой учёт лидов до их регистрации.

## Находки живой разведки прода (основание модели)

1. **Календарь не знает о курсах.** Ни `lesson_slot`, ни `lesson_occurrence` не имеют
   `course_id`. Слот = преподаватель + день недели + время + список учеников
   (`lesson_slot_student`). Поэтому «частота по курсу» технически невыводима — выводится
   только «частота ученика» (сколько раз в неделю он занимается вообще). Это и есть причина,
   по которой цена привязана к ученику (Я2).
2. **Распределение частот** (34 ученика с активным расписанием): 13 → 1 занятие/нед,
   20 → 2, 1 → 3.
3. **24 ученика из 34** зачислены сразу на пару «Python для ЕГЭ» (id=88) +
   «ЕГЭ по информатике» (id=112) — это один продукт, а не два.
4. **Цен в БД нет вообще.** Ни таблицы, ни поля, ни enum: `price|tariff|payment|subscription`
   по `app/**` и по всем миграциям — ноль совпадений. Чистое поле.
5. Все 7 продаваемых курсов — корневые (ни одной строки в `course_parents` как `course_id`).
6. Ни у одного ученика нет одновременно курсов группы А и группы Б — правило склейки
   разрешается на текущих данных однозначно.

## Границы

### Входит

- Назначение роли `marketer` пользователю id=2.
- Справочник тарифных групп и вариантов тарифа; привязка курса к группе; явный статус
  продаваемости курса.
- Резолвер частоты ученика по календарю и расчёт его цены.
- Роут-группа SPW `app/(marketer)/marketer/*`: цены (список + редактирование),
  ученики с расчётной ценой (просмотр), лиды (CRUD + привязка).
- Модель `leads` + справочник каналов, CRUD под ролью `marketer`.
- Место в навигации под будущую очередь платежей — **как пункт архитектуры, без пустого экрана**.

### Не входит (явно)

- **Система оплат (tsk-010)**: платёжный шлюз, вебхуки, идемпотентность, чеки, юр. аспекты —
  отдельная сессия (Я9).
- Сущность «подписка ученика» (какой тариф реально оплачен) — появится в tsk-010.
- Правка календаря (добавление курса в слот) — рассмотрено и отклонено оператором.
- История изменения цен, аналитика конверсии, воронка лидов по стадиям.
- Расширение `_PEOPLE_READ_GATE` — маркетолог НЕ получает общий доступ к карточкам людей.

## Ограничения

1. **Гейт персональных данных.** `GET /api/v1/users/search` и `GET /api/v1/users/` закрыты
   `require_role("methodist","admin")` и используются ботами по legacy-ключу. Расширять их
   на `marketer` нельзя — нужен отдельный узкий эндпоинт с урезанной схемой ответа
   (прецедент `/roles/catalog`).
2. **`require_role` пропускает сервисный токен без проверки роли** — для новых эндпоинтов
   учесть осознанно.
3. **Alembic head** на момент старта: `tsk498_parent_access_links`. Ревизии именуются
   `tskNNN_slug`, не хешем.
4. **Порядок маршрутов**: литеральные пути объявлять до параметрических; свои хендлеры —
   до `include_router(crud_router)` (иначе generic-CRUD перекроет и уведёт на legacy `?api_key=`).
5. **SPW**: типы только из автогена `pnpm gen:api-types`; DESIGN.md обязателен
   (токены цвета, `StatusBadge`, `lib/format-date.ts`, `isPending` вместо `isLoading`,
   все четыре состояния экрана).
6. Деньги хранить целым числом в копейках — никакого `float`.
7. Cross-project: новые эндпоинты + миграция → обновить `contracts/lms-api.md`,
   `contracts/lms-db-schema.md`, `CHANGELOG.md`, `STATE.md` в ContentBackbone.

## Модель данных

### Тарифы (tsk-505)

```
pricing_group           — тарифная группа («Базовый», «ИИ-предприниматель»)
  id, name (uniq), description, is_active, created_at, updated_at

pricing_tariff          — вариант тарифа внутри группы
  id, group_id FK→pricing_group
  name                  — «2 раза в неделю», «для своих»
  price_minor int       — копейки
  currency              — 'RUB'
  period                — 'month'
  match_kind  text NULL — 'attendance_frequency' | 'segment' | NULL
  match_value text NULL — '1' | '2' | 'insider' | 'street'
  is_default bool, sort_order, is_active, created_at, updated_at

course_pricing          — 1:1 с курсом, статус продаваемости
  course_id PK FK→courses
  sale_status           — 'paid' | 'free' | 'not_for_sale'
  group_id FK→pricing_group NULL   (обязателен при sale_status='paid')
  note, updated_at, updated_by FK→users
```

Гибкость (Я7) держится на паре `match_kind` / `match_value`: новая ось тарификации —
это новое значение `match_kind`, а не миграция схемы.

Отсутствие строки в `course_pricing` = «цена не назначена». Явное `not_for_sale` — это
осознанное «не продаётся», отличимое от `free`.

### Расчёт цены ученика (Я1 + Я2)

1. `frequency(student)` = число активных строк `lesson_slot_student` с активным `lesson_slot`.
2. Множество активных курсов ученика (`user_courses.is_active`) со `sale_status='paid'`
   → множество **различных** `pricing_group`.
3. Для каждой группы выбирается один вариант тарифа:
   - точное совпадение `match_kind='attendance_frequency'` и `match_value = frequency`;
   - иначе — наибольший `match_value ≤ frequency` (ученик с 3 занятиями попадает на тариф
     «2 раза», и это показывается явной пометкой, а не молча);
   - если у группы варианты по `segment` — авто-выбор невозможен, отдаётся статус
     `needs_choice` со списком вариантов (заготовка под tsk-010, не догадка);
   - если частота 0 (нет расписания) — статус `no_schedule`, цена не считается.
4. Итог ученика = сумма по различным группам. Пара ЕГЭ = одна группа = 5500 один раз.

### Лиды (tsk-506)

```
lead_source             — справочник каналов, seed в миграции
  id, code (uniq), name, is_active, sort_order

leads
  id
  source_id FK→lead_source
  source_detail text NULL   — приписка, обязательна при code='other' (Я4)
  full_name text NULL
  contact text              — ссылка/ник/телефон, без строгой валидации формата
  note text NULL
  linked_student_id FK→users NULL   — привязка после регистрации (Я6)
  created_by FK→users, created_at, updated_at
```

Seed каналов: `avito`, `yandex_direct`, `telegram`, `vk`, `referral`, `website`, `other`.

## API

| Метод и путь | Гейт | Назначение |
|---|---|---|
| `GET /api/v1/marketer/pricing/courses` | marketer, admin | корневые курсы + их статус продаваемости, группа, варианты тарифа |
| `PUT /api/v1/marketer/pricing/courses/{course_id}` | marketer, admin | назначить курсу статус и группу |
| `GET /api/v1/marketer/pricing/groups` | marketer, admin | группы с вариантами |
| `POST/PATCH/DELETE /api/v1/marketer/pricing/groups[/{id}]` | marketer, admin | CRUD групп |
| `POST/PATCH/DELETE /api/v1/marketer/pricing/tariffs[/{id}]` | marketer, admin | CRUD вариантов |
| `GET /api/v1/marketer/students/pricing` | marketer, admin | ученики: курсы, частота, применённый тариф, цена, статус расчёта (узкая схема, без email) |
| `GET /api/v1/marketer/students/search?q=` | marketer, admin | узкий поиск учеников для привязки лида (id + имя, без ПДн) |
| `GET/POST/PATCH/DELETE /api/v1/marketer/leads[/{id}]` | marketer, admin | CRUD лидов, фильтр `linked=true\|false` |
| `POST /api/v1/marketer/leads/{id}/link` · `DELETE .../link` | marketer, admin | привязка/отвязка ученика |
| `GET /api/v1/marketer/lead-sources` | marketer, admin | справочник каналов |

## Критерии готовности

1. `SELECT` на проде показывает у пользователя id=2 роль `marketer` рядом с прежними ролями,
   прежние роли не потеряны.
2. `alembic upgrade head` → `downgrade -1` → `upgrade head` на dev проходит без ошибок.
3. Все 7 продаваемых курсов имеют `sale_status='paid'` и привязку к группе; остальные курсы
   в списке отображаются как «не продаётся» (не пустым полем и не нулём).
4. `GET /marketer/students/pricing` на проде: ученик с парой ЕГЭ и 2 слотами → 5500;
   ученик с парой ЕГЭ и 1 слотом → 2750; ученик «Трек 1» → статус `needs_choice`
   с двумя вариантами (10000 / 20000).
5. `GET /marketer/*` под ролями `teacher`, `student`, `methodist`(без admin) и без роли → 403.
6. `GET /api/v1/users/search` остаётся под прежним гейтом — маркетолог получает 403.
7. Лид создаётся с каналом из справочника; при канале «другое» пустая приписка отклоняется;
   привязка к ученику проставляет `linked_student_id`, фильтр «не привязан» его больше не
   показывает; повторная привязка идемпотентна.
8. `pytest` новых тестов LMS — зелёный; `pnpm type-check`, `pnpm lint`, `pnpm test` в SPW — зелёные.
9. `grep -rn "toLocaleDate\|toLocaleString\|toLocaleTime" components/ app/` в SPW → 0.
10. Живая проверка на проде под ролью marketer: цена меняется и сохраняется, экран учеников
    показывает новую цену, лид создаётся и привязывается — **со скриншотами, глазами**.
11. `git status` в LMS, SPW, Root показывает синхронизацию с origin.

## Риски

| Риск | Мера |
|---|---|
| Резолвер частоты молча даёт неверную цену | Каждая строка экрана учеников показывает частоту, выбранный вариант и статус расчёта; расхождение видно глазами до того, как на модель сядут деньги |
| Ученик с 3 слотами получает тариф «2 раза» как догадку | Статус расчёта помечает применение ближайшего меньшего тарифа явной пометкой, а не выдаёт за точное совпадение |
| Расширение гейта поиска людей отдаёт маркетологу ПДн | Отдельный узкий эндпоинт `marketer/students/search` (id + имя), общий `/users/search` не трогаем; критерий готовности 6 это проверяет |
