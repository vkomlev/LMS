## 1. Что уже есть в LMS backend под роль `methodist`

- **Один выделенный эндпоинт:** `GET /api/v1/methodist/escalations/pending` — персональный notification-инбокс методиста (`kind IN ('review_escalated','course_pending_review')`), читает из общей таблицы `notifications`. Больше ничего под префиксом `/methodist` нет ни в коде, ни в `docs/openapi.json`.
- **`methodist_notify_service.py`** — генерирует эти уведомления ВСЕМ методистам разом по двум триггерам (таймаут ручной проверки; ученик завершил курс с pending TA/SA_COM). Нет «своей» очереди/claim — кто фактически возьмёт работу в проверку, решается через общий `teacher_reviews.py`.
- **Роль `methodist` = глобальный ACL-bypass**, а не scoped-доступ (в отличие от teacher, у которого доступ через `teacher_course_acl`/`student_teacher_links`). Bypass пронизывает почти весь teacher-контракт: `teacher_activity_feed`, `teacher_assignments`, `teacher_task_search`, `teacher_task_history`, `teacher_progress` (включая мутации — зачесть/снять зачёт), `teacher_reviews` (claim/grade/regrade — reviews И help-requests), `task_results_extra` (чужая статистика/детали), `tasks_extra`, `attempts` (вложения), `me.py` (`course-state`), `teacher_learning` (снятие лимита попыток), `messages_extra` (сообщения любому). Список файл:строка — в отчёте разведки, войдёт в `/change-plan-architect`.
- **Чего нет вообще:** workflow модерации/публикации курса (нет полей статуса в модели `courses`); процесс калибровки сложности (есть только статический справочник `difficulty_levels`, без methodist-специфичной логики пересмотра); отдельная «моя очередь» методиста, отделённая от teacher; scoped-реестр «методист → курсы/преподаватели». `GET /task-results/by-pending-review` — легаси-эндпоинт без auth-гейта, не пригоден как есть.

**Вывод:** backend для «операционного» слоя (эскалации, ревью/regrade, help-requests, activity-feed, статистика, сообщения, прогресс) — готов **сегодня**, через тот же teacher-контракт с methodist bypass. Backend для «авторского» слоя (CRUD курсов/материалов/заданий, управление карточками студентов/преподавателей) — **generic CRUD без methodist-специфичного контракта**, не оформлен как часть «методист-портала».

## 2. Что умеет методист через ТГ-бота (функционально, без UI)

Бот (`bots/methodist/*`, TG_LMS) даёт СУЩЕСТВЕННО больше операционного слоя:

- **Просмотр:** эскалации (=дублирует п.1 эндпоинт), очередь ручной проверки (обязательная/опциональная), заявки студентов (help requests), список/карточки студентов и преподавателей (с их курсами), дерево курсов + карточка + зависимости + пользователи курса, материалы курса, задания курса + предпросмотр «глазами ученика», статистика (по курсу/заданию/пользователю), внутренние сообщения.
- **Действия — операционные (= тот же teacher-контракт, что и п.1):** grade/regrade работы, claim/release, ответ на help-request, увеличение лимита попыток, отправка сообщений.
- **Действия — авторские (НЕТ отдельного methodist-эндпоинта, generic CRUD):** полное создание/редактирование/удаление курсов (включая дерево, зависимости, импорт из Sheets), материалов (включая перенос/копирование между курсами) и заданий; редактирование карточек студентов/преподавателей (имя/email, привязка курсов, привязка друг к другу).

**Единственное буквальное дублирование бот↔LMS-methodist-эндпоинт** — список эскалаций (п.1). Остальной операционный функционал бота идёт через общий teacher-контракт (методист там допущен ACL). Авторский CRUD-функционал бота — это отдельный и заметно больший пласт работы, не имеющий сегодня отдельного «methodist portal»-оформления в backend.

**Скилл `/methodist`** (проектирование учебных планов/заданий, LMS-импорт через Google Sheets/JSON, коврверждение сложности через Bloom+coverage-review) закрывает **офлайн-авторинг силами оператора+AI**, не через веб-UI методиста — это не то же самое, что «методист руками правит курс в браузере», но подтверждает, что предметная область авторинга (создание/калибровка курсов) — часть компетенции методиста, просто сегодня реализована другим каналом (Claude-скилл → JSON/Sheets → bulk-import), а не CRUD-экранами.

## 3. SPW: готовый паттерн (teacher-портал, tsk-298)

- Role-guard **уже generic**: `hasRole(me, "methodist")` сработает без правок (`lib/server/get-me.ts`), при условии что `/api/v1/me` отдаёт `"methodist"` в `roles[]` (уже отдаёт — общий для всех ролей код).
- Структура: `app/(teacher)/layout.tsx` — серверный guard + shell; страницы — тонкие server components, один client-компонент на экран, хуки в `lib/<домен>/use-*.ts` поверх `useApiClient()` + `@tanstack/react-query`, типы — codegen из OpenAPI (`lib/api-types.ts`).
- `app/(admin)/*` (tsk-432) — **не существует**, проектировать methodist-портал придётся так же с нуля по этому паттерну (не «скопировать готовое», а «повторить структурный паттерн»).
- **Известный техдолг teacher-портала, НЕ копировать:** нет общего `StatusBadge`/`DataTable` в `components/ui` — каждый экран форматирует даты/статусы по-своему → 5 форматов дат/5 визуальных языков бейджей (аудит tsk-422/451). Для methodist-кабинета — закладывать общие компоненты сразу, это и есть смысл «пройти цикл сразу, не задним числом» из постановки задачи.

## 4. Развилки, требующие решения оператора (не додумывать)

1. **Объём Фазы 1** — операционный слой (эскалации/ревью/help-requests/лента/сообщения/статистика — прямой аналог teacher-портала, backend готов сегодня) vs операционный + авторский CRUD (курсы/материалы/задания/карточки студентов-преподавателей — то, что умеет бот, backend для этого не оформлен под methodist-портал, объём в разы больше).
2. **Судьба ТГ-бота методиста** после релиза веб-кабинета — параллельный канал (как решено для teacher: бот = пуши/мобильный, веб = богатый интерактив) vs полная замена vs частичная замена (что именно остаётся в боте).

**Решения оператора (2026-07-29, `AskUserQuestion`):**

1. **Объём Фазы 1 — операционный + авторский CRUD.** Веб-кабинет методиста должен дать функциональный паритет с ТГ-ботом: и проверка/эскалации/заявки/сообщения, и полное управление курсами, материалами, заданиями, карточками студентов и преподавателей.
2. **ТГ-бот — параллельный канал.** Бот не выводится из эксплуатации: пуши и мобильный доступ остаются за ним, веб даёт богатый интерактив поверх тех же данных (то же решение, что принято для teacher-портала в tsk-298).

Следствие: рамка «ещё один кабинет по образцу teacher» узка — методист получает фактически контент-админку LMS. Поэтому цепочка идёт через `/ceo-review` (рамка) и `/architect-system-analyst` (границы контракта, TO-BE, ADR), а не сразу в дизайн.
