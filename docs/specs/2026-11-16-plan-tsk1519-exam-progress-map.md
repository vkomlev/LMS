## 1. Problem Framing

**Objective.** Автоматизировать ручной цикл финальной подготовки: ученик проходит фиксированный вариант, исправляет ошибки, видит динамику по номерам КИМ; преподаватель видит, каким заданиям не хватает видеоразбора.

**Scope.** Новый поддомен `exam_progress` в модульном монолите LMS; ученический экран и экран преподавателя в SPW; описание варианта и шкалы в публикуемом контенте CB. Существующие проверка ответов, `tasks`, `attempts`, `task_results`, `hints_video`, ACL и уведомления переиспользуются.

**Non-goals v1:** Telegram-интерфейс; генерация вариантов; ручная проверка развёрнутых ответов; новый интерактивный движок tsk-1247; конструктор шкал в UI; автоматическое создание видео; пересчёт уже завершённых вариантов после смены КИМ или эталона.

**Success criteria:**
1. Один и тот же вариант можно продолжить после перезахода без потери ответов и активного времени.
2. Первый ответ фиксируется неизменяемо; РНО не меняет первичный балл и не тратит обычный лимит попыток.
3. Верный ответ в РНО нельзя завершить без выбранной причины исходной ошибки.
4. Таблица однозначно восстанавливается из сохранённых данных: green/yellow/red/orange, дата старта, время, первичный и итоговый балл.
5. Красная ячейка без видео появляется в рабочем списке преподавателя; после добавления `hints_video` исчезает из него без ручной синхронизации.
6. Новый вариант открывается по правилу завершения РНО, а отложенные красные доступны для отработки позже.

## 3. AS-IS Snapshot

### C4-Context

- Ученик работает в SPW, LMS принимает ответы и хранит учебную историю.
- Преподаватель/методист работает в SPW, LMS применяет ACL и формирует рабочие списки.
- CB публикует курсы/задания в LMS через API; источник контента — не ручные записи в БД.
- Видео размещены вне LMS; LMS хранит URL в `task_content.hints_video`.

### C4-Container

`SPW Next.js → LMS FastAPI → PostgreSQL`; CB → LMS publish API; браузер → внешний video host. Отдельный сервис, очередь и новая БД не нужны.

### Существующие возможности

- `final_check` доказывает рабочий шаблон изолированной диагностики: фиксированный состав, `task_results.source_system='final_check'`, исключение из учебного пути.
- `final_check` нельзя расширять до tsk-1519: один прогон на курс, один ответ, нет пауз и РНО, состав выбирается из пройденных заданий. Переиспользуются проверка и запись результата, не его lifecycle.
- `attempts` — контейнер сдач, не модель экзаменационного варианта: паузы, номер КИМ и цвета в нём не выражены.
- `learning_time_session` измеряет присутствие с допустимой погрешностью; его нельзя считать точным экзаменационным таймером.
- `help_requests.reflection_*` относится к реакции на помощь преподавателя, а не к причине ошибки в конкретной ячейке; сущности не объединяем.
- `hints_video` — действующий источник наличия разбора. Дублировать URL в новой таблице не нужно.

## 4. Gaps and Ambiguities

### Блокируют утверждение, не блокируют проектирование

1. **Завершение РНО:** обязательно исправить всё до жёлтого либо достаточно поработать над каждым неверным, оставив неосвоенное красным? Рекомендация: разрешить следующий вариант после попытки РНО по каждой ошибке; красные остаются долгом. Иначе ученик без разбора блокируется бесконечно.
2. **Рефлексия:** рекомендован закрытый словарь + необязательный комментарий: `не_знал_правило`, `ошибся_в_алгоритме`, `вычислительная_ошибка`, `не_понял_условие`, `невнимательность`, `не_успел`, `другое`. Свободный текст вместо словаря затруднит работу преподавателя.
3. **Оранжевый:** рекомендован для красной ячейки, решённой после завершения РНО текущего варианта. Жёлтый означает «исправлено в основной РНО», оранжевый — «добито позже». Первичный балл не меняется ни в одном случае.
4. **Шкала:** для ЕГЭ показывать первичный и тестовый балл по версионированной таблице; для ОГЭ — первичный балл и отметку. Нужно подтвердить, что именно требуется на экране. Для ЕГЭ-2026 максимум 29 первичных; задачи 1–25 по 1, 26–27 по 2. Для ОГЭ-2026 максимум 31; ориентиры 0–11/12–18/19–25/26–31 требуют сверки с официальной таблицей до наполнения.
5. **Неполный вариант:** может ли ученик явно завершить вариант с неотвеченными заданиями? Рекомендация: да, после подтверждения; неотвеченные получают red/0 и идут в РНО.
6. **Доступ:** рекомендовано выдавать конкретный вариант через курс/программу ученика, без отдельного механизма назначения в v1.

### Технические уточнения перед реализацией

- Полный инвентарь типов заданий в пилотных вариантах; v1 принимает только целиком автопроверяемые.
- Правила пересдачи при исправлении эталона: начатый run использует snapshot эталона либо помечается `invalidated`; молча перепроверять старые ответы новым правилом нельзя.
- Официальные шкалы и их версии вносятся контентным пакетом с источником и датой, не константами в коде.

## 5. Anti-patterns found / Duplication Decisions

- **Documentation drift — ACTIVE:** mirror отстаёт от кода; при реализации обновить все затронутые контракты.
- **Dual source of truth для видео — RISK:** копия `hints_video` в exam-таблице запрещена; читать task content.
- **Dual write прогресса — RISK:** нельзя менять обычный статус задания из exam flow. Все exam-результаты получают отдельные source values и включаются в `NON_LEARNING_PATH_SOURCES`; в `REAL_STUDENT_SOURCES` не добавляются. Решение о включении в общую активность/retrieval принимается отдельно, по умолчанию нет.
- **JSON без контракта — RISK:** snapshot, scale и reflection описываются Pydantic-схемами; CB валидирует при публикации.
- **Повторное использование checking/task_results — must-centralize:** одна проверка и один writer результатов.
- **Состояние ячейки — must-centralize:** вычисляет только LMS, SPW получает готовый enum, а не раскрашивает по своим правилам.
- **Отдельный exam lifecycle — acceptable divergence:** отличия от `final_check` существенны; общий сервис создавал бы условную сложность.

## 6. Target Architecture

### C4 TO-BE

- SPW: `/me/exam-progress` — список/карта; `/me/exam-progress/runs/[id]` — вариант и РНО; `/teacher/exam-reviews` — список заданий без разбора.
- LMS API `/exam-progress/*`: read map; start/resume/pause/finish; initial answer; review answer + reflection; teacher review queue.
- LMS `exam_progress_service`: lifecycle и авторизация; `exam_scoring_service`: чистый расчёт; существующий `CheckingService`/`TaskResultsService`: вердикт и хранение ответов.
- PostgreSQL: каталог вариантов, run, активные сеансы, состояния заданий. Обычные таблицы курсов не расширяются exam-полями.
- CB: публикация варианта, состава, номеров, баллов и шкалы; run хранит snapshot опубликованной версии.

### Модель данных (логическая)

**`exam_variant`**: id, exam_kind (`ege|oge`), root_course_id, title, external_uid unique, status, published_version, scoring_scale jsonb, created/updated.

**`exam_variant_item`**: variant_id FK, position, exam_number, task_id FK, primary_score, unique(variant_id, position), unique(variant_id, task_id). Номер КИМ — явные данные, не `order_position` и не название задания.

**`exam_run`**: id, student_id, variant_id, variant_version, content_snapshot jsonb, scale_snapshot jsonb, status (`in_progress|paused|review|completed`), started_at, initial_finished_at, review_finished_at, completed_at, active_seconds, created/updated. unique(student_id, variant_id) в v1: один полный цикл на вариант.

**`exam_run_session`**: id, run_id, started_at, last_heartbeat_at, ended_at, end_reason (`pause|initial_finish|stale|logout`), seconds. Суммарное активное время = закрытые интервалы + текущий ограниченный интервал; РНО сеансов не создаёт.

**`exam_run_item`**: id, run_id, position, exam_number, task_id, initial_result_id FK task_results, review_result_id FK nullable, review_attempt_count, reflection_reason, reflection_comment nullable, reflected_at, first_correct_at, resolved_at, resolution (`initial|rno|late|null`), timestamps. unique(run_id, task_id). Цвет вычисляется: initial pass → green; review pass во время основной РНО → yellow; unresolved → red; pass после `review_finished_at` → orange.

### Правила состояний

- `in_progress ↔ paused`; heartbeat только в `in_progress`; stale-сеанс закрывается сервером на следующем вызове, не требует фонового worker.
- Последний первичный ответ или явное завершение → `review`, фиксируется время варианта.
- В `review` разрешены неограниченные сдачи только по первично неверным/пропущенным. Ответы пишутся отдельным `source_system='exam_review'`; первичный — `'exam_initial'`.
- При верном РНО требуется reflection reason; транзакция «проверка + результат + рефлексия + состояние» атомарна.
- `review → completed` по утверждённому правилу РНО. В `completed` разрешены late-ответы только к red.
- Повтор HTTP-запроса не создаёт второй результат: run/item lock + проверка состояния + client request id для retry.
- Изменение контента после старта не переставляет состав и номера run. Политика смены эталона должна быть выбрана до пилота.

### UX flow ученика

1. Карта → выбрать доступный вариант → старт/продолжить.
2. Экран варианта: номер КИМ, общий прогресс, активное время, «Пауза»; переходы между заданиями без обязательной линейности.
3. После каждого первичного ответа показывается только факт принятия; правильность/эталон до завершения варианта не раскрываются.
4. Завершение → итог первичного прохождения → список ошибок → РНО без таймера.
5. Верный РНО → форма причины → сохранение → yellow. При наличии видео доступна ссылка; без него — понятный статус «преподаватель увидит, что нужен разбор».
6. Завершить РНО → следующий вариант; red остаются доступны для поздней отработки.
7. Таблица: строки номеров, столбцы variant + started date; фильтр/горизонтальная прокрутка на мобильном; цвет дублируется подписью/иконкой. Внизу по каждому столбцу active time и балл по green.

### UX flow преподавателя

Список «Нужны видеоразборы»: exam, номер, задание, число учеников/красных ячеек, ссылки на задание и учеников. Это вычисляемая проекция red + отсутствие `hints_video`, а не заявки и не уведомления. Добавление видео штатным путём убирает строку. ACL преподавателя — только его ученики; методист/админ — все.

## 7. Simplification Decisions

- Не вводим event bus, фоновый scheduler, микросервис и отдельную БД.
- Не строим на `final_check` и не смешиваем с `trainer`.
- Не храним вычислимый цвет, балл и итоговое время как конкурирующие источники; snapshot баллов/шкалы храним, итоги читаем расчётом.
- Не создаём help request на каждую красную ячейку.
- Не делаем free-form reflection обязательным; аналитический словарь + короткий комментарий.
- Не обещаем точность активного времени выше heartbeat-интервала; на экране округление до минут.

## 8. Contract Changes

Все API аддитивны, префикс `/api/v1/exam-progress`:

- `GET /me/map` → variants, runs, rows/cells, totals, scale labels.
- `POST /me/variants/{id}/start` → run; идемпотентно возвращает существующий.
- `POST /me/runs/{id}/pause`, `/resume`, `/heartbeat`, `/finish-initial`, `/finish-review`.
- `GET /me/runs/{id}` → lifecycle, items, safe task data, active time, available actions.
- `POST /me/runs/{id}/items/{item_id}/answer` → `{phase: initial|review|late, answer, reflection?}`; initial один раз; correct review требует reason.
- `GET /teacher/review-queue` → красные без видео, существующий staff ACL.
- CB publish: версионированный variant + items + scale; LMS валидирует полноту номеров, уникальность, автопроверяемость и соответствие суммы primary scores шкале.

Ответы не содержат эталон до разрешённой фазы. OpenAPI, LMS API mirror, DB mirror, SPW mirror и cross-project CHANGELOG обновляются в фазах реализации.

## 9. ADR entries (черновики)

### ADR-A: Отдельный lifecycle экзаменационного варианта

**Status:** Proposed. В контексте пауз, РНО и повторной поздней отработки выбрали отдельный `exam_progress`, а не расширение `final_check`, чтобы сохранить понятные инварианты обоих контуров, принимая небольшое дублирование orchestration. Checking и task results остаются общими.

### ADR-B: Неизменяемый снимок варианта и шкалы

**Status:** Proposed. Run хранит состав, номера, primary scores и scale version на старт; последующая публикация создаёт новую версию. Это защищает историю и сопоставимость таблицы ценой хранения snapshot и явной политики invalidated content.

### ADR-C: Активное время по серверным сеансам

**Status:** Proposed. Считаем heartbeat-сеансы с cap и закрытием stale при следующем вызове, а не `finished_at-started_at` и не `learning_time_session`. Получаем воспроизводимое активное время без фонового worker, с документированной погрешностью.

### ADR-D: Цвет — производная учебного результата

**Status:** Proposed. Green/yellow/red/orange вычисляются из фаз и результатов, не записываются как самостоятельный статус. Первичный балл считается только по green. Late-отработка меняет отображение, но не исторический балл.

### ADR-E: Очередь видеоразборов как read-model

**Status:** Proposed. Список строится из unresolved red и отсутствия `hints_video`, без новых заявок/уведомлений. Это устраняет синхронизацию двух состояний; стоимость — запрос агрегации с индексами и ACL.

## 10. Implementation Phases

### Фаза 0 — решения и пилотный контент

Утвердить 6 gaps, официальные шкалы, один ЕГЭ и/или ОГЭ variant. **Exit:** решения записаны в задаче, контент проходит инвентарь автопроверки. **Rollback:** нет изменений.

### Фаза 1 — контракт и read-only прототип

Pydantic contracts, пример опубликованного variant JSON, SPW prototype карты на fixture, UX-ревью всех экранов и back/recovery. **Exit:** согласованные состояния и тексты; нет production writes. **Rollback:** удалить неподключённый код.

### Фаза 2 — схема и backend initial flow

Миграция, публикация variant, start/pause/resume/heartbeat/finish, initial answer, scoring, изоляция source. **Exit:** API-тесты гонок, retry, ACL, snapshot и отсутствия влияния на курс; миграция up/down/up. **Rollback:** feature flag off; код совместим со старой схемой, миграция аддитивна.

### Фаза 3 — РНО, рефлексия и карта

Review/late answers, словарь причин, map, totals. **Exit:** все цветовые переходы и неизменность балла покрыты; следующий вариант подчинён правилу. **Rollback:** flag off, данные сохраняются.

### Фаза 4 — SPW ученика

Вариант, пауза/возобновление, РНО, таблица, мобильный и доступность не по цвету. **Exit:** unit/e2e + живой сценарий учеником, включая перезаход и back с каждого экрана. **Rollback:** скрыть маршрут/вход flag.

### Фаза 5 — SPW/LMS преподавателя

Read queue и навигация к заданию/ученику. **Exit:** красная без видео видна; с видео отсутствует; ACL проверен; живой admin+teacher flow. **Rollback:** скрыть маршрут.

### Фаза 6 — ограниченный пилот

Один курс/несколько учеников, метрики завершения, ошибок, времени, очереди. **Exit:** нет расхождений ручной сверки; оператор разрешает расширение. **Rollback:** flag off без удаления истории.

## 11. Risk Register

| Риск | Митигация |
|---|---|
| Красные без видео навсегда блокируют следующий вариант | Явное правило «поработал, но не решил»; решение оператора |
| Ученик подбирает ответ по мгновенному вердикту | В initial фазе не возвращать correctness/feedback |
| РНО портит обычный статус/аналитику | Два новых source + центральный exclusion list + regression tests |
| Двойной submit меняет первый результат | Lock, state guard, idempotency key |
| Закрытие вкладки раздувает время | Heartbeat cap, stale close, серверные timestamps |
| Смена эталона меняет прошлое | Snapshot и явная invalidation policy |
| Цвет не различим | Подпись/иконка, контраст, мобильная таблица |
| Очередь преподавателя раскрывает чужих учеников | Центральный teacher ACL и тесты |
| Контентный drift | Валидация CB + LMS, версии, никаких ручных SQL |

## 12. Validation Plan / NFR compliance

**Performance:** map p95 < 500 мс при 50 вариантах × 27 номеров; один агрегированный запрос без N+1; heartbeat не чаще 30 с; очередь p95 < 1 с. Текущих значений нет — измерить на dev до пилота; деградация > 2× блокирует rollout.

**Reliability:** retry без дублей; ответ и run state в одной транзакции; stale timer восстанавливается при любом следующем вызове; недоступность video host не мешает сдаче. Availability — как у LMS; MTTR через feature flag < 15 мин.

**Security:** cookie auth; student только свой run; teacher ACL; Pydantic limits (comment ≤500, idempotency key); ответы/эталоны не утекают в initial; URL видео только из проверенного task content; reflection экранируется React.

**Maintainability:** чистые функции scoring/color/time; централизованные source filters; API/schema contracts; миграция up/down/up; OpenAPI и mirrors в том же изменении.

**Observability:** structured logs run_id/student_id/variant_id/phase/result; метрики starts, finishes, review completion, stale closes, retry conflicts, queue size. Не логировать текст рефлексии и ответы.

## 16. Независимое ревью Claude — обязательные поправки

Вердикт Claude: **FAIL** для старта backend до устранения находок; уверенность medium. Kimi подтверждает 2 P0, 9 P1 и 2 P2; P3 о дублировании snapshot принят как упрощение. Все поправки ниже обязательны и имеют приоритет над более общими формулировками выше.

1. **Скрытие initial-результата во всех API.** До `initial_finished_at` ни один существующий или новый endpoint не отдаёт correctness, score, feedback и эталон `exam_initial`. Реализация обязана централизованно скрывать такие результаты либо откладывать запись проверки до finish; одного исключения из learning path недостаточно. Негативные тесты всех read-path обязательны.
2. **Checker snapshot.** При старте run отдельно сохраняются закрытый `checker_snapshot` (solution rules + версия checker) и публичный content snapshot. Все initial/review/late проверяются только snapshot; живой эталон не используется. Закрытый snapshot никогда не сериализуется в ученический API. Альтернатива invalidated отклонена для v1.
3. **Серверная фаза и идемпотентность.** `phase` из запроса только сверяется с серверной, несовпадение → 409. Добавить `exam_answer_request(run_id, client_request_id, response_json)` с unique(run_id, client_request_id); locks run+item и хранимый ответ retry обязательны.
4. **ACL/IDOR.** item выбирается одним predicate по run_id,item_id,current student; чужой ресурс → 404. Teacher queue использует существующий `ensure_can_edit_progress`/teacher-student scope; ACL фильтрует и строки, и агрегаты.
5. **Таймер.** Partial unique `(run_id) WHERE ended_at IS NULL`; heartbeat cap 90 секунд; stale закрывается на `last_heartbeat_at + min(fактический_разрыв,90s)`, не на now. Heartbeat вне in_progress → 409 без записи. Зафиксировать таблицу допустимых переходов; тесты двух вкладок и обрыва сети.
6. **Баллы.** v1 допускает только целиком автопроверяемые задания с бинарным полным первичным баллом; частичные и ручные проверки исключены при публикации. Это не расширять без нового ADR.
7. **Blank.** `initial_result_id` nullable; `initial_outcome=correct|wrong|blank` обязателен после finish-initial. Цвет/балл/очередь читают это поле, а не наличие FK.
8. **Порядок вариантов.** Добавить `exam_variant.sequence` в рамках root_course_id+exam_kind. Start следующего разрешён, когда у предыдущего run каждый wrong/blank имеет review_attempt_count≥1; zero errors и all blank покрыты тестами.
9. **Публикация.** Фаза 2 включает идемпотентный CB→LMS publish по external_uid с published_version. Migration up/down/up обязателен только dev/CI; production rollback — feature flag без down-миграции и удаления истории.
10. **Очередь.** Это живой SQL read-model только по `run.status=completed`, unresolved red и пустым hints_video; активная РНО в неё не попадает. Нужны индексы и ACL-тесты.
11. **Аудит читателей.** Фаза 2 включает grep всех `source_system`/REAL_STUDENT_SOURCES и regression-тест неизменности статистики, стриков, прогресса и дашбордов.
12. **Рефлексия/UX.** Коды причин версионируются контрактом; UI различает «ещё в РНО» и «red после completed», хотя цвет red общий.
13. **Snapshot без двойного источника.** position/exam_number/task_id принадлежат `exam_run_item`; content_snapshot содержит только публичный контент/версии, checker_snapshot — только закрытые правила.
