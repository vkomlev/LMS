## Развилки, решённые оператором до этого плана

5. **Триггер назначения — существующего движка ADR-0002 достаточно** (`task_failed`, `course_failed` в рамках одной попытки, ручное назначение учителем); новый вид триггера не нужен для старта.

## Целевая возможность

Методист связывает мини-курс повторения с основным курсом через `course_dependencies`. Ученик, дошедший до курса с непройденной зависимостью, не может продолжить прохождение (next-item отдаёт `blocked_dependency`), видит понятную причину **с названием** нужного курса и прямой переход к нему — в SPW и в TG_LMS. После завершения мини-курса блокировка снимается автоматически (кеш `student_course_state` уже пересчитывается синхронно/фоново, tsk-541/545 — без изменений).

## Пробелы и недостающие ресурсы (блокирующие)

1. **[БЛОКИРУЮЩИЙ] Ретроактивное доназначение при добавлении зависимости к УЖЕ идущему курсу.** `CourseDependenciesService.add_dependency`/`bulk_add_dependencies` (`app/services/course_dependencies_service.py:30-63`) сейчас пересчитывает только кеш состояния (tsk-541), но НЕ вызывает `course_dependencies_enrollment_service.ensure_dependencies_assigned` для уже зачисленных на `course_id` учеников. `ensure_dependencies_assigned` вызывается только в момент НОВОГО зачисления (`user_courses_service.create/bulk_assign_courses`, `assignment_rules_service.assign_course_to_student`). Итог: методист добавляет мини-курс зависимостью к курсу, на котором уже 30 учеников — все 30 мгновенно блокируются, но НЕ зачислены на мини-курс (его нет в их `user_courses`) → замок висит вечно без выхода. Это ровно тот класс регрессии, что уже случался в tsk-523 («блокировка раздела «Множества» даже для методист-аккаунта»), только теперь по недостающему зачислению, а не по недостающему кешу. **Без этой правки функция задачи технически неработоспособна для реального сценария** (методист почти всегда добавляет зависимость к курсу с уже зачисленными учениками).
2. **[БЛОКИРУЮЩИЙ] Название курса-зависимости недоступно клиентам.** И `dependency_course_id` в next-item, и `blocked_courses: list[int]` в syllabus-states — голые числа. SPW (`findBlockedByTitle`, `use-course-syllabus.ts:386-398`) сейчас резолвит title НЕПРАВИЛЬНОГО курса (самого заблокированного узла, не курса-зависимости — это признано в комментарии кода). TG_LMS показывает только `id=N`. Оба клиента органичены тем, что отдаёт API — без правки backend UX-часть задачи нерешаема.
3. **Нет прямого перехода к курсу-зависимости.** В SPW кнопка ведёт на общий список «Мои курсы», в TG_LMS кнопки действия нет вовсе — только текст. Ученику придётся искать нужный курс вручную. Не блокирующий, но именно это и есть буквальный смысл требования «клиенты показывают... вход в мини-курс».
4. **Нет предупреждения о блокировке при её создании.** UI методиста (`DependenciesBlock`) добавляет зависимость без подтверждения и без указания, скольких уже зачисленных учеников это заблокирует немедленно. Учитывая глобальный и мгновенный характер блокировки (решение оператора выше) и прецедент tsk-523 — минимальная защита нужна.

## Решение по UX-сложности

Прямой переход к курсу-зависимости (Фаза 3.1, 4.2) — не лишний экран, а единственный actionable-выход из блокировки; без него ученик физически не может понять, что делать (текущее состояние — тупик, ровно то, что просил избежать оператор в исходном требовании: «ученик должен понимать, что заблокировано, почему и что сделать»). Confirm-диалог методиста (Фаза 3.3) — `justified`: явная причина (мгновенная необратимая массовая блокировка) + acceptance test (число учеников показано перед подтверждением, прецедент tsk-523).
