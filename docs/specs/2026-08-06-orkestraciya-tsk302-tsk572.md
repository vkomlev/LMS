# Оркестрация двух смежных задач: tsk-302 (защита от списывания) и tsk-572 (ИИ-наставник)

**Дата:** 2026-08-06
**Статус:** **УТВЕРЖДЕНО оператором 2026-08-06** (решения — раздел 6)
**Назначение:** общий контракт разделения работ. Читают оба чипа — и tsk-302, и tsk-572.

> ## Решения оператора (обязательны к исполнению обоими чипами)
>
> 1. **Режим работы — последовательный.** Один чип пишет код в единицу времени. Второй в это время может планировать (документы конфликтов не создают), но не правит код, схемы и миграции.
> 2. **Очередь:** `Этап 0 (tsk-302, без ИИ)` → `Этап 1 (общий LLM-транспорт)` → `Этап 2 (tsk-572, наставник)` → `Этап 3 (tsk-302, ИИ-оценка всех языков)`.
> 3. Общий LLM-транспорт проектируется **под требования tsk-572** (стриминг, интерактивные бюджеты, счётчик расхода) и переиспользуется задачей tsk-302 без переделки.

---

## 1. Почему вопрос вообще возник

Обе задачи независимо пришли к одной потребности — **вызывать LLM из прод-LMS**, которого сейчас не существует. Плюс обе встраиваются в один и тот же участок кода. Без явной договорённости получится либо два несовместимых LLM-клиента, либо конфликт в общих файлах.

| | tsk-302 | tsk-572 |
|---|---|---|
| Суть | Защита от списывания: чистота кода + признак ИИ-авторства | ИИ-наставник ученику + автоконтур мини-курсов |
| Статус | В работе, код направления 1 написан (в `main`, **не на проде**) | `active`, бриф `finalized`, кода нет, следующий шаг — `change-plan-architect` |
| Кому польза | Преподаватель и методист (контроль) | Ученик (помощь в момент провала: 527 неверных ответов за 30 дней, 24.6%) |
| Нужен LLM | Да, батч, без стриминга | Да, интерактив, **стриминг обязателен** по UX |

## 2. Точки пересечения (проверены по коду)

| № | Ресурс | tsk-302 | tsk-572 | Тип |
|---|---|---|---|---|
| 1 | **LLM-транспорт в LMS** (не существует) | батч-вызов судьи | интерактив + стриминг + бюджеты + счётчик расхода | `must-centralize` |
| 2 | `app/api/v1/attempts.py`, участок после проверки ответа | ставит задачу «оценить работу» | точка входа наставника «после неверного ответа» | конфликт правок |
| 3 | `ReviewClaimItem` (`app/schemas/teacher_next_modes.py`) | добавляет отчёт о качестве/ИИ | добавляет след диалога наставника («виден персоналу») | конфликт схемы |
| 4 | `SPW/components/teacher/ReviewGradePanel.tsx` | блок «чистота кода + сигнал ИИ» | показ следа диалога с наставником | конфликт UI |
| 5 | **Alembic + одна dev-БД** | миграция под колонку отчёта | миграции под таблицы диалогов | конфликт heads |

## 3. Почему параллельная работа сейчас опасна — три независимые причины

1. **Одно рабочее дерево.** Оба чипа сидят в `D:\Work\LMS` (`git worktree list` — один рабочий каталог). Это ровно сценарий ADR-0008. Симптомы уже наблюдались в этой сессии: файл-маркер `.skill-engaged-note.md` перезаписывался чужой сессией дважды, а в полном прогоне `pytest` падали чужие тесты (`test_tsk559_*`), которые в изоляции проходят.
2. **Одна dev-БД на оба чипа.** В `.env` один `DATABASE_URL`. Обе задачи требуют миграций. Две ветки миграций в одной БД разведут Alembic heads — а по журналу межагентного реестра dev-схема уже и так ушла вперёд прода (`tsk303_feedback_reports` против `tsk427_profile_extra_fields` на проде).
3. **Пересечение в 4 точках кода**, включая один и тот же участок `attempts.py`. Это не соседние файлы, а одни и те же строки.

**Реестр захватов `Root/agents/` сейчас пуст** — то есть формально ресурсы не разделены вообще, обе задачи идут «на честном слове».

## 4. Предлагаемая топология

Ключевая идея: **общий транспорт выносится в отдельную работу и делается один раз, по требованиям более требовательного потребителя (tsk-572)**. Остальное разводится по времени, а не по дереву.

```
ЭТАП 0 (сейчас, без LLM)          ЭТАП 1 (общее)         ЭТАП 2            ЭТАП 3
tsk-302, «слой без ИИ»       →   LLM-транспорт LMS   →   tsk-572      →   tsk-302
                                                          наставник        ИИ-оценка
• починить перезапись metrics    • async httpx           • диалоги        • ИИ-судья
• расширить ReviewClaimItem      • env-канон ADR-0046    • мини-курсы     • все языки
• блок в ReviewGradePanel        • стриминг (для 572)    • свои таблицы   • фоновая
• деплой + живая проверка        • счётчик расхода       • SPW UI           очередь
                                 • бюджеты таймаутов
   польза сразу:                    разблокирует            польза              польза
   препод видит чистоту              обе задачи             ученику            контроля
   кода (Python)
```

**Почему Этап 0 идёт первым и вне очереди на LLM:** он вообще не зависит от транспорта. Это починка блокеров (`metrics` стирается, отчёт не виден преподу) плюс вывод на прод уже написанного pylint-контура для Python. Даёт быструю пользу и снимает долг предыдущего захода, не мешая tsk-572 планироваться параллельно (планирование — это документы, а не код, конфликтов не создаёт).

**Почему транспорт проектируется под tsk-572, а не под tsk-302:** у tsk-572 требования строго шире (стриминг, интерактивные бюджеты первого токена, деградация вместо ошибки). Клиент, написанный под батч-нужды tsk-302, пришлось бы переписывать. Обратное неверно — батч-вызов на «стриминг-годном» клиенте делается тривиально.

## 5. Разделение ответственности и ресурсов

### Владение файлами (кто правит без спроса)

| Ресурс | Владелец | Второй чип |
|---|---|---|
| `app/services/llm/*` (новый транспорт) | Этап 1, затем **tsk-572** | tsk-302 только потребляет, не правит |
| Таблицы/эндпоинты диалогов наставника | tsk-572 | не трогает |
| Колонка отчёта в `task_results`, фоновая оценка | tsk-302 | не трогает |
| `attempts.py` (участок после ответа) | **общий, по захвату** | строго по очереди |
| `ReviewClaimItem`, `ReviewGradePanel.tsx` | **общий, по захвату** | аддитивно, разными полями |
| Alembic-миграции | **строго по очереди** | второй ждёт, затем `alembic upgrade head` |

### Каким механизмом координироваться (важное уточнение)

Межагентный реестр `D:\Work\Root\agents\` для этого случая **не подходит и засорять его не нужно**. Его карта владения (`agents/ownership.md`) покрывает инфраструктуру — деревья скиллов, глобальные инструкции, реестры ошибок, контент курсов, конфиги окружения. **Код репозиториев (`app/`, `SPW/components/`, миграции) в карту не входит**, а раздел «Что НЕ является общим ресурсом» прямо просит не заводить лишние захваты.

Реальные механизмы координации здесь:

1. **Решение оператора о последовательности** (раздел 6) — основной и достаточный при последовательном режиме.
2. **Этот документ** — лежит в самом репозитории, оба чипа его читают.
3. **Файлы задач** `Root/tasks/tsk-302*.md` и `tsk-572*.md` — там фиксируется, кто на каком этапе (это уже общий ресурс, изменения видны обоим).
4. **Механический гейт `index_scope_gate`** — уже работает: блокирует `git commit` без pathspec, если в индексе оказались файлы, которых сессия не касалась. Это защита от случайного присвоения чужой работы, а не замена договорённости.

При последовательном режиме (выбран оператором) больше ничего не требуется. Захваты понадобились бы только при параллельном режиме с общими файлами.

### Если оператор всё же хочет строгий параллелизм

Тогда обязательны оба условия, иначе повторится инцидент ADR-0008:
1. Второму чипу — **отдельный git worktree** со своим `.venv` (291 МБ) и своим `.next`-аналогом;
2. Второму чипу — **отдельная dev-БД** (иначе Alembic heads разъедутся независимо от worktree).

Это заметная разовая настройка. При текущем объёме задач она, вероятно, дороже, чем последовательный проход.

## 6. Что должен решить оператор

Единственная развилка, которую нельзя решить инженерно — **приоритет этапов 2 и 3** (что вперёд: наставник или ИИ-оценка списывания). Аргументы:

- **Наставник вперёд** — прямая польза ученику в момент провала, задача уже отревьюирована (бриф finalized), транспорт всё равно проектируется под неё.
- **Защита вперёд** — работа наполовину сделана, а без неё контроль честности остаётся дырой; но пользу видит только персонал, не ученик.

Рекомендация: **этап 0 (сейчас) → транспорт → наставник → ИИ-оценка**. Причина: этап 0 закрывает блокеры и даёт преподу первую пользу за малую цену; далее продуктовая ценность для ученика опережает контрольный контур, а tsk-302 достраивается на готовом транспорте без переделок.

**РЕШЕНО оператором 2026-08-06: принята рекомендация.** Режим — последовательный; очередь — этап 0 → транспорт → наставник → ИИ-оценка.

### Что это значит практически для каждого чипа

**Чип tsk-302 (этот):** начинает этап 0 немедленно. Правит `task_results_extra.py` (починка перезаписи), `teacher_next_modes.py` (`ReviewClaimItem`), миграцию под колонку отчёта, `SPW/components/teacher/ReviewGradePanel.tsx`. Выкатывает на прод с живой проверкой. По завершении — освобождает код и передаёт очередь.

**Чип tsk-572:** пока чип tsk-302 занят этапом 0 — **планирование, без правок кода**: `change-plan-architect` по фазам, проработка контракта LLM-клиента (стриминг, бюджеты, счётчик расхода), методика наставника. Документы (`docs/specs/`, `docs/briefs/`) конфликта не создают. Как только этап 0 закрыт — забирает очередь и делает этап 1 (транспорт) под свои требования, затем этап 2.

**Общий контракт LLM-клиента** (этап 1) фиксируется до написания кода и согласуется с обеими задачами: tsk-572 нужен стриминг и интерактивные бюджеты, tsk-302 — только батч-вызов с `temperature=0` и разбором JSON-ответа. Клиент обязан покрывать оба режима.

## 7. Гейты

| Гейт | Где | Критерий |
|---|---|---|
| `spec-gate` | перед этапом 1 | контракт LLM-клиента согласован с требованиями обеих задач (стриминг, бюджеты, счётчик расхода) |
| `execution-gate` | каждый этап | зелёный `pytest`, smoke затронутых эндпоинтов |
| `review-gate` | перед merge каждого этапа | независимое PASS/FAIL |
| живая проверка | после деплоя этапа 0 | препод реально видит блок на экране проверки работы (прод, браузер) |
