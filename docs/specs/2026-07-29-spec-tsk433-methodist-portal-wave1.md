# Спека — кабинет методиста в SPW, Волна 1 (tsk-433)

> Скиллы: `/spec-writer` → `/change-plan-architect` → `/tech-spec-composer`. Дата: 2026-07-29.
> Вход: [AS-IS](2026-07-29-as-is-tsk433-methodist-portal.md) · [бриф](../briefs/tsk-433-methodist-portal.md) · [DESIGN.md SPW](../../../SPW/DESIGN.md)
> Режим: СОКРАЩЕНИЕ волнами. Волна 1 = операционка + контент-ревизия (решение оператора).

## 1. Что делаем

Кабинет методиста `/methodist/*` в SPW: методист выполняет дневную работу в вебе —
разбирает эскалации, проверяет работы, отвечает на заявки помощи, ведёт переписку,
смотрит ленту активности и **ревизует контент** (дерево курсов, материалы, задания,
статистика, предпросмотр задания глазами ученика).

**Редактирование контента — вне Волны 1** (решение оператора: веб = точечная правка
и ревизия, но правка — следующая волна; массовое создание остаётся за конвейером
`/methodist` → Sheets → bulk-upsert).

## 2. Сценарии методиста (критерии готовности)

| # | Сценарий | Готово, когда |
|---|---|---|
| С1 | Вход в кабинет | Пользователь с ролью `methodist` открывает `/methodist` и видит кабинет; без роли — редирект; из кабинета ученика/преподавателя есть переход в кабинет методиста и обратно |
| С2 | Обзор дня | На `/methodist` видны счётчики (работ на проверке, открытых заявок, просроченных) и свежие эскалации со ссылкой на разбор |
| С3 | Проверка работы | Методист открывает очередь, берёт работу, видит условие + ответ ученика + вложения, ставит балл с комментарием; счётчики обновляются без перезагрузки |
| С4 | Заявка помощи | Видит открытые заявки, отвечает, закрывает, при `blocked_limit` снимает лимит попыток |
| С5 | Переписка | Видит диалоги с учениками и преподавателями, отвечает |
| С6 | Лента активности | Видит поток событий по всем ученикам (не только своим) |
| С7 | Дерево курсов | Открывает список корневых курсов, проваливается в подкурсы, видит карточку курса (состав зачисленных — следующая волна, вместе с course-ACL) |
| С8 | Ревизия материалов | В карточке курса видит список материалов, открывает карточку материала |
| С9 | Ревизия заданий | Видит список заданий курса, открывает задание: условие, варианты, правило проверки, сложность, `external_uid`, активность |
| С10 | Предпросмотр глазами ученика | В карточке задания переключает режим «как видит ученик» — правильные ответы скрыты, видно ровно то, что увидит ученик |
| С11 | Статистика | Видит статистику по курсу и по заданию (попытки, средний балл, доля верных) |

## 3. Границы

**В Волне 1:** С1–С11 (просмотр, операционные действия, предпросмотр).

**Вне Волны 1 (следующие волны, tsk-433 остаётся открытой):**
- Редактирование курсов/материалов/заданий, дерево (перенос/копирование), импорт из Sheets.
- Карточки студентов и преподавателей, привязки «ученик↔преподаватель↔курс».
- Списки пользователей с фильтром по роли (требует cookie-гейта на PII-эндпоинт `/users/?role=`).

**Вне задачи целиком:** модерация/публикация курса, калибровка сложности, scoped-ACL
методиста, вывод ТГ-бота (см. бриф §6).

## 4. Backend: что придётся добавить

Операционный слой готов — веб зовёт существующие teacher-эндпоинты, методист проходит
их ACL по bypass (`REVIEW_ACL_SQL`, `HELP_REQUESTS_ACL_SQL`, `_ELEVATED_ROLES`). Своя
логика оценки не пишется.

Контентный слой заблокирован: часть эндпоинтов сидит на legacy-гейте `get_db`
(`APIKeyQuery` — **только** `?api_key=` в query), то есть из браузера по cookie
недоступна. Нужен перевод на `get_current_user` + роль:

| Эндпоинт | Сейчас | Нужно | Для сценария |
|---|---|---|---|
| `GET /courses/roots` | `get_db` | cookie + `require_role("teacher","methodist","admin")` | С7 |
| `GET /courses/{id}/children` | `get_db` | то же | С7 |
| `GET /courses/{id}` (карточка) | генерик CRUD под `get_db` | override в `courses_extra.py` (роутер подключён раньше CRUD) | С7 |
| `GET /task-results/stats/by-course/{id}` | `get_db` | cookie + `require_role` | С11 |
| `GET /task-results/stats/by-task/{id}` | `get_db` | то же | С11 |

**Намеренно НЕ переводятся** (решение по итогам `/review-gate`):
`GET /courses/{id}/users` — отдаёт email/ФИО/tg_id зачисленных; роль-гейт без
`teacher_course_acl` открыл бы состав любого курса любому преподавателю, а потребителя
в Волне 1 нет. `GET /courses/{id}/materials/stats` — карточка курса считает материалы
по основному списку, отдельный агрегат не нужен. Оба остаются на legacy-гейте: не
расширяем доступ без потребителя.

Уже доступны по cookie, править не нужно: `/courses/{id}/materials`, `/materials/{id}`,
`/tasks/by-course/{id}`, `/tasks/{id}`, `/tasks/by-external/{uid}`, `/me`,
`/teacher/*` (reviews, help-requests, workload, activity-feed, messages, progress),
`/task-results/stats/by-user/{id}`.

**Совместимость:** сервисный ключ должен продолжать работать (ТГ-боты живут на нём) —
`get_current_user` принимает `X-API-Key`/`?api_key=`, `require_role` пропускает
`is_service` без проверки роли. Это ровно тот переход, что делали в tsk-298 Фазе 3.

**Предпросмотр (С10) backend не требует:** `GET /tasks/{id}` уже отдаёт всё под cookie.
Скрывает ответы фронт — два режима рендера одного `TaskRead`.
⚠ Важно: это же и означает, что бэкенд отдаёт `solution_rules` ученику — отдельная
задача [[tsk-460]], в этой волне не чиним.

## 5. SPW: состав

**Фундамент (до экранов):**
- `app/(methodist)/layout.tsx` — серверный guard `hasRole(me, "methodist")`, шапка.
- `components/layout/MethodistHeader.tsx` — бренд, навигация, переключатели кабинетов.
- Переключатель «Кабинет методиста» в `AppHeader` и `TeacherHeader` (у Виктора роли
  ученика, преподавателя и методиста одновременно — переходы нужны во все стороны).
- Общие компоненты по DESIGN.md §7: `status-badge`, `page-header`, `data-list`,
  `empty-state`, `stat-tile`.
- `lib/format-date.ts` — используется всеми новыми экранами (§4 DESIGN.md).

**Экраны:**

| Маршрут | Содержимое | Источник |
|---|---|---|
| `/methodist` | Счётчики + эскалации | `/teacher/workload`, `/methodist/escalations/pending` |
| `/methodist/reviews`, `/reviews/[id]` | Очередь проверки, оценка | `/teacher/reviews/*` |
| `/methodist/help-requests`, `/[id]` | Заявки помощи | `/teacher/help-requests/*` |
| `/methodist/messages` | Переписка | `/messages/*` |
| `/methodist/activity-feed` | Лента | `/teacher/activity-feed` |
| `/methodist/courses` | Дерево курсов | `/courses/roots`, `/children` |
| `/methodist/courses/[id]` | Карточка курса: подкурсы, материалы, задания, статистика | `/courses/{id}`, `/children`, `/materials`, `/tasks/by-course`, stats |
| `/methodist/tasks/[id]` | Карточка задания + предпросмотр как ученик | `/tasks/{id}` |

**Переиспользование, не копирование.** Операционные экраны (С3–С6) визуально и
функционально совпадают с teacher-версиями, а разница только в охвате данных (ACL шире).
Компоненты `ReviewQueue`, `ReviewGradePanel`, `HelpRequestsList`, `HelpRequestPanel`,
`ActivityFeed`, `TeacherMessages` переиспользуются с параметром базового пути
(`basePath: "/teacher" | "/methodist"`), потому что сейчас ссылки на детальные экраны
в них захардкожены. Копировать эти компоненты в `components/methodist/` запрещено —
это воспроизведёт расхождение, ради борьбы с которым и заведён DESIGN.md.

## 6. Риски и как закрываем

| Риск | Закрытие |
|---|---|
| Перевод эндпоинта с `get_db` на cookie ломает ТГ-ботов | `get_current_user` принимает api_key; регресс-тест «сервисный ключ по-прежнему проходит» на каждый тронутый эндпоинт |
| `require_role` на `/courses/*` отрежет ученика, который сейчас туда ходит | Проверить потребителей до правки: ученический SPW использует `/courses/{id}/materials` и `/tasks/by-course` (они уже на cookie+ACL и НЕ трогаются); правим только те, что сегодня недоступны из браузера вообще |
| Предпросмотр «как ученик» покажет ответы | Режим предпросмотра рендерит `options` без признака правильности и не выводит `solution_rules`; тест на это обязателен |
| Пустой список читается как ошибка | Все четыре состояния экрана (DESIGN.md §8), `isPending` вместо `isLoading` при гейтованных запросах (урок tsk-452) |
| Методист = глобальный bypass, случайная правка чужих данных | В Волне 1 мутации только операционные (оценка, ответ, лимит) — те же, что у преподавателя, с тем же аудитом |
