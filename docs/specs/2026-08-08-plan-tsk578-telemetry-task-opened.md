# План внедрения: tsk-578 — событие «задание открыто»

**Дата:** 2026-08-08 · **Автор:** change-plan-architect (Claude) · **Задача:** [tsk-578](D:/Work/Root/tasks/tsk-578-telemetriya-sobytie-zadanie-otkryto-dlya-izmereniya-vremeni-resheniya.md)

## Целевая возможность

Настоящее событие «ученик открыл задание» вместо прокси (медиана промежутка
между соседними сдачами). Признаки «трудно даётся» / «проходят не думая» в
`topic_mastery_service.py` (tsk-577) переходят на реальное время «открыл →
ответил», сохраняя обратную совместимость на переходный период, пока данных
мало.

## Текущее состояние

- `task_results.received_at` — момент сдачи, единственная временная точка в
  системе. Момента показа задания ученику не существует нигде.
- `topic_mastery_service.py` считает `median_pace_seconds` как медиану
  промежутка между СОСЕДНИМИ сдачами одного ученика внутри темы (LAG-окно по
  `received_at`, выбросы длиннее часа отброшены). Опорные цифры прода
  (90 дней, 1923 промежутка): медиана 26 с, p10 7 с, p90 386 с.
- В системе уже есть работающий, проверенный на проде паттерн клиентской
  телеметрии учебного события: `POST /learning/tasks/{task_id}/hint-events`
  (`app/api/v1/learning.py:761`) → `record_hint_open`
  (`app/services/learning_events_service.py:89`) → таблица `learning_events`
  (`student_id`, `event_type`, `payload JSONB`, `created_at`), с
  антидублирующим advisory-lock и окном дедупа.
- Универсальная точка «ученику показано задание, и он может по нему
  отвечать» уже существует и используется ОБОИМИ клиентами:
  `POST /learning/tasks/{task_id}/start-or-get-attempt`
  (`app/api/v1/learning.py:322`). SPW вызывает её в `useEffect` при монтировании
  страницы задания (`app/(authed)/courses/[course_uid]/task/[external_uid]/page.tsx:382-399`),
  ДО показа формы ответа, и НЕ вызывает для уже решённых/заблокированных
  заданий (`state === PASSED | BLOCKED_LIMIT` — ранний `return`). TG_LMS вызывает
  тот же эндпоинт через `learning_engine_service.start_or_get_attempt`
  (`TG_LMS/src/common/services/learning_engine_service.py:89`) перед показом
  задания в диалоге. Guest-режим (embed-api) использует отдельный контур
  (`/learning/guest/attempts`) без персистентного `student_id` — вне периметра
  метрики методиста.
- `attempts` НЕ 1:1 с заданием: одна попытка может охватывать до 22 заданий
  подряд ([[project_lms_attempt_spans_many_tasks]]) и может жить много дней —
  время на самой попытке не годится для метки «когда открыто ЭТО задание».

## Пробелы и недостающие ресурсы

Прочитан [resource-gap-checklist.md](../../../skills/core/change-plan-architect/references/resource-gap-checklist.md) (общий чеклист claude-booster). Релевантные пункты:

- **Данных нет на старте.** В момент деплоя `learning_events` не содержит ни
  одной строки `task_opened` — весь прошлый трафик остаётся без реального
  времени. Пороги `FAST_PACE_SECONDS`/`SLOW_PACE_SECONDS` пересчитать на
  реальных данных СЕЙЧАС физически нечем — блокирующий пробел для полной
  замены прокси, закрывается только временем работы прода после деплоя.
- **Нет данных для валидации формулы "последнее открытие перед сдачей".**
  Гипотеза (открытие ближайшее ПЕРЕД `received_at` этого же `task_id` у этого
  же `student_id`) логически вытекает из потока экрана, но не проверена на
  живых данных — первая неделя прода служит одновременно проверкой корректности
  джойна.
- Не пробел, а осознанное ограничение: guest-сессии (embed-режим) вне охвата.

## Допущения и открытые вопросы — решены здесь

**Кто пишет событие.** Ни SPW «при показе», ни LMS «при выдаче next-item» из
исходной постановки — третий вариант, обнаруженный анализом кода: **LMS,
внутри уже существующего `start-or-get-attempt`**, серверным эффектом без
нового вызова с фронта. Обоснование:
- `next-item` вызывается только в сценарии «продолжить», НЕ вызывается при
  прямом клике по заданию из дерева прогресса (syllabus-states) — событие
  потерялось бы для значимой доли открытий.
- `start-or-get-attempt`, наоборот, вызывается ОБОИМИ клиентами (SPW, TG_LMS)
  ровно в момент, когда ученику становится доступна форма ответа, независимо
  от пути навигации, и НЕ вызывается повторно для уже решённых заданий —
  ровно то смысловое событие, которое нужно.
- Сервер-сайд эффект = нулевые правки в SPW/TG_LMS, нулевой риск рассинхрона
  версий клиентов, работает для всех текущих и будущих клиентов сразу.

**Куда пишет.** Существующая `learning_events` (`event_type='task_opened'`,
`payload={task_id, attempt_id, is_new_attempt}`) — НЕ новая таблица и НЕ
колонка в `attempts`/`tasks`. Колонка на `attempts` невозможна по смыслу
(попытка не 1:1 с заданием, [[project_lms_attempt_spans_many_tasks]]).
Отдельная новая таблица дублировала бы то, что `learning_events` уже
предоставляет: дедуп-паттерн, индексацию, прецедент чтения (`get_hint_open_counts`).

**Повторное открытие.** Пишем КАЖДЫЙ вызов (с коротким антидубль-окном ~30 с
на дребезг типа React StrictMode double-effect/повторный рендер — не смысловой
дедуп, как у `help_requested`/`hint_open`, а просто защита от мусорных строк
впритык). Повторные открытия — это ЦЕННЫЙ сигнал, а не шум: студент открыл
вчера, закрыл, сегодня открыл и за 10 секунд ответил — реальное время
раздумья 10 с, не «вчера-сегодня». Поэтому при подсчёте пейса берётся
БЛИЖАЙШЕЕ ПЕРЕД сдачей открытие того же `(student_id, task_id)`, не первое.

**Уход без ответа.** Ничего специально не делается — событие остаётся в
`learning_events` ненайденным парой, безвредно. Отдельная метрика «открыл, не
ответил» — потенциально полезная, но вне периметра tsk-578 (можно добавить
позже как самостоятельный показатель, не блокирует эту задачу).

**Пороги и обратная совместимость (миграционный путь).** Прокси остаётся
ДЕФОЛТОМ для темы, пока по ней недостаточно РЕАЛЬНЫХ пар «открытие → сдача»
(новая константа `MIN_REAL_PACE_SAMPLES`, по аналогии с `MIN_SUBMISSIONS`).
Как только у темы набирается достаточно реальных пар — используется медиана
реального времени вместо прокси, теми же пороговыми константами
`FAST_PACE_SECONDS`/`SLOW_PACE_SECONDS` как временное значение (задокументировано
как провизорное: единица измерения та же — секунды от показа до сдачи, и
прокси систематически НЕ меньше реального времени, так как включает ещё и
переход/авторедирект между заданиями — реальный порог, вероятно, будет чуть
ниже нынешнего, но не выше). Пересчёт числовых порогов на реальных данных —
отдельный follow-up после накопления телеметрии (создаётся в трекере при
закрытии tsk-578), не блокирует эту поставку.

## Решение по дублированию

Переиспользуется существующий слой `learning_events_service` +
`learning_events` — не заводится параллельный механизм. Единственная новая
сущность — индексы для нового `event_type`, по уже устоявшемуся прецеденту
(`hint_open_index_stage36`).

## Guard по UX-сложности

Прочитан [ux-complexity-guard.md](../../../skills/core/change-plan-architect/references/ux-complexity-guard.md).
Применимо частично: новых экранов/UI нет (весь эффект серверный), поэтому
большинство пунктов guard неприменимо. Единственный релевантный пункт —
«не добавлять экран/шаг ради данных, если данные можно получить без нового
взаимодействия пользователя» — выполнен: ноль новых кликов, полей или
экранов для ученика.

## План проверки

- `pytest` (LMS) — весь набор, целевые новые тесты: запись события при новой/
  существующей попытке, дедуп короткого окна, pace-CTE с реальными данными и
  с fallback на прокси, `pace_source` в ответе API.
- `EXPLAIN ANALYZE` на пейс-CTE с реальными объёмами (или dev-приближение) —
  подтвердить использование частичных индексов, не full-scan `learning_events`.
- Живой прогон на проде (см. Этап 7): открыть → сдать → сверить
  `learning_events` и ответ `topic-mastery` API.
- `/review-gate` перед мержем в `main`, артефакт в `reviews/`.

## Риски и меры снижения

- **Риск:** LATERAL-джойн пейс-CTE по `learning_events` на каждую сдачу
  окна (90 дней) деградирует производительность `topic_mastery` API.
  **Мера:** партиционированный частичный индекс под `event_type='task_opened'`
  (шаг 2), `EXPLAIN` до мержа; при деградации — ограничить окно поиска события
  (например, не искать открытие раньше `received_at - 1 час`, тем же капом,
  что уже есть у прокси `PACE_OUTLIER_CAP_SECONDS`).
- **Риск:** формула «ближайшее открытие ПЕРЕД сдачей» ошибочна для крайних
  случаев (несколько вкладок, повторный submit после wrong-answer в той же
  сессии без нового открытия — тогда у ВТОРОЙ сдачи того же задания в той же
  сессии не будет своего `task_opened` события, ближайшее event останется от
  первого открытия, что и корректно: это и есть время от показа до
  окончательного верного ответа, включая промежуточные попытки).
  **Мера:** явный unit-тест на этот сценарий (retry внутри одной сессии), живой
  прогон на проде на первой неделе для проверки правдоподобности цифр.
- **Риск:** индекс/запись события добавляют накладные расходы на
  `start-or-get-attempt` — эндпоинт на горячем пути учебного цикла.
  **Мера:** запись — один INSERT без доп. SELECT для дедупа (в отличие от
  `hint_open`/`help_requested`, дедуп здесь не смысловой, можно упростить до
  INSERT с `ON CONFLICT DO NOTHING` через уникальный индекс на короткое окно
  ИЛИ вовсе без дедупа на запись — дубли в пределах секунд не искажают
  «ближайшее событие перед сдачей», DISTINCT/MAX в CTE их поглощает бесплатно).
  Решение при реализации: **не делать advisory-lock/SELECT-дедуп** — просто
  INSERT, экономия одного round-trip на каждый вызов; MAX(created_at) в
  пейс-CTE делает точные дубли безвредными.
- **Риск (P3, не блокирует):** пороги `FAST_PACE_SECONDS`/`SLOW_PACE_SECONDS`,
  унаследованные для реального сигнала, — временное приближение, не строгий
  пересчёт. **Мера:** зафиксировано как осознанный fallback-путь (см.
  «Пороги и обратная совместимость» выше), follow-up задача заводится при
  закрытии.

## Критерии Go/No-Go

**Go**, если после шагов 1-4: полный `pytest` LMS зелёный, `EXPLAIN` пейс-CTE
не показывает full-scan `learning_events`, `/review-gate` — PASS, живая
проверка на проде (шаг 7) подтверждает запись события и ненулевой
`median_pace_seconds` из реального источника хотя бы для одной пары
открытие→сдача.

**No-Go / стоп-точка:** если живая проверка показывает, что
`start-or-get-attempt` в проде вызывается НЕ на каждое открытие (например,
клиентское кеширование attemptId переживает разные заходы дольше, чем
ожидается по чтению кода SPW) — тогда предпосылка «start-or-get-attempt ==
открытие» неверна для реальных пользователей, и решение о точке записи нужно
пересмотреть до продолжения (вернуться к обсуждению с оператором).

## Решение по UX-сложности

Не применимо в смысле нового UI — ученик ничего не замечает. Для методиста
разница видна только числом в `median_pace_seconds` — минимальное изменение,
плюс новое прозрачное поле `pace_source` в ответе API (не в UI SPW пока, это
не входит в объём этой задачи: экран `/methodist/topic-mastery` уже
существует и продолжит работать без изменений, поле для будущей отладки/
доверия к цифрам).
