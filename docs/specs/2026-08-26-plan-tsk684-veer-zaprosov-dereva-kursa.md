# tsk-684 — план: убрать веер запросов страницы дерева курса

**Дата.** 2026-08-26
**Задача.** `tsk-684` (P2, LMS + SPW)
**Скилл.** `/change-plan-architect`
**Правок кода в этом документе НЕТ** — только план. База не тронута (ни одного
запроса к боевой БД в ходе разбора).

---

## Целевая возможность

Открытие страницы курса в кабинете ученика перестаёт выдавать сотню запросов к
API. Экран показывает то же самое: названия заданий и материалов, ссылки на них,
значки состояния, проценты по разделам.

**Не-цели.**
- Не трогаем сам механизм обхода дерева на сервере (это `tsk-662`, сделано) и
  его остаток (`WITH RECURSIVE`, опора на сохранённую позицию).
- Не трогаем предел одновременности `courseTreeQueue` (`tsk-622`) — он остаётся
  сеткой безопасности для всего, что ещё ходит списками.
- Не меняем вид и порядок разделов на экране.
- Не занимаемся сводкой занятия (известный долг, 6,7 с на группу 13).

## Текущее состояние

### Откуда берётся веер

Единственный источник — `SPW lib/learning/use-course-syllabus.ts`, хуки
`useTasksForCourses` и `useMaterialsForCourses`. На каждый подкурс из ответа
`syllabus-states` уходит по два запроса:

| Запрос | Зачем он нужен клиенту |
|---|---|
| `GET /api/v1/tasks/by-course/{cid}?limit=500` | `external_uid` (ссылка на страницу задания), `task_content.title`, `task_content.type`, `task_content.stem` (запасное название, если своего нет) |
| `GET /api/v1/courses/{cid}/materials?is_active=true&limit=500` | `title`, `type` материала |

Больше ничего из этих ответов не используется: `buildTask` и `buildMaterial`
берут ровно перечисленные поля (`use-course-syllabus.ts:398–358`). Всё
остальное — состояния, попытки, баллы, обязательность, блокировки, названия и
глубина разделов — уже приходит одним запросом `syllabus-states`.

**То есть сотня запросов уходит за названиями.** Ради них браузер ученика
скачивает полное содержимое всех заданий курса: у флагмана это 361 задание с
формулировками и вариантами ответа плюс 94 материала.

Потребители хука — `components/course/CourseSyllabus.tsx` и
`components/course/CourseFeed.tsx`; ключи запросов у них общие, так что двойного
веера два компонента не дают.

## Варианты и выбор

| Вариант | Запросов на открытие | Оценка |
|---|---|---|
| **A. Обогатить `syllabus-states` названиями** | 110 → **0** дополнительных (всего 1 на дерево) | Поля лежат в тех же строках, что уже читает SQL: `t.external_uid`, `t.task_content->>'title'`, `t.task_content->>'type'` (тип уже читается), `m.title`, `m.type`. Ни одного нового обращения к базе. Трафик клиента падает: вместо полного содержимого 361 задания — короткие названия |
| B. Пакетный запрос `POST /tasks/by-courses` со списком ID | 110 → 2 | Новый контракт, новый ACL-разбор на список курсов, а веер за названиями остаётся веером — просто свёрнутым. Хуже A при большей цене |
| C. Подгрузка по раскрытию узла | 110 → ~2 на раскрытие | Не убирает работу, а размазывает её. Ломает две вещи, которые сейчас работают: проценты по разделам считаются по элементам (`aggregateProgress`), и `detectCurrentSection` ищет первый незавершённый элемент по всем разделам — оба требуют данных всего дерева сразу. Плюс лишний шаг для ученика (см. «Решение по UX-сложности») |

**Выбор — A.** B и C оставлены как запасные и в план не входят.

Отдельно и независимо от A — **проверить повторную выдачу веера при возврате в
вкладку.** `lib/query-client.ts` не задаёт `refetchOnWindowFocus`, а в React
Query 5 он включён по умолчанию; `staleTime` у запросов веера 30 секунд. По
коду выходит, что каждое возвращение на вкладку старше 30 секунд выдаёт веер
заново. Это **гипотеза, а не вывод**: подтверждать замером на живой странице, не
правкой кода вслепую. Если подтвердится — после A вопрос отпадает сам (веера
больше нет), но проверить стоит до правок: это объясняет, откуда 433 запроса на
адрес за четыре часа при `staleTime` в полминуты.

## Пробелы и недостающие ресурсы

1. **Запасное название задания.** Сейчас клиент строит его из `stem`
   (`makeTaskFallbackTitle` + `toPlainLabel`, `tsk-469`: у 480 активных заданий
   своего названия нет). Решение: сервер отдаёт `title` как есть (может быть
   `null`) **и** короткий `stem_preview` — сырой `stem`, обрезанный по длине.
   Чистку разметки оставить на клиенте: она общая с кабинетом методиста и уже
   покрыта тестами. Длину обрезки взять с запасом к нынешним 72 символам после
   чистки — предлагается 300 символов сырого текста; **точное число утвердить
   на замере**, чтобы чистка не съела всё до пустой строки.
   *Не блокирующий, но требует решения до кода.*
2. **`task_content->>'title'` — jsonb, не колонка** (`project_task_title_lives_
   in_task_content`). Оператор `->>` уже применяется в этом же SQL для `type`,
   риска нет; отдельного индекса не требуется — выборка и так идёт по
   `course_id`.
3. **Поле `is_active` у заданий.** Веер зовёт `by-course` БЕЗ фильтра
   активности, а `syllabus-states` отдаёт только активные. Расхождение сегодня
   безвредно (неактивные всё равно не рисуются), но после A исчезнет само —
   зафиксировать в отчёте, чтобы не искали потерянные строки.
4. **Регенерация контракта.** `docs/openapi.json` пересобирается pre-commit
   хуком LMS (`project_openapi_precommit_hook`), затем в SPW обновляется
   `lib/api-types.ts`. Порядок обязателен: без свежих типов правка SPW не
   соберётся.
5. **Порядок выката.** LMS раньше SPW. Поля аддитивные, поэтому старый SPW со
   свежим LMS работает без изменений, а новый SPW со старым LMS — нет.
   Обратный порядок — авария на экране курса.
6. **Мёртвый код.** `lib/learning/use-course-content.ts` (`useCourseTasks`,
   `useCourseMaterials`) не импортируется ниоткуда — у методиста свои хуки.
   Удалять **не в этой задаче**: отдельный чип, чтобы не смешивать удаление с
   правкой контракта.
7. **Замера «до» на живом проде нет** — числа из караула сняты по журналу
   обращений, а не с открытой страницы. Нужен собственный замер до правок,
   иначе «стало лучше» нечем доказать (`feedback_measure_before_naming_root_
   cause`).

**Блокирующих пробелов нет.**

методиста, где полное содержимое задания нужно по делу.

## Критерии Go/No-Go

**Go в фазу 1:** замер «до» снят, ответ по Д3 получен, длина `stem_preview`
утверждена.

**Go в фазу 3:** LMS выкачен, новые поля видны в живом ответе, старый SPW на
том же проде работает без ошибок.

**No-Go / стоп:**
- число обращений к базе на `syllabus-states` выросло;
- тело ответа выросло настолько, что время до отрисовки стало хуже;

## Решение по UX-сложности

Лишних экранов и шагов правка не добавляет: ученик открывает курс и сразу видит
дерево — как сейчас. Вариант C (подгрузка по раскрытию узла) отклонён в том
числе по этой оси: он требовал бы от ученика лишнего действия там, где сегодня
всё видно сразу, и ломал бы «текущий раздел» (он ищется по всем разделам).

Отдельно: наполнение по частям, за которое держались в `tsk-622`, после правки
теряет смысл — данных больше не 110 кусков, а один ответ. Проверить в фазе 4,
что ожидание не воспринимается как «ничего, ничего, всё сразу»: если ответ
`syllabus-states` окажется медленнее, чем прежнее постепенное наполнение, —
показывать скелет разделов из `sections` до готовности элементов. Помечено как
`justified` только при подтверждении замером.
