# Спека — tsk-433 Волна 2.1: правка материалов в кабинете методиста

> Скилл: `/spec-writer`. Дата: 2026-07-29. Задача: `tsk-433` (Root-трекер).
> Предшествует: Волна 1 (просмотр, на проде) + карточка материала (`51b4e85`).
> Решения оператора зафиксированы в §«Контекстные якоря».

---

## Цель

Дать методисту править материал прямо в кабинете так, чтобы правка **не исчезала
при следующей публикации из источника**.

## Контекстные якоря (решения оператора, обязательны к исполнению)

1. **Флаг «правлено вручную».** Правка через кабинет помечает материал; импорт
   такие поля не перезаписывает. Выбрано вместо «просто предупреждать» —
   предупреждение проблему не решает, правки продолжали бы теряться.
2. **Начинаем с материалов**, задания — следующим заходом. Причина: у материала
   контент — одно поле, у задания это вложенный JSON (`task_content` +
   `solution_rules`), риск сломать проверку ответов заметно выше.
3. **Материалы и задания равноправны** в просмотре и правке (указание от
   2026-07-29) — здесь закрывается половина про материалы.

## Границы

**Входит:**
- Правка полей материала: `title`, `content` (текст), `is_active`,
  `order_position`, `requirement_level`.
- Механизм «правлено вручную»: колонка-провенанс + защита в `bulk_upsert`.
- Эндпоинт правки, доступный браузеру по cookie под ролью методиста/админа.
- Возврат материала «к источнику» (снять пометку → следующий импорт обновит).

**Не входит:**
- Правка заданий (следующий заход Волны 2).
- Создание и удаление материалов; перенос между курсами (есть `move`/`copy`
  под сервисным ключом — отдельный вопрос).
- Правка структуры курса, дерева, зависимостей.
- Загрузка медиа, работа с файлами.
- Правка материалов типов `video`/`image`/`link` в части их источников —
  правим только текстовые поля и служебные атрибуты.

## Ограничения

- **Гейт.** `PUT/DELETE /materials/{id}` из generic CRUD (`app/api/v1/crud.py`)
  сидит на `Depends(get_db)` — принимает только `?api_key=` в query, браузеру
  недоступен. Правку придётся регистрировать в `materials_extra.py`, который
  подключается **раньше** CRUD и перекрывает маршрут (тем же приёмом, что
  Y-5.1 сделал для `GET /materials/{id}`).
- **Импорт перезаписывает контент безусловно.** `MaterialsService.bulk_upsert`
  (`app/services/materials_service.py:380-412`) кладёт в `payload_data` поля
  `title`, `content`, `description`, `caption` всегда; условная запись есть
  только у `is_active`, `order_position`, `requirement_level` (tsk-377/378/407).
- **Конвенция провенанса уже есть** — `tasks.difficulty_provenance` (jsonb,
  tsk-381). Новую колонку делать по этому образцу, а не изобретать свою форму.
- Прод-миграция — только через `/db-check` (протокол read → план → dry-run →
  транзакция → верификация).
- Cross-project: меняется поведение `POST /materials/bulk-upsert` →
  обязательное обновление `ContentBackbone/docs/cross-project/`.

## Форма провенанса

```json
{
  "source": "manual_web",
  "edited_at": "2026-07-29T18:40:00+00:00",
  "edited_by": 2,
  "fields": ["title", "content"]
}
```

Правило для `bulk_upsert` (по аналогии с tsk-381):
- `source = "manual_web"` → поля из `fields` **не перезаписываются**, остальные
  обновляются как раньше;
- провенанс отсутствует (NULL) → поведение прежнее, ничего не меняется;
- защищаем **по списку полей**, а не материал целиком: если методист поправил
  заголовок, обновление содержимого из источника всё ещё полезно.

## Критерии готовности

1. Методист правит заголовок материала в кабинете → изменение видно на странице
   и в `GET /materials/{id}`.
2. После правки повторный `POST /materials/bulk-upsert` с прежним содержимым из
   источника **не возвращает** старый заголовок; проверено тестом на реальном
   пути импорта, не только на моке сервиса.
3. Поля, которых методист не касался, импорт по-прежнему обновляет (тест: правим
   `title`, импорт меняет `content` → `content` обновился, `title` остался).
4. Материал без пометки ведёт себя ровно как до изменения (регресс tsk-378/407
   зелёный).
5. `PATCH /materials/{id}` под учеником → 403; без cookie → 401; под сервисным
   ключом → работает (совместимость с ботом).
6. В карточке материала виден признак «правлено вручную» с датой, и есть
   действие «вернуть к источнику», после которого импорт снова обновляет поле.
7. Живая проверка на проде: правка сохраняется, страница не ломается,
   тёмная тема цела — **подтверждено скриншотами, просмотренными глазами**.
8. `contracts/lms-api.md` и `CHANGELOG.md` в ContentBackbone обновлены в том же
   заходе.

## Риски

| Риск | Мера |
|---|---|
| Правка «залипнет»: источник обновит материал, а в LMS останется старое, и никто не заметит | Признак «правлено вручную» с датой видно в карточке; действие «вернуть к источнику» рядом. В отчёте по волне — список помеченных материалов |
| Методист вставит сломанный HTML и материал перестанет рендериться | На выводе уже стоит `SanitizedHTML` (DOMPurify). Дополнительно — не принимать `content`, у которого после санитайзинга пустой текст |
| Правка `content` у нетекстовых типов (video/image) сломает структуру jsonb | Правим только `content.text` и только для `type = "text"`; для остальных типов поле содержимого в форме недоступно |
| Конфликт с параллельной правкой из бота | Пока N методистов мал — принимаем. В `updated_at` видно время; полноценные блокировки — вне волны |
| Миграция на проде задевает 3000+ строк | Колонка nullable без дефолта — только метаданные таблицы, данные не переписываются. Через `/db-check` |
