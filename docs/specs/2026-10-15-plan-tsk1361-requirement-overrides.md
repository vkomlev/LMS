## 2. Инвентарь (по коду)

### Где задаётся
- `tasks.requirement_level`, `materials.requirement_level` (`required|recommended|skippable`, миграция tsk-111). `courses.is_required` — другая сущность (обязательность курса в зависимостях).
- `student_program_scope` (tsk-798) — хранимый план объёма, пишется **только при выдаче ДЗ** (`homework_service.issue` → `program_scope_service.store_scope`).
- Прощение нового (`content_grace_service`, tsk-692/1261/1294) — **не хранится**, считается на лету: 3 SQL + Python на (ученик, корень), кэш на одну сессию БД.
- Ручной пропуск учителем — статус SKIPPED (`/progress/tasks/{id}/skip`), уровень не меняет.

### Кто читает (Прощение / Объём)
| Потребитель | Прощение | Объём |
|---|---|---|
| next-item (`learning_engine._effective_*_rows`) | да, от корня | да |
| `compute_course_state` → замки, крон зависимостей | да, **от подкурса** (предки не видны) | да |
| числитель `compute_course_state` | **нет** (прощённое закрытое идёт в «сделано») | нет |

| программа курса ученика (`me_service.get_syllabus_states`) | да, отдаёт как `recommended` | **нет** |
| прогресс и дашборд учителя (`student_dashboard_service`) | да | **нет** |
| сводка урока (`teacher_lesson_summary_service`) | да, от `course_id` прогресса | **нет** |
| `manual_progress_service` (обход для ДЗ, ручной зачёт) | **нет** | нет |

| лента, уведомления, кроны отчётов | не читают | — |

Литерал «что обязательно» продублирован в 5+ модулях LMS и в SPW.

### Главные дефекты AS-IS
1. Две оси (прощение и объём) применяются в разных наборах потребителей → ученик и учитель видят «долг», которого движок уже не требует (это и есть жалоба оператора).
2. Причина нигде не хранится и не показывается; регрессию вроде tsk-1294 видно только по жалобе.
3. Ширина прощения разная (корень / подкурс) у разных потребителей.
4. План объёма устаревает без выдачи ДЗ.

## 3. Проект (TO-BE)

### 3.1 Модель: `student_requirement_override`
| Колонка | Смысл |
|---|---|
| `id` | |
| `student_id` | FK users |
| `target_kind` | `task` / `material` / `course` (узел — действует на поддерево) |
| `target_id` | |
| `level` | `required` / `recommended` / `skippable` |
| `reason_code` | `grace_new_content` (tsk-692), `grace_ahead` (tsk-1261), `program_trim` (tsk-798), `course_switch`, `teacher` |
| `reason_text` | человеческий текст для ученика/учителя |
| `source` | `rule` / `human` |
| `rule_version` | версия правила (для перепроверки при правке правила) |
| `created_by`, `created_at` | |
| `revoked_at`, `revoked_by` | мягкая отмена — история остаётся |

Уникальность: одна **активная** строка на (ученик, вид, цель) — частичный уникальный индекс `WHERE revoked_at IS NULL`. Индекс `(student_id) WHERE revoked_at IS NULL`.

Порядок: переопределение на элементе > на ближайшем узле-предке > уровень элемента в курсе. **Человек > правило**: правило никогда не перезаписывает и не отменяет строку `source=human`.

### 3.2 Правила пишут, а не вычисляют молча
- **tsk-692/1261/1294 (новизна):** тот же алгоритм `content_grace_service`, но запускается не в запросе, а (а) при создании/активации задания или материала — для зачисленных на дерево, (б) ночной сверкой. Результат — upsert/revoke строк `grace_*` с текстом причины. Чтение на лету убирается.
- **tsk-798 (объём):** `store_scope` пишет `program_trim` на выпавшие узлы-номера и отменяет их при возврате; пересчёт — при выдаче ДЗ и ночным кроном (закрывает дефект 4).
- **Смена курса (сценарий 3):** правило `course_switch` — см. вопрос оператору.

### 3.3 Единый источник
`requirement_resolver.effective_levels(db, student_id, root_ids)` → `{(kind,id): (level, reason)}` одним индексированным запросом. Его зовут все потребители из таблицы выше; `REQUIREMENT_LEVELS` — одна константа. API отдаёт `requirement_level` (уже персональный) + новое `requirement_reason {code, text, source}`. SPW перестаёт угадывать: показывает причину, счётчики берёт по полю.

### 3.4 Экраны
- Ученик: бейдж «Необязательно» + строка причины («вы прошли тему раньше, чем задание добавили», «не входит в вашу программу до экзамена»).
- Учитель: в сводке урока, прогрессе и ДЗ — причина рядом с элементом; кнопки «Сделать необязательным / обязательным» (пишут `source=human`), история изменений.

### 3.5 Миграция данных
1. Alembic: таблица + индексы (без данных).
2. Режим тени: правила пишут строки, потребители ещё читают старое; скрипт сверки «на лету vs таблица» по всем 140 ученикам — расхождение 0.
3. Переключение потребителей на резолвер (экраны — с `Hold-For-Operator`).
4. Удаление вычисления на лету.

### 3.6 Производительность (урок tsk-1250)
- Сейчас прощение — 3 запроса + Python на каждый (ученик, корень) в каждом запросе экрана. После — один запрос по индексу; тяжёлое уходит из пути запроса в события и ночной крон → нагрузка на пул падает.
- Крон и заполнение — пачками по ученику, каждое в своей короткой сессии, без держания соединения во время расчёта; ограничение параллельности 1.
- Событие «добавили задание» на большой курс → фоновая задача, не в запросе методиста.
