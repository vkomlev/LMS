# tsk-644 — выкат и проверка на проде: наряд для местного чипа

**Кому.** Чипу, который запускается на машине оператора (Windows, `D:\Work\LMS`),
где настроен SSH-алиас `lms-spw-vds`.

**Почему не сделал предыдущий чип.** Он работал в облачном контуре: `/opt/lms`
там нет, systemd нет, SSH-клиента нет и он не ставится, а на боевой хост
сетевой прокси отвечает `403 policy denial`. Ключи по замыслу живут на машине
оператора и на самом VPS — в репозитории их нет и быть не должно.

**Время.** 15–25 минут, из них ожидание выката ~2 минуты.

**Чего НЕ делать.** Ничего не чинить в коде без отдельного согласования. Все
проверки ниже, кроме шага 1, — только чтение. Денег задача не касается:
контрольная цифра августа (41 начисление на 179 284,70 ₽) сдвинуться не должна.

## Что уже сделано (переделывать не надо)

Разбор tsk-644 завершён, код в `main`.

- **Гипотеза задачи опровергнута замером.** Молчащая модель проверки кода приём
  ответа не держит: 600 живых запросов при полностью молчащем провайдере —
  худший 0,16 с.
- **Причина — молчащее файловое хранилище на пути приёма ответа.** Клиент S3
  работал на умолчаниях botocore (60 с соединение, 60 с чтение, повторы
  `legacy`). Одно чтение вложения держало приём ответа 310,8 с; живая сдача
  через API — 64,2 с и **отказ 503**, то есть работа не записывалась вовсе.
- Починено: таймауты хранилища, потолки ожидания на пути ученика, честный 503 с
  `Retry-After` вместо минуты тишины, фоновая оценка кода больше не держит
  транзакцию через вызовы модели.
- Заведена видимость: таблица `slow_request` + недельный чек `slow-requests`.

`origin/main` = `af489f0` (или новее). Артефакт ревью:
`reviews/2026-08-22-tsk644-slow-submit-diagnosis-review.md`.

**Что осталось недоказанным и ради чего этот наряд:** что хранилище болело
именно 18.08. Механизм доказан на стенде, совпадение с числами полное, но
боевого лога облачный контур не видел. Шаг 3 либо подтверждает версию, либо
опровергает — и второе не менее ценно.

## Шаг 3. Решающая улика: болело ли хранилище 18.08

**Логов на проде два, и нужен первый:**

- `/opt/lms/logs/app.log` — структурный лог приложения (**в нём и лежат нужные
  строки**), ротация 5 МБ × 5 копий;
- `/var/log/lms/app.log` — stdout процесса, перенаправленный systemd.

**Сначала проверить, что окно 18.08 вообще ещё не уехало в ротацию** — прошло
пять дней, а ротация по размеру:

```
ssh lms-spw-vds "ls -la /opt/lms/logs/"
ssh lms-spw-vds "head -c 400 /opt/lms/logs/app.log"
```

Если самая ранняя запись в `app.log` уже позже 18.08 — искать в `app.log.1` …
`app.log.5`. Если 18.08 нет нигде, так и записать: улика утрачена, версия
остаётся недоказанной (и это отдельный аргумент за то, что журнал наблюдения
нужен был в БД, а не в файле).

**Сам поиск** (по всем копиям сразу):

```
ssh lms-spw-vds "zgrep -c 'ошибка соединения с S3' /opt/lms/logs/app.log* 2>/dev/null; grep -c 'ошибка соединения с S3' /opt/lms/logs/app.log"
ssh lms-spw-vds "grep 'ошибка перечисления' /opt/lms/logs/app.log* | head -20"
ssh lms-spw-vds "grep 'slow request' /opt/lms/logs/app.log* | grep '2026-08-18' | head -30"
```

**Как читать результат:**

- Строки про S3 **есть** в окне 12:11–12:25 → версия tsk-644 подтверждена
  окончательно. Записать в задачу.
- Строк про S3 **нет вовсе**, а медленные запросы за 18.08 есть → **версия
  неверна**, и это надо честно записать. Тогда причину держало что-то третье, и
  следующий шаг — улавливатель на проде (`pg_stat_activity` + `py-spy`), как в
  разборе аварии 17.08 (tsk-621). Не додумывать, а ставить улавливатель.
- Лог за 18.08 не сохранился → так и написать, версия остаётся недоказанной.

## Шаг 4. Не потерялись ли работы учеников 18.08

Отказ 503 строки в базе не оставляет по определению, поэтому здесь — косвенные
улики (скрипт уже в репозитории, только чтение):

```
ssh lms-spw-vds "sudo -u app bash -lc 'cd /opt/lms && venv/bin/python scripts/audit_lost_submissions_tsk644.py'"
```

Скрипт сам возьмёт `DATABASE_URL` из прод-`.env` и напечатает: сколько ответов
записалось в окне, сколько попыток было открыто без единого ответа, и те же
числа за три соседних дня для сравнения фона.

**Как читать:** если «попыток без ответа» в окне заметно больше, чем в соседние
дни в те же минуты, — работы терялись. Если столько же, скорее всего нет.

## Шаг 5. Два числа, от которых зависит вывод про очередь (только чтение)

```
ssh lms-spw-vds "nproc; systemctl show lms -p ExecStart | head -c 300"
ssh lms-spw-vds "grep -n 'proxy_read_timeout\|client_max_body_size' /etc/nginx/sites-enabled/lms.conf"
```

**Ожидаемо:** `nproc` = 2, uvicorn **без** `--workers`, `proxy_read_timeout 60s`.

Из этих чисел собран вывод разбора: один процесс → один общий пул потоков на
`min(32, cpu+4)` = 6 работников, и при одновременной сдаче класса девятая-десятая
сдачи просто стоят в очереди. Если `nproc` окажется больше двух — пул шире,
очередь собиралась медленнее, и цифру в артефакте надо поправить.

`proxy_read_timeout 60s` важен отдельно: значит 18.08 ребёнок увидел **504 на
60-й секунде**, а не «ждал две минуты» — приложение дожёвывало запрос уже без
него. Если в конфиге другое число — поправить артефакт и тело задачи.

## Шаг 6. Завести недельный чек в планировщик

```
powershell -ExecutionPolicy Bypass -File scripts\install_weekly_checks.ps1 -Only slow-requests
```

Затем сразу прогнать вручную, чтобы убедиться, что он видит боевую базу:

```
python scripts/weekly_checks.py slow-requests
type logs\slow_requests_check.log
```

**Ожидаемо на свежей таблице:** «OK: за 7 дн. запросов дольше порога не было» —
таблица только что заведена и пуста. Это нормальный результат, а не поломка.
Через неделю в журнале появится первая осмысленная сводка.
