## Класс 1 — Граничные значения (Г5.3, off-by-one)

**Точка внедрения:** LMS, polygon-only роутер `app/api/v1/poligon/promo.py`
(новый код, см. `deploy/poligon/new-code/`), Pydantic-схема применения промокода.

**Механизм:** UI-подсказка на странице `/poligon-checkout` («промокод — до 12
символов») формально верна для отображения, но backend-схема объявляет
`code: str = Field(..., max_length=11)` — код длиной ровно 12 символов
отклоняется с 422, хотя интерфейс обещал, что 12 — это ещё допустимо.

**Как воспроизвести:**
1. Открыть `/poligon-checkout` на любом tier (dev/test/stage).
2. Ввести тестовый код длиной ровно 12 символов, например `WELCOME2026A`
   (не настоящий промокод из посева — используется только для проверки границы,
   поведение схемы не зависит от того, существует ли код в таблице
   `poligon_promo_codes`: валидация длины срабатывает раньше проверки на
   существование).
3. Ожидаемый (дефектный) результат: 422 `String should have at most 11 characters`.
4. Корректное поведение: код ≤12 символов должен пройти валидацию длины (и
   только затем получить ответ «код не найден», если его нет в таблице).

**Ожидаемый вердикт ученика:** баг-репорт класса «граничное значение»/off-by-one,
severity — Minor/Major в зависимости от того, реально ли существуют 12-символьные
промокоды в бизнес-практике (в посеве — нет, оба реальных кода короче, поэтому
дефект не блокирует штатный сценарий, но нарушает документированный контракт).

## Класс 2 — UI ≠ API (Г8.6) — ПОДТВЕРЖДЕНО уроком 6.4

**Источник:** урок 6.4 «Баг-репорт» разбирает построчно готовый пример:
«Промокод `SUMMER2026` не применяет скидку при оплате картой».

**Точка внедрения:** `app/api/v1/poligon/checkout.py`, функция оформления
заказа. Ветвление по `payment_method`:
- `payment_method == "wallet"` — скидка применяется корректно
  (`final_amount = base_price * (1 - discount_percent/100)`).
- `payment_method == "card"` — **дефект**: `final_amount = base_price`
  (скидка не учитывается), при этом ответ API всё равно возвращает
  `promo_applied: true` и `discount_percent: 15` (значения из применённого
  промокода) — UI рисует зачёркнутую старую цену + новую со скидкой, хотя
  фактически спишется полная цена.

**Как воспроизвести:**
1. `/poligon-checkout` → ввести `SUMMER2026` → применяется, скидка 15% видна
   в интерфейсе (зачёркнутая цена).
2. Выбрать способ оплаты «Картой» → «Оформить».
3. UI показывает сумму со скидкой в чеке/подтверждении, но `GET
   /poligon/orders/{id}` (или прямой запрос в Postman/Swagger к тому же
   эндпоинту) отдаёт `amount_charged` = полная цена без вычета.
4. Оплата через «Баланс» (wallet) — скидка применяется корректно, тот же
   промокод — расхождение проявляется только для card-ветки.

**Ожидаемый вердикт:** ровно эталонный баг-репорт из урока 6.4 — заголовок,
severity, шаги совпадают с уже опубликованным текстом.

## Класс 3 — API ≠ БД, «200, но записи нет» (Г9)

**Точка внедрения:** `app/api/v1/poligon/enroll.py`, эндпоинт записи на курс.

**Механизм:** обработчик коммитит транзакцию до попытки `INSERT` в
`poligon_enrollments` (или наоборот — `INSERT` обёрнут в `try/except
IntegrityError: pass` без re-raise и без отдельного commit), возвращает
`200 {"enrolled": true}` в обоих случаях. Реальная причина — гонка/пропущенный
`await conn.commit()` после INSERT в конкретной ветке (нужно закрепить именно
эту форму бага при кодировании — самая правдоподобная и самая частая в
реальных инцидентах, см. `docs/ai/PROJECT_MEMORY.md`
`project_lms_service_side_effects.md`: BaseService.create уже коммитит внутри
чужой транзакции в реальном LMS — семейство одного и того же класса ошибок).

**Как воспроизвести:**
1. Войти под `poligon-student-01`, открыть каталог, нажать «Записаться» на
   курс `poligon-basics`.
2. UI показывает «Вы записаны!» (200 OK).
3. Обновить страницу каталога — курс всё ещё показан как «не записан».
4. SQL-проверка (задание Г9): `SELECT * FROM poligon_enrollments WHERE
   user_id = <id> AND course_id = <id>` — 0 строк, хотя API отчитался успехом.

**Ожидаемый вердикт:** дефект расхождения API↔БД, критичный (ученик думает,
что записан, реального доступа к курсу нет).

## Класс 4 — Дефект сессии, «разлогинивает при обновлении» (Г3.5)

**Точка внедрения:** SPW, `lib/server/get-me.ts`, функция `getServerMe()`.

**Механизм:** в реальном (прод) коде запрос к `/api/v1/me` идёт с
`cache: "no-store"` (`get-me.ts:66`) — специально, чтобы Next.js никогда не
кэшировал ответ о текущем пользователе. В `poligon`-ветке этот параметр
убирается (или меняется на `cache: "force-cache"`). Next.js Data Cache тогда
кэширует ответ `fetch()` по умолчанию — после логина хардрефреш (F5) в
пределах окна кэша может отдать студенту РАНЕЕ закэшированный ответ (например,
`401`/`null`, полученный до входа, или ответ ДРУГОГО пользователя при
серверном рендеринге в общем процессе) — пользователь выглядит разлогиненным,
хотя cookie-сессия на сервере всё ещё валидна.

**Как воспроизвести:**
1. Зайти через `/poligon-login`, убедиться, что открыт личный кабинет.
2. Несколько раз подряд быстро обновить страницу (F5) — в некоторых прогонах
   (не всегда — суть бага именно в недетерминированности через кэш)
   отображается состояние «не авторизован» / редирект на `/poligon-login`.
3. Проверка через DevTools → Network: cookie `session` присутствует и валиден
   на всех запросах, но сервер-рендер иногда использует устаревший закэшированный
   `/api/v1/me`.

**Ожидаемый вердикт:** дефект класса «сессия теряется без реальной причины на
сервере» — важно, что это НЕ баг браузерного `sessionStorage` (SPW вообще не
хранит токен в JS-хранилищах, только httpOnly cookie) — типичная ошибка
новичка «предположить причину до проверки» здесь ловится напрямую (см.
[[project_yandex_answer_extraction]]-класс уроков «не гадать, а проверить»).

## Класс 5 — Вёрстка на средних экранах (Г7.2) — ПОДТВЕРЖДЕНО уроком 7.2

**Источник:** урок 7.2, «Пример на полигоне» — на **планшетной** ширине
карточки курсов в каталоге «наезжают друг на друга, частично перекрывая текст
соседних карточек».

**Точка внедрения:** SPW, компонент сетки каталога (`/poligon-catalog`, новый
код — `deploy/poligon/new-code/CatalogGrid.tsx`). Grid объявлен как
`grid-cols-3` без `md:`-переопределения (Tailwind) — на десктопе (≥1024px)
и мобильном (<640px, где браузер сворачивает grid в 1 колонку через явный
`max-md:grid-cols-1`) выглядит нормально, но в диапазоне планшета (768–1023px)
3 колонки физически не помещаются в контейнер без переполнения — карточки
частично перекрываются.

**Как воспроизвести:**
1. Открыть `/poligon-catalog` в DevTools responsive mode.
2. Установить ширину 800px (планшет).
3. Карточки курсов визуально наезжают друг на друга, текст обрезается/
   перекрывается.
4. На 375px (мобильный) и 1280px (десктоп) — вёрстка корректна.

**Ожидаемый вердикт:** дефект вёрстки/адаптивности, конкретная ширина и
точная формулировка совпадают с уроком 7.2.

## Класс 6 — Барьеры доступности (Г7.5) — ПОДТВЕРЖДЕНО уроком 7.5

**Источник:** урок 7.5, скриншот и разбор — форма регистрации, поле подписано
только плейсхолдером (не заменяет видимую подпись — плейсхолдер исчезает при
вводе, скринридер его не видит).

**Точка внедрения:** SPW, новая страница `/poligon-register`
(`deploy/poligon/new-code/PoligonRegisterPage.tsx`) — сознательно НЕ трогаем
реальную `app/(public)/auth/magic-link/request/page.tsx`, где `<Label
htmlFor="email">` уже корректно связан с `<Input id="email">` (проверено этой
сессией) — ломать существующий верно работающий код ради дефекта не нужно,
раз есть новая страница специально под этот тред.

**Механизм:** поле email/имя на `/poligon-register` использует только
`placeholder`, без `<Label>`/`aria-label`, без `htmlFor`/`id`-связи.

**Как воспроизвести:**
1. Открыть `/poligon-register`.
2. Осмотреть DOM (DevTools → Accessibility panel) — у полей нет
   Accessible Name, кроме плейсхолдера.
3. Начать вводить текст в поле — подпись (плейсхолдер) исчезает, никакой
   видимой замены не остаётся.
4. Скринридер (NVDA/VoiceOver) объявляет поле без названия или использует
   placeholder как fallback (не по стандарту, непредсказуемо).
5. Дополнительно (ловушка фокуса, тоже часть класса «барьеры доступности» из
   формулировки tsk-182): модальное окно подтверждения email на этой же
   странице не возвращает фокус в модалку при Tab с последнего элемента —
   фокус уходит в скрытый фон.

**Ожидаемый вердикт:** дефект accessibility, ровно два под-пункта из
формулировки tsk-182 («нет подписей полей, ловушка фокуса») в одном месте.

## Класс 8 (бонус, сверх обязательных 7) — Нарушение бизнес-правила «один раз на аккаунт» — ПОДТВЕРЖДЕНО уроком 6.7

**Источник:** урок 6.7 «Баг-трекеры» — «Промокод `STUDENT20` должен
применяться один раз на аккаунт, но при повторном вводе скидка срабатывает
снова», Severity: Major.

**Точка внедрения:** `app/api/v1/poligon/promo.py`, таблица
`poligon_promo_redemptions` — миграция создаёт её БЕЗ `UNIQUE (user_id,
promo_code)`. Эндпоинт `POST /poligon/promo/apply` не проверяет существующую
запись перед INSERT (или проверяет, но по неверному ключу — например, только
по `promo_code` глобально, не по паре с `user_id`).

**Как воспроизвести:**
1. Войти под любым тестовым студентом, применить `STUDENT20` на checkout —
   скидка 20% применена.
2. Повторно ввести `STUDENT20` (например, вернувшись на страницу и введя код
   заново) — скидка снова засчитывается (например, стакается или просто
   повторно отображается «применено»).
3. SQL-проверка: `SELECT COUNT(*) FROM poligon_promo_redemptions WHERE
   user_id = <id> AND promo_code = 'STUDENT20'` — 2+ строки вместо
   максимум 1.

**Ожидаемый вердикт:** ровно эталонный баг-репорт из урока 6.7.
