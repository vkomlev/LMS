# Полнота покрытия и двойная проверка плана

Источник истины для skill `methodist`. Подключается в Шаге 0. Защищает от
поверхностных планов: гейт полноты против инвентаря источника + самопроверка
«двумя глазами» (ученик / сеньор) перед выдачей.

## Часть 1: Гейт полноты против инвентаря источника

Для запроса уровня **курса / куррикулума** (а не одного модуля) план обязан
покрыть весь инвентарь курса, а не только «модуль по теме».

**Алгоритм (Шаг 0 / Шаг 2):**
1. Glob по `source-root` профиля курса (`course-profile.md`) — получить полный
   список файлов-материалов. Для флагмана это `docs/v2/*.md`, для курса
   CreateCourses — `courses/<slug>/materials/**/*.md`.
2. Для **каждого** файла зафиксировать решение: `включён в план` / `исключён`
   с причиной (например: «X3 = Трек 2+3, к Треку 1 не относится»).
3. Сверить результат с обязательным-по-стадии минимумом ниже. Пропуск
   обязательного = план не готов, доработать.
4. В артефакт включить раздел **«Карта покрытия источника»**: таблица файл →
   включён/исключён → где в плане / причина исключения.

### Обязательный минимум по стадии

**Общий инвариант (любой курс).** Для стадии `новичок` не срезаются ради
компактности: вводный онбординг («как проходить курс», что получится на выходе),
базовые понятия / глоссарий темы в начале, фундамент предметной области целиком
(не «сжатый обзор»), техника безопасности и правила работы с инструментом (если
тема их предполагает), бесплатные/доступные альтернативы платных инструментов
(cost-блокер). Для `с-базой` эти же блоки идут ускоренно, для `уверенного` — по
запросу, но не исчезают из карты покрытия молча: исключение фиксируется с причиной.

**Надстройка профиля** — конкретные обязательные файлы курса. Ниже — пример
надстройки профиля флагмана (`IT_Businessman`); к другим курсам она не
применяется, у них свой список из их `source-root`.

| Материал (тип), профиль флагмана | новичок | с-базой | уверенный |
|---|---|---|---|
| Онбординг: манифест, карта экосистемы, квиз, «как проходить» | обязательно | обязательно | кратко |
| Базовые понятия / глоссарий (`F-Глоссарий`) | **обязательно, в начале** | обзорно | по запросу |
| Полный Фундамент Claude (все `F-Claude*` файлы) — отдельная фаза, не сжимать | **обязательно** | ускоренно | ускоренно |
| Техбаза (Ф0–Ф6) | по необходимости, глоссарий первым | опционально | пропуск |
| Бесплатные альтернативы (`F-Бесплатные-альтернативы`) | **обязательно** (cost-блокер) | обязательно | обязательно |
| Безопасность (`F-Безопасность`) | обязательно | обязательно | обязательно |
| Промпт-библиотека (`F-Промпт-библиотека`) | как опора в каждом паттерне | да | да |
| Кросс-трековые модули (`X1*`, `X2*` с участием Трека 1) | показать как мост (опционально) | предложить | предложить |
| Расходы/оптимизация Claude (`F-Claude-расходы*`) | обязательно | обязательно | обязательно |

**Принцип для новичка:** ни «базовые понятия», ни «бесплатные альтернативы», ни
полный фундамент НЕ срезаются ради компактности. Срез фундамента для нулевого
ученика = блокер прохождения, не оптимизация.

**Смежные модули:** материалы источника, относящиеся к соседним трекам/курсам
(у флагмана — `X*`-файлы с участием Трека 1), минимум упомянуть как мост в финале;
не выкидывать молча.

### Часть 1a: Курируемая выборка `courses` ContentAnalyzer — НАВОДКА, не источник текста

Опциональный дополнительный вход (Шаг 0 п.11, tsk-207). В обязательный гейт Шага 0
**не входит**: нет находки по теме или оператор пропускает шаг — работать как обычно,
только по источнику курса.

Если у модуля есть тематическая привязка к теме из потока ContentAnalyzer — предложить
оператору посмотреть курируемую выборку:

```
cd D:\Work\ContentAnalyzer && python -m content_analyzer.curate --bucket courses --topic "<ключевые слова>" [--days N]
```

Это **дополнительный** вход наряду с источником курса, не замена инвентарю (Часть 1)
и не источник правды: план строится по-прежнему из источника, находка полностью
переформулируется своими словами (голос и методика курса не наследуются из чужого
текста). Две роли находки:
- **Сверка покрытия:** находка показывает, что тема уже полно закрыта существующим
  планом модуля → явно отметить это в интервью/плане, не игнорировать молча.
- **Материал для заданий:** находка, годная как реальный кейс/пример → предлагать
  оператору как основу практического задания (Шаг 3), не только как пункт содержания
  урока.

Второй опциональный вход того же происхождения — `content-analyzer-findings.md`
(курируемые внешние находки по педагогике/методике, tsk-207/208): просматривать, если
существует и релевантен теме.

## Часть 2: Двойная проверка (гейт перед верификацией)

После черновика плана/заданий — прогнать **двумя взглядами**. Это обязательный
шаг, не опция. Любой ответ «нет/не уверен» = доработать до повторного прохода.

### Глазами ученика (целевая ЦА × стадия)

Поставить себя на место конкретной стадии (для новичка — 0–1 год, без
коммерческого опыта) и честно ответить:

**Механическая трассировка предпосылок (обязательная процедура, не «на глаз»):**
Для **каждого** шага S:
1. Выписать список понятий / терминов / инструментов, без которых S не выполнить
   (например, для «посчитать токены и стоимость API» это: токен(AI), модель,
   Claude API, промпт).
2. Для каждого пункта списка найти **более ранний** шаг, где он **явно разобран**
   (учебный/глоссарный шаг, стоящий по порядку ДО S).
3. Если хоть один требуемый пункт разбирается **позже S**, **параллельно S** или
   формулировкой «по мере встречи / по необходимости» — это **дефект порядка**.
   Переставить разбор понятия в шаг строго до S. «Параллельно» и «по ходу» не
   считается «разобрано раньше».

> Инвариант: служебный/инфраструктурный шаг (счёт токенов, калькулятор расходов,
> запрос к API, деплой) НЕ может идти раньше шага, где явно разобраны понятия,
> которые он использует. Базовые понятия — раньше инструмента, который их требует.

**Реюз-узлы (second-parent) — трассировка распространяется и на них (повтор-дефект,
курс kolledzh-informatika-bpla, tsk-956).** Трассировка предпосылок выше обычно
применяется к «шагам плана», а подключаемый через второго родителя узел (§3.6
assignment-rules — тот же механизм графа) при этом идёт одним шагом — его ВНУТРЕННИЕ
мостики «Вспомни: …» и `requires` в трассировку не попадают. Итог: методист расставляет
порядок реюз-узлов по СВОЕМУ плану (например, ради срочной темы), а подключаемый узел
открывается «на прошлом уроке мы…» ссылкой на другой реюз-узел, который в СОБРАННОМ
порядке идёт ПОСЛЕ него. Правило: для каждого подключаемого узла — прочитать его
собственный callout «Вспомни» и `requires`; узел ставится строго ПОСЛЕ того, на что он
ссылается, в порядке, в котором ученик реально их пройдёт, либо ссылка узла
снимается/переадресуется при подключении.

**Реюз-узлы — нагрузка недели считается по собранному дереву (повтор-дефект, тот же
курс).** Готовый узел, подключённый вторым родителем, приносит СВОИ задания целиком —
занятие из двух подключённых узлов легко превышает бюджет недели (10-13 заданий), даже
если план честно пишет «преподаватель назначает минимум N» устной договорённостью: у
LMS нет механизма «минимум», ученик видит полный банк как обязательный. При проектировании
карты занятий с реюзом — явная строка «задач в неделю по собранному дереву», сверенная с
бюджетом формата (Часть 3 `difficulty-and-design.md` п.6); два готовых узла на одну неделю
допустимы только если их сумма ≤ бюджет, иначе второй — в резерв или отдельный облегчённый
лист.

- [ ] Механическая трассировка пройдена: ни одного понятия, требуемого шагом,
      не разобрано позже/параллельно этого шага
- [ ] Я физически смогу выполнить **каждый** шаг с теми предпосылками, что уже
      даны ранее в плане? (нет скрытого «и тут просто сделай X», где X не учили)
- [ ] Нет ли скачка сложности между соседними шагами (перегруз)?
- [ ] Нет ли шагов слишком тривиальных для заявленной стадии (недогруз, скука)?
- [ ] Хватает ли заложенного времени реально, а не по оптимистичной оценке?
- [ ] Понятно ли, что именно я предъявляю на каждом шаге (критерий не размыт)?
- [ ] Если я застряну — план говорит, куда идти (опора, цепочка AI-наставника)?

### Глазами сеньора по теме

Поставить себя на место практикующего эксперта именно по этой теме (не общего
методиста) и проверить:

- [ ] Прогрессия логически последовательна, без дыр (каждый шаг следует из
      предыдущего, ничего не «телепортируется»)?
- [ ] Все ключевые вопросы темы закрыты (нет «а про это забыли»)?
- [ ] Дан **полный набор инструментов/материалов** под цель — ничего
      обязательного не выпало (инструмент, понятие, источник)?
- [ ] Нет поверхностности: каждый учебный результат подкреплён конкретным
      файлом источника курса, а не общими словами?
- [ ] Порядок тем соответствует тому, как это осваивают на практике, а не
      «как удобно записать»?
- [ ] Нет ли устаревших/неактуальных для текущего стека вещей?

### Линза освоения (mastery) — финальная, по ЗАДАНИЯМ темы

После двух взглядов — последний проход именно по ЗАДАНИЯМ темы (не по плану).
Цель скилла — чтобы ученик НАУЧИЛСЯ ДЕЛАТЬ тему сам, а не чтобы тема была
формально «покрыта материалом».

- [ ] **Сможет ли ученик САМ сделать эту тему после ЭТИХ заданий** (а не просто
      прочитать материал)?
- [ ] **Каждый ли изученный приём/метод он где-то применил руками** (срезы,
      `count`/`find`/`replace` и т.п. не остались «только в материале»)? Сверить с
      гейтом покрытия приёмов (assignment-rules §3.4).
- [ ] **Хватает ли объёма и РАЗНООБРАЗИЯ** (не 3 однотипных задания на
      содержательную тему; микс типов — assignment-rules §8 п.8)?
- [ ] **Рост по профилю ЦА** (difficulty-and-design, «Профиль прогрессии»): объём и
      сложность заданий растут от старта к финалу в коридоре профиля; для не-детской
      ЦА к концу есть многострочные программы и ≥ требуемого числа проектных
      (assignment-rules §3.5)? «Детский» одношаговый формат весь курс при
      предвузовской/взрослой ЦА = брак.

Любой «нет» = задания дают узнавание, а не умение → доработать задания (не план),
не выдавать.

### Анти-поверхностность (общий критерий)

- [ ] Каждый пункт плана трассируется к источнику (файл `source-root` в `docs-refs`).
- [ ] Нет формулировок-заглушек («разобрать основы», «познакомиться с темой»)
      без конкретного результата-действия и источника.
- [ ] Глубина соответствует заявленному уровню детализации (карта-план — связи и
      результаты; модуль — задания с критериями).
- [ ] **Конверт урока** (difficulty-and-design Часть 3 п.7): у КАЖДОГО урока цель-действие
      на входе («после урока сможешь …») и итог на выходе («Итог: …»); для спиральных —
      мостик «Вспомни: …»; первый программирующий урок — подсказка запуска. Урок без
      цели/итога = незавершён.
- [ ] **Визуал на абстрактной теме:** темы без наглядного объекта (логика/таблицы
      истинности, системы счисления, структуры данных, алгоритмы, функции) помечены как
      требующие ASCII-схему ВНУТРИ материала, не только обложку (см. SKILL «Визуалы»).
      Абстрактная тема с одной обложкой = визуальный голод, брак.
- [ ] **Исполнимость (гейт, повтор-дефект: курс ЕГЭ информатика, блок «Задание 23»,
      грейд F до правки).** Если хоть одно задание темы требует от ученика написать и
      ЗАПУСТИТЬ свою программу по приложенному файлу — у темы обязан быть урок-заготовка:
      где взять файл, куда его положить, целая программа от открытия файла до печати
      ответа, признак успеха, разбор типовой ошибки («файл не найден»). Понятность текста
      (проверяют остальные пункты этого чек-листа) не гарантирует исполнимость на машине
      ученика — это отдельная проверка (родственная W9 `/naive-learner-review`, К3
      `/expert-course-review`). Смежное правило: имя файла в примере кода совпадает с
      реальным именем вложения задания (расхождение `23.txt` vs `23_s1.txt`/`demo_23.txt` —
      находка того же прецедента).

**Вывод двойной проверки** включить в Контракт результата отдельным полем:
что проверено, что переделано после прохода, остаточные риски.

## Часть 3: Ретрофит корпуса при изменении структуры курса (ОБЯЗАТЕЛЬНО)

Курсы CreateCourses пишутся и публикуются волнами, часто не по номерному порядку глав.
Каждое из событий ниже уже роняло опубликованный курс — раньше фикс закрывал ОДНО найденное
место точечно, класс рецидивировал в других местах того же корпуса. Проверять корпус-вайд
(grep по всем уже опубликованным урокам), не полагаться на память о конкретном прошлом
инциденте.

**Событие: появилась новая глава (публикация очередной волны).**
1. Прогнозные фразы устаревают молча. Grep по всему корпусу уроков курса на паттерны
   «ещё не написан*», «не опубликован*», «пока нет подробностей» и т.п. — такая фраза
   в конце предыдущей главы была правдой в момент авторинга и стала ложью, как только
   появилась глава, о которой она говорит (повтор-дефект: одна и та же фраза дожила до
   3 разных уроков курса ruchnoe-testirovanie после того, как её уже один раз находили
   и чинили точечно).
2. `total` у всех УЖЕ существующих `topic_nav` пересчитывается и republish-ится заново —
   правило действует одинаково и для вставки главы В СЕРЕДИНУ, и для добавления В КОНЕЦ.
   Добавление в конец интуитивно кажется «не затрагивающим предыдущие главы» (index/
   prev/next действительно не меняются), но `total` («Раздел N из M») меняется у ВСЕХ
   уже опубликованных глав в обоих случаях одинаково.

**Событие: глава дописывается ПОЗЖЕ по времени, чем главы с большим номером
(авторинг вне номерного порядка).**
3. Grep по всему корпусу на паттерн «в главе про <X> мы (уже|вы уже)…» / «который вы
   (оформляли|разбирали|видели)…» — сверить номер главы X с номером текущей главы и с
   `course_dependencies`. Если X физически недостижима ДО текущей главы по порядку
   прохождения — это ложная форвард-ссылка (автор в момент письма УЖЕ знал контент
   главы X, потому что писал её раньше по времени, и спутал «уже написано мной» с
   «уже пройдено учеником»).

**Событие: правка формулировки/термина/названия элемента интерфейса в одном месте.**
4. Найдя расхождение (термин, название кнопки, формулировка) — грепнуть ВЕСЬ курс по
   исправляемой строке и починить все вхождения разом, не только то место, где нашли
   (повтор-дефект: название кнопки поправили в разделе 1, тот же дефект остался в
   разделе 5 того же курса).

**Согласованность вердиктов по одному и тому же объекту (расширение сквозной проверки
определений выше).** Проверка «термин не противоречит термину» не покрывает случай, когда
курс даёт РАЗНЫЕ вердикты по ОДНОМУ И ТОМУ ЖЕ конкретному примеру/объекту в разных местах
(не омонимия слова — расхождение оценки): интуитивная формулировка вводится ДО термина/
модели, формальная оценка — ПОСЛЕ, без явной фразы-мостика между ними. При финальной
сборке — сверить: там, где курс возвращается к одному и тому же примеру дважды, вердикт
совпадает или расхождение явно объяснено фразой-мостиком («на первый взгляд казалось X,
но по модели/термину — Y»).
