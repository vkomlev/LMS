# Правила создания заданий (LMS-адаптированные)

Источник истины для skill `methodist` по заданиям. Подключается в Шаге 0,
применяется в Шаге 3. Вынесен отдельным файлом — переиспользуется при разных
режимах генерации. Все коды/сложности сверены с `d:\Work\LMS` (см.
`lms-wp-export.md`). НИЧЕГО не выдумывать сверх enum LMS.

## 1. Типы заданий (строго enum LMS)

Допустимы **только**: `SC`, `MC`, `SA`, `SA_COM`, `TA`. Кода `COM` не
существует — это `SA_COM`.

| Код | Что | Когда применять | Проверка |
|---|---|---|---|
| `SC` | Single Choice — 1 верный вариант | факт/выбор/различение понятий | авто |
| `MC` | Multiple Choice — неск. верных | «выбери всё, что верно», классификация | авто (partial) |
| `SA` | Short Answer — короткий ответ | термин, значение, имя функции, результат запуска | авто (accepted_answers) |
| `SA_COM` | Авто-ответ (SA) + проверка качества (COM) | **задачи с кодом/решением**: авто-чек правильности + ручная/ИИ оценка качества по рубрике | авто + ручная/ИИ |
| `TA` | Text Answer — развёрнутый, рубрика | **только крупные проектные / защита** | ручная по `rubric` |

**Правильная семантика `SA_COM`** (см. § 7, критично): это НЕ «короткий ответ +
сочинение почему». Это **двухфазная проверка задач с кодом/решением**: сначала
быстрый авто-чек верного результата (SA: тест прошёл / ответ совпал), затем
препод или ИИ оценивает **качество решения/кода** (COM) по рубрике.

**Приоритет типов:** быстрые авто-проверки `SC`/`MC`/`SA` — основная масса
(мгновенная обратная связь, ноль трения). `SA_COM` — для практических задач
**с кодом/решением** (есть и авто-результат, и артефакт для качественной
оценки). `TA` — только крупные проектные/защита.

**Анти-школьность (жёстко):** «напиши словами, почему так» как массовый формат
ЗАПРЕЩЁН — обилие текстовых «сочинений» убивает вовлечённость, ученики
сливаются. Понимание проверять **через действие** (§ 8), не через эссе.

**`MC` с `all_or_nothing` завышает сложность формата, не темы (повтор-дефект, прод-замер
LMS-онбординга, tsk-773/899-контур).** Замер по всему блоку (не выборка): MC-задания
(«отметь всё, что верно», без частичного зачёта) провалены при первой попытке в 90,9%
случаев против 32,4% у SC и 41,7% у SA на том же материале — разброс в 2,8 раза при
корректном содержании и формулировках. Причина не в теме: `all_or_nothing` наказывает
одну забытую/лишнюю галочку так же, как полное непонимание. Правило: `MC` с
`all_or_nothing` использовать только там, где верных вариантов не больше 2 и общий список
короткий (≤4); шире — предпочитать `SC` или несколько `SC` подряд вместо одного `MC` на
5+ пунктов. Если платформа поддерживает `partial` scoring для MC — порог смягчается,
проверить перед проектированием узла с MC-заданиями.

## 2. Сложность → справочник LMS `difficulties`

Маппинг бакетов методиста на коды LMS (фиксированный):

| Бакет (методист) | LMS `difficulty` (uid/code) | weight |
|---|---|---|
| Базовая (recall, чистое воспроизведение) | `theory` / `THEORY` | 1 |
| Базовая (применение по образцу) | `easy` / `EASY` | 2 |
| Повышенная / средняя | `normal` / `NORMAL` | 3 |
| Сложная | `hard` / `HARD` | 4 |
| Проектная | `project` / `PROJECT` | 5 |

Соответствие Блуму: THEORY/EASY ≈ L1–L3, NORMAL ≈ L4, HARD ≈ L5, PROJECT ≈ L6.

## 3. Количество и микс заданий по узлам LMS

LMS не имеет отдельной сущности «подкурс/лист» — это узлы графа `Courses`
(см. lms-wp-export.md). Правила по позиции узла:

**Сначала классифицировать узел ПО СОДЕРЖАНИЮ, не по форме графа.** Тема, на
которой ученик ОСВАИВАЕТ навык (числа, строки, условия, циклы — несколько
приёмов/методов внутри), — это **подкурс 1-го уровня (§3.2)**, даже если в графе
она пока без детей. «Лист» (§3.1, ровно 3) — только узкая подтема с одним
приёмом/фактом, не несущая самостоятельного навыка. Сомнение «лист или подкурс?»
→ решать в пользу подкурса (§3.2). **3 задания на содержательную тему = недодача,
брак** (ученик не научится делать тему с 3 однотипных заданий).

### 3.1. Узел-лист (узкая подтема, один приём/факт)
**Ровно 3 задания** в порядке возрастания сложности:
1. базовое (EASY, при чистом recall — THEORY)
2. повышенное/среднее (NORMAL)
3. сложное (HARD)
Типы: преимущественно `SA_COM` / `SC` / `MC`.

### 3.1a. Урок-тема школьного курса (решение оператора, курс «Информатика 5-11»)
Школьный урок — это **содержательная тема**, а не узкая подтема: ученик осваивает
понятия и должен уметь их применять. Норматив: **10 заданий на урок** — не просто числа,
а роли: **6 простых** на узнавание и прямое применение, **3 средних** на перенос и
комбинирование, **1 проектное** (или мини-практика; `PROJECT`, авто-проектное — `SA_COM`).
Десятое, проектное, задание урока по умолчанию **авто-проверяемое** — многошаговая
задача с вычисляемым результатом (`SA_COM`/`HARD`). Развёрнутый ответ (`TA`) десятым
заданием урока **не ставится по умолчанию**: он допускается только как итог главы или
курса и подчиняется гейту частоты §3.5a.
Три задания на урок — недодача (узнавание вместо умения), §3.1 сюда не применять.
**Меньше 10 допустимо только для очень короткого урока и только с явным обоснованием.**
Считать по каждому урок-узлу, не в среднем по главе. Проверка — `expert-course-review`
рубрика К4.

**Перенос: объекты вне материалов — норма, а не брак.** В заданиях НУЖНЫ варианты и
объекты, которых в материале не было: ученик обобщает признак понятия и применяет его
к новому объекту (тачскрин, новое устройство, незнакомый файл). Условие одно: **признак,
по которому объект относят к понятию, в материалах дан**. Задание только из объектов
материала проверяет память, не умение. Ревьюеру это не флагать (см. К5).

**Минимум SA/SA_COM среди 6 простых (tsk-176, повтор-дефект).** Из 6 простых заданий
минимум **2 — типа `SA`/`SA_COM`** (впиши ответ), не только `SC`/`MC` (выбор из
вариантов). Причина: банк 10 заданий/урок, целиком собранный из `SC`/`MC`, формально
проходит норматив 6+3+1, но по факту — 9 заданий узнавания-с-подсказкой-варианта и один
изолированный `TA`-проект; ученик ни разу не воспроизводит термин самостоятельно до
проектного уровня. Найдено дубль-треком (Claude+Codex) на курсе «Информатика 5-11»
класс 5 после волны 5C1 — 7 из 16 уроков имели 0 заданий SA/SA_COM. Проверка —
`expert-course-review` К5.

### 3.2. Подкурс первого уровня (прямой ребёнок курса; напр. «Фаза 0», «Фаза 1»)
**10–15 заданий**, микс по сложности:
- **базовая 70%** → EASY (чистый recall → THEORY)
- **повышенная/средняя 25%** → NORMAL
- **сложная 5%** → HARD
Плюс **2–3 варианта проектного задания** (difficulty `PROJECT`; авто-проектное —
тип `SA_COM`, не `TA`, см. §3.5).

Округление: при 10 заданиях ≈ 7 базовых / 2–3 средних / 0–1 сложное (минимум
1 сложное, если узел не вводный); при 15 ≈ 10–11 / 4 / 1.

**Микс зависит от профиля прогрессии ЦА** (difficulty-and-design, «Профиль
прогрессии»). 70/25/5 — базовый ориентир для детского/подросткового профиля. Для
**предвузовского / взрослого** профиля к финальным узлам курса доля NORMAL/HARD и
проектных РАСТЁТ за счёт базовых (низкий вход → крутой подъём): в финальных подкурсах
допустимо ~50/35/15 + ≥2 проектных. Брак — держать 70/25/5 одношаговых заданий весь
курс там, где профиль требует выхода на многострочные программы.

### 3.3. Распределение по листам внутри подкурса
Сначала по 3 задания на каждый лист (3.1), затем добор до 10–15 на уровне
подкурса так, чтобы суммарный микс соблюдал 70/25/5 + 2–3 проектных.

### 3.4. Гейт глубины практики и покрытия приёмов (ОБЯЗАТЕЛЬНО)
Цель скилла — чтобы ученик **НАУЧИЛСЯ ДЕЛАТЬ тему сам**, а не чтобы тема была
формально «покрыта материалом». Перед сдачей заданий темы пройти три проверки:

1. **Покрытие приёмов.** Выписать КАЖДЫЙ приём / понятие / метод из материала темы
   (для строк это, в т.ч., общие срезы + распространённые `count`/`find`/`replace`/
   `upper`/`lower`/`split`). Каждый приём → **≥1 задание, где ученик его ПРИМЕНЯЕТ
   руками** (не «прочитал в материале»). Приём изложен в материале, но нигде не
   применён = дыра, добавить задание. (Повтор-дефект: про срезы строк рассказали —
   ученик срезы ни разу не использовал.)
   **«Применяет» ≠ «предсказывает» (повтор-дефект, курс «Excel», тема «Основы
   VBA»).** Тип (а) «предскажи вывод данного кода» (§7 п.7) НЕ закрывает этот пункт
   ни для одного приёма программирующей темы — это чтение чужого кода, а не умение
   писать свой. Пункт 1 считается выполненным для приёма только заданием буквы
   б/б2/в/г (§7 п.7: написать код приёмом / дописать пропущенное / исправить ошибку /
   применить в новой формулировке). Если у темы **все** задания — тип (а) или чистый
   факт-вопрос (SC/MC на определение), гейт провален целиком, даже если чек-лист §6
   формально отмечен галочкой — самоотметка «применено» без хотя бы одного б/б2/в/г
   в теме недостоверна.
2. **Не недодавать распространённые приёмы темы.** Если в материале темы пропущен
   общеупотребимый приём (для строк — `count`/`find`/`replace`), сперва **дополнить
   материал**, затем дать на него задание. Тема без своих ходовых приёмов = неполная.
3. **Достаточный объём РАЗНООБРАЗНЫХ заданий** (ориентир §3.2: 10–15 + 2–3
   проектных), микс типов практики по §8 п.8 — не 3 однотипных «предскажи вывод».
4. **Обратная трассировка «задание → материал» (ОБЯЗАТЕЛЬНО, повтор-дефект: курс
   «Excel», тема «Основы VBA» — задание про `Array()`/`ReDim Preserve`/`Split`, ни
   один из трёх фактов в материале темы не объяснён).** Для КАЖДОГО задания темы —
   факт/приём/синтаксис, который оно проверяет, найти **дословно или явным перефразом
   в тексте материала ЭТОЙ ЖЕ темы** (не «это общеизвестно», не ссылка на другую
   тему без явного мостика). Не нашли → либо добавить объяснение в материал, либо
   заменить/убрать задание. Проверка идёт в обе стороны с п.1: п.1 — от приёма
   материала к заданию, п.4 — от задания обратно к материалу; выполнение одной не
   гарантирует другую.
5. **Конверсия SA_COM→SA не должна опустошать тип б/б2/в/г.** Если проектное
   `SA_COM` переводится в `SA` (трассировка) из-за находки по К5 «автопроверка не
   доказывает, что ученик написал код» — после конверсии заново пройти пункт 1 по
   ВСЕЙ теме: если в теме не осталось ни одного задания буквы б/б2/в/г, чинить
   K5-находку конверсией нельзя, это создаёт новую K4-дыру взамен старой. Вариант —
   отдельный WP-only проект с ручной/чек-лист проверкой (не в LMS-автопроверку).
6. **Трассировка по массиву/коллекции/структуре не повторяет данные уже показанного
   обучающего примера (повтор-дефект, курс Excel, тема 5.7 «Массивы и коллекции»).**
   Если материал темы уже показал конкретный код-пример с явным результатом (в
   комментарии, тексте или ASCII) — проверочное задание на тот же приём обязано
   использовать ДРУГИЕ данные: другой набор значений или другое количество элементов,
   не тот же пример с тем же входом. Иначе задание не проверяет вычисление — ученик
   вспоминает число, увиденное абзацем выше, и это не ловится content-lint'ом
   `answer-in-stem` (тот сверяет ответ ЗАДАНИЯ с его же `stem`/`context`, а утечка
   здесь — из ДРУГОГО блока документа, обучающего материала).

Любой «нет» → доработать, не выдавать.

### 3.4a. Код-блок задания и подсказка (дубль-трек Claude+Codex, курс «Python-подростки»)
Два инварианта авторинга задания — проверять по КАЖДОМУ заданию:

1. **Код-блок в `stem` = код ИМЕННО этого вопроса.** Если задание показывает
   «Исходный код…», этот код должен соответствовать формулировке и вариантам:
   та же конструкция, те же имена переменных, те же числа, и упомянутые в вопросе
   команды физически присутствуют в коде. Нельзя переиспользовать один пример-код
   как шаблон для разных вопросов. Провал-класс: код `while x<3` под вопросом про
   `for i in range(3)`; код без `break` под вопросом «что делает `break`»; переменная
   `x` в коде vs `ochki` в вопросе. Вопрос теоретический (код не нужен) — код-блок не
   вставлять. Гейт: прочитать `stem` целиком и сверить код ↔ вопрос ↔ варианты.

2. **Подсказка даёт ХОД рассуждения, не готовый ответ.** `hint` не должен содержать
   эталонный `answer` — ни дословно, ни как «Шаблон: `<готовый код>`», ни вычислять
   финальное число. Для код-задания — назвать метод и его сигнатуру БЕЗ аргументов
   задачи (`.replace(что, на_что)`, не `.replace("о","0")`); для числового — наводящий
   вопрос, не подстановку («сколько чисел в `range(7)` и с какого начинается?», не
   «`range(7)` = 7 чисел, столько раз повторится»). Программный флаг слива:
   `position(accepted_answer в hint) > 0` → переписать. Провал-класс: 13/64 SA-подсказок
   курса содержали точный ответ через «Шаблон:».

3. **Формула/оператор решения — в `hints_text`, НЕ в `stem` (tsk-343, курс «Числа»).**
   Курс формирует ДВА разных навыка: (1) алгоритмическое мышление — самому перевести
   словесную задачу в шаги решения; (2) записать готовый алгоритм на Python. Если
   формула или конкретный оператор/метод для решения (`% 10`, `int(X*10)%10`,
   `d // 400`, готовая расписанная формула с подстановками) стоит в `stem` —
   он виден ученику ДО попытки безусловно, значит первый навык (алгоритмическое
   мышление) вообще не тренируется: ученик просто транскрибирует данное выражение,
   Bloom L1. `hints_text` в LMS — отдельная сущность, скрытая по умолчанию и
   раскрываемая по запросу ученика **после** попытки подумать самому. Формула/имя
   метода допустимы ТАМ (по правилам качества п.2 выше — как ход рассуждения, не
   готовый ответ), но не в `stem`. Правило применимо к любому заданию, где часть
   учебной цели — самостоятельно выбрать подход (не только к «числам»): если формула
   уже названа в условии, задание проверяет только навык 2, а не оба. Не путать с
   заданиями, где сама формула ДАНА как условие (например, `d = v · t` — исходные
   данные физической задачи, не искомый приём) — убирать только ту часть, которая
   ЕСТЬ искомый алгоритмический шаг.

### 3.5. Рост объёма заданий по профилю прогрессии (не-детские ЦА)
Объём кода и многошаговость заданий обязаны РАСТИ по ходу курса в коридоре профиля
ЦА (difficulty-and-design, таблица «Профиль прогрессии»): напр. предвузовский —
4–5 строк в начале → 8–10 в середине → 10–15 в конце, плюс ≥2 проектных. Гейт:
выписать объём (строк кода / шагов) типичного задания по узлам в порядке курса —
если в финале он не вырос относительно старта, профиль нарушен, доработать.

**Многошаговые и проектные авто-задания с детерминируемым результатом — типом
`SA_COM`.** Конвертер ContentBackbone `lms_publish/blocks_to_lms.py` разворачивает
`SC | SA | SA_COM | TA` — начиная с tsk-176 `TA` тоже разворачивается (`_ta_rules`,
уходит в `manual_review_required: true` с рубрикой). Правка (2026-07-10): более
ранняя версия этого файла утверждала «`TA` не разворачивается» — это устарело,
не проверять и не воспроизводить это утверждение. Тем не менее для «напиши
программу целиком» и авто-проектного с ОДНИМ детерминируемым эталоном по-прежнему
предпочтителен `SA_COM` с продиктованной структурой ответа (см. §7): SA-фаза ловит
ключевые идентификаторы/числа/имена методов и их порядок (нормализация
`trim/lower/strip_punctuation/collapse_spaces` стирает символы `= " ( ) { }`, но
СОХРАНЯЕТ слова, идентификаторы и числа), COM-фаза оценивает качество кода — это
даёт мгновенную авто-обратную связь на SA-фазе, которой `TA` не даёт. `TA` —
осознанный выбор для защиты/проекта без детерминируемого эталона (см. §7 про
инвариант поля `answer`), не запасной вариант «раз SA_COM не подошёл». Открытое
«делание» без единого эталона (свой проект/игра) — ручная проверка
(`manual_review_required`) или WP-миссия `lms_skip`, не авто. Так проектная глубина
достигается без ручной проверки там, где эталон есть и её можно избежать.

### 3.5a. Частота `TA` в курсе — считаемый гейт (tsk-658, решение оператора 2026-08-24)

§3.5 говорит «`SA_COM` предпочтителен, `TA` — осознанный выбор». Как предпочтение это
не работает: замер прода 24.08 — **148 активных `TA` на 142 курса** (почти в каждом
ровно один) и **142 из них стоят последним заданием курса**. То есть развёрнутый
ответ стал не осознанным выбором, а дежурным способом закрыть тему. Поэтому правило
переводится в счёт.

**Гейт (считать по курсу целиком, до сдачи):**

1. Сосчитать `TA` и позиции, на которых они стоят. **`TA` последним заданием каждой
   темы = брак**, независимо от качества формулировок.
2. Норма частоты — **не чаще одного `TA` на главу/модуль**, и это итог главы или
   курса, а не рядовой конец урока. Тему завершает авто-проверяемая многошаговая
   задача (§3.1a).
3. Каждый оставшийся `TA` обязан быть **привязан к личной работе ученика** (свой
   проект, свои данные, свой прибор, защита на разборе). Развёрнутый ответ, который
   можно написать, ничего своего не имея, — это вопрос, который ученик задаёт чату,
   и он не отличается от списанного.
4. Рубрика (`solution_rules.text_answer.rubric`) — обязательна и пишется так, чтобы
   по ней **ставили баллы по пунктам**, а не «зачёт целиком»: каждый пункт —
   наблюдаемый признак в тексте ответа, а не «раскрыл тему».

**Почему не «переписать все на авто».** Авто-проверяемое задание **не защищает от
списывания** — его вопрос так же можно задать чату. Оно даёт другое: вердикт, который
не требует человека и который нельзя принять вслепую. Проектная работа с защитой даёт
третье — то, чего чат не сделает за ученика. Разные инструменты, и `TA` остаётся ради
третьего, а не как замена первому.

**Цена нарушения — не теоретическая.** По тем же данным прода: из 64 сдач `TA`
зачтено 60 (94 %), все — на полный балл, и **ни в одной не проставлены баллы по
пунктам рубрики**. Слот, который проверяет только человек, в каждой теме превращается
в слот, который не проверяет никто.

**Реюз-узлы входят в счёт (повтор-дефект, курсы kolledzh-oaip-pascal / kolledzh-
informatika-bpla, tsk-955/956).** Второй родитель (`shared`/`attach_to`, §3.6 использует
тот же механизм графа) приносит в главу СВОИ уже готовые задания, включая собственные
`TA`. Автор, считающий частоту `TA` только по своим НОВЫМ заданиям, легко получает
2-3 `TA` на главу вместо ≤1 — подключаемые узлы существуют в другом файле/каталоге и не
видны при подсчёте «на глаз». Правило: частоту `TA` (и любой другой считаемый гейт —
§3.1a плотность, порядок/мостики ниже) считать по **собранному дереву целиком**, включая
чужие узлы, а не только по тому, что написано в этой сессии.

### 3.6. Интерливинг-узел (опционально, точечно)

Отдельно от spiral-мостика (difficulty-and-design.md, Часть 3 п.3 — старое понятие
возвращается ОДНИМ заданием в новом узле). Interleaving — намеренное чередование
заданий РАЗНЫХ, но похожих тем в одном наборе практики (не блокировать по одной
теме подряд) — доказанно улучшает различение близких понятий, которые ученики
типично путают. Разные приёмы, разное назначение: spiral-мостик = напоминание,
интерливинг-узел = тренировка различения.

**Когда применять (узкий критерий, не по умолчанию):** только если 2-3 узла-листа
подряд внутри одного подкурса (§3.1) держат **легко путаемые** понятия одной
предметной области — близкие по имени/сигнатуре методы (`count` vs `find`,
`append` vs `extend`), похожие структуры (`if/elif` vs вложенный `if`), смежные
термины школьного курса (растр/вектор, файл/путь). Если темы подкурса тематически
далеки друг от друга (не путаются) — интерливинг-узел не нужен, спирального
мостика достаточно.

**Механизм — без нового типа узла, без миграции LMS-схемы.** Граф курса и
публикатор ContentBackbone уже поддерживают узел с несколькими родителями
(ADR-0042 Stage 3 `shared`/`attach_to`/`requires`, реализовано и используется в
проде для переиспользуемых узлов). Тот же механизм даёт «сводную практику»:

1. Авторить новый узел-лист `course_uid` (доп. суффикс, напр. `...-mix`) сразу
   после последнего из 2-3 путаемых листьев в подкурсе.
2. `shared: true`, `attach_to: [uid_листа_1, uid_листа_2, (uid_листа_3)]` —
   привязка к нескольким родителям одновременно.
3. `requires: [те же uid]` — гейт: узел открывается только когда ВСЕ
   источники-листья пройдены (обычный, уже готовый механизм requires §4).
4. Свои 4-6 заданий узла: **вперемешку** ссылаются на понятия из РАЗНЫХ
   источников-листьев не блоками («2 задания темы A, потом 2 темы B»), а
   чередованием (A, B, A, C, B — порядок задаёт разброс, не группировку).
   Каждое задание — про ОДНО понятие, но набор в целом заставляет ученика
   переключаться между темами, а не «доигрывать» одну тему подряд.
5. Типы/сложность — как у обычного листа (§3.1): SC/MC/SA, преимущественно
   NORMAL (цель — различение, не новизна и не пик сложности).

**Не для каждого подкурса.** Точечный приём для мест с реальной путаницей —
не универсальное правило на весь курс. Пилот — на одном модуле, сверка эффекта с
оператором перед распространением на другие курсы (см. `errors.md` CreateCourses,
backlog «Interleaving», tsk-178).

### 3.7. Узел-измеритель (пробник/эмуляция экзамена) — отдельный класс, не обучающий узел

Обучающие правила выше (подсказка обязательна и не сливает ответ, §6) написаны для узла,
где цель — ОБУЧИТЬ. У узла-**измерителя** (эмуляция экзамена/вступительного испытания,
пробник, зачётный прогон) цель другая — **измерить**, и заполненная подсказка у каждого
задания это ломает: ученик решает с подсказкой, результат завышается, слабые темы не
проявляются, повторение идёт не по тем разделам (повтор-дефект, курс vstupitelnye-it-vuz —
45 из 45 заданий трёх узлов-эмуляций несли заполненную подсказку, правила прохождения
запрещали только материалы курса, подсказку — нет).

Правило: при проектировании узла-измерителя явно пометить его как измеритель (не
обучающий узел) в плане. Для него: (1) подсказка НЕобязательна (уместна пустая/скрытая —
это не брак для этого класса узла, в отличие от обучающего); (2) в правилах прохождения
узла — **явный текстовый запрет** пользоваться подсказкой/материалами на зачётном
прогоне, не только «материалы курса». Тот же класс — у любого курса с пробником/финальной
эмуляцией.

### 4a. Разметка `stem` — НЕ эмитить markdown-выделение (tsk-212, класс A5)

Рендер стема в SPW (`TaskContentRenderer`) **не поддерживает markdown-выделение
ни в одном режиме**: `**жирный**`/`__жирный__`/`*курсив*` показываются ученику
литеральными звёздочками/подчёркиваниями. Режим выбирается по содержимому:
- **HTML-режим** — если `format='html'` ИЛИ в тексте есть реальный HTML-тег из
  белого списка (`<p> <strong> <code> <pre> <br> <em>`…). Тогда markdown литерален,
  а HTML-теги работают.
- **plain-режим** — иначе. Поддержаны переносы строк, ``` code-fence ```, KaTeX
  (`$x$`/`$$`), автолинки, spoiler — но **НЕ** markdown-выделение.

Правило автору (для `stem`, `hint`, `options` — любого текста задания):
- **никогда не писать `**` / `__` / одиночные `*` как выделение;**
- нужно выделение в **HTML-стеме** → тег `<strong>` (или `<em>`);
- **plain-стем** (использует `$…$`/code-fence и без HTML-тегов) → **без выделения
  вообще.** Не добавлять `<strong>` в plain-стем: единственный тег флипнет его в
  HTML-режим и сломает plain-препроцесс (KaTeX/code-fence перестанут рендериться).
  Если выделение критично — переверстать стем целиком в HTML-режим осознанно, но по
  умолчанию для plain обходиться без выделения (порядок слов, двоеточие, кавычки).
- **Осторожно с `**` как оператором:** в математике/коде `**` — это степень
  (`2**3`, `(x)**0,5`) или `**kwargs`; такие `**` НЕ выделение, их не трогать. Не
  путать при массовой правке (разбор — по границе слова и режиму стема).

### 4b. `normalization` — как сверять короткий ответ (tsk-262/265)

Для **любого** SA/SA_COM с `accepted_answers` методист **явно** выдаёт
`solution_rules.short_answer.normalization` — список шагов приведения ответа
и эталона к общему виду ПЕРЕД сравнением. Решение принимается **при проектировании
задания**: движок не угадывает вид ответа по эталону и не будет (`тест-кейс`
разбирается как вычитание имён, `example.ru` — как обращение к атрибуту).
Не выдал → импорт подставит дефолт `["trim","lower"]`, и для задания-кода это
худший вариант из возможных.

Словарь **закрыт** — ровно пять значений; любое другое (опечатка `code-ast`) даёт
**422 на импорте**, а не тихое игнорирование:
`trim` · `lower` · `strip_punctuation` · `collapse_spaces` · `code_ast`.

Выбор по виду ответа — один вопрос: **ответ на это задание является программой
на Python?**

| Ответ | `normalization` |
|---|---|
| **Код на Python** (выражение, вызов, строка программы) | `["trim", "strip_punctuation", "collapse_spaces", "code_ast"]` |
| **Текст / слово / число / имя** | `["trim", "lower", "strip_punctuation", "collapse_spaces"]` |

- **`code_ast`** = «сравнивать как ПРОГРАММЫ»: обе строки приводятся к канону через
  `ast.unparse(ast.parse(v))`. Кавычки, пробелы вокруг синтаксиса, комментарии и
  форматирование становятся незначимы (`print(slovo .lower())` = `print(slovo.lower())`,
  `find('и')` = `find("и")`). Если ответ **или** эталон не разбирается как Python
  (фрагмент `for i in range(10):`, ответ `.env`, эталон-проза) — сравнение падает
  обратно на текстовые шаги из этого же списка. Режим не может ужесточить проверку,
  только спасти валидный ответ.
- **`lower` в задании-коде НЕ ставить.** Регистр в Python значим: с `lower`
  `IMPORT RANDOM` засчитается за `import random`, а `print(I)` — за `print(i)`.
  `code_ast` регистр имён сохраняет — это его сознательное свойство, не пробел.

Авторитет: `D:\Work\ContentBackbone\docs\cross-project\contracts\lms-api.md`
§ «Нормализация короткого ответа». Читается в `checking_service._matches_short_answer`.

**Сам эталон — четыре проверяемых правила (tsk-796).** Движок сверяет строки и
морфологии не знает: что не перечислено в `accepted_answers`, то незачёт.

1. **Эталон — в именительном падеже, единственном числе.** Вопрос грамматически
   требует другого («Все цифры вместе называют её…») — переформулировать
   **вопрос**, а не эталон: «Как называется набор всех цифр системы счисления?»
   Проверка при заведении: эталон совпадает со словарной формой слова.
2. **Синонимы перечисляются явно** в `accepted_answers`, а не додумываются
   проверкой. Проверка: назвал понятие вторым словом сам — оба в списке.
3. **Тип ответа согласован с вопросом.** Ждём слово — условие не должно
   допускать число. Проверка: в условии есть «Впиши слово» / «назови одним
   словом», а не только «Найди…».
4. **Правка эталона у задания, которое уже сдавали, — событие, а не мелочь.**
   Перед сменой эталона посмотреть сдачи: на 5863 двое учеников сдали одно
   задание противоположными ответами, потому что эталон поменяли между их
   попытками. Меняешь — старый вариант остаётся в списке, не удаляется.

Правило 1 действует **вперёд**: у 257 уже заведённых заданий словоформы
проставлены офлайн-морфологией (`D:\Work\LMS\scripts\gen_wordforms_tsk796.py`,
отчёт `LMS\docs\qa\2026-09-05-tsk796-wordforms-review.md`). Дописывать формы
руками к новому заданию не нужно — нужен эталон в начальной форме.

### 4c. Порядок вариантов SC/MC — не кодировать ответ позицией (tsk-216)

Прод-аудит вскрыл структурный слив ответа, отдельный от текстового (§6 «подсказка не
выдаёт ответ»): верный вариант стоял на позиции 0 в **95%** SC-заданий (1878/1970),
в MC верные занимали ведущий блок в **76%** (174/230) — против ~25% при случайном
порядке. Авторинг (человек и LLM) неосознанно пишет самый очевидный/канонический
вариант первым, а он часто и есть верный. Платформа перемешивает варианты на
рендере (SPW, per-attempt shuffle) — это защищает УЖЕ ОПУБЛИКОВАННЫЙ банк, но не
избавляет авторинг от привычки кодировать ответ порядком: то же смещение при
следующем прогоне снова уйдёт в исходные `options`.

Правило: порядок вариантов в `options` при авторинге — содержательно случаен
относительно правильности (не «верный вариант первым, потому что он самый
очевидный», не «дописан последним по ходу генерации»). Не писать в `stem` или
в тексте вариантов позиционные/буквенные отсылки к другому варианту («см. вариант
выше», «как в пункте А», «варианты 2 и 3 неверны, потому что…») — после
перемешивания такая отсылка станет бессмысленной или введёт в заблуждение.

Если природа задания требует явной нумерации/буквенных меток ВНУТРИ самого вопроса
(варианты перечислены как часть `stem`, а ответ — буква/номер из этого перечисления)
— такое задание НЕ проектировать как SC/MC с shuffle: либо `SA` с фиксированным
вводом метки, либо переформулировать так, чтобы ответ не зависел от порядка показа.

- [ ] **Глубина практики (§3.4):** каждый приём/метод материала применён ≥1 заданием буквы б/б2/в/г (не только тип (а) «предскажи вывод»/факт-вопрос); распространённые приёмы темы не пропущены (для строк — срезы + `count`/`find`/`replace`); микс типов практики (§8 п.8), не 3 однотипных; для программирующей темы — хотя бы одно задание, где ученик пишет/дописывает/чинит код сам
- [ ] **Обратная трассировка (§3.4 п.4):** для каждого задания темы факт/приём, который оно проверяет, явно найден в материале ЭТОЙ темы — не выдумано и не унаследовано без ссылки из другой темы
- [ ] Микс сложности соблюдён (посчитать фактически), difficulty по §2; для предвузовского/взрослого профиля к финалу доля NORMAL/HARD/проектных растёт (§3.2)
- [ ] **Профиль прогрессии (§3.5):** объём заданий растёт по коридору профиля ЦА (старт → середина → финал); не «детский» одношаговый формат весь курс для не-детской ЦА; многошаговые/проектные авто с ОДНИМ детерминируемым эталоном — предпочтительно `SA_COM` (мгновенная авто-обратная связь); `TA` — для защиты/проекта без детерминируемого эталона, не запасной вариант
- [ ] **Инвариант `answer` у SA/SA_COM (§7, ОБЯЗАТЕЛЬНО):** короткий детерминированный ответ → `answer` заполнен, `stem` диктует формат ввода; открытый ответ (объяснение/обоснование/генерация) → `answer: null` + критерий «Принято, если…» в `stem`. Не оставлять текст рубрики в поле `answer` — непустой `answer` всегда означает точное совпадение, ручного review не будет
- [ ] **Эталон короткого ответа (§4b, tsk-796):** в именительном падеже и единственном
      числе (требует падежа сам вопрос — переписать вопрос, не эталон); синонимы
      перечислены явно; тип ответа согласован с вопросом; правка эталона у задания
      со сдачами — старый вариант остаётся в списке
- [ ] **Разметка `stem`/`hint`/`options` (§4a, tsk-212):** нет markdown-выделения
      `**`/`__`/одиночных `*` (рендерятся литеральными звёздочками). HTML-стем → `<strong>`;
      plain-стем (`$…$`/code-fence) → без выделения (тег флипнет режим и сломает KaTeX).
      Математические `**` (степень `2**3`, `(x)**0,5`) — не выделение, не трогать
- [ ] У каждого задания: external_uid, course_uid, наблюдаемые solution_rules
- [ ] Приоритет быстрых авто-проверок (SC/MC/SA); `SA_COM` только у задач с кодом/решением (§7); нет «сочинений» массой
- [ ] **Вовлечённость (§8):** каждое задание — действие с видимым результатом, не школьный вопрос; есть нарастающая сложность; проектные «зажигают» (реальный артефакт/кейс)
- [ ] external_uid стабильны (повторный импорт = upsert, не дубль)
- [ ] **Проектный SA_COM (§7):** в `stem` есть видимый блок «Принято, если…» (3–5
      пунктов), не только закрытая рубрика для проверяющего
- [ ] **Подсказка (`hint`) не выдаёт ответ и не пустая заглушка (3 проверки):**
      (1) *арифметический слив* — из текста прямо получается финальное значение
      `accepted_answers` (переписать: метод/формула/направление, не готовый расчёт);
      (2) *смысловой слив* — подсказка не подстрока ответа, но раскрывает его СМЫСЛОМ:
      синоним («Скруглённая фигура.» при ответе «овал»), корень слова («Есть цикл.» при
      ответе «циклический»), англ./иноязычный термин-эквивалент («LIFO.» при ответе
      «стек»), перечисление элементов ответа («Только 0 и 1.» при ответе «два») — искать
      СМЫСЛОМ, не подстрокой `hint LIKE '%answer%'`; тест — прочитать hint изолированно
      (без stem) и спросить «называет ли он ответ другими словами?»; (3) *пустая
      заглушка* — generic-текст без специфики вопроса («Вспомни определение из урока и
      сопоставь с вариантами», «Сначала выпиши правило или формулу, затем посчитай по
      шагам») повторяется на разных заданиях без адаптации — детектируемо программно
      (точное совпадение строки `hint` у >1 задачи в уроке/главе); тест «убери stem —
      подсказка ещё понятна, ПРО КАКУЮ она задачу?» — если нет, переписать под конкретику
      вопроса (пример из материала/расчёта, а не мета-инструкция «как решать такой тип»)
- [ ] **Механический проход по ВСЕМУ готовому банку темы/главы перед публикацией
      (RECURRING, курс ruchnoe-testirovanie — правило §9 п.3 существовало с 2026-07-08,
      нарушено повторно в 19 заданиях этого же курса).** Проверки подсказки (3 проверки
      выше) и формы эталона (§9 п.3 — падеж/синоним/регистр) написаны как authoring-
      инструкция «что делать при написании нового задания» — этого недостаточно на
      банке из сотен заданий, где часть написана до правки правила или без него в
      уме. Перед сдачей ГОТОВОГО банка — отдельный проход по КАЖДОМУ уже существующему
      заданию темы/главы (не только новым), не полагаясь на память о том, что правило
      применялось в момент написания. Кандидат на детерминированный скрипт
      (сверка склонения/числа слов эталона с вопросом, точное совпадение строки `hint`).
- [ ] **Интерливинг (§3.6, опционально):** если в подкурсе есть 2-3 листа с легко
      путаемыми понятиями — рассмотреть интерливинг-узел; не применять по умолчанию
      везде, только точечно там, где путаница реальна
- [ ] **Порядок вариантов SC/MC (§4c, tsk-216):** верный вариант не стоит систематически
      первым/рядом с вопросом; в `stem`/тексте вариантов нет позиционных или буквенных
      отсылок к другому варианту («см. выше», «как в А»)

## 7. `SA_COM` — двухфазная проверка (точная семантика)

`SA_COM` создан для **задач с кодом/решением**, где нужно быстро и дёшево:

1. **SA-фаза (авто):** проверить **правильность результата** автоматически —
   тест прошёл / вывод совпал / ответ из `accepted_answers`. Мгновенно,
   без участия человека.
2. **COM-фаза (ручная/ИИ):** препод или ИИ оценивает **качество** решения/кода
   по рубрике (читаемость, структура, без хардкода секретов, идиоматичность).

Это НЕ «короткий ответ + объясни словами почему». COM — это проверка артефакта
(кода), а не эссе ученика. Применять только там, где есть И авто-проверяемый
результат, И артефакт-решение для качественной оценки (обычно — код, конфиг,
запрос). На онбординге/теории без кода `SA_COM` почти не нужен — там `SC/MC/SA`.

`solution_rules` для `SA_COM`: `short_answer.accepted_answers` (SA-фаза) +
`text_answer.rubric` или `manual_review_required: true` (COM-фаза, критерии
качества кода).

**Проектный SA_COM (артефакт крупнее кода — бот/брендбук/пайплайн) — критерии
готовности ОБЯЗАТЕЛЬНЫ в `stem` (не только в закрытой `rubric` для проверяющего).**
SA-фаза здесь часто проверяет тривиальное поле (число шагов, имя модели) — это
не заменяет проверку самого артефакта. **Авто-поле обязано быть ОДИНАКОВЫМ у всех
учеников** (число полей в спроектированной таблице, число составленных запросов), а НЕ
личное значение (объём ОЗУ его компьютера, его средний балл) — у личного значения нет
эталона, любой ученик впишет своё и все получат 0. Тест: «одинаков ли верный ответ у всех,
кто сделал задание правильно?» Нет → поле не годится для авто-фазы. Добавить в `stem`
видимый ученику ДО сдачи блок «Принято, если…» (3–5 наблюдаемых пунктов: что именно
должно получиться, какие требования к артефакту). Без этого блока проектное задание не
измеряет заявленную цель «сделать» — ученик не знает, что предъявлять. Повтор-дефект:
65 проектных заданий флагмана «AI-предприниматель» сверяли только факт-пропуск,
без рубрики готовности артефакта.

**Каждое действие проекта в СТОРОННЕМ сервисе — шаг + образ в материале (повтор-дефект,
курс kolledzh-informatika-bpla, tsk-956).** Если проектное задание требует действий в
чужом сервисе (облако, магазин, мессенджер, личный кабинет — не в среде, которую сам
курс строит с нуля), а материал темы описывает это одним абзацем без конкретных шагов
и скриншота — задание невыполнимо самостоятельно, даже если формулировка `stem` понятна.
Политика визуалов требует скриншот для UI-состояний вообще, но проверка «есть ли скриншот
под КАЖДОЕ действие проектного задания» отдельно не проводилась. Гейт: выписать глаголы-
действия проектного задания, выполняемые в стороннем сервисе (создать/загрузить/выдать
доступ/найти/выбрать), и под каждым — либо явный пошаговый текст + детерминированный
скриншот (класс 3 визуал-политики) в материале, либо задание переформулировать.

**Инвариант поля `answer` (ОБЯЗАТЕЛЬНО, любой SA/SA_COM, не только проектный).**
Конвертер (`_short_answer_rules`) кладёт ЛЮБОЙ непустой `answer` целиком в
`accepted_answers` для точного совпадения (после `trim/lower/strip_punctuation/
collapse_spaces`) и одновременно ставит `manual_review_required = not accepted`
— то есть непустой `answer` ВСЕГДА означает «только точное совпадение», ручной
проверки не будет, даже если `answer` — рассуждение на 300 символов, а не короткий
ответ. Правило: если у задания есть ОДИН короткий детерминированный ответ (число,
слово, имя переменной, короткая фраза) — `answer` заполнен этим ответом, `stem`
диктует формат ввода (§9 п.3). Если ответ ОТКРЫТЫЙ (объяснение, обоснование,
сгенерированный список, любое «своими словами») — `answer: null`, а критерий
«Принято, если…» переносится в `stem` (видим ученику до сдачи, как для проектного
SA_COM выше). Смешивать нельзя: открытый ответ с непустым `answer`-рубрикой не
пройдёт ни авто-, ни ручную проверку (rubric-текст в `answer` не совпадёт с ответом
ученика дословно, а `manual_review_required` останется `false`, раз `answer`
непуст). Повтор-дефект (2026-07-10, курс «Тестировщик ПО», tsk-181): 8 из 9
заданий `SA_COM` и 6 заданий `SA` в одной главе несли в `answer` текст рубрики
вместо короткого ответа или `null` — открытые ответы учеников были бы забракованы
без права на ручной review.

**Вопрос про ЛИЧНЫЙ выбор ученика не годится для auto-check `answer`, даже с одним
детерминированным словом (повтор-дефект, курс ai-predprinimatel, tsk-444).** Если `stem`
спрашивает «какой ты выбрал / взял / использовал» — у разных учеников законно разные верные
ответы (ученик мог взять любую валидную модель/инструмент), а `all_or_nothing` авто-check
принимает одну строку → ученик, ответивший правдиво и правильно по сути, получает 0. Признак
в формулировке: местоимение 2-го лица + глагол выбора/действия («который ты взял», «которую
вы выбрали», «что использовал»), а не объективный факт задачи. Два законных решения: (а)
переформулировать вопрос в детерминированный факт, не зависящий от личного выбора ученика
(«какой уровень модели самый дешёвый?» вместо «какой ты взял для дешёвого теста»); (б) если
вариативность — цель вопроса (проверяем именно выбор), это `TA`/`manual_review_required`,
не auto-check одной строкой. Тест перед сдачей: **у двух учеников, ответивших правильно по
сути, но разными словами, — засчитает ли `answer` обоих?** Нет → поле спрашивает выбор, а
не факт, чинить по (а) или (б).

## 8. Вовлечённость, игровые механики, жизненность (ОБЯЗАТЕЛЬНО)

Источники: требование оператора + @teachcase #998 (В. Устюгова) — «знание
проявляется не в согласии с объяснением, а в способности действовать без
готовой инструкции».

**Принципы (каждое задание проверять по ним):**

1. **Задание = миссия с видимым результатом, не вопрос.** Ученик ДЕЛАЕТ и
   видит исход: бот ответил, токен получен, путь скопирован, тест позеленел.
   Не «расскажи, что такое X», а «сделай X и покажи результат».
2. **Проверка через действие (teachcase):** «выбери следующий шаг», «допиши
   недостающий фрагмент», «найди и исправь чужую ошибку», «примени подход в
   новой формулировке» — вместо пересказа теории.
3. **Управляемая нарастающая сложность:** неполный пример → дополни → сделай
   с нуля → перенеси на свой проект. Внутри узла сложность растёт.
4. **Игровые механики:** явная цель и «зачем это круто»; уровни/прогресс
   (THEORY→EASY→NORMAL→HARD); проектные = «боссы» с реальным артефактом;
   персонализация (на своём кейсе — нельзя списать и интересно); мгновенная
   обратная связь (авто-чек SC/MC/SA).
5. **Жизненность:** контекст из реальной практики (реальный клиент-симуляция,
   свой бот/проект, реальный сервис вроде @BotFather), не абстрактные «задачи
   из учебника».
6. **Проектные «зажигают»:** не реферат/сочинение, а маленький реальный
   результат, которым можно гордиться/показать. Формулировать как вызов.
7. **Написание кода, не только узнавание (с момента, когда ученик уже пишет).**
   Как только в курсе введён синтаксис, в уроке ОБЯЗАТЕЛЬНО ≥1 авто-задание на
   НАПИСАНИЕ кода («напиши команду», «допиши недостающий фрагмент»), а не только
   выбор/предсказание/чтение. Учитывать нормализацию SA (`trim/lower/
   strip_punctuation/collapse_spaces`): символы (`= " ( ) { }`) при сверке стираются,
   а слова и идентификаторы (`print`, `f`, имена переменных, числа) сохраняются и
   упорядочены. Поэтому авто-«напиши код» опирать на слова/идентификаторы и их
   порядок — так надёжно отсекаются «забыл f» и «захардкодил число», а варианты
   кавычек/пробелов принимаются. Свободные программы целиком (нет одного эталона) —
   WP-миссия (`lms_skip`) или ручная проверка (`TA`/manual), не авто-SA.

8. **Разнообразие практики (не один тип массой).** Содержательную тему
   отрабатывать МИКСОМ типов: (а) предсказать вывод; (а2) **трассировка** — что
   лежит в переменной после каждой строки / сколько раз выполнится тело цикла
   (ответ — число/значение, определимо и авто-проверяемо); (б) **написать код каждым
   приёмом** темы (по заданию на приём — см. §3.4); (б2) **допиши пропущенное**
   ключевое слово / имя метода / строку целиком (fill-in, один определимый ответ);
   (в) найти и исправить ошибку в чужом коде; (г) применить приём в НОВОЙ формулировке
   (не копия примера из материала); (д) мини-проект. **Для программирующего урока
   задания на ПРИМЕНЕНИЕ (б/б2/в/г) обязательны — «предскажи вывод» в одиночку даёт
   чтение чужого кода, а не умение писать свой = брак** (повтор-дефект, курс
   Информатика 5-11: вся код-практика была «предскажи вывод»). «Напиши программу с
   нуля» без единого эталона — не авто-SA (строковый чек не тянет): проектное/ручное
   или WP-миссия `lms_skip` (см. §3.5, §9 п.3). Нормализация SA стирает
   символы (`= " ( ) { }`), но СОХРАНЯЕТ слова и идентификаторы — имена методов
   (`upper`, `count`, `replace`, `find`, `split`) survive: поэтому «напиши код
   методом X» надёжно авто-проверяется по имени метода и прямо поощряет практику
   самих приёмов.

**Трассировка ≠ диктант решения (tsk-343).** Пункт 1/а2 списка выше разрешает
трассировку — предсказать вывод ДАННОГО кода. Если же `stem` задания «напиши
программу» приводит ГОТОВЫЙ рабочий код целиком (все ветви `if/elif/else`
дословно, с точными `print`), ученику остаётся только перепечатать и посчитать —
это трассировка под видом написания кода (Bloom L1, не L2-L3 из п.7). Такой формат
допустим только с `difficulty: THEORY/EASY` и не может быть единственным заданием
содержательной темы: тема всё равно обязана иметь отдельные задания б/б2/в/г
(§3.4), где код пишет сам ученик, а не копирует из `stem`.

**Запрещено:** «напиши эссе почему», «перечисли определение», длинные
текстовые ответы массой, «школьный» тон. Скучное/абстрактное задание = брак,
переформулировать в миссию с результатом.

## 9. Граница «материал ↔ задание» и однозначность (ОБЯЗАТЕЛЬНО, LMS)

В LMS материал статичен и читается ДО заданий, причём при выполнении задания текст
материала не виден. Отсюда два жёстких инварианта (нарушение = повторяющийся брак):

1. **Материал = только статичная теория.** Любой блок, который просит ученика
   ДЕЙСТВОВАТЬ — «упражнение N», «сделай / поменяй / запусти / выбери / попробуй /
   ответь» — это НЕ материал, это **задание** (или квиз). Инструкции-упражнения,
   «выбор пути/трека», код «поменяй и запусти» — выносить в задачи, не в материал.
   Перед сдачей: прочитать каждый материал-блок и спросить «требует ли он действия
   ученика?» Если да → перенести в задание. (Повтор-дефект: «Выбери путь» и
   «Упражнение 1/2» оставались в материалах.)
2. **Self-contained + однозначность.** Задание не ссылается на то, что только в
   материале (вшивать исходник в задание). **Исходник — в поле `context`** (рендерится
   и на WP, и в LMS после tsk-130), а НЕ в `stem` и НЕ ссылкой «программа выше/ниже»:
   дублирование кода в `stem` при заполненном `context` даёт код дважды. **Никогда не спрашивать «на какой строке»**
   фрагмента — комментарии и пустые строки делают нумерацию неоднозначной. Ссылаться
   на **элемент кода**: имя переменной/функции, ключевое слово, процитированную строку
   целиком. ❌ «какую строку поменять, чтобы…» → ✅ «как называется переменная, которая
   задаёт число углов?» (ответ — `uglov`) или «впиши строку целиком, которую изменишь».
   **Приземление (tsk-945): условие несёт всё, на что опирается ответ и проверяющий** —
   код, данные, текст файла, описание экрана словами. Внешний файл (zip, ссылка, «из
   урока», «файл к заданию») — только дополнение, а не единственный носитель: проверяется
   «что не так в коде» → код в `context`; «что показал robots.txt» → фрагмент robots.txt в
   условии; ответ — скриншот → критерии называют, что на нём должно быть видно.
   ❌ «Возьми файл с ошибкой из материалов урока, найди причину и почини» (ученик сдал одну
   строку «нет `bot.infinity_polling()`», проверить нечего) → ✅ код бота в `context` +
   «назови причину словами и напиши строку, которую добавишь, и куда». **Одно задание —
   один проверяемый вопрос:** «найди, почини и прокачай» — три задания или три
   пронумерованных пункта ответа, каждый зачитывается отдельно. Эвристика публикатора
   «код-блоки с последнего заголовка» на явный `context` не заменяется: код под другим
   заголовком в задание не попадёт (#6195 — три код-блока в уроке, в задании кода не было).
   Заметка проверяющему — в критерии (`review_note`/`grading_criteria`), не в текст условия.
3. **Определимый ответ + явный формат ввода (для авто-проверки SA/SA_COM/SC/MC).**
   У задания должен быть ОДИН ответ, который ученик может однозначно вывести из условия,
   и в стеме **прямо сказано, ЧТО и в каком виде вводить** (одно слово / число / имя
   переменной / выбрать вариант). Если ученик не понимает, что писать — брак.
   **Форма эталона совпадает с формой, которую провоцирует вопрос** (критично для русского):
   вопрос «**чем** отделяется?» ждёт творительный («точкой»), «**что / название** знака?» —
   именительный («точка»). Стем НЕ смешивает два падежных запроса в одном вопросе
   (❌ «Чем отделяется… впиши *название* знака» → эталон «точкой» отвергнет верное «точка»).
   Две защиты, применять **обе**: (а) стем диктует однозначную форму («Впиши знак: `.`»);
   (б) `accepted_answers` терпимы к закономерным формам (`["точкой","точка","."]`, регистр,
   синоним папка/каталог). Тест перед сдачей: **мысленно ввести естественный правильный
   ответ ученика и сверить с `accepted_answers` посимвольно** — не отвергается ли верный
   ответ из-за падежа/синонима/регистра/знака. Повтор-дефект: задача «название знака» ждала
   «точкой», ученик ввёл «точка» → 0 баллов за верный ответ.
   **Тест ведёт не только новичок из урока, но и ЗНАЮЩИЙ ученик** (tsk-187, операторское
   ревью #7401): новичок дисциплинированно впишет термин из материала («накопитель»), а
   знакомый с темой — верный синоним или аббревиатуру («диск», «HDD», «SSD», «ПЗУ»,
   «внешняя память») и получит 0 за правильный ответ. Спросить по каждому SA: **есть ли у
   верного ответа синонимы, аббревиатуры, закономерные падежные формы или коммутативные
   варианты?** Если да — задать их ВСЕ. **Отдельно пройти по ответам с буквой `ё`**
   (`Счётчик`, `отчёт`, `распределённая`): `lower` снимает регистр, но НЕ сводит `ё`→`е`,
   а ученик почти всегда набирает через `е` → задать `е`-форму в массив. Регистр в массив
   добавлять НЕ нужно (нормализация `lower` его уже снимает — не засорять список).
   **Составной (multi-run/multi-field) ответ — обязателен готовый пример строки
   (tsk-343).** Если в одно поле «Ответ» сводится вывод НЕСКОЛЬКИХ запусков/значений,
   словесного описания разделителя («через пробел/перевод строки») недостаточно:
   нормализация снимает пунктуацию/регистр/пробелы, но не приводит к одному виду
   разные ПО СМЫСЛУ, но содержательно верные формулировки вывода (число `6` vs фраза
   «Первое число больше на 6»). `stem` обязан показать готовый пример итоговой
   строки-ответа целиком, не только описание формата словами. Повтор-дефект:
   задание с каскадом `if/elif/else` и тремя прогонами дало 0 баллов за содержательно
   верную программу — ученик вывел описательную фразу вместо голого числа, т.к.
   эталонной строки в `stem` не было.
   **Пример ОБЯЗАН использовать вход, который НЕ входит в зачётный расчёт** — если
   зачётные числа/данные названы в `stem` явно (как в §9 п.3 выше), пример с ТЕМИ ЖЕ
   числами не иллюстрирует формат, а дословно выдаёт готовый ответ (ученику больше не
   нужно ни запускать код, ни считать — задание превращается в копирование примера).
   Взять произвольное демонстрационное значение (напр. «Пример формата для входа `41`:
   `Первая цифра больше` / `Цифры не одинаковы`»), явно пометить его как пример, не
   входящий в расчёт.
   **Формат `answer` (блочный авторинг, после tsk-187 в CB-конвертере):**
   - скаляр `"answer": "накопитель"` — один эталон (для чисел, однозначных терминов);
   - **массив** `"answer": ["накопитель","диск","HDD","SSD","ПЗУ","внешняя память"]` —
     все равнозначны, любой засчитывается (для терминов с синонимами/падежами; первый
     элемент — канонический, совпадает с термином урока);
   - dict `"answer": {"regex": "накопител.*|диск|HDD|SSD"}` — regex (`use_regex:true`),
     для форматов вроде `\d+` или множества словоформ; массив проще и безопаснее, regex —
     только когда вариантов слишком много.
   **Формула / код / адрес с ЛЮБЫМ значащим символом → SC/MC, не SA** (не «массив
   порядков»). Нормализация `strip_punctuation` стирает `= * + / $ ( ) : ; -`, поэтому
   разные формулы становятся одной строкой: `=A2*B2` == `=A2+B2` == `A2/B2` → все `a2b2`;
   `=C2*$B$1` == `=C2*B1`. Массив «оба порядка» НЕ спасает — он не различает оператор.
   Значит SA пропустит и сложение вместо умножения, и потерю `$`. Инвариант: **если
   правильность ответа зависит от символа-операции, скобки, `$` или знака — это SC/MC**
   (варианты-формулы с дистракторами, где отличается именно операция/`$`), либо `regex`
   (`use_regex:true`, точное совпадение без стирания). SA оставлять только для ответов из
   слов/чисел/имён, где символы не несут смысла. (Повтор-дефект: коммутативные и
   абсолютная адресация Excel через SA давали ложный зачёт — tsk-180, находка Codex.)
   **Подсказка (`hint`) не должна содержать НИ ОДНОГО из принятых ответов** — при массиве
   `answer` сверять hint против ВСЕХ форм, не только канонической. Добавив синоним в
   `accepted`, перечитать hint: не назвал ли он теперь принимаемый ответ (❌ hint «от слова
   *ключ*» при `accepted` с `ключ`). Повтор-дефект: расширение accepted превратило законную
   подсказку в сливающую, а проверка «только по первому ответу» это пропустила.
   **Открытое творческое действие** («собери свою игру», «придумай бота», «сделай свой
   проект») НЕ годится для SA-автопроверки (нет единого ответа, поле «краткий ответ»
   бессмысленно): либо переформулировать в проверяемый вопрос о результате/коде
   (❌ «собери игру и выиграй» → ✅ «как называется переменная с фразой победы?» → `pobeda`),
   либо оформить как проектное задание с ручной проверкой (`TA` / `manual_review_required`),
   а само «делание» оставить в инструкции на витрине (WP/`lms_skip`), не в авто-задаче.
   **Сигнальные слова в `stem` — механический признак открытости (повтор-дефект,
   курс ruchnoe-testirovanie).** Если формулировка задания содержит «сам»/«сформулируй»/
   «придумай»/«предложи свою формулировку» — это надёжный сигнал, что у ответа нет
   единственно верной строки: задание обязано быть `SA_COM` с `answer:null`+критерием
   «Принято, если…», а не строгим `SA` с одним эталоном. Автор, пишущий по шаблону
   «числовой/терминологический SA», может не заметить, что сама формулировка stem уже
   провозглашает открытость — проверять эти слова явно, не полагаться на то, что тип
   задания «само подскажется» по смыслу вопроса.
4. **Disclaimer природы проверки — не одна шаблонная фраза на все задания.** Если
   несколько заданий подряд (например, серия «часть 2» с творческим файлом-ответом)
   генерируются по общему шаблону текста, disclaimer о характере проверки («ответ
   файлом, проверка не мгновенная» / «сверяется по числу на выходе» / «проверяется
   вручную по критериям») ОБЯЗАН отражать РЕАЛЬНУЮ природу проверки КОНКРЕТНОГО
   задания, а не копироваться дословно с соседнего задания другой природы.
   Проверить при генерации серии: у задания с детерминируемым числовым/строковым
   выводом текст не должен утверждать «ручная проверка», и наоборот. Повтор-дефект:
   серия 13-16 ОГЭ информатика — текст банка 16 ошибочно скопирован с 13/15.
5. **Обобщение, а не только поиск в тексте.** Если в уроке дан критерий (признак
   классификации, правило), часть заданий должна просить **применить его к НОВОМУ
   примеру**, которого в материале не было, а не найти готовый ответ в тексте.
   ❌ «какой вид ПО у Windows?» (есть в тексте) → ✅ «программа-архиватор обслуживает сам
   компьютер — это системное или прикладное ПО?» (вывод по критерию). Так задание
   проверяет понимание, а не память на абзац.
6. **Миссии и практические задания — безопасность и формат.** Задание/миссия с
   «деланием» (обычно WP-инструкция `lms_skip`) обязано: (а) НЕ просить вводить/показывать
   **чувствительное** — настоящий пароль, ПД, «покажи/проверь у друга» (повтор-дефект: миссия
   «Сильный пароль» просила проверить пароль друга, противореча уроку «пароль никому не
   показывай»); использовать вымышленные примеры для оценки по чеклисту; (б) НЕ противоречить
   тому, чему учит этот же урок; (в) иметь **формат результата и критерий самопроверки** —
   что сдать/выписать и как ученик поймёт, что сделал верно.
   **Живой внешний маршрут — пройти руками ДО КОНЦА сценария, не только до входа
   (повтор-дефект, курс ruchnoe-testirovanie, глава 16).** Если задание отправляет ученика
   на живой внешний маршрут (страница оплаты, форма стороннего сервиса, чужое приложение) —
   перед публикацией пройти путь кликов ЦЕЛИКОМ, до результата, который спрашивает задание,
   а не только убедиться, что входная точка (каталог/ссылка) существует и кликается.
   Проверка «дошёл до входа» — недостаточна: маршрут может упираться в 404 или заглушку
   дальше по пути, и все задания, построенные на этом маршруте, окажутся невыполнимы.
7. **Словарь условия — термины из материалов курса, не синонимы ради невторяемости
   (повтор-дефект, курс vstupitelnye-it-vuz).** Слово, которым сформулировано задание
   (не только проверяемый факт), обязано либо встречаться в материалах курса, либо быть
   расшифровано прямо в `stem`. Автор, ищущий формулировку, не повторяющую уже занятую в
   банке, рискует взять синоним/новый термин («прокторинг», «знак фирмы» вместо принятого
   «логотип»), которого ученик нигде не видел — задание при этом остаётся решаемым (факт
   в материалах есть), но стоит ученику лишних секунд и уверенности. Проверка при заведении:
   каждое существительное-термин условия сверить со словарём курса, не только с фактом,
   который задание проверяет.
