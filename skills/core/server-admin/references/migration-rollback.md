# Перенос и откат

1. Инвентарь источника: версии, объём, пользователи, cron, маршруты, `.htaccess`, домены,
   HTTPS, почта и публикатор. Определить TTL и окно работ.
2. Собрать совместимую цель по [baseline-ubuntu.md](baseline-ubuntu.md). Обновление ОС,
   CMS или СУБД не совмещать с переносом без отдельного объёма задачи.
3. Перенос одним контролируемым rsync/tar с ограничением нагрузки, дамп и импорт через
   `db-check`. Проверить rewrite/sitemap, абсолютные пути в `.user.ini` (`auto_prepend_file`)
   и конфигурации, количество записей, uploads и кириллицу.
4. Применить [hardening.md](hardening.md). До переключения проверить цель с нужным Host/SNI,
   страницы, canonical, robots, состав sitemap, API и журналы; независимое ревью готовности.
5. В разрешённое окно остановить записи, перенести дельту и свежие данные, проверить
   целостность, изменить нужные DNS-записи доступным разрешённым способом. Поддомены и
   MX/SPF/DKIM вне задачи не менять. Проверить TLS и публичные резолверы.
6. Наблюдать ошибки, ресурсы, ботов и публикатор. Пробные записи только в разрешённом
   объёме. Источник сохранять минимум 7 дней либо дольше по плану восстановления.

## План отката до переключения

- До DNS источник продолжает обслуживать трафик.
- После DNS: заморозить новые записи, согласованно вернуть трафик и восстановить изменения
  на цели по журналу/дельте с проверкой конфликтов. Возврат A-записи данные не возвращает;
  TTL не гарантирует переход всех клиентов за 5 минут.
- До отказа от источника проверить финальный архив и завершить наблюдение. Удаление —
  только в явно разрешённых границах.

Для конфигов подготовить точные команды восстановления, проверки синтаксиса и reload
конкретного сервиса. Для SSH/firewall — сохранённая первая сессия или проверенная консоль.
Шаблон `<сервис> -t` не является универсальной командой.
