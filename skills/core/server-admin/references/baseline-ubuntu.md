# Базовая сборка Ubuntu VPS

Применять к серверу без боевого трафика после инвентаря. Версии, часовой пояс и ресурсы
выбирать по требованиям приложения, не по старому снимку.

1. Настроить вход по ключу, фактический SSH-порт и запасной доступ. Сохранить доступ
   оператора. Приложение запускается отдельным пользователем; записи в его дерево — от
   его имени. Узкий sudoers проверить `visudo -cf`; необходимость PTY — по политике.
2. Установить требуемые пакеты, настроить security-обновления и проверить разрешённые
   источники `unattended-upgrades`, включая используемые PPA. Автоперезагрузку учитывать
   в плане доступности. Swap и память рассчитывать по измерениям.
3. nginx: `nginx -t`, журналы времени запроса и кеша. Python: systemd под пользователем
   приложения, защищённый `EnvironmentFile`. WordPress: совместимые PHP/расширения,
   отдельный пул, лимит процессов по памяти, OPcache; `php-fpm<ver> -t`.
4. СУБД слушает только нужные локальные/частные интерфейсы. Импорт и права — `db-check`.
   Collations MySQL/MariaDB не заменять вслепую: меняются сравнение строк и уникальность.
5. Cron: абсолютные пути и пользователь приложения. Если WP cron отключён, проверить
   `wp cron event run --due-now` и отсутствие просроченных событий. Проверить systemd timers.
6. Почта: доступный SMTP, актуальные ограничения провайдера. Секреты получать защищённым
   способом, не в чате. Минимальные права с чтением нужному сервису (например, `640
   root:<service-group>`). Отправка тестового письма требует разрешения на отправку сообщений.
7. Копии вне веб-корня, ограниченные права и срок хранения; проверить восстановление
   в отдельном контуре, а не только наличие архива.

Кеш: исключить авторизованные запросы, запись, админку и нужные API. Политику query string
задать явно. `?cb_nocache=...` сам по себе не гарантирует обход кеша: проверить все слои
и подтверждение обращения к источнику. Завершение — [readiness-checks.md](readiness-checks.md).
