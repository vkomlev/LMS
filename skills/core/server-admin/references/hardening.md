# Защита без потери доступа

## SSH и firewall

1. Установить реальный порт и интерфейсы по SSH-конфигу, `ss -tlnp`, `sshd -T` (с контекстом
   подключения для `Match`) и наличию `ssh.socket`. Не считать порт 22 обязательным.
2. Проверить ключ оператора и запасную консоль. Удерживать первую SSH-сессию до успешного
   нового подключения после изменения.
3. До включения ufw разрешить фактический SSH-порт и необходимые сервисы/источники;
   проверить IPv4/IPv6 и путь восстановления. Без этого firewall не включать.
4. Парольный вход отключать после проверки ключей. Учитывать `Include`, первое применённое
   значение и `Match`: имя `10-hardening.conf` не доказывает результат. `sshd -t` → reload
   нужного юнита → новая независимая SSH-сессия → эффективные настройки. При отказе откат
   из первой сессии. Порт без задачи не менять; socket activation может требовать иных шагов.
5. `MaxAuthTries` не снижать без проверки клиентов с несколькими ключами. Проверить доступ
   оператора, деплоя и автоматизаций.

## Конфиги и применение

Копии — в защищённом каталоге вне подключаемых по маске `conf.d`, `sites-enabled`,
`sshd_config.d`, например `/root/bak-tskNNN/<исходный путь>`. До применения — точный откат
и синтаксическая проверка (`nginx -t`, `sshd -t`, `fail2ban-client -t`, `visudo -cf`),
затем reload где поддерживается и функциональная проверка. Копии с секретами защищать
и удалять после нужного срока отката; значения секретов и ключи в отчёт не выводить.

## nginx, TLS и fail2ban

- Лимиты выбирать по нормальной нагрузке. Не банить за объём обычных GET 200/301/304.
  `fail2ban-regex` проверить на вредных и легитимных примерах. HTTP 200 на POST логина
  сам по себе не доказывает неуспешный вход.
- `limit_req`: учитывать burst, задержку, код отказа и исключения; пустой ключ позволяет
  пропускать проверенный белый список. Номер запроса с 429 зависит от конфигурации и времени.
- Запретить исполнение PHP в uploads и доступ к секретам/архивам по правилам приложения.
  `xmlrpc.php`, CSP/iframe и плагины защиты менять с учётом зависимостей, включая Jetpack.
  Минимальные права дерева; не применять `chmod 777`.
- TLS: доверенная цепочка и правильное имя. До DNS возможен DNS-01 или подходящий уже
  выпущенный сертификат; самоподписанный сертификат не означает готовность.

## Белые списки

Подтвердить адрес оператора/публикатора. Не доверять User-Agent или одному наличию
Authorization. За прокси доверять forwarded-IP только от известных доверенных прокси.
Googlebot: актуальный официальный `googlebot.json`, валидные диапазоны и непустой файл
до атомарной замены. Яндекс: обратный DNS с точной границей доверенного доменного суффикса
и прямой DNS на исходный IP; DNS-ошибка не выдаёт доверие. Проверить исключения отдельно
для nginx и fail2ban. При выполнении сверять методы с официальными источниками.
