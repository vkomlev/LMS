# Server Admin

Сначала установить фактическое состояние сервера и путь восстановления, затем применять
одно логическое изменение с проверкой. Не обращаться к серверам только ради обновления навыка.

| Режим | Опорный документ |
|---|---|
| `inventory`, `incident`, `verify` | [Проверки и диагностика](references/readiness-checks.md) |
| `build` | [Базовая сборка](references/baseline-ubuntu.md) |
| `harden` | [Защита и доступ](references/hardening.md) |
| `migrate` | [Перенос и откат](references/migration-rollback.md) |

Исторические адреса — [снимок серверов](references/servers.md), не доказательство текущего
состояния. До SSH сверить цель с задачей, локальным SSH-конфигом и актуальными источниками.

Общие правила полномочий, координации агентов и второго взгляда применять через
[booster-shared.md](../codex-booster/references/booster-shared.md). Действовать в уже
разрешённых пользователем границах без повторного запроса «ОК». Оплата, недоступная панель
или отсутствующие полномочия требуют действия оператора только когда разрешённого способа нет.

Для изменения доступа, переноса трафика и отказа от источника заранее подготовить проверку
и откат. БД и дампы — `db-check`; приложение — `executor-pro`/`fastapi-api-developer`;
проверка сайта — `qa-only`, `seo-specialist`; критичные конфиги — независимое ревью.

Результат в проекте задачи: `tsk-NNN`, контур (`dev/local`, `prod`, `unknown`), сервер,
режим, датированный инвентарь, конфиги и защищённые копии, PASS/FAIL с очищенным от секретов
выводом, откат и срок доступности, непроверенные пункты и препятствия. Обязательная
проверка `pending` означает `NOT_READY`.
